两个核心同时操作变量 `i`，A 核执行 `i++` 后，B 核却可能读到旧值。**这不是编译器玄学，而是多核 Cache 与内存不一致的问题。**

<br><br>

## 痛点引入
***
你知道有 L1/L2/L3，也知道多核每核有私有 Cache，但不知道：写 Cache 后什么时候写回内存？为什么多核会读到旧值？总线嗅探和 MESI 到底解决了什么？

<br><br>

## 知识点 1：写直达与写回
***
<br>

### 问题
CPU 写数据先写 Cache，那内存什么时候更新？

<br>

### 方案
- **写直达 Write Through**：每次写都同时写 Cache 和内存。简单，但每次写都受内存速度限制。
- **写回 Write Back**：命中时只改 Cache 并标脏；只有脏 Cache Line 被替换时才写回内存。命中率高时性能更好。

<br>

### 最小示例
```text
写回策略：
命中写 -> 改 Cache，标 Dirty，不写内存
未命中写 -> 若目标块是脏的，先写回内存；再读入新块；写入并标脏
```

**脏标记表示 Cache 与内存不一致。**

<br>

### 一句话本质
**写直达是“每次都同步内存”，写回是“先记账，替换时再还”。**

<br>

### 易错点
- 写回命中时通常不立刻写内存。
- 未命中写还要判断目标 Cache Line 是否脏，脏则先写回。
- 写回性能好，但一致性维护更复杂。

<br>

## 知识点 2：缓存一致性问题
***
<br>

### 问题
A 核 `i++` 后只改了私有 Cache，B 核读内存为什么可能读到旧值？

<br>

### 方案
多核私有 L1/L2 会导致同一数据在不同核心有不同副本。要保证一致性，至少需要：
- **写传播**：某核更新 Cache，要通知其他核；
- **事务串行化**：所有核对同一数据的修改顺序要看起来一致。

<br>

### 最小示例
```text
初始 i=0
A 核 i++ -> A Cache 中 i=1（脏），内存仍 0
B 核读 i -> 若不知道 A 的更新，可能读到 0
```

**只做写传播还不够，还要保证大家看到相同的修改顺序。**

<br>

### 一句话本质
**缓存一致性要解决两件事：更新要传播，顺序要一致。**

<br>

### 易错点
- 写传播不等于事务串行化。
- 缓存一致性不是“所有 Cache 同时改”，而是最终表现一致。
- 数据竞争和缓存一致性是不同层面的问题。

<br>

## 知识点 3：总线嗅探与 MESI 四状态
***
<br>

### 问题
更新事件怎么通知其他核心？又怎么减少总线压力？

<br>

### 方案
**总线嗅探**：核心监听总线上的读写/失效事件，检查自己 Cache 是否有相同数据。MESI 用四个状态降低不必要广播：
- **M Modified 已修改**：脏，和内存不一致；
- **E Exclusive 独占**：干净，只有本核有；
- **S Shared 共享**：干净，多核可能有；
- **I Invalid 已失效**：不可用。

<br>

### 最小示例
```text
A 读 i：I -> E（其他核没有）
B 读 i：A/B 都变 S
A 写 i：S -> M，并广播让 B 的副本变 I
A 再写 i：M -> M，不需要广播
A 的脏行被替换：先写回内存
```

**M/E 状态修改通常不需要广播；S 状态写要先失效其他副本。**

<br>

### 一句话本质
**MESI 用四个状态记录“这行数据是脏的、独占的、共享的，还是失效的”。**

<br>

### 易错点
- E 和 S 都是干净的，区别在是否可能被其他核共享。
- M 是脏的，替换时要写回。
- 共享状态写入前要先让其他核心副本失效。

<br>

### 自测

## 知识点 4：MESI 状态流转
***
<br>

### 问题
本地读、本地写、远程读、远程写，四状态怎么变？

<br>

### 方案
简化规则：
- 本地读：I→E（无共享）或 I→S（有共享）；
- 本地写：I/E→M；S→M 且先失效其他副本；
- 远程读：M→S（并处理写回）；E→S；
- 远程写：M/E/S→I。

实际协议更细，但核心是**状态机 + 总线事件**。

<br>

### 最小示例
```text
核心A: I --本地读--> E
核心B: I --远程读A--> S，A: E->S
核心A: S --本地写--> M，B: S->I
核心B: I --远程写--> I，A: M->I（A需写回）
```

<br>

### 一句话本质
**MESI 不是死记四个词，而是看“谁读谁写、有没有其他副本、脏不脏”。**

<br>

### 易错点
- 远程写会让其他副本失效，不只是更新。
- M 状态被远程读时通常要处理写回/转发，不能简单当内存读。
- 真实 CPU 还有 store buffer、失效队列等优化，MESI 是基础模型。

<br>

### 自测
A 核处于 M 状态，B 核要读同一行，A 的缓存行还能一直保持 M 吗？

## 完整可运行示例：简化 MESI 状态机
***
```python
# 简化模拟：两个核心，只展示状态变化，不模拟真实总线时序
state = {"A": "I", "B": "I"}

def local_read(core):
    other = "B" if core == "A" else "A"
    if state[core] == "I":
        state[core] = "S" if state[other] in ("S", "M", "E") else "E"
        if state[other] == "E":
            state[other] = "S"
    print(core, "local_read ->", state)

def local_write(core):
    other = "B" if core == "A" else "A"
    if state[core] == "S":
        state[other] = "I"
    if state[core] in ("I", "E", "S"):
        state[core] = "M"
    print(core, "local_write ->", state)

local_read("A")   # A: E
local_read("B")   # A: S, B: S
local_write("A")  # B: I, A: M
local_read("B")   # B 从 I 读，A 从 M 变 S
print("final:", state)
```

输出展示：**A 独占 → 共享 → A 修改后 B 失效 → B 再读后共享。** 这是简化模型，真实 MESI 还涉及写回和总线事务。

## 一句话总结全章
***
**多核私有 Cache 会不一致；写回减少内存写，总线嗅探传播事件，MESI 用四状态在性能和一致性之间做平衡。**
