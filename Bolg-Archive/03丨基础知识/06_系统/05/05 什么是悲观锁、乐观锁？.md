## 痛点引入
***
多线程改共享资源，不加锁会乱；可锁选错了，高并发下性能更差。**互斥锁、自旋锁、读写锁都是悲观锁；乐观锁先改再验证版本，冲突低时才划算。**

<br>

<br>

## 知识点 1：互斥锁 vs 自旋锁
***
### 问题
***
加锁失败后，线程该睡还是该等？

<br>

### 方案
***
**互斥锁**失败释放 CPU 睡眠，内核唤醒，有两次上下文切换成本；**自旋锁**失败忙等待，用户态 CAS，适合锁内代码极短、多核。**锁内短选自旋，锁内长选互斥。**

<br>

### 最小示例
***
```cpp
#include <iostream>
#include <atomic>
#include <thread>

std::atomic<int> lock{0};
int counter = 0;

void spin_add() {
    for (int i = 0; i < 100000; ++i) {
        int expected = 0;
        while (!lock.compare_exchange_weak(expected, 1)) {
            expected = 0;
        }
        ++counter;
        lock.store(0);
    }
}

int main() {
    std::thread a(spin_add), b(spin_add);
    a.join(); b.join();
    std::cout << counter << "\n";
}
```
编译运行：
```bash
g++ lock1.cpp -o lock1 -pthread
./lock1
```
输出：
```text
200000
```
**易错点：** 这是教学自旋锁，真实实现要 `PAUSE`、内存序和公平性；别在生产手搓。

<br>

### 一句话总结
***
**互斥锁睡觉等，自旋锁原地等；锁内短用自旋，锁内长用互斥。**

## 知识点 2：读写锁
***
### 问题
***
读多写少场景，多个读线程其实可以同时读，互斥锁太浪费，怎么办？

<br>

### 方案
***
读写锁：**读锁共享，写锁独占**。写锁未持有时多个读可并发；写锁持有后读写都阻塞。读优先可能饿死写，写优先可能饿死读，公平读写锁用队列按 FIFO。**读多写少用读写锁。**

<br>

### 最小示例
***
```cpp
#include <iostream>
#include <shared_mutex>
#include <thread>
#include <vector>

std::shared_mutex rw;
int data = 0;

void reader(int id) {
    std::shared_lock lock(rw);
    std::cout << "reader " << id << " sees " << data << "\n";
}

void writer() {
    std::unique_lock lock(rw);
    ++data;
    std::cout << "writer sets " << data << "\n";
}

int main() {
    std::thread w(writer);
    std::vector<std::thread> rs;
    for (int i = 0; i < 3; ++i) rs.emplace_back(reader, i);
    w.join();
    for (auto& t : rs) t.join();
}
```
编译运行：
```bash
g++ lock2.cpp -o lock2 -pthread
./lock2
```
**易错点：** `shared_mutex` 不是所有平台/标准库都支持；读锁里不能改共享数据。

<br>

### 一句话总结
***
**读写锁让读并发、写独占，适合读多写少；优先策略要防饥饿。**

## 知识点 3：乐观锁与版本号
***
### 问题
***
冲突概率很低时，每次先加锁太贵。能不能先改，提交时再检查？

<br>

### 方案
***
乐观锁先读版本号，修改后提交时比较版本号；一致则成功并更新版本，不一致则失败重试。**全程不加锁，冲突低才划算；冲突高重试成本爆炸。** Git/SVN、在线文档协作都是这个思想。

<br>

### 最小示例
***
```cpp
#include <iostream>
#include <atomic>
#include <thread>

std::atomic<int> version{1};
int value = 0;

bool update(int expected, int new_value) {
    int v = version.load();
    if (v != expected) return false;
    value = new_value;
    version.store(v + 1);
    return true;
}

int main() {
    std::cout << update(1, 100) << "\n";
    std::cout << update(1, 200) << "\n";
    std::cout << "value=" << value << " version=" << version.load() << "\n";
}
```
编译运行：
```bash
g++ lock3.cpp -o lock3 -pthread
./lock3
```
输出：
```text
1
0
value=100 version=2
```
**易错点：** 这个示例不是线程安全 CAS 实现，只演示版本号逻辑；真实乐观锁要原子比较交换。

<br>

### 一句话总结
***
**乐观锁先改再验版本，冲突低时省锁开销，冲突高时重试代价大。**

## 完整可运行/可复现示例
***
```cpp
#include <iostream>
#include <shared_mutex>
#include <thread>

std::shared_mutex rw;
int data = 0;

int main() {
    std::thread w1([]{ std::unique_lock l(rw); data = 1; });
    std::thread r1([]{ std::shared_lock l(rw); std::cout << data << "\n"; });
    std::thread r2([]{ std::shared_lock l(rw); std::cout << data << "\n"; });
    w1.join(); r1.join(); r2.join();
}
```
编译运行：
```bash
g++ lock_all.cpp -o lock_all -pthread
./lock_all
```
**注意：** 输出顺序不确定；读锁可并发，写锁独占。

## 一句话总结全章
***
