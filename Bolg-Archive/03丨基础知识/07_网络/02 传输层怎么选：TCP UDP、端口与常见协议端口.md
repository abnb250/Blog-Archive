## 知识点 1：应用需求决定传输层选择
***
### 问题
选 TCP 还是 UDP，到底看什么？TCP 可靠但不一定快，UDP 快但不一定可靠，怎么权衡？

<br>

### 方案
应用层对传输层通常有四类需求：**可靠数据传输、吞吐量、定时、安全性**。  
- **TCP**：面向连接、可靠、按序字节流，有流量控制和拥塞控制；适合不能丢数据的应用。  
- **UDP**：无连接、尽最大努力交付、开销小、没有拥塞控制；适合实时性强、能容忍少量丢包，或者自己在应用层做可靠机制的应用。  
- 加密通常由 **TLS** 等提供，不是 TCP 自带。  
现代 HTTP/3 基于 QUIC/UDP，在 UDP 上实现可靠和加密，说明 **UDP 不等于不能用**，只是把可靠性交给上层自己决定。  
所以别把 TCP/UDP 理解成“好协议/坏协议”，它们只是两种不同的服务承诺。

<br>

### 最小示例
用对比表复现“应用需求 → 传输层选择”：

```text
应用/协议        常用传输层        主要原因
Web HTTP/1.1/2   TCP              要可靠
HTTPS            TCP + TLS        可靠 + 加密
DNS 普通查询     通常 UDP 53      短查询快；响应过大或被截断时可能改用 TCP
DNS 区域传送     TCP 53           数据量大，要可靠
视频会议/直播    常 UDP/RTP       低延迟优先
SMTP/POP3/IMAP   TCP              邮件不能丢
HTTP/3           QUIC/UDP         在 UDP 上实现可靠与加密
```

结论：**要可靠选 TCP，要低延迟常选 UDP；安全靠 TLS 等补充，可靠性也可以在上层补。**

<br>

### 一句话本质
**TCP 像挂号信，UDP 像明信片；怕丢选挂号，怕慢常选明信片，重要内容再自己加锁。**

<br>

### 易错点
坑一：**UDP 不是“坏协议”**，它只是把可靠性交给应用自己决定；QUIC/HTTP3 就是基于 UDP 做可靠传输的例子。  
坑二：**TCP 可靠但不保证实时性**，拥塞时延迟也可能变大。  
坑三：**“可靠”不等于“安全”**，需要加密和身份验证时得上 TLS 等机制。

## 知识点 2：端口是进程的“门牌号”，不是进程号
***
### 问题
一台主机同时跑浏览器、邮件客户端、Web 服务器，数据到了主机后怎么交给正确进程？

<br>

### 方案
记住一句话：**IP 找主机，端口找进程，传输层协议区分 TCP/UDP。**  
更准确地说，一次通信常用“源 IP、源端口、目的 IP、目的端口、传输层协议”来区分不同的连接或数据流。服务器常使用知名端口：HTTP 80、HTTPS 443、DNS 53、SMTP 25/587、POP3 110/995、IMAP 143/993、FTP 控制 21。客户端端口通常由系统临时分配。  
**端口不是进程号**，它是传输层用来标识应用进程的编号；知名端口只是默认约定，服务可以改端口。排查问题时不能只盯着默认端口。

<br>

### 最小示例
查看本机监听的常见服务端口：

```bash
ss -tulnp 2>/dev/null | grep -E ':(53|80|443|25|110|143|21)\b' || true
```

有服务监听时显示 `LISTEN`、协议、地址和端口；没有输出说明本机没开这些服务，不代表命令错。  
注意：`ss -p` 显示进程信息可能需要权限；不同系统上 `ss` 的可用性也不同，没有 `ss` 可以改用 `netstat -tulnp`。

<br>

### 一句话本质
**IP 找到主机，端口找到进程，协议决定怎么传。**

<br>

### 易错点
坑一：**DNS 不只走 UDP**，普通查询主要用 UDP 53，区域传送用 TCP 53；响应过大或被截断时也可能改用 TCP。  
坑二：**知名端口可以改**，排查问题时不能只看默认端口。  
坑三：**客户端端口是临时的**，服务端回信要用对方实际端口。

<br>

## 知识点 3：常见协议为什么这么选传输层
***
### 问题
HTTP、DNS、SMTP、视频会议，为什么有的用 TCP，有的用 UDP？

<br>

### 方案
咱们按“应用更怕丢还是更怕慢”来看：  
- **HTTP/1.1、HTTP/2**：通常 TCP，因为网页不能丢数据。  
- **HTTPS**：TCP + TLS，可靠且加密。  
- **HTTP/3**：QUIC/UDP，在 UDP 上实现可靠、加密和多路复用。  
- **DNS 普通查询**：通常 UDP 53，查询短、希望快；区域传送用 TCP 53，因为数据量大且要可靠。  
- **SMTP/POP3/IMAP**：TCP，邮件不能丢。  
- **视频会议/直播**：常 UDP/RTP，低延迟优先，能容忍少量丢包。  
- **FTP**：TCP，控制连接 21；主动模式数据连接常用 20，被动模式是服务器随机端口。

<br>

### 最小示例
```text
协议            传输层        一句话原因
HTTP/1.1/2      TCP           网页要可靠
HTTPS           TCP + TLS     可靠 + 加密
HTTP/3          QUIC/UDP      UDP 上做可靠与加密
DNS 普通查询     UDP 53        短查询快
DNS 区域传送     TCP 53        数据量大要可靠
SMTP/POP3/IMAP  TCP           邮件不能丢
视频会议/直播    UDP/RTP       低延迟优先
FTP 控制/数据    TCP           控制 21；主动数据 20，被动随机
```

结论：**协议选 TCP 还是 UDP，不是看谁“高级”，而是看应用更怕丢还是更怕慢。**

<br>

### 一句话本质
**协议选 TCP 还是 UDP，不是看谁“高级”，而是看应用更怕丢还是更怕慢。**

<br>

### 易错点
坑一：**HTTP/3 不是“UDP 不可靠所以不能用”**，QUIC 在 UDP 上补了可靠性。  
坑二：**DNS 不是永远 UDP**，区域传送用 TCP，普通查询也可能因响应过大改用 TCP。  
坑三：**FTP 的数据连接端口不总是 20**，被动模式是服务器随机端口。

<br>

## 完整可复现示例：查端口并验证 DNS 的 UDP/TCP
***
```bash
set -e

echo "=== 1. 查看本机常见服务端口 ==="
if command -v ss >/dev/null 2>&1; then
  ss -tulnp 2>/dev/null | grep -E ':(53|80|443|25|110|143|21)\b' || true
else
  echo "ss 不可用，可改用 netstat -tulnp"
fi

echo "=== 2. 普通 DNS 查询（通常 UDP 53） ==="
if command -v dig >/dev/null 2>&1; then
  dig example.com A +short
else
  getent hosts example.com || true
fi

echo "=== 3. 观察 DNS 传输层（需要权限） ==="
# sudo tcpdump -ni any port 53 -c 5
```

输出/现象/结论可能类似：

```text
=== 1. 查看本机常见服务端口 ===
（有服务时显示 LISTEN 行；没有则可能为空）

=== 2. 普通 DNS 查询 ===
93.184.216.34

=== 3. 抓包 ===
可能看到 UDP 53 的查询和响应；区域传送才会看到 TCP 53。
```

验证结果：端口帮助定位进程；普通 DNS 查询通常走 UDP 53，区域传送才走 TCP 53；响应过大或被截断时，普通查询也可能转 TCP。传输层选择取决于应用对可靠性和延迟的权衡。  
注意：`dig` 得到的 A 记录会随站点配置和网络环境变化；抓包需要权限，没有权限时看注释即可。
