## 痛点引入
***
一个网页有一张大图和一张小图。浏览器在同一条连接上先请求大图，大图很慢。

你可能会想：小图能不能先回来？它又不依赖大图。

答案是：**HTTP/1.1 下通常不能，小图得等大图响应完。** 这就是“队头阻塞”。

再往下想：HTTP/2 说多路复用解决了，那为什么还有 HTTP/3？HTTP/3 为什么改用 UDP？UDP 不是不可靠吗？

这一章咱们用一条问题链往前走：

1. HTTP/1.1 到底卡在哪，长连接为什么不够？
2. HTTP/2 怎么让同一条连接上的多个资源不再互相干等？
3. HTTP/2 还卡在哪，为什么这个卡点靠 HTTP/2 自己解决不了？
4. HTTP/3 换成 QUIC/UDP 后，阻塞范围怎么缩小，连接迁移又是什么？

<br>

<br>

## 优先级说明
***
这篇是 HTTP 版本演变的主线，面试常问，项目排查也会遇到。先分清主次：

**必须掌握（面试常问、项目真用得上）：**
- HTTP/1.1 的响应队头阻塞：同一连接上响应按序，前一个慢，后面等
- 管道化只缓解请求侧连续发送，没解决响应侧按序
- HTTP/2 头部压缩、二进制帧、Stream 多路复用
- HTTP/2 仍基于 TCP，TCP 丢包时所有 Stream 一起等
- HTTP/3 基于 QUIC/UDP，流之间无 TCP 全局阻塞，但单流内丢包仍要等重传
- QUIC 的连接迁移和 0-RTT，0-RTT 有重放风险
- Stream / Message / Frame 的关系

**了解即可（知道大概，不展开）：**
- HPACK 静态表/动态表/Huffman 编码的具体格式
- QPACK 如何用单向流同步动态表
- PUSH_PROMISE 的具体帧格式
- QUIC 的帧类型和拥塞控制细节

**主线**：HTTP/1.1 单车道排队 → HTTP/2 在 HTTP 层拆成多条 Stream → 但 TCP 仍是一条字节流，丢包全局阻塞 → HTTP/3 换 QUIC/UDP，把阻塞缩小到单条流。

## 知识点 1：HTTP/1.1 的瓶颈——长连接不等于多路复用
***
### 问题

HTTP/1.1 不是有长连接了吗？为什么同一个网页里的资源还会互相排队？性能瓶颈到底在哪？

**你可能会想**：长连接就是一条连接一直用，多个请求应该能一起跑吧？

不能。长连接只是省了反复建连，**同一条连接上的响应仍然要按顺序完成**。前一个响应慢，后面的响应就得等。

<br>

### 核心概念与方案

先把 HTTP/1.1 换成你熟悉的场景：**单车道排队。** 一辆慢车在前面，后面的车再急也过不去。

HTTP/1.1 的瓶颈主要有这几处：

- **头部不压缩且重复**：每次请求都带一大串首部，很多字段反复出现。
- **响应队头阻塞**：服务器通常按请求顺序响应，前一个响应慢，后面的响应就得等。
- **没有请求优先级**：浏览器没法告诉服务器“这个 CSS 更急，先给我”。
- **服务器只能被动响应**：服务器不能主动把关联资源推给客户端。

HTTP/1.1 的管道化允许客户端连续发多个请求，不用等前一个响应回来再发下一个。所以它缓解的是**请求侧**的排队。

但服务器仍要按顺序回响应，**响应队头阻塞**没解决。而且管道化默认不开启，浏览器和中间代理支持都很差，实际基本不用。

<br>

### 最小实验：只看响应是不是按顺序回来

环境前提：Linux/macOS，或 Windows WSL；已安装 `curl`，需要外网。下面只观察 HTTP/1.1 的响应顺序，**具体站点和网络环境会影响结果，需按环境核实**。

````bash
curl --http1.1 -sI --max-time 10 https://example.com/ | head -n 1
````

**这次只看一件事**：第一行是不是 `HTTP/1.1`。

预期输出类似：

````text
HTTP/1.1 200 OK
````

看到 `HTTP/1.1`，说明这次用的是 HTTP/1.1。但 `curl` 一次只发一个请求，看不到“大图堵小图”的排队现象。

想直观感受队头阻塞，可以在浏览器开发者工具 Network 面板看多个资源：HTTP/1.1 下同一域名的请求经常显示 `Queueing` 或 `Stalled`，就是在等前面的响应。**具体表现取决于浏览器和站点，需按环境核实。**

<br>

### 易错点与边界

坑一：**HTTP/1.1 默认长连接，但管道化默认不开启**，浏览器基本不支持。

坑二：**长连接不等于多路复用**，同一连接仍要按顺序完成事务。

坑三：**队头阻塞分请求侧和响应侧**，管道化只缓解请求侧连续发送，响应侧仍按序。

坑四：**浏览器会开多条连接来缓解排队**，但连接数有限，且多连接也有开销。

<br>

### 一句话本质

**HTTP/1.1 是单车道排队：长连接省了建连，但同一条连接上的响应仍按顺序，前一个慢，后面就等。**

<br>

### 自测

HTTP/1.1 管道化为什么没有真正解决队头阻塞？

<details><summary>答案</summary>管道化只让客户端可以连续发多个请求，缓解的是请求侧排队；服务器仍要按顺序回响应，响应侧的队头阻塞没解决。而且管道化默认不开启，浏览器和中间代理支持很差，实际基本不用。</details>

<br>

## 知识点 2：HTTP/2 的优化——把一条连接拆成多条 Stream
***
### 问题

HTTP/2 牛在哪？它怎么让同一条连接上的多个资源不再互相干等？

**你可能会想**：HTTP/1.1 开多条连接不也能并行吗？HTTP/2 是不是就是多开连接？

不是。HTTP/2 是在**一条 TCP 连接**上，用 Stream 把不同请求/响应拆开，让它们的帧可以交错发送。不是靠多开连接。

<br>

### 核心概念与方案

先把 HTTP/2 换成你熟悉的场景：**一条公路上画了多条车道，不同车道的车可以交错通过，不用一辆车堵住整条路。**

HTTP/2 主要做了四件事：

- **头部压缩 HPACK**：静态表 + 动态表 + Huffman 编码，减少重复头部。
- **二进制帧**：HEADERS、DATA 等帧，计算机解析更高效，不像 HTTP/1.1 纯文本那样靠换行分隔。
- **Stream 多路复用**：多个 Stream 复用一条 TCP 连接，不同 Stream 的帧可以交错发送，接收端按 Stream ID 组装；同一 Stream 内帧严格有序。客户端发起的 Stream 用奇数 ID，服务器发起的用偶数 ID。
- **服务器推送**：服务器可主动推送资源，用 PUSH_PROMISE 告知；但实际浏览器支持有限，很多场景已经限制或移除，别把它当成万能优化。

这里的关系可以记成：**一个连接承载多个 Stream，一个 Stream 承载一个 Message（请求或响应），一个 Message 由多个 Frame 组成。**

<br>

### 最小实验：只看响应版本是不是 HTTP/2

环境前提：同上，需要外网；`curl` 需支持 HTTP/2。下面只观察响应第一行。

````bash
curl --http2 -sI --max-time 10 https://example.com/ | head -n 1
````

**这次只看一件事**：第一行是不是 `HTTP/2`。

预期输出类似：

````text
HTTP/2 200
````

看到 `HTTP/2`，说明服务器和 `curl` 协商成功，这次走的是 HTTP/2。如果看到 `HTTP/1.1`，可能是服务器不支持 HTTP/2、中间代理降级，或 `curl` 没编译 HTTP/2 支持，**需按环境核实**。

注意：`curl` 只发一个请求，看不到多路复用的帧交错；想看 Stream 交错，要用浏览器开发者工具或 Wireshark 抓包，**具体表现按环境核实**。

<br>

### 易错点与边界

坑一：**HTTP/2 仍基于 TCP**，底层还是字节流。

坑二：**它解决了 HTTP 层队头阻塞，但 TCP 丢包时所有 Stream 仍可能被阻塞**，因为 TCP 要按序交付字节流。

坑三：**服务器推送不是“想推什么就推什么”**，要用 PUSH_PROMISE 告知，而且浏览器支持有限。

坑四：**Stream ID 有方向**，客户端奇数、服务器偶数，0 用于连接控制。

<br>

### 一句话本质

**HTTP/2 把一条 TCP 连接拆成多条 Stream，头部也压缩了；它解决了 HTTP 层排队，但底层仍是 TCP。**

<br>

### 自测

HTTP/2 的 Stream 多路复用解决了哪一层队头阻塞？没解决哪一层？

<details><summary>答案</summary>解决了 HTTP 层的队头阻塞：不同 Stream 的帧可以交错发送，一个响应慢不会堵住其他 Stream 的响应。没解决 TCP 层的队头阻塞：TCP 是字节流，前一个包丢了，后面的包到了也读不了，所有 Stream 仍要一起等重传。</details>

<br>

<br>

## 知识点 3：HTTP/3 与 QUIC——把阻塞缩小到单条流
***
### 问题

HTTP/2 已经有 Stream 多路复用了，为什么还要 HTTP/3？为什么 HTTP/3 改用 UDP？UDP 不是不可靠吗？

**你可能会想**：HTTP/2 都多路复用了，应该够用了吧？

不够。HTTP/2 的多路复用是在 HTTP 层，底层 TCP 仍是一条字节流。**一个 TCP 包丢了，后面所有 Stream 的包都得等**，因为 TCP 要按序把完整连续的字节流交给应用。

<br>

### 核心概念与方案

先把 HTTP/3 换成你熟悉的场景：**HTTP/2 像多条车道汇入一条隧道，隧道里有一辆车出事，所有车道都堵；HTTP/3 像每条车道各自有独立通道，一条车道出事，其他车道还能走。**

HTTP/2 的队头阻塞在 TCP 层：TCP 是字节流，必须完整连续才能交给应用，前一个包丢了，后面的包到了也读不了，所有 Stream 一起等重传。

HTTP/3 基于 **QUIC（跑在 UDP 上）**，把可靠传输、加密、多路复用都放到用户态实现：

- **无队头阻塞**：某个流丢包只影响该流，其他流不受影响；单流内部丢包仍要等重传。
- **更快连接建立**：QUIC 内部包含 TLS 1.3，首次连接 1 RTT 同时完成传输握手和密钥协商；会话恢复可 0-RTT。
- **连接迁移**：用连接 ID 标识连接，不靠源/目的 IP 和端口四元组，4G 切 WiFi 可复用原连接。
- **头部压缩升级为 QPACK**：用特殊单向流同步动态表，缓解 HPACK 动态表在乱序传输下的队头阻塞。

注意：**QUIC 不是“UDP 直接可靠”**，而是在 UDP 之上自己实现了可靠传输和拥塞控制。UDP 只是承载，可靠性由 QUIC 补上。

<br>

### 最小实验：只看 curl 能不能协商出 HTTP/3

环境前提：同上，需要外网；`curl` 需在编译时支持 HTTP/3。下面只观察响应第一行，**不支持时命令会失败，属正常情况，需按环境核实**。

````bash
curl --http3 -sI --max-time 10 https://example.com/ | head -n 1 || echo "当前 curl 不支持 HTTP/3，或服务器/网络不支持"
````

**这次只看一件事**：第一行是不是 `HTTP/3`。

如果看到：

````text
HTTP/3 200
````

说明这次走了 HTTP/3。如果输出 `当前 curl 不支持 HTTP/3...`，说明客户端或网络不支持，**不代表 HTTP/3 不存在**。很多 `curl` 默认没编译 HTTP/3 支持，需要按版本核实。

想看 QUIC 的握手和流，可以用 Wireshark 抓 UDP 443，**需要环境和权限，按实际情况核实**。

<br>

### 易错点与边界

坑一：**QUIC 不是“UDP 直接可靠”**，而是在 UDP 之上实现可靠传输、加密和拥塞控制。

坑二：**HTTP/3 不是“完全没有队头阻塞”**，是流之间没有 TCP 那种全局阻塞，单流内仍可能等丢包重传。

坑三：**部分网络设备可能丢 UDP 包或限制 UDP**，HTTP/3 普及仍受此影响。

坑四：**0-RTT 有重放风险**，敏感请求要谨慎。

<br>

### 一句话本质

**HTTP/2 堵在 TCP，HTTP/3 换 QUIC/UDP 把每条流解耦；流之间不再全局阻塞，但单流内丢包仍要等重传。**

<br>

### 自测

HTTP/2 和 HTTP/3 遇到丢包时，阻塞范围有什么不同？

<details><summary>答案</summary>HTTP/2 基于 TCP，TCP 丢包时所有 Stream 都要等重传，因为 TCP 要按序交付完整字节流，阻塞是全局的。HTTP/3 基于 QUIC，每个流独立处理丢包，某个流丢包只阻塞该流，其他流不受影响；但单流内部丢包仍要等重传。</details>

<br>

## 完整可复现示例：用 curl 对比 HTTP/1.1、HTTP/2 和 HTTP/3
***
你需要 Linux/macOS 或 WSL，已安装 `curl`，需要外网。下面每个步骤只看响应第一行，不展开头部细节。

````bash
set -e

echo "=== 1. 强制 HTTP/1.1 ==="
curl --http1.1 -sI --max-time 10 https://example.com/ | head -n 1

echo "=== 2. 尝试 HTTP/2 ==="
curl --http2 -sI --max-time 10 https://example.com/ | head -n 1 || echo "HTTP/2 不可用，按环境核实"

echo "=== 3. 尝试 HTTP/3 ==="
curl --http3 -sI --max-time 10 https://example.com/ | head -n 1 || echo "当前 curl 不支持 HTTP/3，或服务器/网络不支持"
````

可能的输出/现象：

````text
=== 1. 强制 HTTP/1.1 ===
HTTP/1.1 200 OK

=== 2. 尝试 HTTP/2 ===
HTTP/2 200

=== 3. 尝试 HTTP/3 ===
HTTP/3 200
或
当前 curl 不支持 HTTP/3，或服务器/网络不支持
````

**关键观察点**：第 1 步看第一行是不是 `HTTP/1.1`；第 2 步看是不是 `HTTP/2`；第 3 步看是不是 `HTTP/3`，还是提示不支持。

验证结果：HTTP/1.1 是文本协议；HTTP/2 用二进制帧和 Stream；HTTP/3 基于 QUIC/UDP，`curl` 需要编译时支持 HTTP/3 才能直接验证。

注意：`example.com` 是否支持 HTTP/2/HTTP/3 会随站点和网络环境变化；`curl --http2` 也需要 `curl` 自身支持 HTTP/2；看不到 HTTP/3 不代表协议不存在，可能只是客户端或网络不支持，**需按环境核实**。

## 常见误区
***
- **以为长连接就是多路复用**：长连接只是省建连，同一连接仍按序完成事务。
- **以为管道化解决了响应队头阻塞**：管道化只缓解请求侧连续发送，响应仍按序。
- **以为 HTTP/2 没有队头阻塞**：HTTP/2 解决了 HTTP 层排队，但 TCP 丢包时所有 Stream 一起等。
- **以为 HTTP/3 完全没有队头阻塞**：流之间没有 TCP 全局阻塞，单流内丢包仍要等重传。
- **以为 QUIC 就是“UDP 直接可靠”**：QUIC 在 UDP 之上自己实现可靠传输、加密和拥塞控制。
- **以为服务器推送是万能优化**：浏览器支持有限，很多场景已限制或移除。
- **以为 0-RTT 越多越好**：0-RTT 有重放风险，敏感请求要谨慎。
- **以为 `curl --http2` 一定走 HTTP/2**：服务器不支持、代理降级、客户端不支持都可能回退。

## 自测三问
***
1. HTTP/1.1 的队头阻塞和 HTTP/2 的队头阻塞分别发生在哪一层？HTTP/3 又解决了哪一层？
2. HTTP/2 的 Stream、Message、Frame 是什么关系？
3. HTTP/3 为什么能减少连接迁移成本？它又为什么能缩小丢包阻塞范围？

<details><summary>参考答案</summary>1. HTTP/1.1 的响应队头阻塞在 HTTP 层：同一连接响应按序，前一个慢后面等。HTTP/2 解决了 HTTP 层排队，但 TCP 层仍有队头阻塞：TCP 丢包时所有 Stream 一起等重传。HTTP/3 基于 QUIC，把阻塞缩小到单条流，流之间不再全局阻塞；单流内丢包仍要等重传。2. 一个连接承载多个 Stream，一个 Stream 承载一个 Message（请求或响应），一个 Message 由多个 Frame 组成；不同 Stream 的帧可交错，同一 Stream 内帧严格有序。3. QUIC 用连接 ID 标识连接，不依赖源/目的 IP 和端口四元组，网络切换时可复用原连接；QUIC 在用户态按流处理丢包，某个流丢包只阻塞该流，其他流不受影响，所以缩小了阻塞范围。</details>

## 总结
***
**HTTP/1.1 单车道排队，HTTP/2 用 Stream 多路复用和头部压缩解决 HTTP 层阻塞，HTTP/3 换 QUIC/UDP 解决 TCP 层阻塞并支持连接迁移和更快握手；但 HTTP/3 单流内仍可能等丢包重传，0-RTT 也有重放风险。**
