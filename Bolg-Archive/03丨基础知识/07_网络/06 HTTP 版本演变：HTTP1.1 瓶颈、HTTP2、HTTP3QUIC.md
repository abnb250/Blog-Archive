## 痛点引入
***
HTTP/1.1 有了长连接，为什么网页还是可能卡？HTTP/2 多路复用看起来很完美，为什么还有 HTTP/3？  
这一章咱们用一条问题链往前走：**HTTP/1.1 卡在哪 → HTTP/2 怎么解 → HTTP/2 还卡在哪 → HTTP/3 怎么换底层。**  
先别急着背“多路复用、二进制帧、QUIC”这些词，先看一个具体场景：一个网页有一张大图和一张小图，浏览器在同一条连接上先请求大图，大图很慢，小图能不能先回来？如果不能，卡在哪一层？HTTP/2 和 HTTP/3 又是怎么分别处理这个问题的？

## 知识点 1：HTTP/1.1 的瓶颈
***
### 问题
HTTP/1.1 不是有长连接了吗？为什么同一个网页里的资源还会互相排队？性能瓶颈到底在哪？

<br>

### 方案
HTTP/1.1 的瓶颈主要有这几处：  
- **头部不压缩且重复**：每次请求都带一大串首部，很多字段反复出现；  
- **响应队头阻塞**：服务器通常按请求顺序响应，前一个响应慢，后面的响应就得等；  
- **没有请求优先级**：浏览器没法告诉服务器“这个 CSS 更急，先给我”；  
- **服务器只能被动响应**：服务器不能主动把关联资源推给客户端。  
HTTP/1.1 的管道化允许客户端连续发多个请求，不用等前一个响应回来再发下一个，所以它缓解的是**请求侧**的排队；但服务器仍要按顺序回响应，**响应队头阻塞**没解决。而且管道化默认不开启，浏览器和中间代理支持都很差，实际基本不用。

<br>

### 最小示例
```text
HTTP/1.1 同一连接：
请求 A（大图） → 等响应 → 请求 B（小图） → 等响应
A 慢，B 就跟着等，这就是响应队头阻塞。

开了管道化也只是：
请求 A → 请求 B → 响应 A → 响应 B
B 的请求可以早发，但 B 的响应仍要等 A 的响应。
```

结论：长连接减少了建连次数，但没有让同一条连接上的响应真正并行。

<br>

### 一句话本质
**HTTP/1.1 是单车道排队，头部还很啰嗦。**

<br>

### 易错点
坑一：**HTTP/1.1 默认长连接，但管道化默认不开启**，浏览器基本不支持。  
坑二：**长连接不等于多路复用**，同一连接仍要按顺序完成事务。  
坑三：**队头阻塞分请求侧和响应侧**，管道化只缓解请求侧连续发送，响应侧仍按序。  
坑四：浏览器会开多条连接来缓解排队，但连接数有限，且多连接也有开销。

<br>

## 知识点 2：HTTP/2 的优化
***
### 问题
HTTP/2 牛在哪？它怎么让同一条连接上的多个资源不再互相干等？

<br>

### 方案
HTTP/2 主要做了四件事：  
- **头部压缩 HPACK**：静态表 + 动态表 + Huffman 编码，减少重复头部。  
- **二进制帧**：HEADERS、DATA 等帧，计算机解析更高效，不像 HTTP/1.1 纯文本那样靠换行分隔。  
- **Stream 多路复用**：多个 Stream 复用一条 TCP 连接，不同 Stream 的帧可以交错发送，接收端按 Stream ID 组装；同一 Stream 内帧严格有序。客户端发起的 Stream 用奇数 ID，服务器发起的用偶数 ID。  
- **服务器推送**：服务器可主动推送资源，用 PUSH_PROMISE 告知；但实际浏览器支持有限，很多场景已经限制或移除，别把它当成万能优化。  
这里的关系可以记成：**一个连接承载多个 Stream，一个 Stream 承载一个 Message（请求或响应），一个 Message 由多个 Frame 组成。**

<br>

### 最小示例
```text
HTTP/2 一条 TCP 连接：
Stream 1（HTML）帧1 → Stream 3（CSS）帧1 → Stream 1 帧2 → Stream 3 帧2
接收端按 Stream ID 组装，互不等待。

同一 Stream 内：
Stream 1 的帧1、帧2 必须按序处理，不能乱。
```

结论：HTTP/2 让不同资源在 HTTP 层并行，不用像 HTTP/1.1 那样一个响应堵住后面所有响应。

<br>

### 一句话本质
**HTTP/2 把一条 TCP 连接拆成多条“流”，头部也压缩了。**

<br>

### 易错点
坑一：**HTTP/2 仍基于 TCP**，底层还是字节流。  
坑二：**它解决了 HTTP 层队头阻塞，但 TCP 丢包时所有 Stream 仍可能被阻塞**，因为 TCP 要按序交付字节流。  
坑三：**服务器推送不是“想推什么就推什么”**，要用 PUSH_PROMISE 告知，而且浏览器支持有限。  
坑四：**Stream ID 有方向**，客户端奇数、服务器偶数，0 用于连接控制。

<br>

## 知识点 3：HTTP/3 与 QUIC
***
### 问题
HTTP/2 已经有 Stream 多路复用了，为什么还要 HTTP/3？为什么 HTTP/3 改用 UDP？UDP 不是不可靠吗？

<br>

### 方案
HTTP/2 的队头阻塞在 TCP 层：TCP 是字节流，必须完整连续才能交给应用，前一个包丢了，后面的包到了也读不了，所有 Stream 一起等重传。  
HTTP/3 基于 **QUIC（跑在 UDP 上）**，把可靠传输、加密、多路复用都放到用户态实现：  
- **无队头阻塞**：某个流丢包只影响该流，其他流不受影响；单流内部丢包仍要等重传。  
- **更快连接建立**：QUIC 内部包含 TLS 1.3，首次连接 1 RTT 同时完成传输握手和密钥协商；会话恢复可 0-RTT。  
- **连接迁移**：用连接 ID 标识连接，不靠源/目的 IP 和端口四元组，4G 切 WiFi 可复用原连接。  
- **头部压缩升级为 QPACK**：用特殊单向流同步动态表，缓解 HPACK 动态表在乱序传输下的队头阻塞。  
注意：QUIC 不是“UDP 直接可靠”，而是在 UDP 之上自己实现了可靠传输和拥塞控制。

<br>

### 最小示例
```text
HTTP/2 over TCP：
Packet 3 丢失 → 即使 4、5、6 到达，应用层也读不了 → 所有 Stream 阻塞

HTTP/3 over QUIC：
Stream A 的 Packet 丢失 → 只阻塞 Stream A
Stream B、C 的包完整 → 应用层可以读
```

结论：HTTP/2 的阻塞是 TCP 全局的，HTTP/3 把阻塞范围缩小到单条流。

<br>

### 一句话本质
**HTTP/2 堵在 TCP，HTTP/3 换 QUIC/UDP 把每条流解耦。**

<br>

### 易错点
坑一：**QUIC 不是“UDP 直接可靠”**，而是在 UDP 之上实现可靠传输、加密和拥塞控制。  
坑二：**HTTP/3 不是“完全没有队头阻塞”**，是流之间没有 TCP 那种全局阻塞，单流内仍可能等丢包重传。  
坑三：**部分网络设备可能丢 UDP 包或限制 UDP**，HTTP/3 普及仍受此影响。  
坑四：**0-RTT 有重放风险**，敏感请求要谨慎。

<br>

## 完整可复现示例：用 curl 看 HTTP 版本
***
```bash
set -e

echo "=== 1. 默认请求，看 HTTP 版本 ==="
curl -sI https://example.com/ | head -n 5

echo "=== 2. 强制 HTTP/1.1 ==="
curl --http1.1 -sI https://example.com/ | head -n 5

echo "=== 3. 尝试 HTTP/2 ==="
curl --http2 -sI https://example.com/ | head -n 5

echo "=== 4. 尝试 HTTP/3（需要 curl 支持 HTTP/3） ==="
curl --http3 -sI https://example.com/ | head -n 5 || echo "当前 curl 不支持 HTTP/3，跳过"
```

输出/现象/结论可能类似：

```text
=== 1. 默认 ===
HTTP/2 200 或 HTTP/1.1 200（取决于服务器和 curl 支持）

=== 2. HTTP/1.1 ===
HTTP/1.1 200

=== 3. HTTP/2 ===
HTTP/2 200

=== 4. HTTP/3 ===
当前 curl 不支持 HTTP/3，跳过
或
HTTP/3 200
```

验证结果：HTTP/1.1 是文本协议；HTTP/2 用二进制帧和 Stream；HTTP/3 基于 QUIC/UDP，curl 需要编译时支持 HTTP/3 才能直接验证。  
注意：`example.com` 是否支持 HTTP/2/HTTP/3 会随站点和网络环境变化；`curl --http2` 也需要 curl 自身支持 HTTP/2。看不到 HTTP/3 不代表协议不存在，可能只是客户端或网络不支持。

## 一句话总结全章
***
**HTTP/1.1 单车道排队，HTTP/2 用 Stream 多路复用和头部压缩解决 HTTP 层阻塞，HTTP/3 换 QUIC/UDP 解决 TCP 层阻塞并支持连接迁移和更快握手。**
