## 痛点引入
***
输入 `www.baidu.com` 能打开网页，输入 IP 也能打开。谁在把域名翻译成 IP？为什么全世界不能只用一台 DNS 服务器？  
这一章咱们用问题链往前走：**为什么必须分布式 → 分层怎么分工 → 一次查询怎么走 → 记录长什么样。**  
先别急着背“根域名服务器、顶级域名服务器、权威域名服务器”这几个名词，先看一个具体场景：你改了一个域名的解析，为什么有的地方立刻生效，有的地方要等好久？为什么全球几十亿设备查域名，没有把一台服务器压垮？

## 知识点 1：DNS 为什么必须分布式
***
### 问题
集中式 DNS 行不行？全世界就放一台大服务器，所有域名都查它，不是更简单吗？

<br>

### 方案
不行，集中式至少会撞上四个问题：**单点故障、通信容量瓶颈、远距离延迟、维护开销巨大**。一台机器挂了，全球域名解析就瘫了；所有查询都挤到一处，带宽和连接数扛不住；离得远的地区查询延迟高；全球域名数据集中维护，更新和备份都麻烦。  
所以 DNS 设计成**分层分布式数据库**，同时它本身也是应用层协议，常被 HTTP、SMTP、FTP 等应用使用。普通查询主要用 **UDP 53**，因为查询短、希望快；区域传送用 **TCP 53**，因为数据量大且要可靠。另外，普通查询的响应如果过大或被截断，也可能改用 TCP 重查。

<br>

### 最小示例
用 `dig` 查一条 A 记录：

```bash
dig example.com A +short
```

输出可能类似：

```text
93.184.216.34
```

结论：DNS 把域名翻译成 IP，靠分布式部署和缓存分摊全球查询压力。  
注意：`example.com` 的 A 记录会随站点配置和网络环境变化，这里重点是看“域名 → IP”这个结果。

<br>

### 一句话本质
**DNS 是互联网的分布式电话簿，一台服务器背不动全人类的电话簿。**

<br>

### 易错点
坑一：**DNS 不只走 UDP**，区域传送用 TCP 53；普通查询响应过大或被截断时也可能转 TCP。  
坑二：**DNS 不是一台大服务器**，是分层分布式数据库，根、顶级域、权威、本地各司其职。  
坑三：**hosts 文件可以本地覆盖解析结果**，排查“为什么域名解析不对”时别忘了看它。  
坑四：**DNS 缓存不只是浏览器有**，操作系统、本地 DNS 服务器、甚至中间代理都可能缓存。

<br>

## 知识点 2：分层架构与查询
***
### 问题
一次查询到底怎么走？我输入一个域名，本地 DNS 服务器、根服务器、顶级域服务器、权威服务器，谁先说话、谁后说话？递归查询和迭代查询又差在哪？

<br>

### 方案
先把四类服务器分清楚：  
- **根 DNS 服务器**：不直接存具体域名，只告诉你“这个顶级域该去问谁”。  
- **顶级域 DNS 服务器**：管 `.com`、`.cn`、`.org` 等后缀，告诉你“这个域的权威服务器是谁”。  
- **权威 DNS 服务器**：保存具体域名的最终映射，比如 `example.com` 的 A 记录。  
- **本地 DNS 服务器**：通常是 ISP 或你网络配置里的递归解析器，它帮你跑腿、缓存结果，**它不属于域名层级架构**，更像一个缓存代理。  
典型路径是：你问本地 DNS → 本地 DNS 问根 → 根指向顶级域 → 顶级域指向权威 → 权威返回 IP。  
**递归查询**是“你帮我查到底”，客户端通常对本地 DNS 发递归查询；**迭代查询**是“告诉我下一步问谁”，本地 DNS 对根、顶级域、权威通常用迭代查询。  
缓存能加速：本地 DNS 在 TTL 内直接返回结果，不用每次从头问。

<br>

### 最小示例
用 `dig +trace` 观察逐级查询：

```bash
dig +trace example.com
```

预期输出会看到根服务器、顶级域服务器、权威服务器的逐级查询，最后返回 A 记录。  
注意：`+trace` 输出较长，而且不同网络环境下看到的根服务器和权威服务器可能不同；它展示的是迭代查询过程，不经过本地递归解析器的缓存。

<br>

### 一句话本质
**根管方向，顶级管后缀，权威管门牌号，本地服务器帮你跑腿。**

<br>

### 易错点
坑一：**本地 DNS 不属于层级架构**，它更像缓存代理和递归解析器。  
坑二：**递归和迭代别混**：递归是让对方查到底，迭代是自己一步步问；客户端对本地 DNS 常用递归，本地 DNS 对上级常用迭代。  
坑三：**缓存能加速，但改解析要等 TTL 过期**，不同缓存点的过期时间还不一样。  
坑四：**根服务器不存具体域名的 IP**，它只指方向。

<br>

## 知识点 3：缓存与资源记录
***
### 问题
为什么有时候域名解析秒开？DNS 里到底存了什么？A、NS、CNAME、MX 这些记录分别管什么？

<br>

### 方案
先看缓存：DNS 结果会按 **TTL** 缓存，在 TTL 过期前直接返回，不用再问上级。所以 TTL 越大，解析越快、上级压力越小，但变更生效越慢；TTL 越小，变更生效越快，但查询压力越大。  
资源记录 RR 可以理解成 `(Name, Value, Type, TTL)`：  
- `A`：主机名 → IPv4 地址。  
- `NS`：域 → 该域的权威 DNS 主机名。  
- `CNAME`：别名 → 规范主机名。  
- `MX`：邮件服务器别名 → 规范主机名及优先级，数字越小优先级越高。  
实际 DNS 还有 `AAAA`（IPv6）、`TXT`、`SOA` 等记录，这里先掌握最常用的四类。

<br>

### 最小示例
```bash
dig example.com A
dig example.com MX
```

输出可能类似：

```text
example.com.  300  IN  A   93.184.216.34
example.com.  3600 IN  MX  10 mail.example.com.
```

结论：A 记录告诉你 IP；MX 记录告诉你邮件服务器和优先级。  
注意：`example.com` 不一定有 MX 记录，输出可能为空或只有 SOA；不同站点 TTL 也不同，这里重点看记录结构。

<br>

### 一句话本质
**DNS 靠分层分摊压力，靠缓存抄近道，靠 RR 记录不同答案。**

<br>

### 易错点
坑一：**CNAME 通常不能和同名的其他记录随意并存**，尤其不能和 A、MX 等同时存在；DNSSEC 相关记录是例外。  
坑二：**TTL 越小，变更生效越快，但查询压力越大**；换 IP 前常建议先把 TTL 调小，等旧 TTL 过期后再切。  
坑三：**CDN 会让同一域名在不同地区解析到不同 IP**，所以“我这边解析是这个 IP”不代表全球都一样。  
坑四：**MX 记录的数字是优先级**，不是端口，也不是权重。

<br>

## 完整可复现示例：用 dig 追踪 DNS
***
```bash
set -e

echo "=== 1. 完整追踪 ==="
dig +trace example.com

echo "=== 2. 查看 A 记录和 TTL ==="
dig example.com A

echo "=== 3. 查看 MX 记录 ==="
dig example.com MX
```

输出/现象/结论可能类似：

```text
=== 1. +trace ===
会输出根 → 顶级域 → 权威服务器的逐级查询

=== 2. A 记录 ===
example.com.  300  IN  A   93.184.216.34

=== 3. MX 记录 ===
example.com.  3600 IN  MX  10 mail.example.com.
```

验证结果：`+trace` 展示迭代查询过程；A 记录带 IP 和 TTL；MX 记录揭示邮件服务器和优先级。  
注意：`+trace` 输出可能很长，而且会直接向根服务器发起查询，受网络环境影响；`example.com` 的 A 记录、TTL 和 MX 记录都可能随站点配置变化，看不到 MX 也正常。没有 `dig` 的系统可以改用 `nslookup` 或 `host`，但输出格式不同。
