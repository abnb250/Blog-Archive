## 痛点引入
***
你用 FTP 客户端连服务器，登录成功，切目录正常，列文件也正常。

但一点下载，卡住了。控制连接明明还活着，命令也还能发，文件就是传不过来。

你可能会想：**能登录不就说明网络通了吗？为什么下载不行？**

因为 FTP 把“下命令”和“搬文件”拆成了两条 TCP 连接。登录成功只说明控制连接通了，数据连接可能根本没打通。

这一章咱们用一条问题链往前走：

1. FTP 为什么非要两条连接，一条不够吗？
2. 主动模式和被动模式到底谁连谁，端口为什么有时是 20、有时是随机？
3. 客户端在 NAT/防火墙后，为什么被动模式更容易成功？
4. 只放行 21 端口，为什么经常“能登录、不能传”？

<br>

<br>

## 优先级说明
***
这篇是 FTP 与文件传输的核心，面试常问，项目里排查“FTP 登录正常但传不了文件”也天天用。先分清主次：

**必须掌握（面试常问、项目真用得上）：**
- FTP 双连接：控制连接 21 传命令，数据连接传文件或目录列表
- 主动模式：服务器从 20 端口主动连客户端
- 被动模式：客户端主动连服务器随机端口
- 主动模式叫“主动”，是服务器主动，不是客户端主动
- 只放行 21 端口不够，数据连接也要放行
- 被动模式更适合客户端在 NAT/防火墙后的场景
- FTPS 是 FTP 加 TLS，SFTP 是 SSH 上的文件传输，不走 FTP 的 21/20

**了解即可（知道大概，不展开）：**
- `PORT`、`PASV`、`EPSV` 命令的具体格式
- 被动模式 227 响应里 IP 和端口的编码方式
- FTP over TLS 的握手细节
- 各种 FTP 服务器对被动端口范围的配置差异

**主线**：FTP 把命令和文件分开走两条连接 → 控制连接一直保持，数据连接按需建立 → 数据连接由谁发起，分主动和被动 → 主动模式服务器连客户端，NAT 后容易失败 → 被动模式客户端连服务器，更适合 NAT/防火墙 → 排查时两条连接都要看。

## 知识点 1：FTP 为什么两条连接——命令和文件分开走
***
### 问题

FTP 为什么两条 TCP 连接？一条不够吗？控制连接和数据连接分别传什么？

**你可能会想**：一条连接又能发命令又能传文件，不是更简单吗？

一条连接也能做，但传大文件时，文件数据会把命令响应堵在后面。FTP 的设计是：**命令通道一直保持，数据通道按需建立和关闭**，这样传文件时不会把命令响应卡住。

<br>

### 核心概念与方案

先把 FTP 换成你熟悉的场景：**控制连接像对讲机，数据连接像货运通道。**

- **控制连接**：常用 21 端口，传命令和响应，比如 `USER`、`PASS`、`LIST`、`RETR`、`STOR`，连接保持较久。
- **数据连接**：传文件内容或目录列表，端口取决于主动/被动模式。

控制与数据分离是 FTP 的重要设计：命令通道可以一直保持，数据通道按需建立和关闭；传大文件时不会把命令响应堵在文件数据后面。

但这也带来一个麻烦：**防火墙和 NAT 要同时放行控制连接和数据连接**，只放 21 可能登录成功、列目录或下载却失败。

<br>

### 最小实验：只看 FTP 交互里有没有 227、150、226

环境前提：Linux/macOS，或 Windows WSL；已安装 `curl`，需要外网。下面用公开 FTP 服务器观察交互，**服务器是否可用、是否允许匿名登录，需按环境核实**。

````bash
curl -v --max-time 10 ftp://ftp.gnu.org/gnu/README 2>&1 | head -n 30
````

**这次只看一件事**：输出里有没有 `227`、`150`、`226` 这些响应码。

可能看到类似：

````text
< 220 ...
> USER anonymous
< 331 ...
> PASS ...
< 230 ...
> TYPE I
< 227 Entering Passive Mode (...)
< 150 ...
< 226 ...
````

`227` 表示进入被动模式，响应里带服务器数据连接地址和端口；`150` 表示数据连接即将打开；`226` 表示数据传输完成。

**控制连接和数据连接是分开的：`USER`、`PASS` 走控制连接，文件内容走数据连接。** 如果只看到登录成功，没看到 `227`/`150`/`226`，说明数据连接没建立起来。

注意：`ftp.gnu.org` 的匿名 FTP 服务可能已调整或不可用，不同网络环境下输出会不同；连不上就换一个可用的测试 FTP 服务器，**重点看响应码和命令顺序，不是背服务器地址**。

<br>

### 易错点与边界

坑一：**主动模式 20 端口是服务器主动连客户端**，源端口是 20，目的端口是客户端 `PORT` 命令里给的端口；容易被客户端防火墙挡。

坑二：**被动模式数据端口是服务器随机端口**，不是固定 20；客户端主动连服务器。

坑三：**FTPS、SFTP 和传统 FTP 不是同一个东西**：FTPS 是 FTP 加 TLS；SFTP 是 SSH 上的文件传输协议，不走 FTP 的 21/20。

坑四：**控制连接成功不等于数据连接成功**，只放行 21 端口经常出现“能登录、不能传”。

<br>

### 一句话本质

**FTP 把“下命令”和“搬文件”分开走两条 TCP 连接：21 控制连接传命令，数据连接传文件；登录成功只说明控制连接通了。**

<br>

### 自测

为什么被动模式通常更适合客户端在 NAT/防火墙后的场景？

<details><summary>答案</summary>被动模式下数据连接由客户端主动发起，客户端在 NAT 后也能主动连服务器；主动模式是服务器主动连客户端，客户端在 NAT 后没有公网可达地址，服务器往往连不进来。所以被动模式对客户端防火墙和 NAT 更友好。</details>

<br>

<br>

## 知识点 2：主动模式与被动模式——谁发起数据连接
***
### 问题

主动和被动到底谁连谁？端口为什么有时是 20、有时又是随机端口？为什么客户端在 NAT 后，主动模式容易失败？

**你可能会想**：主动模式是不是客户端主动发起数据连接？

不是。**主动模式叫“主动”，是服务器主动发起数据连接，不是客户端主动。** 这一点最容易搞反。

<br>

### 核心概念与方案

两种模式的区别在于**数据连接由谁发起**：

- **主动模式（PORT）**：客户端通过控制连接告诉服务器自己的 IP 和端口，服务器从 **20 端口作为源端口**主动连客户端指定的端口。
- **被动模式（PASV）**：客户端发 `PASV`，服务器返回一个随机端口，客户端主动连服务器该端口。

被动模式对客户端防火墙更友好，因为数据连接也是客户端发起的；主动模式下服务器主动连客户端，客户端在 NAT 后没有公网可达地址，服务器就连不进来。

注意：主动模式叫“主动”，是**服务器主动**发起数据连接，不是客户端主动。

<br>

### 最小实验：只看 227 响应里是不是服务器地址和随机端口

环境前提：同上，已安装 `curl`，需要外网；公开 FTP 服务器可用性**需按环境核实**。下面只观察被动模式返回的地址和端口。

````bash
curl -v --max-time 10 ftp://ftp.gnu.org/gnu/README 2>&1 | grep '227'
````

**这次只看一件事**：`227` 响应里有没有服务器地址和一个随机端口。

可能看到类似：

````text
< 227 Entering Passive Mode (209,51,188,20,195,100).
````

括号里前四个数字是 IP，后两个数字是端口的高字节和低字节。**端口不是 20，而是服务器临时分配的随机端口。** 看到 `227`，说明服务器让客户端去连这个地址和端口，这就是被动模式。

如果没看到 `227`，可能是服务器不支持被动模式、网络被拦，或者 `curl` 走了主动模式，**需按环境核实**。

<br>

### 易错点与边界

坑一：**主动模式不是“客户端主动”**，数据连接是服务器从 20 端口主动连客户端。

坑二：**被动模式服务器端口随机**，不是固定 20；`227 Entering Passive Mode` 响应里会带 IP 和端口。

坑三：**防火墙要放行控制连接和数据连接**，只放 21 可能传不了文件。

坑四：**被动模式返回的 IP 在某些 NAT 环境下可能是内网地址**，客户端可能需要忽略该 IP、改用控制连接的对端地址，具体看客户端配置，**需按环境核实**。

<br>

### 一句话本质

**主动模式服务器来找你，被动模式你去找服务器；主动模式端口 20 是服务器源端口，被动模式端口是服务器随机端口。**

<br>

### 自测

如果客户端在 NAT 后，为什么被动模式更容易成功？

<details><summary>答案</summary>被动模式下数据连接由客户端主动发起，客户端在 NAT 后也能主动连服务器；主动模式是服务器主动连客户端，客户端在 NAT 后没有公网可达地址，服务器往往连不进来。所以被动模式更容易成功。</details>

<br>

<br>

## 完整可复现示例：用 curl 看 FTP 控制连接、227 响应和传输完成
***
你需要 Linux/macOS 或 WSL，已安装 `curl`，需要外网。下面每个步骤只看一件事，不展开无关字段。

````bash
set -e

echo "=== 1. 看 FTP 交互里的命令和响应码 ==="
curl -v --max-time 10 ftp://ftp.gnu.org/gnu/README 2>&1 | grep -E '^[<>] (USER|PASS|TYPE|227|150|226)' || true

echo "=== 2. 只看被动模式 227 响应 ==="
curl -v --max-time 10 ftp://ftp.gnu.org/gnu/README 2>&1 | grep '227' || true
````

可能的输出/现象：

````text
=== 1. 命令和响应码 ===
> USER anonymous
< 331 ...
> PASS ...
< 230 ...
> TYPE I
< 227 Entering Passive Mode (...)
< 150 ...
< 226 ...

=== 2. 227 响应 ===
< 227 Entering Passive Mode (209,51,188,20,195,100).
````

**关键观察点**：第 1 步看有没有 `USER`、`PASS`、`227`、`150`、`226`；第 2 步看 `227` 括号里是不是服务器地址和随机端口。

验证结果：`USER`/`PASS` 走控制连接，`227` 告诉客户端被动模式的数据地址和端口，`150` 表示数据连接即将打开，`226` 表示传输完成。**控制连接和数据连接配合完成文件传输，只放行 21 不够。**

注意：`ftp.gnu.org` 的匿名 FTP 服务可能已调整或不可用，不同网络环境下输出会不同；如果连不上，换一个可用的测试 FTP 服务器，**重点看响应码和命令顺序，不是背服务器地址**。`curl` 默认通常使用被动模式，想看主动模式需要显式指定 `--ftp-port` 等参数，具体取决于 `curl` 版本。

## 常见误区
***
- **以为能登录就说明 FTP 全通了**：登录只说明控制连接通了，数据连接可能没打通。
- **以为主动模式是客户端主动**：主动模式是服务器主动发起数据连接。
- **以为被动模式端口固定 20**：被动模式是服务器随机端口，20 是主动模式下服务器的源端口。
- **以为只放行 21 端口就行**：数据连接也要放行，否则能登录、不能传。
- **把 FTPS、SFTP 和 FTP 混为一谈**：FTPS 是 FTP 加 TLS；SFTP 是 SSH 上的文件传输，不走 FTP 的 21/20。
- **以为被动模式一定成功**：被动模式返回的 IP 在 NAT 环境下可能是内网地址，客户端配置也要配合。

## 自测三问
***
1. FTP 为什么要把控制连接和数据连接分开？只放行 21 端口为什么可能传不了文件？
2. 主动模式和被动模式分别是谁发起数据连接？端口分别是什么？
3. 为什么客户端在 NAT 后，被动模式更容易成功？被动模式返回的 IP 一定是公网地址吗？

<details><summary>参考答案</summary>1. FTP 把命令和文件分开：控制连接 21 传命令，数据连接传文件或目录列表；传大文件时不会把命令响应堵住。只放行 21 只通了控制连接，数据连接可能被防火墙/NAT 挡住，所以能登录、不能传。2. 主动模式由服务器从 20 端口主动连客户端；被动模式由客户端主动连服务器随机端口。3. 被动模式数据连接由客户端发起，客户端在 NAT 后也能主动连服务器；主动模式服务器主动连客户端，客户端在 NAT 后没有公网可达地址。被动模式返回的 IP 不一定是公网地址，某些 NAT 环境下可能是内网地址，客户端可能需要忽略该 IP、改用控制连接对端地址。</details>

<br>

## 总结
***
**FTP 用两条 TCP 连接：21 控制连接传命令，20 或随机端口传数据；主动模式服务器连客户端，被动模式客户端连服务器，后者更适合 NAT/防火墙；排查时不能只看 21，数据连接也要放行。**
