## 痛点引入
***
晚高峰看视频，前几分钟还是 1080p，突然卡住转圈，然后画面自动变糊了。

你可能会想：**播放器怎么知道我网速掉了？它为什么能自己降级，而不是直接卡死？**

再想一个场景：一部热门剧同时有几百万人看。如果所有人都去同一个源站拉流，源站扛得住吗？

这两个问题，正好引出流式视频最核心的两件事：**自适应码率（DASH）** 和 **内容分发网络（CDN）**。这一章咱们用一条问题链往前走：

1. 视频在网络里到底是什么，为什么动作片更容易卡？
2. 网速掉了，播放器为什么能自动变糊而不是卡死？
3. CDN 怎么把内容送到用户门口，为什么地理最近不等于网络最快？
4. Netflix 和 YouTube 路线有什么不同，为什么 Netflix 的视频不在 AWS？

## 优先级说明
***
这篇是流式视频与 CDN 的入门，面试常问，项目里做视频、静态资源加速也会用到。先分清主次：

**必须掌握（面试常问、项目真用得上）：**
- 视频是压缩编码后的比特流，存在 HTTP 服务器上就是普通文件或分块文件
- CBR 固定比特率，VBR 可变比特率；比特率不等于文件大小
- DASH：视频切块、每块多码率、客户端测带宽和缓冲水位自适应
- DASH 仍走 HTTP GET，不是新传输层协议
- CDN 把内容缓存到离用户更近的节点，减少骨干网传输和源站压力
- Enter Deep 节点多延迟低但贵，Bring Home 节点少好维护
- 地理最近不等于网络最快，要实时测延迟、丢包、负载
- Netflix 自建 Open Connect、偏 Push；YouTube 用 Google CDN、偏 Pull
- Netflix 的视频不在 AWS，Open Connect 才是视频分发网络

**了解即可（知道大概，不展开）：**
- MPD 清单文件的具体格式
- Anycast、HTTP 重定向等 CDN 调度方式
- Open Connect 设备部署和 ISP 合作细节
- 具体编码格式（H.264、H.265、AV1）的压缩率差异

**主线**：视频是按比特率吞吐的压缩文件 → 网速不同，用 DASH 分块多码率自适应 → 距离远、流量大，用 CDN 把内容推到离用户更近的地方 → Netflix 推热门、YouTube 拉长尾。

## 知识点 1：视频不是“流”出来的，是按比特率吞吐的压缩文件
***
### 问题

视频在网络里到底是什么？是“流”出来的，还是一个文件？为什么有的视频文件大小差不多，看动作片却更容易卡？

**你可能会想**：视频是不是存在某种“流式数据库”里，一边生成一边传？

不是。视频就是压缩编码后的图像流，存在 HTTP 服务器上通常就是**普通文件或分块文件**。播放器通过 HTTP 分段下载，边下边播。

<br>

### 核心概念与方案

先把视频换成你熟悉的场景：**视频像一本很厚的连环画，按每秒多少页的速度翻给你看。** 每秒翻的页数越多、每页越复杂，需要的“吞吐”就越大。

比特率分两种：

- **CBR（固定比特率）**：每秒数据量基本固定，适合实时流，编码简单。
- **VBR（可变比特率）**：画面复杂时比特率高，静态画面时比特率低，适合点播，能在相同画质下省带宽。

注意：**比特率不等于文件大小**，还要乘时长；VBR 视频在网络传输时的瞬时速率会随画面复杂度变化。

<br>

### 最小案例：看一组 VBR 数字，理解为什么动作片更容易卡

不需要联网，看下面这组数字：

````text
1080p 视频（VBR）：
平均比特率 4.5 Mbps
动作场景 12 Mbps
对话场景 1.2 Mbps
````

**这次只看一件事**：动作场景的瞬时比特率是不是远高于平均值。

是。同一个视频文件，动作场景瞬时传输速率可能远高于平均值；网速不够时，播放器更容易在动作场景卡住。

**结论**：VBR 让复杂画面多花流量、简单画面省流量；平均比特率不能用来判断瞬时卡顿。

<br>

### 易错点与边界

坑一：**视频不是“流式数据库”里流出来的**，HTTP 流通常就是普通文件或分块文件。

坑二：**VBR 不是固定速率**，画面复杂时传输速率会变高，别拿平均比特率去判断瞬时卡顿。

坑三：**比特率不等于文件大小**，还要看时长；4.5 Mbps 乘 3600 秒才是大约的文件大小。

坑四：**CBR 和 VBR 不是“谁更高级”**，实时流常用 CBR，点播常用 VBR，看场景。

<br>

### 一句话本质

**视频就是按比特率吞吐的压缩图像文件，VBR 让复杂画面多花流量、简单画面省流量；比特率不等于文件大小，平均比特率也不代表瞬时速率。**

<br>

### 自测

VBR 视频在爆炸特效场景，网络传输速率会变高还是变低？为什么？

<details><summary>答案</summary>会变高。VBR 下画面越复杂，编码器分配的比特率越高，瞬时传输速率也随之变高；静态或简单画面比特率低。所以动作场景更容易在网速不够时卡住。</details>

## 知识点 2：DASH——网速掉了，播放器为什么能自动变糊
***
### 问题

网速不同的用户怎么都看得动？网速突然掉下来，播放器为什么能自动变糊而不是直接卡死？DASH 到底改了哪一层？

**你可能会想**：DASH 是不是一种新的传输层协议，或者新的视频编码？

都不是。**DASH 仍走 HTTP，也不是编码格式，而是一种分发策略。** 它改的是“怎么把视频切块、怎么让客户端自己选码率”。

<br>

### 核心概念与方案

先把 DASH 换成你熟悉的场景：**传统 HTTP 流是食堂给什么吃什么，DASH 是自助餐看网速拿菜。**

传统 HTTP 流只有一个版本，网速慢就只能缓冲等待。**DASH（Dynamic Adaptive Streaming over HTTP）** 把视频切成几秒一块，每块准备多个码率版本；客户端实时测带宽和缓冲水位，网速快拉高清块，网速慢拉标清块。

关键点：

- **DASH 不是全新底层协议**，仍用 HTTP GET 下载视频块。
- **DASH 不是编码格式**，而是一种分发策略；H.264、H.265、AV1 才是编码。
- **自适应决策在客户端**，服务器只负责存多个版本和清单文件。
- 实际常配合 **MPD（Media Presentation Description）** 清单文件，告诉客户端有哪些码率、分块地址和时长。

<br>

### 最小案例：看一次码率切换流程

不需要真实播放器，看下面这段流程就能理解自适应：

````text
当前带宽 8 Mbps → 拉 5 Mbps 1080p 块
带宽掉到 2 Mbps → 自动降级拉 1 Mbps 480p 块
带宽恢复 → 再逐步升回高清块
````

**这次只看一件事**：带宽掉到 2 Mbps 时，播放器是不是换成了更低码率的块，而不是继续拉 1080p。

是。DASH 让播放器在“清晰度”和“不卡顿”之间动态权衡，而不是一条路走到黑。

**结论**：自适应在客户端，服务器只提供多版本和清单；切换点通常在分块边界。

<br>

### 易错点与边界

坑一：**DASH 仍走 HTTP**，不是新传输层协议，也不是 UDP。

坑二：**自适应在客户端**，服务器只提供多版本和清单，不替客户端决定拉哪个码率。

坑三：**DASH 不是编码格式**，是分发策略；H.264、H.265、AV1 才是编码。

坑四：**码率切换不是瞬间无感**，切换点通常在分块边界，块太长会导致适应慢。

<br>

### 一句话本质

**传统 HTTP 是食堂给什么吃什么，DASH 是自助餐看网速拿菜；切块、多码率、客户端自适应，仍走 HTTP。**

<br>

### 自测

如果不用 DASH，网速突降时播放器通常会怎样？DASH 又是怎么避免的？

<details><summary>答案</summary>不用 DASH 时，播放器通常只有一个码率版本，网速突降只能缓冲等待，表现为卡顿转圈。DASH 把视频切块并准备多个码率版本，客户端实时测带宽和缓冲水位，网速掉时切到低码率块，避免卡死，代价是清晰度下降。</details>

<br>

## 知识点 3：CDN——把内容放到离用户更近的地方
***
### 问题

CDN 怎么把内容送到用户门口？为什么“地理最近”不等于“网络最快”？Enter Deep 和 Bring Home 到底怎么选？

**你可能会想**：CDN 不就是在地理近的地方放个缓存吗？选离用户最近的那个节点不就行了？

地理近只是一个因素。**路由绕行、拥塞、跨运营商都可能让近节点更慢。** CDN 选节点要综合地理、实时网络质量和负载。

<br>

### 核心概念与方案

先把 CDN 换成你熟悉的场景：**CDN 是网络里的前置仓，哪个驿站快就去哪个。**

CDN 的核心是**把内容缓存到离用户更近的节点**，减少骨干网传输和源站压力。两种典型部署策略：

- **Enter Deep**：把服务器部署到接近用户接入网，延迟低，但节点多、维护贵，典型如 Akamai。
- **Bring Home**：部署到 IXP（互联网交换点）附近，节点少、好维护，延迟稍高。

服务器选择不能只看地理距离，还要**实时测量延迟、丢包、负载**，因为地理近不等于网络路径近。CDN 常通过 **DNS 重定向**把用户带到最近/最快的缓存节点；节点拥堵时也可能重定向到其他节点。

<br>

### 最小实验：用 C++ 模拟“首选节点负载高就切备用”

环境前提：Linux/macOS，或 Windows WSL；已安装 `g++` 且支持 C++17。下面代码只做本地模拟，不联网。

保存为 `cdn_route.cpp`：

````cpp
#include <iostream>
#include <map>
#include <string>

struct Node {
    std::string name;
    int load;      // 当前负载，0-100
    int capacity;  // 容量阈值
};

std::string cdn_route(const std::string& user_ip,
                      const std::map<std::string, Node>& nodes) {
    std::string loc;
    if (user_ip.rfind("192.168.", 0) == 0) {
        loc = "Beijing";
    } else if (user_ip.rfind("10.0.", 0) == 0) {
        loc = "Shanghai";
    } else {
        loc = "Unknown";
    }

    auto it = nodes.find(loc);
    if (it == nodes.end()) return "Backup-CDN";
    if (it->second.load >= it->second.capacity) return "Backup-CDN";
    return it->second.name;
}

int main() {
    std::map<std::string, Node> nodes = {
        {"Beijing",  {"CDN-BJ-01", 40, 80}},
        {"Shanghai", {"CDN-SH-02", 90, 80}},  // 负载过高
    };

    std::cout << cdn_route("192.168.1.10", nodes) << "\n";
    std::cout << cdn_route("10.0.0.5", nodes) << "\n";
    return 0;
}
````

编译运行：

````bash
g++ -std=c++17 -O2 cdn_route.cpp -o cdn_route
./cdn_route
````

**这次只看一件事**：上海节点负载 90 超过阈值 80 时，返回的是不是 `Backup-CDN`。

预期输出：

````text
CDN-BJ-01
Backup-CDN
````

北京节点负载正常，返回 `CDN-BJ-01`；上海节点负载过高，切到 `Backup-CDN`。

**结论**：CDN 选节点不是只看地理，还要看负载；真实调度还会结合实时延迟、丢包、带宽、成本等多维指标。

<br>

### 易错点与边界

坑一：**地理最近不等于网络最快**，路由绕行、拥塞、跨运营商都可能让近节点更慢。

坑二：**CDN 不只是“缓存”**，还包括调度、回源、安全、日志等。

坑三：**Enter Deep 和 Bring Home 是权衡**，不是谁绝对更好；节点多延迟低但成本高。

坑四：**DNS 重定向只是常见手段之一**，还有 Anycast、HTTP 重定向等调度方式。

<br>

### 一句话本质

**CDN 是网络里的前置仓，哪个驿站快就去哪个；地理近只是一个因素，实时网络质量和负载同样重要。**

<br>

### 自测

为什么 CDN 选节点不能只看地理距离？实时测量通常看哪些指标？

<details><summary>答案</summary>地理近不代表网络路径近，路由绕行、拥塞、跨运营商都可能让近节点更慢。实时测量通常看延迟、丢包、可用带宽、节点负载等指标，综合决定把用户调度到哪个节点。</details>

## 知识点 4：Netflix 推，YouTube 拉
***
### 问题

两大视频巨头路线一样吗？为什么 Netflix 要自建 CDN 把设备放进 ISP 机房，而 YouTube 用 Google 全球 CDN？Push 和 Pull 到底差在哪？

**你可能会想**：Netflix 用 AWS，那视频文件也在 AWS 上吧？

不是。Netflix 的控制面、登录、推荐、账单等在 AWS，但**视频文件在自建的 Open Connect**，不在 AWS。

<br>

### 核心概念与方案

先把两家换成你熟悉的场景：

- **Netflix 像总仓提前把热门大片推到门店**（Push）。自建私有 CDN **Open Connect**，在 ISP 机房部署缓存设备，热门视频提前推到本地缓存。
- **YouTube 像门店下单后再向上层调货**（Pull）。用 Google 全球 CDN，本地缓存没有就向上层拉，拉到后再给用户，广泛使用 DASH。

Push 是“提前把热门内容推到边缘”，适合可预测的热门内容；Pull 是“用户点了再逐层回源拉”，适合长尾和不可预测的访问。两者不是绝对对立，实际系统常混合使用。

<br>

### 最小案例：用对比表看清两条路线

````text
平台       CDN 模式             内容分发方式           典型特点
Netflix    自建 Open Connect    Push 热门内容到 ISP    热门剧提前铺货，减少骨干网传输
YouTube    Google 全球 CDN      Pull 按需回源          长尾内容按需拉取，缓存后再给用户
````

**这次只看一件事**：Netflix 是 Push 为主，YouTube 是 Pull 为主。

**结论**：Netflix 偏“提前铺货”，YouTube 偏“按需调货”，但都在用 CDN 把内容推到离用户更近的地方。

<br>

### 易错点与边界

坑一：**Netflix 的视频不在 AWS**，Open Connect 才是视频分发网络。

坑二：**Push 和 Pull 不是绝对对立**，可以混合；热门内容 Push、长尾内容 Pull 很常见。

坑三：**自建 CDN 成本高**，不是所有公司都适合；Netflix 体量大才摊得平。

坑四：**Open Connect 放进 ISP 机房不是“白送”**，是双方在带宽成本上的合作安排。

<br>

### 一句话本质

**Netflix 总仓提前发货到门店，YouTube 下单后门店再调货；一个偏 Push 热门，一个偏 Pull 长尾。**

<br>

### 自测

为什么 Netflix 要在 ISP 机房部署 Open Connect，而不是全部放云端？

<details><summary>答案</summary>Netflix 体量大、热门内容可预测，把缓存设备放进 ISP 机房可以提前把热门视频推到离用户更近的地方，减少骨干网传输和延迟，也降低带宽成本。全部放云端则流量要经过骨干网，成本和延迟都更高。这是 Netflix 体量下摊得平的私有 CDN 方案，不是所有公司都适合。</details>

<br>

## 常见误区
***
- **以为视频是“流式数据库”流出来的**：HTTP 流通常就是普通文件或分块文件。
- **拿平均比特率判断瞬时卡顿**：VBR 下动作场景瞬时比特率可能远高于平均值。
- **以为 DASH 是新传输层协议**：DASH 仍走 HTTP，是分发策略，不是编码格式。
- **以为自适应在服务器**：DASH 的自适应决策在客户端，服务器只提供多版本和清单。
- **以为 CDN 只看地理距离**：路由、拥塞、跨运营商、负载都会影响，地理近不等于网络快。
- **以为 Netflix 视频在 AWS**：控制面在 AWS，视频文件在 Open Connect。
- **以为 Push 和 Pull 绝对对立**：实际系统常混合使用，热门 Push、长尾 Pull。

## 自测三问
***
1. DASH 如何解决带宽波动导致卡顿？它为什么仍能走 HTTP？
2. Enter Deep 和 Bring Home 分别适合什么场景？为什么地理最近不等于网络最快？
3. Netflix 的 Push 和 YouTube 的 Pull 有什么区别？为什么 Netflix 的视频不在 AWS？

<details><summary>参考答案</summary>1. DASH 把视频切块、每块准备多个码率版本，客户端实时测带宽和缓冲水位，网速掉时切低码率块，避免卡死。它仍走 HTTP GET 下载视频块，不是新传输层协议，也不是编码格式。2. Enter Deep 把服务器部署到接近用户接入网，延迟低但节点多、维护贵；Bring Home 部署到 IXP 附近，节点少、好维护、延迟稍高。地理近不代表网络路径近，路由绕行、拥塞、跨运营商都可能让近节点更慢，所以要实时测延迟、丢包、负载。3. Netflix 偏 Push，自建 Open Connect 把热门内容提前推到 ISP 机房；YouTube 偏 Pull，用 Google 全球 CDN 按需回源拉取。Netflix 的视频文件不在 AWS，而在 Open Connect；AWS 主要承载控制面、登录、推荐、账单等。</details>

<br>

<br>

## 总结
***
**视频靠压缩和 DASH 自适应解决网速变化，靠 CDN 前置仓解决距离和流量；Netflix 推热门、YouTube 拉长尾，各自用 CDN 撑起全球播放；地理近不等于网络快，CDN 调度要综合延迟、丢包和负载。**
