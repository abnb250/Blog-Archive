## 痛点引入
***
你开视频会议，网络偶尔丢一两个包。画面花一下，声音还能继续。

你可能会想：**丢包不是该重传吗？为什么不等重传，画面花一下就过去了？**

如果换成 TCP，丢一个包就要等重传，后面所有数据都得排队，会议可能直接卡住。UDP 就是在这种“宁可丢一点，也别全卡住”的场景里出场的。

再想一个问题：UDP 首部只有 8 字节，它到底装了什么？检验和发现错了，UDP 会帮你重传吗？

这一章咱们用一条问题链往前走：

1. UDP 到底提供什么服务，比 IP 多了什么？
2. 为什么实时音视频和 DNS 会选它，而不是 TCP？
3. 8 字节首部装了什么，长度字段算不算首部？
4. 检验和发现错误后会重传吗，应用层 `recvfrom` 拿到的是首部还是数据？

## 优先级说明
***
这篇是 UDP 的核心，面试常问，项目里做实时音视频、DNS、游戏、QUIC 也会用到。先分清主次：

**必须掌握（面试常问、项目真用得上）：**
- UDP 只比 IP 多做两件事：多路复用/分解和少量差错检测
- UDP 无连接、不保证可靠、不保证按序、无拥塞控制、无流量控制
- 应用选 UDP 的四个常见理由：发送控制更精细、无需建连、无连接状态、首部开销小
- 首部四个字段各 16 位：源端口、目的端口、长度、检验和
- 长度字段包含 8 字节首部，应用数据长度 = 长度字段 − 8
- 检验和只“验伤”不“治病”，发现错误通常直接丢弃，不重传
- 应用层 `recvfrom` 拿到的是应用数据，不是 UDP 首部

**了解即可（知道大概，不展开）：**
- 检验和的反码运算细节
- IPv4 下 UDP 检验和可选、IPv6 下通常必选
- 原始套接字和抓包看首部的具体方法
- QUIC 在 UDP 上如何实现可靠和拥塞控制

**主线**：UDP 是极简运输层 → 只做端口分发和轻量校验 → 首部 8 字节 → 检验和发现错误就丢，不重传 → 应用层看不到首部，只拿到数据。

## 知识点 1：UDP 是极简运输层协议——快、轻、不管售后
***
### 问题

UDP 到底提供什么服务？它比 IP 多了什么？为什么实时音视频和 DNS 会选它，而不是 TCP？

**你可能会想**：UDP 不可靠，那为什么不用 TCP？可靠不是更好吗？

可靠不是免费的。TCP 要握手、要确认、要重传、要按序交付，丢一个包后面全得等。**视频会议宁可丢一帧，也不愿整个会议卡住。** UDP 就是把“要不要重传、要不要等”这个决定权交给应用。

<br>

### 核心概念与方案

先把 UDP 换成你熟悉的场景：**UDP 像寄明信片，贴上地址就扔出去，能不能收到看命；TCP 像挂号信，要签收、丢了重寄。**

UDP 只比 IP 多做了两件核心事：

- **多路复用/分解**：靠端口找到进程。
- **少量差错检测**：靠检验和发现比特差错。

它无连接、不保证可靠、不保证按序、没有拥塞控制、没有流量控制。

应用选 UDP 的常见理由有四个：

- **发送控制更精细**：应用自己决定什么时候发、发多少。
- **无需建连**：不用三次握手，直接发。
- **无连接状态**：服务器不用为每个客户端维护连接状态。
- **首部开销小**：8 字节，比 TCP 首部小得多。

所以“UDP 不可靠”不是缺点本身，而是把控制权交还给应用：你要什么机制，自己在上层补。QUIC/HTTP3 就是在 UDP 上自己实现可靠和拥塞控制的例子。

<br>

### 最小案例：看一次 DNS 查询走 UDP 的文字流程

不需要敲代码，看下面这段流程就能理解 UDP 的角色：

````text
DNS 客户端构造查询 → UDP 加源端口/目的端口 53 → IP 发出
没响应？UDP 不知道，靠 DNS 客户端自己超时重发。
````

**这次只看一件事**：UDP 有没有帮 DNS 做超时重发。

没有。**UDP 只负责“贴端口、发出去、做个轻量校验”，丢包恢复、超时重传这些事，UDP 不管，得应用自己来。**

**结论**：DNS 选 UDP，是因为查询短、一次往返就能搞定，握手开销小；视频会议选 UDP，是因为宁可丢帧也不愿被重传卡住后面所有数据。

<br>

### 易错点与边界

坑一：**UDP 无连接不代表不需要端口**，端口仍然是多路分解的关键。

坑二：**UDP 不可靠不代表不能用**，QUIC/HTTP3 就在 UDP 上自己实现可靠和拥塞控制。

坑三：**UDP 没有拥塞控制，不等于“想发多快就发多快”**，应用自己不管，可能把网络和其他流量一起拖垮。

坑四：**“无连接状态”是指 UDP 不维护连接状态**，不是指应用不能自己维护会话。

<br>

### 一句话本质

**UDP 是把包裹扔给 IP 就下班的信使：快、轻、不管售后；可靠性、重传、拥塞控制，要的话应用自己补。**

<br>

### 自测

DNS 普通查询为什么常用 UDP 而不是 TCP？视频会议又为什么常考虑 UDP？

<details><summary>答案</summary>DNS 普通查询报文短，UDP 不用握手、开销小，一次往返就能搞定；TCP 要三次握手，反而拖慢。视频会议更怕延迟和卡顿，能容忍少量丢包；TCP 丢一个包要等重传，后面所有数据排队，会议可能卡住。UDP 让应用自己决定要不要重传、要不要等。</details>

<br>

## 知识点 2：UDP 首部与检验和——8 字节标签，验伤不治病
***
### 问题

UDP 首部只有 8 字节，装了什么？长度字段算不算首部？检验和能纠错吗？发现错误后会重传吗？

**你可能会想**：检验和发现错误，UDP 应该会重传吧？

不会。**UDP 检验和发现错误，通常直接丢弃，不重传。** 它只“验伤”，不“治病”。

<br>

### 核心概念与方案

先把 UDP 首部换成你熟悉的场景：**首部就是包裹上的极简标签：从哪来、到哪去、包多大、有没有坏。**

四个字段各 16 位：

- **源端口**：从哪个进程来。
- **目的端口**：到哪个进程去。
- **长度**：包含 8 字节首部和数据，所以应用数据长度 = 长度字段 − 8。
- **检验和**：用反码运算检测比特差错；发现错误通常直接丢弃，不重传。

注意：UDP 首部在网络上明文传输，但**应用层通过普通 Socket API 看不到它**：内核在发送时加首部，接收时剥掉首部再交给应用。想看首部，得用抓包工具或原始套接字。

<br>

### 最小实验：只看 recvfrom 拿到的是 8 字节数据还是 16 字节首部+数据

环境前提：Linux/macOS，或 Windows WSL；已安装 `g++` 和 `nc`。下面只在本机回环地址上运行，不对外网开放。

保存为 `udp_recv_demo.cpp`：

````cpp
#include <arpa/inet.h>
#include <netinet/in.h>
#include <sys/socket.h>
#include <unistd.h>

#include <iostream>

int main() {
    const int port = 9999;

    int sock = socket(AF_INET, SOCK_DGRAM, 0);
    if (sock < 0) {
        std::cerr << "socket failed\n";
        return 1;
    }

    sockaddr_in addr{};
    addr.sin_family = AF_INET;
    addr.sin_addr.s_addr = INADDR_ANY;
    addr.sin_port = htons(port);

    if (bind(sock, reinterpret_cast<sockaddr*>(&addr), sizeof(addr)) < 0) {
        std::cerr << "bind failed\n";
        close(sock);
        return 1;
    }

    std::cout << "UDP server listening on " << port << "\n";

    char buf[2048];
    sockaddr_in client{};
    socklen_t clientLen = sizeof(client);

    ssize_t n = recvfrom(sock, buf, sizeof(buf) - 1, 0,
                         reinterpret_cast<sockaddr*>(&client), &clientLen);
    if (n < 0) {
        std::cerr << "recvfrom failed\n";
        close(sock);
        return 1;
    }

    buf[n] = '\0';
    std::cout << "received bytes: " << n << "\n";
    std::cout << "payload: " << buf << "\n";

    close(sock);
    return 0;
}
````

编译运行：

````bash
g++ -std=c++17 -O2 udp_recv_demo.cpp -o udp_recv_demo
./udp_recv_demo
````

另开终端发送 8 字节数据：

````bash
echo -n "HelloUDP" | nc -u -w1 127.0.0.1 9999
````

**这次只看一件事**：接收端输出的 `received bytes` 是 8，还是 16。

预期输出：

````text
UDP server listening on 9999
received bytes: 8
payload: HelloUDP
````

是 8，不是 16。**如果 `recvfrom` 拿到的是“8 字节首部 + 8 字节数据”，应该是 16；但实际是 8，说明 UDP 首部已经被内核处理掉了，应用层只拿到数据。**

如果输出不是 8，先检查发送端发的是不是正好 8 字节，端口是否一致。

<br>

### 易错点与边界

坑一：**长度字段包含 8 字节首部**，算数据长度时要减 8。

坑二：**检验和只能“验伤”不能“治病”**，更不能替代重传。

坑三：**差错检查不等于可靠传输**，UDP 发现错了就丢，不保证送达。

坑四：**应用层 `recvfrom` 拿到的是应用数据，不是 UDP 首部**；首部已经被内核处理掉了，别把应用数据前 6 字节当成首部去解析。

<br>

### 一句话本质

**UDP 首部就是极简标签：从哪来、到哪去、包多大、有没有坏；长度包含首部，检验和发现错误就丢，不重传，应用层看不到首部。**

<br>

### 自测

UDP 长度字段是 2000 字节，应用数据是多少字节？检验和发现错误后，UDP 会做什么？

<details><summary>答案</summary>应用数据是 2000 − 8 = 1992 字节，因为长度字段包含 8 字节首部。检验和发现错误后，UDP 通常直接丢弃该报文，不重传；可靠恢复要靠应用层或上层协议。</details>

<br>

## 完整可复现示例：C++ 接收端 + 发送端 + 可选抓包
***
你需要 Linux/macOS 或 WSL，已安装 `g++` 和 `nc`。下面把 UDP 接收和发送串起来，只看关键观察点。

终端 1 编译并运行接收端：

````bash
g++ -std=c++17 -O2 udp_recv_demo.cpp -o udp_recv_demo
./udp_recv_demo
````

终端 2 发送 8 字节：

````bash
echo -n "HelloUDP" | nc -u -w1 127.0.0.1 9999
````

终端 1 预期输出：

````text
UDP server listening on 9999
received bytes: 8
payload: HelloUDP
````

**关键观察点**：`received bytes: 8`，不是 16。

如果想看真正的 UDP 首部，可以在终端 3 抓包（需要权限）：

````bash
# 需要权限；先启动接收端，再抓包和发送
sudo tcpdump -ni lo -XX udp port 9999 -c 1
````

抓包输出可能类似：

````text
0x0000:  4500 001c ...  ; IP 首部
0x0010:  3039 270f 0008 ...  ; UDP 首部：源端口、目的端口、长度、检验和
0x0020:  4865 6c6c 6f55 4450  ; "HelloUDP"
````

验证结果：UDP 首部确实在网络上传输，长度字段包含 8 字节首部和数据；但应用层通过 `recvfrom` 只拿到数据部分。**应用层看到 8 字节，网络上看到 8 字节首部 + 8 字节数据。**

注意：`nc -u` 的可用性和参数在不同系统上可能不同；没有 `nc` 可以用另一个 UDP 发送程序。抓包需要权限，没有权限时看 C++ 输出的 `received bytes: 8` 就够说明问题，**需按环境核实**。

## 排障速查表
***
| 现象 | 先查什么 | 常用命令/观察点 | 解释 |
|---|---|---|---|
| UDP 服务“没反应” | 服务是否启动、端口是否对、防火墙 | `ss -lunp \| grep ':端口'`；抓包看有没有 UDP 报文 | UDP 无连接，没有握手失败提示，容易表现为“发出去没回” |
| `recvfrom` 收到的字节数不对 | 发送端实际发了多少、长度字段 | 看发送端字节数；抓包看 UDP 长度字段 | 长度字段包含 8 字节首部；应用层只拿到数据部分 |
| 应用数据前几个字节被当成首部解析 | 是否误以为 `recvfrom` 返回首部 | 看 `recvfrom` 返回值；抓包对比 | 应用层拿不到 UDP 首部，首部已被内核剥离 |
| UDP 包被丢弃 | 检验和错误、缓冲区满、防火墙 | 抓包看检验和；查系统丢包统计 | 检验和错误通常直接丢弃；缓冲区满或防火墙也会丢 |
| UDP 发送太猛把网络拖垮 | 是否自己做拥塞控制 | 看发送速率；查应用层限速 | UDP 没有拥塞控制，应用不管可能影响其他流量 |
| DNS 查询超时 | 是否 UDP 丢包、是否该重试 | `dig` 重试；抓包看有没有响应 | UDP 不重传，超时要应用自己重发；DNS 客户端通常有重试机制 |
| 同端口 TCP 能用 UDP 不能用 | 是否绑错协议 | `ss -ltnp` 和 `ss -lunp` 分别看 | TCP 和 UDP 端口空间分开，要确认服务实际监听的是哪个 |

## 常见误区
***
- **以为 UDP 无连接就不需要端口**：端口仍然是多路分解的关键。
- **以为 UDP 不可靠所以不能用**：QUIC/HTTP3 就在 UDP 上自己实现可靠和拥塞控制。
- **以为 UDP 没有拥塞控制就可以随便发**：应用不管可能把网络和其他流量一起拖垮。
- **把长度字段当成纯数据长度**：长度包含 8 字节首部，数据长度要减 8。
- **以为检验和能纠错或触发重传**：检验和只验伤，发现错误通常直接丢弃，不重传。
- **以为 `recvfrom` 能拿到 UDP 首部**：应用层只拿到数据，首部已被内核剥离。
- **把“无连接状态”当成“应用不能维护会话”**：UDP 不维护连接状态，应用可以自己维护会话。

## 自测三问
***
1. UDP 除多路复用/分解外还提供什么？它为什么不保证可靠和按序？
2. 应用选 UDP 的四个常见理由是什么？
3. UDP 检验和发现错误后会重传吗？应用层 `recvfrom` 拿到的是首部还是数据？

<details><summary>参考答案</summary>1. UDP 还提供少量差错检测（检验和）。它不保证可靠和按序，是因为它只做“贴端口、发出去、轻量校验”，重传、确认、按序交付这些机制它不实现，把控制权交给应用。2. 发送控制更精细、无需建连、无连接状态、首部开销小。3. 检验和发现错误通常直接丢弃，不重传；可靠恢复要靠应用层或上层协议。应用层 `recvfrom` 拿到的是应用数据，不是 UDP 首部，首部已被内核处理掉。</details>

<br>

<br>

## 总结
***
**UDP 是运输层极简主义代表：无连接、无重传、无拥塞控制，只靠 8 字节首部做进程寻址和轻量校验，把可靠性难题甩给应用层，换取速度和自由；检验和只验伤不治病，应用层看不到首部，只拿到数据。**
