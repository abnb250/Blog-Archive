## 痛点引入
***
DNS 查域名、视频会议、直播常考虑 UDP。**UDP 看起来只会“丢包”，为什么还离不开它？它的首部到底有什么？检验和发现错误后会重传吗？**  
先别急着背“无连接、不可靠”这几个字，先看一个具体场景：你开视频会议，网络偶尔丢一两个包，画面花一下但声音还能继续；如果换成 TCP，丢一个包就要等重传，后面所有数据都得排队，会议可能直接卡住。UDP 就是在这种“宁可丢一点，也别全卡住”的场景里出场的。再想一个问题：UDP 首部只有 8 字节，它到底装了什么？检验和发现错了，UDP 会帮你重传吗？

## 知识点 1：UDP 是极简运输层协议
***
### 问题
UDP 到底提供什么服务？它比 IP 多了什么？为什么实时音视频和 DNS 会选它，而不是 TCP？

<br>

### 方案
UDP 只比 IP 多做了两件核心事：**多路复用/分解**（靠端口找到进程）和**少量差错检测**。它无连接、不保证可靠、不保证按序、没有拥塞控制、没有流量控制。  
应用选 UDP 的常见理由有四个：**发送控制更精细、无需建连、无连接状态、首部开销小**。  
- 实时音视频：宁可丢帧，也不愿被 TCP 重传卡住后面所有数据；  
- DNS 查询：查询短，UDP 一次往返就能搞定，握手开销小；  
- 游戏、QUIC：在 UDP 上自己实现需要的可靠性和拥塞控制，而不是全盘接受 TCP 的机制。  
所以“UDP 不可靠”不是缺点本身，而是把控制权交还给应用：你要什么机制，自己在上层补。

<br>

### 最小示例
```text
DNS 客户端构造查询 → UDP 加源端口/目的端口 53 → IP 发出
没响应？UDP 不知道，靠 DNS 客户端自己超时重发。
```

结论：UDP 只负责“贴端口、发出去、做个轻量校验”，丢包恢复、超时重传这些事，UDP 不管，得应用自己来。

<br>

### 一句话本质
**UDP 是把包裹扔给 IP 就下班的信使：快、轻、不管售后。**

<br>

### 易错点
坑一：**UDP 无连接不代表不需要端口**，端口仍然是多路分解的关键。  
坑二：**UDP 不可靠不代表不能用**，QUIC/HTTP3 就在 UDP 上自己实现可靠和拥塞控制。  
坑三：**UDP 没有拥塞控制，不等于“想发多快就发多快”**，应用自己不管，可能把网络和其他流量一起拖垮。  
坑四：**“无连接状态”是指 UDP 不维护连接状态**，不是指应用不能自己维护会话。

<br>

## 知识点 2：UDP 首部与检验和
***
### 问题
UDP 首部只有 8 字节，装了什么？长度字段算不算首部？检验和能纠错吗？发现错误后会重传吗？

<br>

### 方案
UDP 首部四个字段各 16 位：**源端口、目的端口、长度、检验和**。  
- **长度**：包含 8 字节首部和数据，所以应用数据长度 = 长度字段 − 8。  
- **检验和**：用反码运算检测比特差错；**发现错误通常直接丢弃，不重传**。可靠恢复要靠应用层或上层协议。  
注意：UDP 检验和是“验伤”，不是“治病”；它只能告诉你这个报文可能坏了，不能帮你修好，也不会自动重发。  
另外，UDP 首部在网络上明文传输，但**应用层通过普通 Socket API 看不到它**：内核在发送时加首部，接收时剥掉首部再交给应用。想看首部，得用抓包工具或原始套接字。

<br>

### 最小示例
```text
UDP 首部（8 字节）：
源端口(16) | 目的端口(16)
长度(16)   | 检验和(16)
应用数据...
```

结论：UDP 首部就是极简标签：从哪来、到哪去、包多大、有没有坏。

<br>

### 一句话本质
**UDP 首部就是极简标签：从哪来、到哪去、包多大、有没有坏。**

<br>

### 易错点
坑一：**长度字段包含 8 字节首部**，算数据长度时要减 8。  
坑二：**检验和只能“验伤”不能“治病”**，更不能替代重传。  
坑三：**差错检查不等于可靠传输**，UDP 发现错了就丢，不保证送达。  
坑四：**应用层 `recvfrom` 拿到的是应用数据，不是 UDP 首部**；首部已经被内核处理掉了，别把应用数据前 6 字节当成首部去解析。

<br>

## 完整可复现示例：用 C++ 观察 UDP 应用数据与首部边界
***
这个示例分两部分：先用 C++ 写一个 UDP 接收端，证明应用层 `recvfrom` 拿到的是**应用数据**，不是 UDP 首部；再用 `tcpdump` 抓包看真正的 UDP 首部。  
注意：抓包需要权限；没有权限时，只看 C++ 部分的输出也能理解“应用层看不到首部”。

```cpp
// udp_recv_demo.cpp
// 编译：g++ -std=c++17 -O2 udp_recv_demo.cpp -o udp_recv_demo
// 运行：./udp_recv_demo
// 环境：Linux/POSIX

#include <arpa/inet.h>
#include <netinet/in.h>
#include <sys/socket.h>
#include <unistd.h>

#include <cstring>
#include <iostream>
#include <string>

int main() {
    const int port = 9999;

    int sock = socket(AF_INET, SOCK_DGRAM, 0);
    if (sock < 0) {
        std::cerr << "socket failed\n";
        return 1;
    }

    sockaddr_in addr{};
    addr.sin_family = AF_INET;
    addr.sin_addr.s_addr = INADDR_ANY;
    addr.sin_port = htons(port);

    if (bind(sock, reinterpret_cast<sockaddr*>(&addr), sizeof(addr)) < 0) {
        std::cerr << "bind failed\n";
        close(sock);
        return 1;
    }

    std::cout << "UDP server listening on " << port << "\n";

    char buf[2048];
    sockaddr_in client{};
    socklen_t clientLen = sizeof(client);

    ssize_t n = recvfrom(sock, buf, sizeof(buf) - 1, 0,
                         reinterpret_cast<sockaddr*>(&client), &clientLen);
    if (n < 0) {
        std::cerr << "recvfrom failed\n";
        close(sock);
        return 1;
    }

    buf[n] = '\0';
    std::cout << "received bytes: " << n << "\n";
    std::cout << "payload: " << buf << "\n";

    close(sock);
    return 0;
}
```

另开终端发送数据：

```bash
echo -n "HelloUDP" | nc -u -w1 127.0.0.1 9999
```

C++ 端输出：

```text
UDP server listening on 9999
received bytes: 8
payload: HelloUDP
```

结论：`recvfrom` 拿到的是 8 字节应用数据，**不是** 8 字节 UDP 首部加 8 字节数据。UDP 首部已经被内核处理掉了。  
如果想看真正的 UDP 首部，可以抓包：

```bash
# 需要权限；先启动 C++ 接收端，再另开终端抓包和发送
sudo tcpdump -ni lo -XX udp port 9999 -c 1
```

现象可能类似：

```text
0x0000:  4500 001c ...  ; IP 首部
0x0010:  3039 270f 0008 ...  ; UDP 首部：源端口、目的端口、长度、检验和
0x0020:  4865 6c6c 6f55 4450  ; "HelloUDP"
```

验证结果：UDP 首部确实在网络上传输，长度字段包含 8 字节首部和数据；但应用层通过 `recvfrom` 只拿到数据部分。  
注意：`nc -u` 的可用性和参数在不同系统上可能不同；没有 `nc` 可以用另一个 UDP 发送程序。抓包需要权限，没有权限时看 C++ 输出的“received bytes: 8”就够说明问题。
