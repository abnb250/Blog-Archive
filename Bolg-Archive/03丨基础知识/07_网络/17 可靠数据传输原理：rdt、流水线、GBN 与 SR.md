## 痛点引入
***
你写了一个网络程序，调 `send()` 发一段数据。底层 IP 会丢包、比特会翻转、包会乱序。

你可能会想：**底层都不可靠了，为什么我用 TCP 的时候感觉数据总能完整到达？可靠传输到底靠什么？**

再想一个问题：如果每个包都要等对方确认再发下一个，链路带宽很高、延迟很大时，会发生什么？这就是停等协议的瓶颈。

这一章咱们用一条问题链往前走：

1. 不可靠信道上怎么保证可靠？为什么不能直接发？
2. 加了校验和就够了吗？ACK 丢了怎么办？重复包怎么处理？
3. 停等太慢，流水线怎么提速？
4. 丢了一个包，GBN 和 SR 各自怎么处理，差在哪？

<br>

<br>

## 优先级说明
***
这篇是可靠传输的理论基础，面试常问，理解 TCP 重传、SACK、QUIC 也会用到。先分清主次：

**必须掌握（面试常问、项目真用得上）：**
- 可靠传输四件套：校验和、序号、确认、定时重传
- rdt 1.0 到 3.0 每一步解决了什么问题
- 停等协议正确但带宽利用率低
- 流水线：不等确认，连续发多个包
- GBN：接收方只按序收，丢包后重传该包及之后所有包
- SR：接收方缓存乱序包，发送方只重传丢失的包
- SR 窗口不能超过序号空间一半，否则序号歧义
- TCP 更像 GBN 累积确认 + SR 选择重传的混合

**了解即可（知道大概，不展开）：**
- rdt 2.1/2.2 的状态机细节
- SR 发送方每个包的定时器管理
- TCP SACK 选项的具体格式
- 窗口大小和序号空间的精确计算

**主线**：信道不可靠 → 加校验和发现坏包 → 加序号去重 → 加 ACK 和定时器处理丢包 → 停等太慢 → 流水线提吞吐 → GBN 简单但浪费，SR 精细但要缓存。

## 知识点 1：从 rdt 1.0 到 rdt 3.0——一步步加机制
***
### 问题

不可靠信道上怎么保证可靠？为什么不能直接发？加了校验和就够了吗？ACK 丢了怎么办？重复包怎么处理？

**你可能会想**：TCP 可靠不就是“发出去、对方收到”吗？为什么还要设计这么多协议？

因为底层信道会出四种问题：**比特损坏、丢包、ACK 丢失、重复包**。每一种都要单独对付，少一个机制都不行。

<br>

### 核心概念与方案

先把可靠传输换成你熟悉的场景：**两个人隔着一堵墙传纸条，墙会掉纸条、纸条会模糊。**

咱们一步步加机制：

- **rdt 1.0**：假设信道完全可靠。发送方直接发，接收方直接收。这是理想情况，不是真实网络。
- **rdt 2.0**：加校验和。接收方发现比特坏了回 NAK，好了回 ACK。但 ACK/NAK 本身也可能坏。
- **rdt 2.1/2.2**：加 0/1 序号，防止 ACK 丢失导致发送方重发、接收方重复接收。rdt 2.2 进一步取消 NAK，只用 ACK 和超时来处理坏包。
- **rdt 3.0**：加定时器，超时没收到 ACK 就重传，形成“停等协议”：发一个包，等确认，再发下一个。

停等协议正确，但慢：发送方发一个包后要等一个 RTT，高速高延迟网络中带宽利用率很低。这就是后面要引入流水线的原因。

<br>

### 最小实验：只看停等协议发一个包后是不是在等 ACK

环境前提：Linux/macOS，或 Windows WSL；已安装 `g++` 且支持 C++17。下面只做本地模拟，不联网。

保存为 `stop_and_wait.cpp`：

````cpp
#include <iostream>

int main() {
    int base = 0;
    const int total = 3;

    for (int next = 0; next < total; ++next) {
        std::cout << "发送包 " << next << "，等待 ACK...\n";
        std::cout << "收到 ACK " << next << "，窗口滑动\n";
        base++;
    }

    std::cout << "全部发送完成，base=" << base << "\n";
    return 0;
}
````

编译运行：

````bash
g++ -std=c++17 -O2 stop_and_wait.cpp -o stop_and_wait
./stop_and_wait
````

**这次只看一件事**：每发一个包，是不是先打印“等待 ACK”，再打印“收到 ACK”。

预期输出：

````text
发送包 0，等待 ACK...
收到 ACK 0，窗口滑动
发送包 1，等待 ACK...
收到 ACK 1，窗口滑动
发送包 2，等待 ACK...
收到 ACK 2，窗口滑动
全部发送完成，base=3
````

**关键观察点**：发送包 0 之后，有没有在收到 ACK 0 之前发下一个包。

没有。这就是停等：**发一个，等一个，再发下一个。** 如果输出顺序不是这样，说明模拟逻辑写错了。

注意：这个程序只模拟停等的顺序，不模拟超时和重传；真实 rdt 3.0 还要处理 ACK 丢失后的超时重发。

<br>

### 易错点与边界

坑一：**定时器太短会无谓重传**，太长反应慢；超时时间要结合 RTT 估计。

坑二：**停等协议在高速高延迟网络中带宽利用率很低**，因为大部分时间在等 ACK。

坑三：**rdt 2.0 的 NAK 不是必须的**，rdt 2.2 取消 NAK 也能工作，靠 ACK 和超时。

坑四：**序号不是用来排序的，至少 rdt 2.x 里是用来去重的**；乱序处理要到流水线协议才展开。

<br>

### 一句话本质

**可靠传输就是：编号、确认、超时重传；坏了重来，重复丢弃。**

<br>

### 自测

rdt 3.0 为什么叫停等协议？它的瓶颈在哪？如果链路带宽很高、RTT 很大，停等协议会浪费什么？

<details><summary>答案</summary>停等协议发一个包后要等 ACK 才能发下一个，所以叫停等。瓶颈在于大部分时间在等 ACK，链路空闲。带宽高、RTT 大时，发送方等一个 RTT 才能发下一个，带宽利用率很低，浪费的是链路容量。</details>

<br>

## 知识点 2：流水线、GBN 与 SR——一人犯错全队重来 vs 谁犯错谁重来
***
### 问题

停等太慢，怎么提速？连续发多个包后，丢了一个包，后面怎么办？GBN 和 SR 各自怎么处理乱序和重传？

**你可能会想**：连续发多个包，丢了一个就重传那一个不就行了？

可以，但接收方要缓存乱序包，发送方要记住每个包的确认状态。GBN 选了更简单的做法：**丢一个，后面全丢，重传该包及之后所有包。** SR 选了更精细的做法：**只重传丢的那个，其他缓存。**

<br>

### 核心概念与方案

先把流水线换成你熟悉的场景：**停等是一个人送快递，送一个等签收再送下一个；流水线是同时派出多个快递员。**

**流水线**：不等确认，连续发多个包，把网络填满。发送方维护一个窗口，窗口内的包可以连续发送。

- **GBN 回退 N 步**：接收方只按序收；包 2 丢了，3/4/5 到了也丢弃；发送方超时后重传 2 及之后所有包。实现简单，但丢包率高时浪费带宽。
- **SR 选择重传**：接收方缓存乱序包；发送方只重传丢失的包，接收方补齐后一起交付。省带宽，但接收方要缓存，发送方要维护每个包的确认状态。

SR 的窗口大小不能超过序号空间的一半，否则接收方分不清“新包”和“旧包重传”，会出现序号歧义。

<br>

### 最小实验：只看丢包后 GBN 和 SR 各重传了几个包

环境前提：同上。下面只做本地模拟，不联网。

保存为 `gbn_vs_sr.cpp`：

````cpp
#include <iostream>
#include <vector>

int main() {
    std::vector<int> packets = {1, 2, 3, 4, 5};
    int lost = 2;

    std::cout << "发送序列: ";
    for (int p : packets) std::cout << p << " ";
    std::cout << "\n包 " << lost << " 丢失\n\n";

    std::cout << "GBN：接收方丢弃 3/4/5，发送方重传 ";
    for (int p : packets) {
        if (p >= lost) std::cout << p << " ";
    }
    std::cout << "\n";

    std::cout << "SR：接收方缓存 3/4/5，发送方只重传 " << lost << "\n";
    return 0;
}
````

编译运行：

````bash
g++ -std=c++17 -O2 gbn_vs_sr.cpp -o gbn_vs_sr
./gbn_vs_sr
````

**这次只看一件事**：GBN 重传了几个包，SR 重传了几个包。

预期输出：

````text
发送序列: 1 2 3 4 5 
包 2 丢失

GBN：接收方丢弃 3/4/5，发送方重传 2 3 4 5 
SR：接收方缓存 3/4/5，发送方只重传 2
````

**关键观察点**：GBN 重传 4 个包，SR 只重传 1 个包。

GBN 是“一人犯错全队重来”，SR 是“谁犯错谁重来，其他人缓存待命”。丢包率高时，SR 明显更省带宽；但 SR 要缓存乱序包，实现更复杂。

注意：这个程序只模拟丢包后的重传数量，不模拟窗口滑动、定时器和 ACK 状态；真实 GBN/SR 还要处理这些。

<br>

### 易错点与边界

坑一：**GBN 接收窗口通常为 1**，因为它只按序收，乱序包直接丢。

坑二：**SR 窗口过大可能导致序号歧义**，所以窗口大小不能超过序号空间的一半。

坑三：**TCP 实际更像 GBN 累积确认 + SR 选择重传的混合**，不是纯 GBN 或纯 SR；SACK 选项让接收方告诉发送方缺了哪些块。

坑四：**流水线不是“无限发”**，窗口大小受序号空间、接收缓存和拥塞控制限制。

<br>

### 一句话本质

**GBN 是一人犯错全队重来，实现简单但浪费；SR 是谁犯错谁重来，省带宽但要缓存；TCP 吸收两者优点，累积确认加选择重传。**

<br>

### 自测

丢包率很高的环境下，GBN 和 SR 哪个更省带宽？为什么？SR 又付出了什么代价？

<details><summary>答案</summary>SR 更省带宽。GBN 丢一个包要重传该包及之后所有包，丢包率高时重传浪费大；SR 只重传丢失的包，其他乱序包缓存，补齐后一起交付。SR 的代价是接收方要缓存乱序包，发送方要维护每个包的确认状态，实现更复杂；窗口还不能超过序号空间一半，否则序号歧义。</details>

<br>

## 完整可复现示例：用 C++ 模拟 SR 窗口等待缺失包
***
下面这个程序模拟 SR 接收方的窗口滑动逻辑：收到 ACK 1 和 ACK 3，但包 0 还没到，所以窗口左边界不能滑。

````bash
g++ -std=c++17 -O2 sr_window.cpp -o sr_window
./sr_window
````

````cpp
#include <iostream>
#include <vector>

int main() {
    const int window = 4;
    int base = 0;
    std::vector<bool> acked(10, false);

    auto recv_ack = [&](int n) {
        acked[n] = true;
        std::cout << "收到 ACK " << n << "，";

        bool moved = false;
        while (base < static_cast<int>(acked.size()) && acked[base]) {
            std::cout << "包 " << base << " 确认，窗口滑动；";
            base++;
            moved = true;
        }

        if (!moved) {
            std::cout << "窗口不滑（等待包 " << base << "）\n";
        } else {
            std::cout << "\n";
        }
    };

    recv_ack(1);
    recv_ack(3);

    std::cout << "最终 base=" << base
              << "，虽然 1/3 已确认，但 0 没到，窗口不能滑\n";

    return 0;
}
````

输出：

````text
收到 ACK 1，窗口不滑（等待包 0）
收到 ACK 3，窗口不滑（等待包 0）
最终 base=0，虽然 1/3 已确认，但 0 没到，窗口不能滑
````

**关键观察点**：收到 ACK 1 和 ACK 3 后，`base` 是不是还是 0。

是。SR 可以缓存乱序确认，但窗口左边界必须等最左边缺失包补齐；这就是“选择重传”的代价：接收方要缓存，发送方要记录每个包的 ACK 状态。

注意：这个示例只模拟接收方窗口滑动逻辑，不是完整 SR 协议；真实 SR 还要处理定时器、重传、接收缓存和交付顺序。

## 排障速查表
***
| 现象 | 先查什么 | 常用命令/观察点 | 解释 |
|---|---|---|---|
| TCP 传输慢、吞吐上不去 | 窗口是否太小、是否频繁重传 | `ss -ti` 看 cwnd/rwnd；抓包看重传 | 窗口小或丢包多会限制吞吐；停等和 GBN 在丢包时浪费大 |
| 抓包看到大量重复 ACK | 是否丢包触发快速重传 | 看同一 ACK 重复次数；看后续重传 | 重复 ACK 常是接收方在提示“我缺这个包” |
| 抓包看到重传 | 是超时重传还是快速重传 | 看时间间隔和重复 ACK | 超时重传反应慢；快速重传由重复 ACK 触发，更快 |
| SACK 选项出现 | 接收方是否支持选择重传 | 抓包看 TCP 选项 | SACK 让接收方告诉发送方缺了哪些块，减少不必要重传 |
| 高丢包下吞吐骤降 | 是 GBN 式重传还是 SR 式 | 看重传范围 | GBN 丢一个重传一片，丢包率高时浪费大；SR/SACK 只补缺失块 |
| 序号回绕导致混乱 | 窗口是否超过序号空间一半 | 看窗口大小和序号位宽 | SR 窗口过大可能导致新旧包歧义；TCP 用 32 位序号和窗口限制避免 |

## 常见误区
***
- **以为加了校验和就可靠了**：校验和只发现比特错误，丢包、ACK 丢失、重复包还要序号和定时器。
- **以为停等协议够用**：带宽高、RTT 大时停等利用率很低，需要流水线。
- **以为 GBN 和 SR 只是实现细节**：丢包率高时两者带宽浪费差别很大。
- **以为 SR 窗口可以任意大**：不能超过序号空间一半，否则序号歧义。
- **以为 TCP 是纯 GBN 或纯 SR**：TCP 更像累积确认加选择重传的混合，SACK 让重传更精确。
- **以为序号只是用来排序**：早期 rdt 里序号主要用来去重；乱序处理要到流水线协议才展开。

## 自测三问
***
1. 可靠传输四件套是什么？为什么 rdt 2.0 加了校验和还不够？
2. GBN 和 SR 在丢包后的处理有什么不同？各自适合什么场景？
3. 为什么 SR 窗口不能超过序号空间一半？TCP 又为什么不是纯 GBN 或纯 SR？

<details><summary>参考答案</summary>1. 四件套是校验和、序号、确认、定时重传。rdt 2.0 加校验和只能发现比特错误，ACK/NAK 本身可能丢或坏，还需要序号去重、定时器处理 ACK 丢失。2. GBN 接收方只按序收，丢包后丢弃后续包，发送方重传该包及之后所有包，实现简单但丢包率高时浪费带宽；SR 接收方缓存乱序包，发送方只重传丢失的包，省带宽但要缓存和记录每个包的 ACK 状态。3. SR 窗口超过序号空间一半时，接收方分不清新包和旧包重传，出现序号歧义。TCP 用累积确认加选择重传的混合，SACK 让接收方告诉发送方缺了哪些块，既不是纯 GBN 也不是纯 SR。</details>

## 总结
***
**可靠数据传输靠校验、序号、确认和重传来对抗丢包/损坏/重复；停等保证正确但慢，流水线提高利用率，GBN 简单粗暴，SR 精细省带宽，TCP 则吸收两者优点。**
