## 优先级说明
***
这篇是 TCP 连接管理的核心，面试必问，项目里排查连接异常、TIME_WAIT 堆积也天天用。先分清主次：

**必须掌握（面试常问、项目真用得上）：**
- TCP 连接由四元组唯一确定：源 IP、源端口、目的 IP、目的端口
- 序号按字节编号，不是按包编号；确认号是期望收到的下一个字节
- 累积确认：Ack=2000 表示 2000 之前都收到了
- 三次握手：同步双方初始序列号、确认收发能力、防历史连接
- 四次挥手：TCP 全双工，两个方向分别关闭
- TIME_WAIT 两个作用：防旧连接延迟报文误收、保证最后 ACK 能到达
- TIME_WAIT 只出现在主动关闭方

**了解即可（知道大概，不展开）：**
- 延迟确认导致四次挥手合并成三次的具体条件
- 2MSL 的具体取值和 Linux 内核参数
- RST 的常见触发场景
- SYN 队列、Accept 队列和半连接/全连接的关系

**主线**：四元组定连接 → 序号/确认号按字节编号 → 三次握手同步初始序列号 → 四次挥手分别关闭两个方向 → TIME_WAIT 防旧报文和保最后 ACK。

## 知识点 1：TCP 连接是四元组，序号按字节编号
***
### 问题

TCP 靠什么标识一条连接？序号和确认号到底是什么意思？为什么说 TCP 是“字节流”而不是“报文流”？

**你可能会想**：TCP 的序号是不是按包编号？发第一个包 Seq=1，第二个包 Seq=2？

不是。**TCP 序号按字节编号，不是按包编号。** 一个报文段可以携带多个字节，下一个报文段的序号要加上本段数据长度。

<br>

### 核心概念与方案

先把 TCP 连接换成你熟悉的场景：**四元组像一条电话线路的唯一编号，序号像字节的流水号。**

TCP 连接由**四元组**唯一确定：**源 IP、源端口、目的 IP、目的端口**。同一个服务器 80 端口可以同时服务多个客户端，就是因为每个连接的源 IP 或源端口不同，四元组不同。

TCP 是**字节流协议**：

- **序号**：标识本报文段第一个数据字节的编号。
- **确认号**：表示期望收到的下一个字节序号，采用**累积确认**——确认号之前的字节都收到了。

控制位：**SYN** 建连、**ACK** 确认、**FIN** 结束、**RST** 重置。TCP 头还有窗口字段用于流量控制，首部通常 20 字节，选项可变长。

<br>

### 最小实验：用 ss 看一次连接的本地/对端地址和端口

环境前提：Linux/macOS，或 Windows WSL；已安装 `ss`。下面先在本机起一个监听端口，再用客户端连一下，观察连接的四元组。

终端 1 起一个简单 TCP 监听：

````bash
nc -l 18080
````

终端 2 发起连接并保持：

````bash
nc 127.0.0.1 18080
````

终端 3 查看连接：

````bash
ss -tan | grep ':18080'
````

**这次只看一件事**：输出里有没有一行同时显示本地地址:端口和对端地址:端口。

可能看到类似：

````text
ESTAB  0  0  127.0.0.1:18080  127.0.0.1:54321
ESTAB  0  0  127.0.0.1:54321  127.0.0.1:18080
````

两行分别是从服务端和客户端看到的同一条连接。**源 IP、源端口、目的 IP、目的端口四个字段合起来，唯一确定这条连接。** 54321 是客户端临时端口，每次可能不同。

如果没有输出，先检查 `nc` 是否可用、端口是否一致。`nc` 的参数在不同系统上可能不同，**需按环境核实**。

<br>

### 易错点与边界

坑一：**序号不是按包编号，是按字节**；一个报文段可以携带多个字节，下一个报文段的序号要加上本段数据长度。

坑二：**确认号是期望的下一个字节**，不是“最后收到的字节”；Ack=501 表示 501 之前都收到了。

坑三：**累积确认意味着 Ack=2000 表示 2000 之前都收到**，中间缺了会重复确认之前的字节。

坑四：**四元组相同不代表是同一条连接**，还要看时间；旧连接的延迟报文可能和新连接撞四元组，这正是 TIME_WAIT 要防的。

<br>

### 一句话本质

**TCP 连接是四元组契约，序号按字节编号，确认号表示“我下一个想要谁”；累积确认意味着确认号之前都收到了。**

<br>

### 自测

收到 Ack=2000 意味着什么？如果发送方发了 Seq=1500、Len=600，接收方会回什么确认号？

<details><summary>答案</summary>Ack=2000 表示 2000 之前的字节都收到了，期望下一个收到 2000。发送方发了 Seq=1500、Len=600，覆盖字节 1500 到 2099，如果全部收到，接收方应回 Ack=2100。</details>

## 知识点 2：三次握手、四次挥手与 TIME_WAIT
***
### 问题

为什么建连三次、断连四次？三次握手能不能改成两次？四次挥手为什么不能合并成两次？TIME_WAIT 到底在等什么？

**你可能会想**：建连三次是因为“多一次更保险”吧？断连四次是不是也可以合并？

不是“更保险”这么模糊。**三次握手是为了双方都确认彼此的收发能力，并同步初始序列号；四次挥手是因为 TCP 全双工，两个方向要分别关闭。**

<br>

### 核心概念与方案

先把握手挥手换成你熟悉的场景：**三次握手是“你听得到我吗、我听得到你、好开聊”；四次挥手是“我发完了、知道了、我也发完了、好拜拜”。**

**三次握手**：

1. 客户端发 SYN（携带 `client_isn`）。
2. 服务端回 SYN+ACK（携带 `server_isn`，`Ack=client_isn+1`）。
3. 客户端回 ACK（`Ack=server_isn+1`）。

目的有三个：**同步双方初始序列号、确认双方收发能力、防止历史连接**。第三次握手可以携带数据。

**四次挥手**：

1. 主动方发 FIN。
2. 被动方回 ACK（此时可能还有数据要发）。
3. 被动方发 FIN。
4. 主动方回 ACK。

因为 TCP 是全双工，两个方向要分别关闭；被动方收到 FIN 后可能还有数据没发完，所以 ACK 和 FIN 通常不能合并。

**TIME_WAIT**：主动关闭方最后进入 TIME_WAIT，等待 **2MSL**。目的有两个：

- **防止旧连接延迟报文被新同四元组连接误收**。
- **保证最后的 ACK 能让被动方收到**；如果 ACK 丢了，被动方重发 FIN，主动方还能再回一次 ACK。

补充：如果被动方没数据要发且开启延迟确认，四次挥手可能合并成三次；但标准流程仍是四次。

<br>

### 最小实验：用 C++ 客户端 + tcpdump 看 SYN、FIN 和 TIME_WAIT

环境前提：Linux/macOS，或 Windows WSL；已安装 `g++`、`nc`、`tcpdump`。抓包需要权限，没有权限时用 `ss -tan` 观察状态也可以，但看不到逐包标志位。

保存为 `tcp_connect_demo.cpp`：

````cpp
#include <arpa/inet.h>
#include <netinet/in.h>
#include <sys/socket.h>
#include <unistd.h>

#include <cstring>
#include <iostream>

int main() {
    const char* server_ip = "127.0.0.1";
    const int server_port = 18081;

    int sock = socket(AF_INET, SOCK_STREAM, 0);
    if (sock < 0) {
        std::cerr << "socket failed\n";
        return 1;
    }

    sockaddr_in addr{};
    addr.sin_family = AF_INET;
    addr.sin_port = htons(server_port);
    if (inet_pton(AF_INET, server_ip, &addr.sin_addr) <= 0) {
        std::cerr << "invalid address\n";
        close(sock);
        return 1;
    }

    if (connect(sock, reinterpret_cast<sockaddr*>(&addr), sizeof(addr)) < 0) {
        std::cerr << "connect failed\n";
        close(sock);
        return 1;
    }

    const char* msg = "Hello";
    send(sock, msg, std::strlen(msg), 0);

    close(sock);
    std::cout << "client done\n";
    return 0;
}
````

运行步骤：

````bash
# 终端 1：起服务端
nc -l 18081

# 终端 2：抓包（需要权限）
sudo tcpdump -i lo -n tcp port 18081 -c 20

# 终端 3：编译并运行客户端
g++ -std=c++17 -O2 tcp_connect_demo.cpp -o tcp_connect_demo
./tcp_connect_demo
````

**这次只看一件事**：tcpdump 输出里有没有 `[S]`、`[S.]`、`[.]`、`[F.]` 这些标志。

可能看到类似：

````text
Flags [S]    客户端 → 服务端   ; 第一次握手 SYN
Flags [S.]   服务端 → 客户端   ; 第二次握手 SYN+ACK
Flags [.]    客户端 → 服务端   ; 第三次握手 ACK
Flags [P.]   客户端 → 服务端   ; 发送 "Hello"
Flags [F.]   客户端 → 服务端   ; 主动关闭 FIN
Flags [.]    服务端 → 客户端   ; ACK
Flags [F.]   服务端 → 客户端   ; 服务端 FIN
Flags [.]    客户端 → 服务端   ; 最后 ACK
````

`[S]` 是 SYN，`[S.]` 是 SYN+ACK，`[.]` 是 ACK，`[F.]` 是 FIN+ACK。**建连三步、断连四步，在抓包里一眼就能看到。**

客户端作为主动关闭方，最后会进入 TIME_WAIT。可以用 `ss -tan | grep 18081` 观察，**具体状态停留时间取决于系统和 2MSL 配置，需按环境核实**。

如果抓包没权限，可以只用 `ss -tan` 看状态变化，但看不到逐包标志位。`nc` 的参数在不同系统上可能不同，**需按环境核实**。

<br>

### 易错点与边界

坑一：**TIME_WAIT 只出现在主动关闭方**，被动关闭方通常进入 CLOSE_WAIT，等应用调用 `close` 后才发 FIN。

坑二：**2MSL 不是随便等的**，MSL 是报文最大生存时间，2MSL 保证旧报文在网络中消失，且最后 ACK 有重发机会。

坑三：**如果被动方没数据要发且开启延迟确认，四次挥手可能合并成三次**，但不要因此认为标准挥手是三次。

坑四：**第三次握手可以携带数据**，但前两次通常不行，因为连接还没完全建立。

坑五：**大量 TIME_WAIT 不一定是 bug**，主动关闭方多、短连接多时就会出现；要结合业务判断，不能无脑调小。

<br>

### 一句话本质

**三次握手是“你听得到我吗、我听得到你、好开聊”，四次挥手是“我发完了、知道了、我也发完了、好拜拜”；TIME_WAIT 是主动关闭方等 2MSL，防旧报文捣乱并保证最后 ACK 到达。**

<br>

### 自测

为什么主动关闭方需要 TIME_WAIT？如果不要 TIME_WAIT，可能出现什么问题？

<details><summary>答案</summary>TIME_WAIT 有两个作用：一是防止旧连接的延迟报文被新同四元组连接误收；二是保证最后的 ACK 能让被动方收到，如果 ACK 丢了，被动方重发 FIN，主动方还能再回一次 ACK。不要 TIME_WAIT，可能出现旧报文串到新连接、最后 ACK 丢失导致被动方一直重发 FIN 等问题。</details>

<br>

## 完整可复现示例：用 C++ 客户端 + tcpdump 观察握手挥手和 TIME_WAIT
***
你需要 Linux/macOS 或 WSL，已安装 `g++`、`nc`、`tcpdump`（抓包需要权限）。下面把前面的实验串起来，每个步骤只看一个观察点。

````bash
# 终端 1：服务端
nc -l 18081

# 终端 2：抓包
sudo tcpdump -i lo -n tcp port 18081 -c 20

# 终端 3：编译运行客户端
g++ -std=c++17 -O2 tcp_connect_demo.cpp -o tcp_connect_demo
./tcp_connect_demo

# 客户端退出后，看 TIME_WAIT
ss -tan | grep 18081 || true
````

可能的输出/现象：

````text
# tcpdump
Flags [S]    客户端 → 服务端
Flags [S.]   服务端 → 客户端
Flags [.]    客户端 → 服务端
Flags [P.]   客户端 → 服务端
Flags [F.]   客户端 → 服务端
Flags [.]    服务端 → 客户端
````

***
| 现象 | 先查什么 | 常用命令/观察点 | 解释 |
|---|---|---|---|
| `connect` 超时或失败 | 服务端是否监听、网络是否通、端口是否对 | `ss -ltnp \| grep ':端口'`；`nc -vz 主机 端口` | 服务端没起、端口写错、防火墙挡住都可能导致连接失败 |
| 大量 `TIME_WAIT` | 是否短连接多、主动关闭方是否集中 | `ss -tan \| grep TIME-WAIT \| wc -l` | 主动关闭方多、短连接多时 TIME_WAIT 会多；不一定是 bug，要结合业务判断 |

| `Connection reset by peer` | 对端是否异常关闭、RST | 抓包看 RST；看服务端日志 | 对端可能崩溃、端口被重置，或中间设备发 RST |
| 连接建立但收不到数据 | 是否握手完成、是否发错连接 | `ss -tan` 看状态；抓包看 Seq/Ack | 可能连到了错误端口，或数据发到了另一条连接 |
| 主动关闭方卡在 `TIME_WAIT` | 2MSL 是否正常 | `ss -tan` 看状态；查内核参数 | TIME_WAIT 是正常状态，等 2MSL 后消失；不要无脑调小 |
| 被动关闭方一直 `CLOSE_WAIT` | 应用是否处理 FIN | `ss -tan`；查应用代码 | 应用收到 FIN 后没 `close`，连接会一直停在 CLOSE_WAIT |

## 常见误区
***
- **以为序号按包编号**：TCP 序号按字节编号，一个报文段可以携带多个字节。
- **把确认号当成“最后收到的字节”**：确认号是期望收到的下一个字节。
- **以为三次握手只是“多一次更保险”**：三次是为了同步双方初始序列号、确认收发能力、防历史连接。
- **以为四次挥手可以随便合并成两次**：TCP 全双工，两个方向要分别关闭；延迟确认下可能合并成三次，但标准仍是四次。
- **以为 TIME_WAIT 是 bug**：主动关闭方等 2MSL 是正常设计，防旧报文和保最后 ACK。
- **以为 TIME_WAIT 只出现在服务端**：主动关闭方才会进入 TIME_WAIT，客户端主动关闭也会。
- **把 CLOSE_WAIT 和 TIME_WAIT 混了**：CLOSE_WAIT 是被动关闭方等应用 `close`，TIME_WAIT 是主动关闭方等 2MSL。

## 自测三问
***
1. TCP 连接四元组是什么？为什么同一个服务器端口能同时服务多个客户端连接？
2. 三次握手的最主要原因是什么？为什么不能只握两次？
3. TIME_WAIT 的两个作用是什么？为什么它只出现在主动关闭方？

<details><summary>参考答案</summary>1. 四元组是源 IP、源端口、目的 IP、目的端口。不同客户端的源 IP 或源端口不同，四元组不同，所以同一个服务器端口可以同时服务多个连接。2. 三次握手是为了同步双方初始序列号、确认双方收发能力、防止历史连接。两次握手无法让双方都确认对方的接收能力和初始序列号，也可能让旧连接的延迟 SYN 被误认为新连接。3. TIME_WAIT 防止旧连接延迟报文被新同四元组连接误收，并保证最后的 ACK 能让被动方收到。它只出现在主动关闭方，因为主动关闭方最后发 ACK，需要等 2MSL 确保 ACK 到达和旧报文消失。</details>

<br>

## 总结
***
**TCP 用四元组标识连接，用序号/确认号保证字节流可靠，用三次握手同步状态并防历史连接，用四次挥手分别关闭两个方向，用 TIME_WAIT 防止旧报文捣乱并保证最后 ACK 到达；序号按字节编号，确认号是期望的下一个字节。**
