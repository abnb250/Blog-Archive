## 痛点引入
***
TCP 发出去的数据没收到 ACK 怎么办？**超时时间 RTO 怎么定？为什么收到 3 个重复 ACK 就快速重传？SACK 又解决什么问题？**  
先别急着背“RTO、快速重传、SACK”这些词，先看几个具体场景：你发了一个包，对方一直没回 ACK，等多久重传？等太短，网络只是抖了一下你就重发，反而加剧拥塞；等太长，真丢包了又反应慢。再想一个场景：你连发 1、2、3、4、5，结果 2 丢了，接收方一直回 ACK1，你收到三个 ACK1，能不能不等超时就直接补发 2？补发 2 之后，3、4、5 要不要也重发？这一章咱们就按“等多久、怎么早发现、怎么少重发”这条线走。

## 知识点 1：超时重传与 RTO
***
### 问题
等多久没 ACK 才重传？RTO 是固定值吗？为什么网络抖动时 RTO 要拉长？超时重传后，下次超时时间为什么还要翻倍？

<br>

### 方案
TCP 给发送数据设定时器，超时没 ACK 就重传。RTO（Retransmission Timeout）应略大于 RTT，但 RTT 会波动，所以 RTO 要动态计算：  
- 采样 RTT，算平滑值 `EstimatedRTT`；  
- 算波动 `DevRTT`；  
- 通常 `RTO = EstimatedRTT + 4 * DevRTT`。  
加 `4 * DevRTT` 是为了给波动留余量：网络稳时 RTO 接近 RTT，网络抖时 RTO 自动拉长，避免误重传。  
超时重传后，下次超时时间通常**加倍（指数退避）**，避免网络差时疯狂重发。  
连接建立后的数据重传最大次数受 `tcp_retries2` 影响，默认 15，但不是简单重传 15 次，还受计算出的 timeout 限制。

<br>

### 最小示例
```text
RTT 稳定 100ms → RTO 约 100ms 多一点
网络抖动变大 → DevRTT 增大 → RTO 拉长，避免误重传
超时一次 → RTO 翻倍；再超时 → 再翻倍
```

结论：RTO 不是拍脑袋定的固定值，而是跟着 RTT 和波动动态调整；超时后还要指数退避。

<br>

### 一句话本质
**RTO 是智能闹钟：网络稳就准，网络抖就宽容；超时后还指数退避。**

<br>

### 易错点
坑一：**RTO 太小会无谓重传加剧拥塞**，把本来只是延迟的包当成丢了。  
坑二：**RTO 太大丢包反应慢**，恢复时间长。  
坑三：**`tcp_retries2` 不是绝对次数**，受 timeout 约束；不同内核版本行为也可能有差异。  
坑四：**指数退避不是“每次都翻倍到无限”**，有上限，具体受内核实现限制。

## 知识点 2：快速重传、SACK、D-SACK
***
### 问题
等超时太慢，能不能早点重传？收到重复 ACK 说明什么？重传一个还是重传所有？SACK 和 D-SACK 又分别解决什么问题？

<br>

### 方案
接收方收到乱序包会重复发 ACK，告诉发送方“我还在等那个缺失的字节”。发送方连续收到 **3 个重复 ACK**，就认为中间包丢了，立刻**快速重传**，不等超时。  
但快速重传有个问题：它只知道“最早缺的那个包”可能丢了，不知道后面还有没有丢。于是有 **SACK（选择性确认）**：接收方在 ACK 里告诉发送方“我已经收到哪些区间”，发送方只重传缺失段，不用把后面全重发。  
**D-SACK（Duplicate SACK）** 用 SACK 告诉发送方“哪些数据重复收到了”，可以用来判断是数据丢了、ACK 丢了，还是网络延迟/复制，帮助发送方区分拥塞和误判。

<br>

### 最小示例
```text
发 1,2,3,4,5，2 丢：
收到 ACK1、ACK1、ACK1 → 触发快速重传 2
若开 SACK，接收方告知已收 3~5，只重传 2。
若 D-SACK 发现 2 被重复收到，说明可能是 ACK 丢了，不是数据丢了。
```

结论：快速重传减少等待，SACK 减少多余重传，D-SACK 帮助判断重复原因。

<br>

### 一句话本质
**快速重传是“听到三次缺货就补发”，SACK 是“告诉我还缺哪一段，别全重发”，D-SACK 是“告诉你有东西重复到了”。**

<br>

### 易错点
坑一：**3 个重复 ACK 是常见触发条件**，但具体实现可能不同；不是收到一个重复 ACK 就重传。  
坑二：**SACK 需双方支持**，不是所有连接都开；协商阶段要通过 TCP 选项确认。  
坑三：**D-SACK 能区分 ACK 丢包和网络延迟，不是普通 SACK**；它报告的是“重复收到的区间”。  
坑四：**快速重传不是“一收到重复 ACK 就重传”**，要够 3 个，避免把乱序误判成丢包。

<br>

## 完整可复现示例：用 C++ 模拟 RTO 指数退避
***
下面这个 C++ 程序模拟超时重传时 RTO 翻倍的过程，并设置一个上限，避免无限增长。  
编译运行：

```bash
g++ -std=c++17 -O2 rto_backoff.cpp -o rto_backoff
./rto_backoff
```

```cpp
// rto_backoff.cpp
#include <algorithm>
#include <iomanip>
#include <iostream>

int main() {
    double rto = 0.2;       // 初始 RTO，单位秒
    const double max_rto = 60.0;  // 上限，避免无限增长

    for (int i = 1; i <= 8; ++i) {
        std::cout << "第 " << i << " 次超时，RTO="
                  << std::fixed << std::setprecision(2) << rto << "s\n";

        rto = std::min(rto * 2.0, max_rto);
    }

    return 0;
}
```

输出/现象/结论：

```text
第 1 次超时，RTO=0.20s
第 2 次超时，RTO=0.40s
第 3 次超时，RTO=0.80s
第 4 次超时，RTO=1.60s
第 5 次超时，RTO=3.20s
第 6 次超时，RTO=6.40s
第 7 次超时，RTO=12.80s
第 8 次超时，RTO=25.60s
```

验证结果：超时后 RTO 翻倍，避免网络差时频繁重传；这里加了 60 秒上限，真实内核也有类似上限，不是无限翻倍。  
注意：这个示例只模拟退避过程，不是完整 TCP 实现；真实 RTO 还会根据新的 RTT 采样重新计算，不是一直翻倍。
