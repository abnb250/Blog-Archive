## 痛点引入
***
TCP 理论很抽象，抓包能“看见”握手、挥手、重传、乱序、零窗口。**怎么抓？Wireshark 里 Seq/Ack 怎么读？为什么抓到的挥手有时是三次？**  
先别急着背“Seq 是序号、Ack 是确认号”，先看几个具体场景：你怀疑客户端连不上服务端，是 SYN 没到、SYN+ACK 丢了，还是服务端队列满了？你看到 Wireshark 里连续三个相同的 ACK，是网络乱序，还是真的丢包触发了快速重传？你抓到的挥手只有三次，是抓包漏了，还是延迟确认把两次合并了？这一章咱们就按“怎么抓、怎么看、怎么对应理论”这条线走。

## 知识点 1：tcpdump 与 Wireshark 分工
***
### 问题
Linux 服务器上怎么抓，怎么分析？为什么服务器上抓包常用 `tcpdump`，而不是直接开 Wireshark？Wireshark 里三次握手的 Seq 为什么常显示 0？那是真实序号吗？

<br>

### 方案
`tcpdump` 是命令行抓包工具，适合 Linux 服务器：没有图形界面也能跑，资源占用小，可以直接把包保存成 pcap 文件。  
Wireshark 是图形化分析工具：把 pcap 拖进去，可以看每层头部、TCP 流量图、相对序号、重传标记等，适合事后分析。  
常用 `tcpdump` 参数：  
- `-i` 指定网卡；`-i any` 表示所有网卡，但容器和部分系统上行为可能不同；  
- `-nn` 不解析 IP 和端口名，避免 DNS 反查拖慢抓包；  
- `-w` 把原始包保存到文件，方便拖进 Wireshark；  
- `-c` 限制抓包数量，避免抓太多。  
过滤表达式如 `tcp and port 80`、`icmp`，能减少无关流量。  
Wireshark 默认常显示**相对序号**：把每个方向的初始序列号映射成 0，方便阅读。取消“Relative Seq”才能看到真实的随机初始序列号。所以看到 Seq=0 不一定是真的从 0 开始，只是显示方式。

<br>

### 最小示例
```bash
# 抓 80 端口前 20 个包，直接看
sudo tcpdump -i any -nn tcp port 80 -c 20

# 抓包保存成 pcap，拖进 Wireshark 分析
sudo tcpdump -i any -nn -w http.pcap tcp port 80
```

输出可能类似：

```text
IP 192.168.1.10.54321 > 93.184.216.34.80: Flags [S], seq 123456789, win 64240, length 0
IP 93.184.216.34.80 > 192.168.1.10.54321: Flags [S.], seq 987654321, ack 123456790, win 65535, length 0
IP 192.168.1.10.54321 > 93.184.216.34.80: Flags [.], ack 987654322, win 64240, length 0
```

结论：`tcpdump` 负责抓，Wireshark 负责看懂；抓包是把 TCP 从抽象变具体的放大镜。

<br>

### 一句话本质
**tcpdump 负责抓，Wireshark 负责看懂；抓包是把 TCP 从抽象变具体的放大镜。**

<br>

### 易错点
坑一：**抓包需要权限**，普通用户通常要 `sudo` 或给 `tcpdump` 相应 capability。  
坑二：**容器/网卡命名会影响 `-i any`**，容器里可能看不到宿主机某些接口，抓不到不代表没流量。  
坑三：**相对 Seq 不是真实初始序列号**，Wireshark 默认把初始序号映射成 0，方便看，不代表真实值。  
坑四：**`tcpdump` 抓包本身也有开销**，高流量下过滤表达式要写准，别抓全量再慢慢筛。  
坑五：**抓包点不同看到的现象不同**，在客户端抓和在服务端抓，可能一边看到重传、另一边看不到。

<br>

## 知识点 2：从抓包看握手、挥手、重传与窗口
***
### 问题
常见现象怎么在抓包里对应？三次握手和四次挥手的标志位长什么样？连续三个相同 ACK 说明什么？零窗口在抓包里是什么样？为什么抓到的挥手有时只有三次？

<br>

### 方案
咱们按“标志位看阶段、Seq/Ack 看顺序和缺失、win 看接收能力”来读：  
- **三次握手**：`[S]`、`[S.]`、`[.]`，分别对应 SYN、SYN+ACK、ACK。  
- **四次挥手**：`[F.]`、`[.]`、`[F.]`、`[.]`，分别对应 FIN+ACK、ACK、FIN+ACK、ACK。被动方没数据要发且开启延迟确认时，ACK 和 FIN 可能合并，抓包看起来像三次；这不是异常。  
- **重复 ACK/快速重传**：接收方连续回相同 Ack，发送方收到 3 个重复 ACK 后重传缺失段。抓包里会看到连续多个相同 Ack，然后发送方重发缺失 Seq。  
- **零窗口**：接收方 `win=0`，发送方停止发送，定时发窗口探测；窗口恢复后继续发。零窗口不是连接断开。  
- **SYN 丢包**：客户端按 `tcp_syn_retries` 指数退避重传 SYN；SYN+ACK 丢包则双方都可能重传。抓包里会看到相同 Seq 的 SYN 多次出现，间隔逐渐拉长。  
注意：Wireshark 的“快速重传”标记是工具根据启发式规则推断的，不是报文里自带字段；别把它当成绝对真相，要结合 Seq/Ack 自己看。

<br>

### 最小示例
```text
三次握手：
[S]   → [S.]  → [.]

四次挥手：
[F.]  → [.]   → [F.] → [.]
被动方没数据且延迟确认时，可能合并成：
[F.]  → [F.]  → [.]

重复 ACK：
ACK 1, ACK 1, ACK 1 → 发送方快速重传缺失段

零窗口：
win=0 → 发送方停发，定时窗口探测
```

结论：抓包读三样——标志位看阶段，Seq/Ack 看顺序和缺失，win 看接收能力。

<br>

### 一句话本质
**抓包读三样：标志位看阶段，Seq/Ack 看顺序和缺失，win 看接收能力。**

<br>

### 易错点
坑一：**Wireshark 的“快速重传”标记是工具推断**，不是报文本身字段；要结合重复 ACK 和重传 Seq 自己判断。  
坑二：**零窗口不是连接断开**，只是接收方暂时没缓存；发送方会窗口探测，窗口恢复后继续。  
坑三：**抓到的挥手三次不一定是异常**，可能是延迟确认合并了 ACK 和 FIN。  
坑四：**重复 ACK 不一定是丢包**，也可能是乱序到达；要看后续是否触发重传、缺失段是否真的没到。  
坑五：**在客户端抓和在服务端抓，看到的重传可能不同**；中间设备丢包时，两端抓包对不上是正常的。

<br>

## 完整可复现示例：抓一次 HTTP 请求并用 tcpdump 读关键行
***
这个示例用 `tcpdump` 抓一次 HTTP 请求，保存 pcap，并用 `tcpdump -r` 读回关键行，观察握手、请求/响应和挥手。  
注意：抓包需要权限；`example.com` 的 80 端口可能被重定向或限制，抓不到完整 HTTP 交互也正常，重点看 TCP 标志位。

```bash
set -e

PCAP=/tmp/http.pcap

echo "=== 1. 开始抓包（后台） ==="
sudo tcpdump -i any -nn -w "$PCAP" tcp port 80 &
PID=$!

echo "=== 2. 发起 HTTP 请求 ==="
curl -s --max-time 10 http://example.com/ -o /dev/null || true

sleep 1
sudo kill "$PID" 2>/dev/null || true
wait "$PID" 2>/dev/null || true

echo "=== 3. 读回抓包关键行 ==="
sudo tcpdump -nn -r "$PCAP" 2>/dev/null | head -n 30 || true

echo "=== 4. pcap 已保存：$PCAP，可拖进 Wireshark ==="
```

输出/现象/结论可能类似：

```text
=== 3. 读回抓包关键行 ===
IP 192.168.1.10.54321 > 93.184.216.34.80: Flags [S], seq 123456789, win 64240, length 0
IP 93.184.216.34.80 > 192.168.1.10.54321: Flags [S.], seq 987654321, ack 123456790, win 65535, length 0
IP 192.168.1.10.54321 > 93.184.216.34.80: Flags [.], ack 987654322, win 64240, length 0
IP 192.168.1.10.54321 > 93.184.216.34.80: Flags [P.], seq 123456790:123456880, ack 987654322, win 64240, length 90
IP 93.184.216.34.80 > 192.168.1.10.54321: Flags [P.], seq 987654322:987655000, ack 123456880, win 65535, length 678
IP 192.168.1.10.54321 > 93.184.216.34.80: Flags [F.], seq 123456880, ack 987655000, win 64240, length 0
IP 93.184.216.34.80 > 192.168.1.10.54321: Flags [F.], seq 987655000, ack 123456881, win 65535, length 0
IP 192.168.1.10.54321 > 93.184.216.34.80: Flags [.], ack 987655001, win 64240, length 0
```

验证结果：抓包能把握手、数据传输、挥手串起来；`[S]`、`[S.]`、`[.]` 是三次握手，`[F.]`、`[.]`、`[F.]`、`[.]` 是四次挥手（这里服务端 ACK 和 FIN 可能合并，看起来少一行也正常）。结合 Seq/Ack 可分析丢包、乱序和重传。  
注意：`curl` 可能走 HTTP/2 或 HTTPS，80 端口也可能被重定向，抓不到完整 HTTP 明文请求是正常的；这个示例重点是看 TCP 标志位和 Seq/Ack。容器或权限受限环境里 `sudo tcpdump` 可能失败，可以先在能抓包的机器上试。
