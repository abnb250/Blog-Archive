## 知识点 1：运输层全貌与能力边界
***
### 问题
运输层到底解决了什么？它比网络层多了什么？为什么说 TCP 的复杂性对应用层是“透明”的？运输层能不能承诺带宽和时延？

<br>

### 方案
运输层把“主机到主机”扩展成“进程到进程”：靠**端口 + 多路复用/分解**，把数据交给正确进程。  
- **UDP** 极简：无连接、不可靠、8 字节首部，适合 DNS、实时音视频、QUIC 底座。  
- **TCP** 可靠：面向连接、字节流、序号/确认、重传、滑动窗口、流量控制、拥塞控制。  
- **可靠传输四件套**：校验和、序号、确认、定时重传；这套理论不只 TCP 能用，QUIC 也在应用层重新实现。  
关键边界：**运输层不能提供底层没有的带宽和时延保证**。IP 是“尽力而为”，TCP 能做可靠传输、流量控制、拥塞控制，但变不出“延迟绝不超过 10ms”或“保证 100Mbps”。  
应用层写起来简单，是因为复杂性被内核封装了：你调 `send/recv`，内核在背后做编号、定时器、窗口、拥塞控制、重传。

<br>

### 最小示例
```text
应用层 send() → 内核 TCP：编号、定时器、窗口、拥塞控制、重传 → IP
应用层感觉简单，是因为复杂被内核封印了。
```

结论：运输层是端到端通信的守护者，但它的能力有边界；它是在 IP 之上做增强，不是变魔术。

<br>

### 一句话本质
**运输层是端到端通信的守护者：端口分发进程，UDP 换速度，TCP 换可靠，QUIC 换进化速度。**

<br>

### 易错点
坑一：**TCP 可靠不等于实时**，重传和拥塞控制会让延迟变大。  
坑二：**ESTABLISHED 不代表对端一定活着**，可能只是没数据要发，也没开 Keepalive。  
坑三：**TIME_WAIT 不是越少越好**，它是正常关闭流程的一部分。  
坑四：**HTTP Keep-Alive 不是 TCP Keepalive**，前者是应用层连接复用，后者是 TCP 层探测。  
坑五：**运输层不能凭空提供带宽和时延保证**，只能基于 IP 的“尽力而为”做增强。

<br>

## 知识点 2：把机制串成一条线，而不是背缩写
***
### 问题
SYN、ACK、RTT、cwnd、ssthresh、TIME_WAIT 这些词，复习时怎么串起来？面试或工作中被问到某个点，怎么快速定位到它属于哪条线？哪些易错点最容易混？

<br>

### 方案
别按字母顺序背，按“一条问题链”串：  
- **进程分发**：端口、多路复用/分解；TCP/UDP 同端口不冲突，连接靠四元组区分。  
- **UDP/TCP 分工**：UDP 极简换速度；TCP 面向连接、可靠、字节流。  
- **可靠传输**：校验和、序号、确认、超时重传；流水线、GBN/SR；TCP 用 RTO 动态计算、3 个重复 ACK 快速重传、SACK 精确补缺。  
- **窗口与拥塞**：`rwnd` 防撑爆接收方，零窗口要探测；`cwnd` 防堵网络，慢启动→拥塞避免→快速恢复，AIMD。  
- **队列与异常**：半连接 SYN 队列、全连接 accept 队列；`accept` 不参与握手；Established 收旧 SYN 回 Challenge ACK；TIME_WAIT 收 SYN 看合法性。  
- **优化与演化**：握手少重试扩队列、挥手管 TIME_WAIT、按 BDP 调缓冲区；QUIC 在 UDP 上实现可靠、TLS1.3、独立 Stream、连接 ID、1/0-RTT。  
复习时抓住这条线：**进程分发 → UDP/TCP 分工 → 可靠传输 → 窗口/拥塞 → 异常与优化 → QUIC 演化**。每个缩写都能挂到线上，就不会散。

<br>

### 最小示例
```text
UDP：无连接、不可靠、8 字节首部、DNS/实时音视频/QUIC
TCP：面向连接、可靠、字节流、四元组、三次握手、四次挥手
可靠传输：校验和、序号、确认、超时重传、流水线、GBN/SR
TCP 重传：RTO 动态计算、3 个重复 ACK 快速重传、SACK 精确补缺
流量控制：rwnd 防撑爆接收方；零窗口要探测
拥塞控制：cwnd 防堵网络；慢启动→拥塞避免→快速恢复；AIMD
队列：半连接 SYN 队列、全连接 accept 队列；accept 不参与握手
异常：Established 收旧 SYN 回 Challenge ACK；TIME_WAIT 收 SYN 看合法性
QUIC：UDP 上实现可靠、TLS1.3、独立 Stream、连接 ID、1/0-RTT
```

结论：这张速查表不是让你背，而是让你每条都能追溯到“它解决什么问题”。

<br>

### 一句话本质
**运输层复习抓住一条线：进程分发 → UDP/TCP 分工 → 可靠传输 → 窗口/拥塞 → 异常与优化 → QUIC 演化。**

<br>

### 易错点
坑一：**不要混 TCP Keepalive 和 HTTP Keep-Alive**，前者是 TCP 层探测，后者是 HTTP 层连接复用。  
坑二：**不要以为 TIME_WAIT 收到 SYN 一定 RST**，合法 SYN 可以复用连接。  
坑三：**不要以为 `accept` 参与握手**，它只从全连接队列取连接。  
坑四：**不要以为 UDP 没有端口**，端口仍然是多路分解的关键。  
坑五：**不要以为 QUIC 是 UDP 直接可靠**，它是在 UDP 之上实现可靠传输、加密和拥塞控制。  
坑六：**不要以为 `tcp_tw_recycle` 还能用**，Linux 4.12 后已移除，旧文章里的调参别照抄。

<br>

## 完整可复现示例：运输层知识全景回顾
***
这一章没有代码，咱们用一张分层图把运输层串起来：

```text
【应用层】HTTP/DNS/邮件/Socket
      ↓
【运输层】端口 + 多路复用/分解
   ├─ UDP：无连接、8字节、检验和
   └─ TCP：三次握手、四次挥手、序号/确认、重传、滑动窗口、流量控制、拥塞控制
      ↓
【网络层】IP 尽力而为：可能丢包、乱序、不保证带宽时延
      ↓
【链路层/物理层】
```

输出/现象/结论：

```text
运输层在不可靠 IP 之上做进程到进程通信；
TCP 用复杂机制换可靠，UDP 用极简换速度；
QUIC 在 UDP 上重新实现可靠、安全、多路复用和连接迁移。
```

验证结果：运输层不是孤立的协议名，而是“端口分发 + 可靠传输理论 + TCP/UDP 工程实现 + 异常优化 + 新协议演化”的一条问题链。  
注意：这张图是逻辑分层示意，实际数据封装是逐层加首部；TCP 和 UDP 共用端口空间但按协议号区分，所以可以同时绑同一端口。

***

3. QUIC 为什么要在 UDP 上重新实现可靠传输，而不是直接改 TCP？它解决了 TCP 的哪几个具体问题？

## 一句话总结全章
***
**运输层是端到端通信的守护者：端口把数据交给正确进程，UDP 用极简换速度，TCP 用序号/确认/重传/窗口/拥塞控制换可靠，QUIC 在 UDP 上重造可靠与安全以绕开 TCP 的僵化；理解这条线，运输层就不再是一堆缩写。**
