***
你把网站服务器的 IP 改了，域名解析也改了。你刷新浏览器，发现有的地方已经能访问新 IP，有的地方还指着旧 IP。

## 知识点 1：DNS 为什么必须分布式——一台服务器背不动全球电话簿
***
### 问题

集中式 DNS 行不行？全世界就放一台大服务器，所有域名都查它，不是更简单吗？

**你可能会想**：集中管理多简单，为什么非要搞分布式，还分根、顶级、权威这么多层？

因为集中式至少会撞上四个问题，而且每一个都足以让全球解析瘫痪。

<br>

### 核心概念与方案

先把 DNS 换成你熟悉的场景：**DNS 是互联网的分布式电话簿。** 你不会把全人类的电话号码都塞进一个本子，也不会只让一个查号台服务全世界。

集中式至少撞上四个问题：

- **单点故障**：一台机器挂了，全球域名解析就瘫了。
- **通信容量瓶颈**：所有查询都挤到一处，带宽和连接数扛不住。
- **远距离延迟**：离得远的地区，查一次要跨半个地球。
- **维护开销巨大**：全球域名数据集中维护，更新和备份都麻烦。

所以 DNS 设计成**分层分布式数据库**。同时它本身也是应用层协议，常被 HTTP、SMTP、FTP 等应用使用。

普通查询主要用 **UDP 53**，因为查询短、希望快；区域传送用 **TCP 53**，因为数据量大且要可靠。普通查询的响应如果过大或被截断，也可能改用 TCP 重查。

<br>

### 最小实验：只看域名有没有解析出地址

环境前提：Linux/macOS，或 Windows WSL；已安装 `dig`（常见于 `dnsutils` 或 `bind-utils` 包），需要外网。没装 `dig` 可用 `getent hosts` 或 `nslookup`。

````bash
dig example.com A +short
````

**这次只看一件事**：输出里有没有一个 IPv4 地址。

预期输出类似：

````text
93.184.216.34
````

有地址，说明 DNS 把域名翻译成了 IP。如果没有输出，先检查网络、`dig` 是否可用，或者换一个域名再试。

注意：`example.com` 的 A 记录会随站点配置和网络环境变化，**需按环境核实**；这里重点看“域名 → IP”这个结果，不是背具体 IP。

<br>

### 易错点与边界

坑一：**DNS 不只走 UDP**，区域传送用 TCP 53；普通查询响应过大或被截断时也可能转 TCP。

坑二：**DNS 不是一台大服务器**，是分层分布式数据库，根、顶级域、权威、本地各司其职。

坑三：**hosts 文件可以本地覆盖解析结果**，排查“为什么域名解析不对”时别忘了看它。

坑四：**DNS 缓存不只是浏览器有**，操作系统、本地 DNS 服务器、甚至中间代理都可能缓存。

<br>

### 一句话本质

**DNS 是互联网的分布式电话簿，一台服务器背不动全人类的电话簿，所以分层、分布、加缓存。**

<br>

### 自测

为什么 DNS 不能集中式部署？说出至少两个理由。

<details><summary>答案</summary>集中式至少会有单点故障、通信容量瓶颈、远距离延迟、维护开销巨大四个问题。一台机器挂了全球解析瘫痪；所有查询挤到一处带宽和连接数扛不住；远距离查询延迟高；全球数据集中维护更新和备份都麻烦。</details>

<br>

## 知识点 2：分层架构与查询——根管方向，顶级管后缀，权威管门牌号
***
### 问题

一次查询到底怎么走？我输入一个域名，本地 DNS 服务器、根服务器、顶级域服务器、权威服务器，谁先说话、谁后说话？递归查询和迭代查询又差在哪？

**你可能会想**：根服务器是不是存了所有域名的 IP？问它一次不就全知道了？

不是。根服务器**不直接存具体域名**，它只告诉你“这个顶级域该去问谁”。真正存 `example.com` 的 A 记录的，是权威服务器。

<br>

### 核心概念与方案

先把四类服务器换成你熟悉的场景：

- **根 DNS 服务器**：像总台，不直接告诉你门牌号，只告诉你“这个方向该去问哪个分局”。
- **顶级域 DNS 服务器**：管 `.com`、`.cn`、`.org` 等后缀，告诉你“这个域的权威服务器是谁”。
- **权威 DNS 服务器**：保存具体域名的最终映射，比如 `example.com` 的 A 记录。
- **本地 DNS 服务器**：通常是 ISP 或你网络配置里的递归解析器，它帮你跑腿、缓存结果。**它不属于域名层级架构**，更像一个缓存代理。

典型路径是：你问本地 DNS → 本地 DNS 问根 → 根指向顶级域 → 顶级域指向权威 → 权威返回 IP。

**递归查询**是“你帮我查到底”，客户端通常对本地 DNS 发递归查询；**迭代查询**是“告诉我下一步问谁”，本地 DNS 对根、顶级域、权威通常用迭代查询。

缓存能加速：本地 DNS 在 TTL 内直接返回结果，不用每次从头问。

<br>

### 最小实验：只看逐级查询有没有出现根、顶级域、权威

环境前提：同上，已安装 `dig`，需要外网。`+trace` 会直接向根服务器发起查询，**受网络环境影响，部分网络可能看不到完整输出，需按环境核实**。

````bash
dig +trace example.com A
````

**这次只看一件事**：输出里有没有依次出现根服务器、`.com` 顶级域服务器、`example.com` 权威服务器。

预期会看到类似结构：

````text
.                        ...  NS  a.root-servers.net.
com.                     ...  NS  a.gtld-servers.net.
example.com.             ...  NS  ...
example.com.             ...  A   93.184.216.34
````

从 `.` 到 `com.` 再到 `example.com.`，就是逐级查询的过程。最后一行 `A` 记录，是权威服务器给出的最终答案。

注意：`+trace` 输出较长，不同网络环境下看到的根服务器和权威服务器可能不同；它展示的是迭代查询过程，**不经过本地递归解析器的缓存**。

<br>

### 易错点与边界

坑一：**本地 DNS 不属于层级架构**，它更像缓存代理和递归解析器。

坑二：**递归和迭代别混**：递归是让对方查到底，迭代是自己一步步问；客户端对本地 DNS 常用递归，本地 DNS 对上级常用迭代。

坑三：**缓存能加速，但改解析要等 TTL 过期**，不同缓存点的过期时间还不一样。

坑四：**根服务器不存具体域名的 IP**，它只指方向。

<br>

### 一句话本质

**根管方向，顶级管后缀，权威管门牌号，本地服务器帮你跑腿；递归是“你帮我查到底”，迭代是“告诉我下一步问谁”。**

<br>

### 自测

为什么修改域名解析后不能立刻全球生效？

<details><summary>答案</summary>因为 DNS 结果会在多个地方按 TTL 缓存：浏览器、操作系统、本地 DNS 服务器、中间代理都可能缓存。改解析后，缓存未过期的节点仍返回旧结果，只有等各缓存点的 TTL 陆续过期，才会逐步查到新记录。不同缓存点的 TTL 和过期时间还不一样，所以不是全球立刻生效。</details>

<br>

<br>

## 知识点 3：缓存与资源记录——TTL 抄近道，RR 表达不同答案
***
### 问题

为什么有时候域名解析秒开？DNS 里到底存了什么？A、NS、CNAME、MX 这些记录分别管什么？

**你可能会想**：DNS 记录不就是“域名 → IP”吗？为什么还有这么多种类型？

因为 DNS 不只回答“IP 是多少”，还要回答“这个域的权威服务器是谁”“这个别名指向哪”“邮件该发到哪”。不同类型回答不同问题。

<br>

### 核心概念与方案

先看缓存：DNS 结果会按 **TTL** 缓存，在 TTL 过期前直接返回，不用再问上级。

- **TTL 越大**：解析越快、上级压力越小，但变更生效越慢。
- **TTL 越小**：变更生效越快，但查询压力越大。

资源记录 RR 可以理解成 `(Name, Value, Type, TTL)`：

- `A`：主机名 → IPv4 地址。
- `NS`：域 → 该域的权威 DNS 主机名。
- `CNAME`：别名 → 规范主机名。
- `MX`：邮件服务器别名 → 规范主机名及优先级，数字越小优先级越高。

实际 DNS 还有 `AAAA`（IPv6）、`TXT`、`SOA` 等记录，这里先掌握最常用的四类。

<br>

### 最小实验：只看 A 记录有没有带 TTL，MX 有没有优先级

环境前提：同上，已安装 `dig`，需要外网。下面分两步，每步只看一件事。

先看 A 记录和 TTL：

````bash
dig example.com A
````

**这次只看一件事**：`ANSWER SECTION` 里有没有 `A` 记录和 TTL 数字。

预期类似：

````text
example.com.  300  IN  A   93.184.216.34
````

`300` 就是 TTL，单位秒。有它，说明这条记录可以缓存 300 秒。

再看 MX 记录：

````bash
dig example.com MX
````

**这次只看一件事**：`ANSWER SECTION` 里有没有 `MX` 和优先级数字。

可能看到类似：

````text
example.com.  3600 IN  MX  10 mail.example.com.
````

`10` 是优先级，数字越小越优先。**`example.com` 不一定有 MX 记录**，输出可能为空或只有 `SOA`，这很正常，**需按环境核实**。

<br>

### 易错点与边界

坑一：**CNAME 通常不能和同名的其他记录随意并存**，尤其不能和 A、MX 等同时存在；DNSSEC 相关记录是例外。

坑二：**TTL 越小，变更生效越快，但查询压力越大**；换 IP 前常建议先把 TTL 调小，等旧 TTL 过期后再切。

坑三：**CDN 会让同一域名在不同地区解析到不同 IP**，所以“我这边解析是这个 IP”不代表全球都一样。

坑四：**MX 记录的数字是优先级**，不是端口，也不是权重。

<br>

### 一句话本质

**DNS 靠分层分摊压力，靠 TTL 缓存抄近道，靠 A/NS/CNAME/MX 等资源记录回答不同问题。**

<br>

### 自测

为什么更换服务器 IP 前常建议先把 TTL 调小？

<details><summary>答案</summary>TTL 决定缓存多久。先把 TTL 调小，让旧缓存尽快过期；等旧 TTL 过期后再切 IP，全球各缓存点能更快查到新记录，减少“有的地方已生效、有的地方还指着旧 IP”的时间窗口。代价是 TTL 小期间查询压力会变大。</details>

<br>

<br>

## 完整可复现示例：用 dig 追踪 DNS、看记录和 TTL
***
你需要 Linux/macOS 或 WSL，已安装 `dig`，需要外网。下面每个步骤只看一件事，不展开无关字段。

````bash
set -e

echo "=== 1. 逐级查询：看有没有根、顶级域、权威 ==="
dig +trace example.com A | grep -E '^\.|^com\.|^example\.com\.' || true

echo "=== 2. A 记录和 TTL：看 ANSWER SECTION 有没有 A 和数字 ==="
dig example.com A | grep -A5 'ANSWER SECTION' || true

echo "=== 3. MX 记录：看有没有 MX 和优先级 ==="
dig example.com MX | grep -A5 'ANSWER SECTION' || true
````

可能的输出/现象：

````text
=== 1. 逐级查询 ===
.                        ...  NS  a.root-servers.net.
com.                     ...  NS  a.gtld-servers.net.
example.com.             ...  NS  ...
example.com.             ...  A   93.184.216.34

=== 2. A 记录和 TTL ===
example.com.  300  IN  A   93.184.216.34

=== 3. MX 记录 ===
（可能为空；example.com 不一定有 MX 记录）
````

**关键观察点**：第 1 步看有没有从 `.` 到 `com.` 再到 `example.com.` 的逐级查询；第 2 步看 `A` 记录有没有 TTL 数字；第 3 步看有没有 `MX` 和优先级。

验证结果：`+trace` 展示迭代查询过程；A 记录带 IP 和 TTL；MX 记录揭示邮件服务器和优先级。

注意：`+trace` 输出可能很长，而且会直接向根服务器发起查询，受网络环境影响；`example.com` 的 A 记录、TTL 和 MX 记录都可能随站点配置变化，看不到 MX 也正常。没有 `dig` 的系统可以改用 `nslookup` 或 `host`，但输出格式不同，**需按环境核实**。

## 排障速查表
***
| 现象 | 先查什么 | 常用命令/观察点 | 解释 |
|---|---|---|---|
| 域名打不开，IP 能打开 | DNS 解析 | `dig 域名 A +short`；`getent hosts 域名` | 先分清“解析失败”还是“连不上端口” |
| 改了解析但本地还是旧 IP | 本地缓存、TTL | `dig 域名 A` 看 TTL；`ipconfig /flushdns`（Windows）或清系统缓存 | 缓存未过期时仍返回旧结果；等 TTL 过期或主动清缓存 |
| 有的地区解析到 A，有的解析到 B | CDN、分地域解析、缓存 | `dig @不同DNS 域名 A`；多地区测试 | CDN 或智能解析会按地区返回不同 IP，不一定是故障 |
| 解析结果和预期不符 | hosts 文件、本地 DNS、搜索域 | 看 `/etc/hosts`（Linux/macOS）或 `C:\Windows\System32\drivers\etc\hosts`；`dig` 指定 DNS | hosts 可本地覆盖；本地 DNS 或搜索域也可能影响结果 |
| `dig +trace` 看不到完整链路 | 网络限制、根查询被拦 | 换网络重试；用 `dig 域名 A` 看最终结果 | 部分网络限制直接向根服务器查询，`+trace` 可能不完整 |
| MX 记录为空 | 域名是否配邮件 | `dig 域名 MX`；`dig 域名 SOA` | 没有 MX 说明该域名没配邮件服务器，不一定是故障 |
| 换 IP 后部分用户仍访问旧服务器 | TTL 和缓存 | 查旧记录 TTL；提前调小 TTL 再切换 | TTL 越大，旧缓存存活越久；切换前先调小 TTL 可缩短窗口 |

## 常见误区
***
- **以为 DNS 只用 UDP**：普通查询主要 UDP/53，区域传送用 TCP/53，截断等场景可能转 TCP。
- **以为根服务器存了所有域名 IP**：根只指方向，具体记录在权威服务器。
- **把本地 DNS 当成层级架构的一层**：本地 DNS 更像缓存代理和递归解析器，不属于根/顶级/权威层级。
- **把递归和迭代混为一谈**：客户端对本地 DNS 常用递归，本地 DNS 对上级常用迭代。
- **以为改了解析全球立刻生效**：多个缓存点按 TTL 缓存，要等过期才逐步生效。
- **以为 TTL 越小越好**：TTL 小变更快，但查询压力大；要按场景权衡。
- **把 MX 的数字当端口或权重**：它是优先级，数字越小越优先。
- **以为 CNAME 可以和任意记录并存**：CNAME 通常不能和同名的 A、MX 等随意并存。

## 自测三问
***
1. 为什么 DNS 普通查询常用 UDP，而区域传送常用 TCP？
2. 本地 DNS 服务器和权威 DNS 服务器的主要区别是什么？递归查询和迭代查询又分别用在哪一段？
3. TTL 对域名解析速度和变更生效时间有什么影响？换 IP 前为什么要先调小 TTL？

<details><summary>参考答案</summary>1. 普通查询报文短，UDP 开销小、不用握手，追求快；区域传送数据量大，需要可靠、有序、完整，所以用 TCP。普通查询响应过大或被截断时也可能转 TCP。2. 本地 DNS 通常是 ISP 或网络配置里的递归解析器，帮客户端跑腿并缓存，不属于域名层级；权威 DNS 保存具体域名的最终记录。客户端对本地 DNS 常用递归查询（你帮我查到底），本地 DNS 对根、顶级域、权威常用迭代查询（告诉我下一步问谁）。3. TTL 越大，解析越快、上级压力越小，但变更生效越慢；TTL 越小，变更生效越快，但查询压力越大。换 IP 前先调小 TTL，让旧缓存尽快过期，再切 IP 可缩短“部分用户还访问旧服务器”的窗口。</details>

## 总结
***
**DNS 用分层分布式数据库解决“一台服务器装不下全球电话簿”，用递归/迭代查询和 TTL 缓存解决效率，用 A/NS/CNAME/MX 等资源记录表达不同映射；改解析不能立刻全球生效，是因为多个缓存点要等 TTL 过期。**
