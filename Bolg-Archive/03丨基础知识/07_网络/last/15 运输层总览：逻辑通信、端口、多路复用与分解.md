## 痛点引入
***
你的电脑同时开着浏览器看网页、微信收消息、邮件客户端收信。

三个程序的数据包都到了同一张网卡、同一个 IP 地址上。操作系统拆开 IP 头之后，凭什么把网页数据给浏览器、把聊天数据给微信，而不是塞错进程？

你可能会想：看数据内容不就行了？

但数据是二进制的，操作系统不认识“这是网页还是聊天”。这一章咱们用一条问题链往前走：

1. IP 只管把包送到主机，为什么还分网络层和运输层？
2. 一台主机上多个应用，数据到底靠什么不串门？
3. 为什么 TCP 和 UDP 能同时监听同一个端口？
4. 运输层到底能“补”什么，不能“补”什么？

<br>

<br>

## 优先级说明
***
这篇是运输层的总图，后面学 TCP/UDP 都挂在这张图上。先分清主次：

**必须掌握（面试常问、项目真用得上）：**
- 网络层是主机到主机，运输层是进程到进程
- 运输层在端系统运行，路由器通常只处理到网络层
- 端口是 16 位，IP 找主机、端口找进程
- 多路复用在发送端，多路分解在接收端
- TCP 和 UDP 可以同端口，因为 IP 头协议号先区分
- TCP 连接套接字由四元组标识，所以同一端口能服务多个客户端

**了解即可（知道大概，不展开）：**
- 端口 0~1023 周知端口的完整分配
- `SO_REUSEPORT` 等多进程绑定同一端口的机制
- UDP 二元组和 TCP 四元组在 NAT 下的具体行为
- 运输层在操作系统内核里的实现细节

**主线**：IP 送到主机 → 运输层按端口送到进程 → 发送端多路复用、接收端多路分解 → TCP/UDP 各自独立 → 运输层只能基于网络层“尽力而为”做增强，不能凭空造带宽和时延保证。

## 知识点 1：网络层是主机到主机，运输层是进程到进程
***
### 问题

IP 和 TCP/UDP 挨着，谁负责什么？为什么说运输层提供的是“逻辑通信”？运输层能不能凭空提供底层没有的带宽和延迟保证？

**你可能会想**：TCP 不是保证可靠、还能控制拥塞吗？那它是不是也能保证带宽和延迟？

不能。**运输层不能凭空提供底层没有的服务。** IP 不给带宽和时延保证，TCP 也变不出“延迟绝不超过 10ms”。

<br>

### 核心概念与方案

先把两层换成你熟悉的场景：**网络层是快递员送到你家门口，运输层是收发室把快递精准塞到对应房间。**

- **网络层**负责主机到主机交付：IP 把数据包送到目标机器，但只做到“尽力而为”，不保证不丢、不保证按序、不保证带宽和时延。
- **运输层**负责进程到进程的逻辑通信：它在端系统里运行，路由器通常只处理到网络层，不处理运输层。

“逻辑通信”的意思是：应用层看起来像两端进程直接连着，实际中间经过复杂网络；运输层把底层的转发细节遮住了。

关键边界：**运输层不能凭空提供底层没有的服务。** IP 不给带宽和时延保证，TCP 也变不出带宽承诺；但 IP 会丢包，TCP 可以用确认、重传、按序交付来做可靠传输。所以运输层是在网络层“尽力而为”的基础上做增强，不是变魔术。

<br>

### 最小实验：只看本机有没有监听中的 TCP 和 UDP 端口

环境前提：Linux/macOS，或 Windows WSL；`ss` 不可用时改用 `netstat -tulnp`。下面只看本机端口，不联网。

````bash
ss -tulnp 2>/dev/null | head -n 20 || netstat -tulnp 2>/dev/null | head -n 20
````

**这次只看一件事**：输出里有没有 `tcp` 和 `udp` 开头的行，以及 `Local Address:Port` 这一列。

可能看到类似：

````text
Netid State  Local Address:Port  Peer Address:Port
udp   UNCONN 127.0.0.1:53         0.0.0.0:*
tcp   LISTEN 0.0.0.0:22           0.0.0.0:*
````

有 `udp` 和 `tcp` 行，说明本机有进程在监听端口。**没有输出也不代表命令错**，可能本机没开这些服务，或者 `ss` 需要权限才能显示进程信息，**需按环境核实**。

这个实验说明：**同一台主机上，运输层用端口区分不同进程；TCP 和 UDP 各自独立。** 网络层只负责把包送到这台主机，送到哪个进程是运输层的事。

<br>

### 易错点与边界

坑一：**运输层协议在端系统运行，不在路由器运行**；路由器主要处理到网络层，别把端口分发画到路由器上。

坑二：**可靠传输不是运输层专属**，链路层、应用层也能做；只是 TCP/IP 体系习惯把端到端可靠性交给 TCP。

坑三：**TCP 的拥塞控制不是“提供带宽保证”**，它是在探测网络、避免把网络压垮，做的是适应和退让，不是承诺带宽。

坑四：**“逻辑通信”不是“真的有一条直连线路”**，只是应用层看起来像直连。

<br>

### 一句话本质

**网络层是快递员送到你家门口，运输层是收发室把快递精准塞到对应房间；运输层只能基于“尽力而为”做增强，不能凭空造带宽和时延保证。**

<br>

### 自测

如果底层 IP 完全不提供带宽保证，TCP 能通过拥塞控制提供带宽保证吗？为什么？

<details><summary>答案</summary>不能。TCP 的拥塞控制是在探测网络、避免把网络压垮，做的是适应和退让，不是承诺带宽。IP 不提供带宽保证，TCP 也变不出带宽承诺；它只能在“尽力而为”的基础上做可靠传输和拥塞适应，不能凭空提供底层没有的服务。</details>

## 知识点 2：端口、多路复用与多路分解
***
### 问题

一台主机同时跑很多应用，数据到了怎么不串门？多路复用和多路分解分别发生在哪一端、靠什么字段？为什么 TCP 和 UDP 能同时监听同一个端口？

**你可能会想**：端口就是进程号吧？看到 8000 端口，就以为是 8000 号进程。

不是。**端口是运输层标识，进程号是操作系统内部编号。** 一个进程可以监听多个端口，一个端口也可能由多个连接共用。

<br>

### 核心概念与方案

先把端口换成你熟悉的场景：**IP 是小区地址，端口是门牌号，进程是住户。**

- **多路复用（发送端）**：运输层把多个应用进程的数据加上源端口、目的端口等首部，一起交给网络层。
- **多路分解（接收端）**：运输层根据目的端口，把报文交给对应套接字。

端口是 16 位，范围 0~65535；0~1023 是周知端口，如 HTTP 80、HTTPS 443、DNS 53；客户端端口通常由系统临时分配。

**TCP 和 UDP 可以同时绑定同一个端口**，因为内核里 TCP/UDP 是两个独立模块，IP 头里的协议号会先区分是 TCP 还是 UDP，再各自按端口分发。

更细一点：UDP 套接字常由“目的 IP + 目的端口”二元组标识；TCP 连接套接字由“源 IP、源端口、目的 IP、目的端口”四元组标识，所以同一个服务器端口可以同时服务多个客户端连接。

<br>

### 最小实验：只看 TCP 和 UDP 能不能同时绑同一端口

环境前提：Linux/macOS，或 Windows WSL；已安装 Python 3。下面只在本机回环地址上运行，不对外网开放。

保存为 `bind_both.py`：

````python
import socket

tcp = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
tcp.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
tcp.bind(("127.0.0.1", 12345))
tcp.listen(1)

udp = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
udp.bind(("127.0.0.1", 12345))

print("TCP and UDP both bound to 127.0.0.1:12345")
tcp.close()
udp.close()
````

运行：

````bash
python3 bind_both.py
````

**这次只看一件事**：程序有没有打印成功，还是报 `Address already in use`。

预期输出：

````text
TCP and UDP both bound to 127.0.0.1:12345
````

如果报 `Address already in use`，先检查 12345 端口是不是被别的程序占了，换个端口再试。**具体行为需按环境核实**，比如 `SO_REUSEADDR` 在不同系统上的语义有差异。

**结论**：TCP 和 UDP 的端口空间是分开的，同一端口号可以分别绑定；IP 头协议号先区分 TCP/UDP，再各自按端口分解。

<br>

### 易错点与边界

坑一：**端口不是进程号**，端口是运输层标识，进程号是操作系统内部编号。

坑二：**知名端口只是默认约定**，服务可以改端口，排查时不能只看 80/443。

坑三：**UDP 套接字常由二元组标识，TCP 连接套接字由四元组标识**，别把两者混成同一个粒度。

坑四：**TCP 和 UDP 同端口不冲突**，因为协议号先区分了；但同一协议下同一地址端口通常不能重复绑定，除非用 `SO_REUSEPORT` 等特殊选项，**具体需按环境核实**。

<br>

### 一句话本质

**IP 找到主机，端口找到进程；多路复用在发送端把多个进程的数据汇到一起，多路分解在接收端按端口分给对应进程；TCP 和 UDP 端口空间分开，所以能同端口。**

<br>

### 自测

TCP 和 UDP 能同时监听 80 端口吗？为什么？那同一个 TCP 端口能同时服务多个客户端连接吗？

<details><summary>答案</summary>TCP 和 UDP 可以同时监听 80，因为 IP 头里的协议号先区分 TCP 和 UDP，内核里两个模块各自按端口分发。同一个 TCP 端口能同时服务多个客户端连接，因为 TCP 连接套接字由四元组（源 IP、源端口、目的 IP、目的端口）标识，不同客户端四元组不同，可以区分。</details>

## 完整可复现示例：看本机端口分发和 DNS 查询
***
你需要 Linux/macOS 或 WSL，已安装 `ss`（或 `netstat`）和 `dig`（或 `nslookup`）。下面每个步骤只看一件事。

````bash
set -e

echo "=== 1. 本机有没有 TCP/UDP 监听端口 ==="
if command -v ss >/dev/null 2>&1; then
  ss -tulnp 2>/dev/null | head -n 10 || true
else
  netstat -tulnp 2>/dev/null | head -n 10 || true
fi

echo "=== 2. DNS 查询能不能解析出 IP ==="
if command -v dig >/dev/null 2>&1; then
  dig example.com A +short
else
  nslookup example.com | head -n 10 || true
fi
````

可能的输出/现象：

````text
=== 1. 本机端口 ===
udp UNCONN 127.0.0.1:53 0.0.0.0:*
tcp LISTEN 0.0.0.0:22   0.0.0.0:*

=== 2. DNS 查询 ===
93.184.216.34
````

**关键观察点**：第 1 步看有没有 `tcp`/`udp` 和本地端口；第 2 步看有没有解析出 IP。

验证结果：端口帮助定位进程，TCP/UDP 各自独立；运输层把“主机到主机”扩展成“进程到进程”。DNS 查询返回 IP，说明应用层 DNS 通过运输层端口 53 找到服务进程。

注意：本机没有服务监听时输出可能为空，这不代表命令错；`example.com` 的 A 记录会随站点和网络环境变化，**需按环境核实**。

## 排障速查表
***
| 现象 | 先查什么 | 常用命令/观察点 | 解释 |
|---|---|---|---|
| 多个应用同时上网，数据会串吗 | 端口是否不同 | `ss -tulnp` 看本地地址和端口 | 运输层按端口分解，不同应用用不同端口，不会串 |
| `bind failed: Address already in use` | 端口是否被占、TCP/UDP 是否分开 | `ss -ltnp` 和 `ss -lunp` 分别看 TCP/UDP | TCP 和 UDP 端口空间分开；同协议同地址端口通常不能重复绑定 |
| 服务监听 127.0.0.1，别的机器连不上 | 监听地址 | `ss -ltnp` 看是 `127.0.0.1` 还是 `0.0.0.0` | `127.0.0.1` 只接受本机回环访问；对外服务要监听 `0.0.0.0` 或具体网卡地址 |
| 端口显示进程信息为空 | 权限 | `sudo ss -ltnp` | `-p` 显示进程信息可能需要权限，没有权限时只看到端口 |
| TCP 和 UDP 同端口，一个能用一个不能用 | 是否绑错协议 | 分别用 `ss -ltnp` 和 `ss -lunp` 查看 | 确认服务实际监听的是 TCP 还是 UDP |
| 同一端口多个连接分不清 | TCP 四元组 | `ss -tan` 看源/目的 IP 和端口 | TCP 连接套接字由四元组标识，同一服务器端口可服务多个客户端 |
| `ping` 通但端口连不上 | 端口、服务、协议 | `curl -v`；`nc -vz 主机 端口` | ICMP 通只说明网络层可达，不代表运输层端口有服务 |

## 常见误区
***
- **把运输层协议画到路由器上**：运输层在端系统运行，路由器主要处理到网络层。
- **以为 TCP 拥塞控制能保证带宽**：它是探测和退让，不是承诺带宽。
- **把端口当进程号**：端口是运输层标识，进程号是操作系统内部编号。
- **以为知名端口不能改**：80、443、53 只是默认约定，服务可以配置到其他端口。
- **以为 TCP 和 UDP 不能同端口**：端口空间按协议分开，同一端口号可以分别绑定 TCP 和 UDP。
- **把 UDP 二元组和 TCP 四元组混为一谈**：UDP 套接字常由目的 IP + 目的端口标识，TCP 连接套接字由四元组标识。
- **以为 `send` 成功就是对方收到**：`send` 只代表交给内核，可靠性由运输层负责。

## 自测三问
***
1. 网络层和运输层在交付对象上有什么本质区别？为什么运输层不能凭空提供带宽和时延保证？
2. 多路复用和多路分解分别发生在发送端还是接收端？靠什么字段？
3. 为什么 TCP 和 UDP 可以使用同一个端口号？TCP 四元组又怎么让同一个端口服务多个连接？

<details><summary>参考答案</summary>1. 网络层负责主机到主机交付，IP 尽力而为，不保证丢包、按序、带宽和时延；运输层负责进程到进程的逻辑通信，在端系统运行。运输层不能凭空提供底层没有的服务，IP 不给带宽和时延保证，TCP 也只能做适应和增强，不能变出带宽承诺。2. 多路复用在发送端，把多个应用进程的数据加端口首部汇到网络层；多路分解在接收端，按目的端口把报文交给对应套接字。3. TCP 和 UDP 可以同端口，因为 IP 头协议号先区分 TCP 和 UDP，内核里两个模块各自按端口分发。TCP 连接套接字由四元组（源 IP、源端口、目的 IP、目的端口）标识，不同客户端四元组不同，所以同一服务器端口可以服务多个连接。</details>

## 总结
***
**运输层是应用进程和底层网络之间的桥梁：IP 找主机，端口找进程，多路复用/分解完成分发；它只能基于网络层“尽力而为”的服务做增强，不能凭空造出底层没有的带宽和时延保证。**
