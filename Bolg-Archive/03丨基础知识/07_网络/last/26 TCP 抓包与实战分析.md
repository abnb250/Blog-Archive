## 痛点引入
***
TCP 理论很抽象：三次握手、四次挥手、快速重传、零窗口，背起来像天书。

你可能会想：**这些字段和标志位，到底在真实网络里长什么样？**

再想几个具体场景：

- 你怀疑客户端连不上服务端，是 SYN 没到、SYN+ACK 丢了，还是服务端队列满了？
- 你在 Wireshark 里看到连续三个相同的 ACK，是网络乱序，还是真的丢包触发了快速重传？
- 你抓到的挥手只有三次，是抓包漏了，还是延迟确认把两次合并了？

## 优先级说明
***
这篇是 TCP 抓包实战的入门，面试常问，项目里排查连接超时、重传多、窗口异常也会用到。先分清主次：

**必须掌握（面试常问、项目真用得上）：**
- `tcpdump` 负责命令行抓包，Wireshark 负责图形化分析
- `-i` 指定网卡，`-nn` 不解析 IP 和端口名，`-w` 保存 pcap，`-c` 限制数量
- Wireshark 默认显示相对序号，初始序列号映射成 0，不是真实值
- 三次握手标志位：`[S]`、`[S.]`、`[.]`
- 四次挥手标志位：`[F.]`、`[.]`、`[F.]`、`[.]`
- 连续重复 ACK 可能触发快速重传，但重复 ACK 不一定都是丢包
- 零窗口是接收方 `win=0`，发送方停止发送并窗口探测，不是连接断开
- Wireshark 的“快速重传”标记是工具推断，不是报文自带字段
- 抓到的挥手只有三次，可能是延迟确认合并了 ACK 和 FIN，不一定是异常

**了解即可（知道大概，不展开）：**
- TCP 流量图、时间序列图等 Wireshark 高级功能
- 容器环境下 `-i any` 的可见性差异
- 抓包对性能的影响和过滤表达式优化
- 中间设备丢包导致两端抓包不一致的具体分析

**主线**：`tcpdump` 抓 → Wireshark 看 → 标志位识别阶段 → Seq/Ack 分析顺序和缺失 → win 判断接收能力 → 重传和零窗口都能从包里找到证据。

## 知识点 1：tcpdump 与 Wireshark 分工——一个抓，一个看
***
### 问题

Linux 服务器上怎么抓，怎么分析？为什么服务器上抓包常用 `tcpdump`，而不是直接开 Wireshark？Wireshark 里三次握手的 Seq 为什么常显示 0？那是真实序号吗？

**你可能会想**：服务器上装个 Wireshark 不就行了，图形界面多直观？

服务器通常没有图形界面，Wireshark 跑不起来，而且资源占用大。**`tcpdump` 命令行抓包，保存成 pcap，再拖进本地 Wireshark 分析，才是常见做法。**

<br>

### 核心概念与方案

先把两个工具换成你熟悉的场景：**`tcpdump` 是摄像机，负责在服务器上录；Wireshark 是播放器，负责在你电脑上慢放、逐帧看。**

- `tcpdump` 是命令行抓包工具，适合 Linux 服务器：没有图形界面也能跑，资源占用小，可以直接把包保存成 pcap 文件。
- Wireshark 是图形化分析工具：把 pcap 拖进去，可以看每层头部、TCP 流量图、相对序号、重传标记等，适合事后分析。

常用 `tcpdump` 参数：

- `-i` 指定网卡；`-i any` 表示所有网卡，但容器和部分系统上行为可能不同。
- `-nn` 不解析 IP 和端口名，避免 DNS 反查拖慢抓包。
- `-w` 把原始包保存到文件，方便拖进 Wireshark。
- `-c` 限制抓包数量，避免抓太多。

过滤表达式如 `tcp and port 80`、`icmp`，能减少无关流量。

Wireshark 默认常显示**相对序号**：把每个方向的初始序列号映射成 0，方便阅读。取消“Relative Seq”才能看到真实的随机初始序列号。所以看到 Seq=0 不一定是真的从 0 开始，只是显示方式。

<br>

### 最小实验：只看 tcpdump 抓到的第一行是不是 SYN

环境前提：Linux，已安装 `tcpdump`，需要 `sudo` 权限。下面只抓本机回环地址上的 TCP 包，不对外网开放。

终端 1 起一个本地 HTTP 服务：

````bash
python3 -m http.server 18083 --bind 127.0.0.1
````

终端 2 抓包：

````bash
sudo tcpdump -i lo -nn tcp port 18083 -c 5
````

终端 3 发起请求：

````bash
curl -s --max-time 5 http://127.0.0.1:18083/ -o /dev/null
````

**这次只看一件事**：tcpdump 输出的第一行，`Flags` 是不是 `[S]`。

可能看到类似：

````text
IP 127.0.0.1.54321 > 127.0.0.1.18083: Flags [S], seq ..., win ..., length 0
IP 127.0.0.1.18083 > 127.0.0.1.54321: Flags [S.], seq ..., ack ..., win ..., length 0
IP 127.0.0.1.54321 > 127.0.0.1.18083: Flags [.], ack ..., win ..., length 0
````

第一行 `[S]` 是 SYN，第二行 `[S.]` 是 SYN+ACK，第三行 `[.]` 是 ACK。**看到这三行，就是三次握手。**

如果第一行不是 `[S]`，先检查 `curl` 是否真的发起了连接、端口是否一致。`tcpdump` 需要权限，没有 `sudo` 可能抓不到包，**需按环境核实**。

<br>

### 易错点与边界

坑一：**抓包需要权限**，普通用户通常要 `sudo` 或给 `tcpdump` 相应 capability。

坑二：**容器/网卡命名会影响 `-i any`**，容器里可能看不到宿主机某些接口，抓不到不代表没流量。

坑三：**相对 Seq 不是真实初始序列号**，Wireshark 默认把初始序号映射成 0，方便看，不代表真实值。

坑四：**`tcpdump` 抓包本身也有开销**，高流量下过滤表达式要写准，别抓全量再慢慢筛。

坑五：**抓包点不同看到的现象不同**，在客户端抓和在服务端抓，可能一边看到重传、另一边看不到。

<br>

### 一句话本质

**`tcpdump` 负责抓，Wireshark 负责看懂；相对 Seq 不是真实序号；抓包是把 TCP 从抽象变具体的放大镜。**

<br>

### 自测

为什么 Wireshark 里三次握手的 Seq 常显示 0？如果想看真实初始序列号，应该怎么设置？

<details><summary>答案</summary>Wireshark 默认开启相对序号，把每个方向的初始序列号映射成 0，方便阅读。想看真实初始序列号，可以在 Wireshark 里取消 “Relative Seq” 选项，或者在 tcpdump 输出里直接看原始 Seq 值。</details>

## 知识点 2：从抓包看握手、挥手、重传与窗口——标志位看阶段，Seq/Ack 看顺序，win 看能力
***
### 问题

常见现象怎么在抓包里对应？三次握手和四次挥手的标志位长什么样？连续三个相同 ACK 说明什么？零窗口在抓包里是什么样？为什么抓到的挥手有时只有三次？

**你可能会想**：抓到三个重复 ACK，就一定是丢包触发快速重传吧？

不一定。**网络乱序也会产生重复 ACK。** 要结合后续有没有重传、缺失段是否真的没到，才能判断。

<br>

### 核心概念与方案

咱们按“标志位看阶段、Seq/Ack 看顺序和缺失、win 看接收能力”来读：

- **三次握手**：`[S]`、`[S.]`、`[.]`，分别对应 SYN、SYN+ACK、ACK。
- **四次挥手**：`[F.]`、`[.]`、`[F.]`、`[.]`，分别对应 FIN+ACK、ACK、FIN+ACK、ACK。被动方没数据要发且开启延迟确认时，ACK 和 FIN 可能合并，抓包看起来像三次；这不是异常。
- **重复 ACK/快速重传**：接收方连续回相同 Ack，发送方收到 3 个重复 ACK 后重传缺失段。抓包里会看到连续多个相同 Ack，然后发送方重发缺失 Seq。
- **零窗口**：接收方 `win=0`，发送方停止发送，定时发窗口探测；窗口恢复后继续发。零窗口不是连接断开。
- **SYN 丢包**：客户端按 `tcp_syn_retries` 指数退避重传 SYN；SYN+ACK 丢包则双方都可能重传。抓包里会看到相同 Seq 的 SYN 多次出现，间隔逐渐拉长。

注意：Wireshark 的“快速重传”标记是工具根据启发式规则推断的，不是报文里自带字段；别把它当成绝对真相，要结合 Seq/Ack 自己看。

<br>

### 最小实验：只看挥手有没有可能是三次

环境前提：同上，已安装 `tcpdump`、`nc`，需要权限。下面只在本机回环地址上观察挥手，不对外网开放。

终端 1 起一个简单服务端：

````bash
nc -l 18084
````

终端 2 抓包：

````bash
sudo tcpdump -i lo -nn tcp port 18084 -c 10
````

终端 3 发起连接并很快关闭：

````bash
nc -vz 127.0.0.1 18084
````

**这次只看一件事**：抓包里 FIN 和 ACK 出现了几行，是不是可能只有三行。

可能看到类似：

````text
Flags [S]    客户端 → 服务端
Flags [S.]   服务端 → 客户端
Flags [.]    客户端 → 服务端
Flags [F.]   客户端 → 服务端
Flags [F.]   服务端 → 客户端
Flags [.]    客户端 → 服务端
````

**关键观察点**：服务端的 ACK 和 FIN 合并成了 `[F.]`，所以看起来像三次挥手，而不是四次。

这是延迟确认把 ACK 和 FIN 合并了，不是抓包漏了。**标准流程仍是四次挥手，但实际抓包可能看到三次，这不是异常。**

如果只看到 `[F.]` 和 `[.]`，先检查抓包数量是否够、端口是否一致。`nc` 参数在不同系统上可能不同，**需按环境核实**。

<br>

### 易错点与边界

坑一：**Wireshark 的“快速重传”标记是工具推断**，不是报文本身字段；要结合重复 ACK 和重传 Seq 自己判断。

坑二：**零窗口不是连接断开**，只是接收方暂时没缓存；发送方会窗口探测，窗口恢复后继续。

坑三：**抓到的挥手三次不一定是异常**，可能是延迟确认合并了 ACK 和 FIN。

坑四：**重复 ACK 不一定是丢包**，也可能是乱序到达；要看后续是否触发重传、缺失段是否真的没到。

坑五：**在客户端抓和在服务端抓，看到的重传可能不同**；中间设备丢包时，两端抓包对不上是正常的。

<br>

### 一句话本质

**抓包读三样：标志位看阶段，Seq/Ack 看顺序和缺失，win 看接收能力；重复 ACK 不一定是丢包，挥手三次不一定是异常。**

<br>

### 自测

Wireshark 里看到连续三个相同 ACK，通常说明什么？为什么抓到的挥手有时只有三次，这算异常吗？

<details><summary>答案</summary>连续三个相同 ACK 通常说明接收方在重复确认同一个缺失段，可能触发发送方快速重传；但网络乱序也会产生重复 ACK，要结合后续是否重传、缺失段是否真的没到判断。抓到的挥手只有三次，可能是被动方没有数据要发且开启延迟确认，把 ACK 和 FIN 合并了；这不是异常，标准流程仍是四次挥手。</details>

<br>

## 完整可复现示例：抓一次本地 HTTP 请求并用 tcpdump 读关键行
***
你需要 Linux 或 WSL，已安装 `tcpdump`、`curl`、`python3`，抓包需要 `sudo`。下面每个步骤只看一件事，不展开无关字段。

````bash
set -e

PCAP=/tmp/http_lab.pcap

echo "=== 1. 启动本地 HTTP 服务 ==="
python3 -m http.server 18085 --bind 127.0.0.1 &
HTTP_PID=$!
sleep 1

echo "=== 2. 开始抓包（后台） ==="
sudo tcpdump -i lo -nn -w "$PCAP" tcp port 18085 &
TCPDUMP_PID=$!
sleep 1

echo "=== 3. 发起请求 ==="
curl -s --max-time 5 http://127.0.0.1:18085/ -o /dev/null || true

sleep 1
sudo kill "$TCPDUMP_PID" 2>/dev/null || true
wait "$TCPDUMP_PID" 2>/dev/null || true
kill "$HTTP_PID" 2>/dev/null || true

echo "=== 4. 读回抓包关键行 ==="
sudo tcpdump -nn -r "$PCAP" 2>/dev/null | head -n 20 || true
````

可能的输出/现象：

````text
Flags [S]    客户端 → 服务端
Flags [S.]   服务端 → 客户端
Flags [.]    客户端 → 服务端
Flags [P.]   客户端 → 服务端   ; HTTP 请求
Flags [P.]   服务端 → 客户端   ; HTTP 响应
Flags [F.]   客户端 → 服务端
Flags [.]    服务端 → 客户端
Flags [F.]   服务端 → 客户端
Flags [.]    客户端 → 服务端
````

**关键观察点**：第 4 步看有没有 `[S]`、`[S.]`、`[.]` 三次握手，以及 `[F.]`、`[.]`、`[F.]`、`[.]` 四次挥手（可能因合并少一行）。

验证结果：抓包能把握手、数据传输、挥手串起来；`[S]`、`[S.]`、`[.]` 是三次握手，`[F.]`、`[.]`、`[F.]`、`[.]` 是四次挥手（服务端 ACK 和 FIN 可能合并，看起来少一行也正常）。结合 Seq/Ack 可分析丢包、乱序和重传。

注意：`curl` 可能走 HTTP/2 或 HTTPS，本地 `python3 -m http.server` 默认 HTTP/1.0，抓不到完整 HTTP 明文请求是正常的；这个示例重点是看 TCP 标志位和 Seq/Ack。容器或权限受限环境里 `sudo tcpdump` 可能失败，可以先在能抓包的机器上试，**需按环境核实**。

## 常见误区
***
- **以为服务器上直接开 Wireshark 就行**：服务器通常没图形界面，`tcpdump` 抓 pcap 再拖进 Wireshark 更常见。
- **把 Wireshark 的相对 Seq 当成真实初始序列号**：默认映射成 0，不代表真实值。
- **以为重复 ACK 一定是丢包**：网络乱序也会产生重复 ACK。
- **以为零窗口是连接断开**：只是接收方暂时没缓存，发送方会窗口探测。
- **以为挥手三次一定是异常**：延迟确认可能合并 ACK 和 FIN。
- **把 Wireshark 的“快速重传”标记当绝对真相**：它是工具推断，要结合 Seq/Ack 自己看。
- **以为两端抓包一定一致**：抓包点不同、中间设备丢包时，两端看到的现象可能不同。

## 总结
***
**抓包是理解 TCP 的显微镜：`tcpdump` 抓、Wireshark 看，标志位识别阶段，Seq/Ack 分析顺序与丢失，win 判断接收能力，重传和零窗口都能从包里找到证据；相对 Seq 不是真实序号，重复 ACK 不一定是丢包，挥手三次不一定是异常。**
