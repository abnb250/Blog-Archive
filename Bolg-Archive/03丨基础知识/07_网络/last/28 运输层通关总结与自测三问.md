## 痛点引入
***
运输层学完，你脑子里全是 SYN、ACK、RTT、cwnd、ssthresh、TIME_WAIT。

合上笔记，我问你一个问题：**用三句话向别人解释“运输层到底在干什么”，你能说清楚吗？**

你可能会想：每个机制我都背过，应该算懂了吧？

但真让你说，很可能变成“TCP 可靠、UDP 快、三次握手、四次挥手、拥塞控制……”一串缩写，串不起来。**说不清，往往不是机制背少了，而是没把“进程分发 → UDP/TCP 分工 → 可靠传输 → 窗口/拥塞 → 异常与优化 → QUIC 演化”串成一条线。**

这一章不学新概念，只做三件事：

1. 把运输层全貌收拢，说清它能承诺什么、不能承诺什么。
2. 把缩写挂到一条问题链上，不再散落。
3. 排一遍最容易混的易错点，向下看一眼它封装了什么。

## 优先级说明
***
这是总结章，没有新知识点，重点是“串起来”和“自检”。先分清主次：

**必须能说清楚（面试常问、项目真用得上）：**
- 运输层把“主机到主机”扩展成“进程到进程”，靠端口和多路复用/分解
- UDP 极简换速度，TCP 复杂换可靠，QUIC 在 UDP 上换进化速度
- 运输层不能凭空提供底层没有的带宽和时延保证，只能基于 IP“尽力而为”做增强
- 应用层简单，是因为复杂性被内核封装了
- 可靠传输四件套：校验和、序号、确认、定时重传
- `rwnd` 保护接收方，`cwnd` 保护网络，实际窗口取 `min(cwnd, rwnd)`
- 半连接队列、全连接队列、`accept` 只取货不握手
- QUIC 在 UDP 上重造可靠、TLS、独立 Stream、连接 ID

**了解即可（知道大概，不展开）：**
- 每个机制的具体公式和内核参数
- 不同拥塞控制算法的差异
- QUIC 的帧格式和包类型
- 具体内核版本的默认值

**主线**：进程分发 → UDP/TCP 分工 → 可靠传输 → 窗口/拥塞 → 异常与优化 → QUIC 演化。

## 知识点 1：运输层全貌与能力边界——进程分发 + 两种服务承诺 + 有边界
***
### 问题

运输层到底解决了什么？它比网络层多了什么？为什么说 TCP 的复杂性对应用层是“透明”的？运输层能不能承诺带宽和时延？

**你可能会想**：TCP 这么复杂，是不是能保证带宽和延迟？

不能。**运输层不能凭空提供底层没有的带宽和时延保证。** IP 是“尽力而为”，TCP 能做可靠传输、流量控制、拥塞控制，但变不出“延迟绝不超过 10ms”或“保证 100Mbps”。

<br>

### 核心概念与方案

先把运输层换成你熟悉的场景：**运输层是端到端通信的守护者，但它只能基于 IP 的“尽力而为”做增强，不能变魔术。**

运输层把“主机到主机”扩展成“进程到进程”：靠**端口 + 多路复用/分解**，把数据交给正确进程。

- **UDP** 极简：无连接、不可靠、8 字节首部，适合 DNS、实时音视频、QUIC 底座。
- **TCP** 可靠：面向连接、字节流、序号/确认、重传、滑动窗口、流量控制、拥塞控制。
- **可靠传输四件套**：校验和、序号、确认、定时重传；这套理论不只 TCP 能用，QUIC 也在应用层重新实现。

关键边界：**运输层不能提供底层没有的带宽和时延保证**。IP 是“尽力而为”，TCP 能做可靠传输、流量控制、拥塞控制，但变不出“延迟绝不超过 10ms”或“保证 100Mbps”。

应用层写起来简单，是因为复杂性被内核封装了：你调 `send/recv`，内核在背后做编号、定时器、窗口、拥塞控制、重传。

<br>

### 最小自检：只看你能不能说出运输层“能”和“不能”各三件事

不需要敲代码，拿一张纸，试着写出：

````text
运输层能做的：
1. 端口分发，把数据交给正确进程
2. TCP 提供可靠、按序、流量控制、拥塞控制
3. UDP 提供极简、低开销的进程到进程通信

运输层不能做的：
1. 不能保证带宽
2. 不能保证时延上限
3. 不能凭空消除 IP 的丢包和乱序，只能做增强
````

**这次只看一件事**：你能不能不看原文，各说出三条。

- 能说出“能”和“不能”各三条，说明能力边界挂住了。
- 只能说出“TCP 可靠、UDP 快”，说不出“不能保证带宽和时延”，说明还停在背结论阶段。

**结论**：运输层是端到端通信的守护者，但它的能力有边界；它是在 IP 之上做增强，不是变魔术。

<br>

### 易错点与边界

坑一：**TCP 可靠不等于实时**，重传和拥塞控制会让延迟变大。

坑二：**ESTABLISHED 不代表对端一定活着**，可能只是没数据要发，也没开 Keepalive。

坑三：**TIME_WAIT 不是越少越好**，它是正常关闭流程的一部分。

坑四：**HTTP Keep-Alive 不是 TCP Keepalive**，前者是应用层连接复用，后者是 TCP 层探测。

坑五：**运输层不能凭空提供带宽和时延保证**，只能基于 IP 的“尽力而为”做增强。

<br>

### 一句话本质

**运输层是端到端通信的守护者：端口分发进程，UDP 换速度，TCP 换可靠，QUIC 换进化速度；它能做增强，但不能凭空造带宽和时延保证。**

<br>

### 自测

为什么说 TCP 的复杂性对应用层是“透明”的？运输层为什么不能承诺带宽和时延？

<details><summary>答案</summary>应用层调 `send/recv`，内核在背后做编号、定时器、窗口、拥塞控制、重传，所以应用层感觉简单，复杂性被内核封装了。运输层不能承诺带宽和时延，因为底层 IP 是“尽力而为”，不提供带宽和时延保证；TCP 只能做可靠传输、流量控制、拥塞控制等增强，不能凭空造出底层没有的保证。</details>

## 知识点 2：把机制串成一条线——进程分发 → UDP/TCP 分工 → 可靠传输 → 窗口/拥塞 → 异常与优化 → QUIC 演化
***
### 问题

SYN、ACK、RTT、cwnd、ssthresh、TIME_WAIT 这些词，复习时怎么串起来？面试或工作中被问到某个点，怎么快速定位到它属于哪条线？哪些易错点最容易混？

**你可能会想**：我按字母顺序背，或者按章节顺序背，不就行了？

按字母或章节背，知识点是散的。**要按“一条问题链”串，每个缩写都挂到“它解决什么问题”上，才不会散。**

<br>

### 核心概念与方案

别按字母顺序背，按“一条问题链”串：

- **进程分发**：端口、多路复用/分解；TCP/UDP 同端口不冲突，连接靠四元组区分。
- **UDP/TCP 分工**：UDP 极简换速度；TCP 面向连接、可靠、字节流。
- **可靠传输**：校验和、序号、确认、超时重传；流水线、GBN/SR；TCP 用 RTO 动态计算、3 个重复 ACK 快速重传、SACK 精确补缺。
- **窗口与拥塞**：`rwnd` 防撑爆接收方，零窗口要探测；`cwnd` 防堵网络，慢启动 → 拥塞避免 → 快速恢复，AIMD。
- **队列与异常**：半连接 SYN 队列、全连接 accept 队列；`accept` 不参与握手；Established 收旧 SYN 回 Challenge ACK；TIME_WAIT 收 SYN 看合法性。
- **优化与演化**：握手少重试扩队列、挥手管 TIME_WAIT、按 BDP 调缓冲区；QUIC 在 UDP 上实现可靠、TLS1.3、独立 Stream、连接 ID、1/0-RTT。

复习时抓住这条线：**进程分发 → UDP/TCP 分工 → 可靠传输 → 窗口/拥塞 → 异常与优化 → QUIC 演化。** 每个缩写都能挂到线上，就不会散。

<br>

### 最小自检：只看你能不能把每个缩写挂到一条线上

不需要背全文，拿一张纸，试着把下面的缩写填到对应的线里：

````text
端口、rwnd、cwnd、RTO、SACK、TIME_WAIT、accept、连接 ID
````

参考挂法：

- **进程分发**：端口
- **窗口/拥塞**：rwnd、cwnd
- **可靠传输**：RTO、SACK
- **异常与优化**：TIME_WAIT、accept
- **QUIC 演化**：连接 ID

**这次只看一件事**：你能不能不看原文，把每个缩写挂到一条线上。

- 能挂对大部分，说明主线挂住了。
- 只能说出缩写含义，说不出它属于哪条线，说明还是散的，回去把六条线再串一遍。

**关键观察点**：每个缩写都要能回答“它解决什么问题”，不只是“它是什么”。

<br>

### 易错点与边界

坑一：**不要混 TCP Keepalive 和 HTTP Keep-Alive**，前者是 TCP 层探测，后者是 HTTP 层连接复用。

坑二：**不要以为 TIME_WAIT 收到 SYN 一定 RST**，合法 SYN 可以复用连接。

坑三：**不要以为 `accept` 参与握手**，它只从全连接队列取连接。

坑四：**不要以为 UDP 没有端口**，端口仍然是多路分解的关键。

坑五：**不要以为 QUIC 是 UDP 直接可靠**，它是在 UDP 之上实现可靠传输、加密和拥塞控制。

坑六：**不要以为 `tcp_tw_recycle` 还能用**，Linux 4.12 后已移除，旧文章里的调参别照抄。

<br>

### 一句话本质

**运输层复习抓住一条线：进程分发 → UDP/TCP 分工 → 可靠传输 → 窗口/拥塞 → 异常与优化 → QUIC 演化；每个缩写都要能回答“它解决什么问题”。**

<br>

### 自测

TCP 连接四元组、可靠传输四件套、拥塞控制四阶段分别是什么？你能把“半连接队列、全连接队列、`accept`”串成一句话吗？

<details><summary>答案</summary>TCP 连接四元组是源 IP、源端口、目的 IP、目的端口；可靠传输四件套是校验和、序号、确认、定时重传；拥塞控制四阶段是慢启动、拥塞避免、快速重传/快速恢复，加上超时重传回到慢启动。半连接队列、全连接队列、`accept` 可以串成：`listen` 创建半连接队列和全连接队列，握手把连接从半连接队列搬到全连接队列，`accept` 只是从全连接队列取货，不参与握手。</details>

## 完整可复现示例：用一张分层图回顾运输层
***
这一章没有代码，咱们用一张分层图把运输层串起来，并给一个自检动作。

````text
【应用层】HTTP/DNS/邮件/Socket
      ↓
【运输层】端口 + 多路复用/分解
   ├─ UDP：无连接、8字节、检验和
   └─ TCP：三次握手、四次挥手、序号/确认、重传、滑动窗口、流量控制、拥塞控制
      ↓
【网络层】IP 尽力而为：可能丢包、乱序、不保证带宽时延
      ↓
【链路层/物理层】
````

**这次只看一件事**：你能不能在这张图里指出“进程分发、两种服务承诺、能力边界”分别在哪一层。

- 进程分发：运输层的端口和多路复用/分解。
- 两种服务承诺：UDP 极简换速度，TCP 复杂换可靠。
- 能力边界：运输层基于 IP“尽力而为”做增强，不能凭空造带宽和时延保证。
- QUIC 演化：在 UDP 之上重新实现可靠、TLS、多 Stream 和连接迁移。

**预期现象**：你能不看原文，把这张图从上到下讲一遍，并说出运输层能做什么、不能做什么。

**不符合预期说明什么**：如果只能背“TCP 可靠、UDP 快”，说不出能力边界和主线，回去把知识点 1 和知识点 2 再串一遍；如果觉得“QUIC 就是 UDP 直接可靠”，回去看 QUIC 那一篇。

验证结果：运输层不是孤立的协议名，而是“端口分发 + 可靠传输理论 + TCP/UDP 工程实现 + 异常优化 + 新协议演化”的一条问题链。

注意：这张图是逻辑分层示意，实际数据封装是逐层加首部；TCP 和 UDP 共用端口空间但按协议号区分，所以可以同时绑同一端口。

| `accept` 很慢，连接堆着 | 全连接队列 | `ss -lnt` 看 `Recv-Q`；`netstat -s \| grep overflowed` | 握手已完成，连接堆在全连接队列等 `accept` 取 |
| TIME_WAIT 很多 | 是否短连接多、主动关闭方集中 | `ss -tan \| grep TIME-WAIT \| wc -l` | TIME_WAIT 是正常关闭流程的一部分，不一定是 bug |
| 大量 CLOSE_WAIT | 应用是否忘记 `close` | `ss -tan \| grep CLOSE-WAIT` | 收到 FIN 后应用没 `close`，连接停在 CLOSE_WAIT |
| HTTP/3 没生效 | UDP 是否被限制、浏览器/服务器支持 | 查浏览器 flags；抓包看 UDP 443 | 部分网络限制 UDP，HTTP/3 回退到 HTTP/2 |
| `tcp_tw_recycle` 调了没效果 | 是否旧内核文章 | 查内核版本 | Linux 4.12 后已移除，现代内核不用再调 |
| QUIC 单流内仍卡 | 是否单流丢包 | 抓包看该流重传 | QUIC 解决流间队头阻塞，单流内丢包仍要等重传 |

## 常见误区
***
- **按字母或章节背缩写**：要按“进程分发 → UDP/TCP → 可靠传输 → 窗口/拥塞 → 异常 → QUIC”主线串。
- **以为 TCP 能保证带宽和时延**：运输层只能基于 IP“尽力而为”做增强，不能凭空造保证。
- **把 TCP Keepalive 和 HTTP Keep-Alive 混了**：前者是 TCP 层探测，后者是 HTTP 层连接复用。
- **以为 TIME_WAIT 收到 SYN 一定 RST**：合法 SYN 可以复用连接。
- **以为 `accept` 参与握手**：它只从全连接队列取连接。
- **以为 UDP 没有端口**：端口仍然是多路分解的关键。
- **以为 QUIC 是 UDP 直接可靠**：QUIC 在 UDP 之上实现可靠、加密和拥塞控制。
- **以为 `tcp_tw_recycle` 还能用**：Linux 4.12 后已移除。
- **以为 ESTABLISHED 就代表对端活着**：可能只是没数据要发，也没开 Keepalive。

## 自测三问
***
1. 运输层为什么不能提供底层没有的带宽和时延保证？
2. TCP 的可靠传输、流量控制、拥塞控制分别保护什么？`rwnd` 和 `cwnd` 取哪个值决定实际发送窗口？
3. QUIC 为什么要在 UDP 上重新实现可靠传输，而不是直接改 TCP？它解决了 TCP 的哪几个具体问题？

<details><summary>参考答案</summary>1. 底层 IP 是“尽力而为”，不提供带宽和时延保证；运输层只能在 IP 之上做可靠传输、流量控制、拥塞控制等增强，不能凭空造出底层没有的保证。2. 可靠传输保护数据不丢、不坏、不乱序；流量控制保护接收方不被撑爆；拥塞控制保护网络不被压垮。实际发送窗口取 `min(cwnd, rwnd)`：`cwnd` 是拥塞窗口，保护网络；`rwnd` 是接收窗口，保护接收方。3. 直接改 TCP 要动内核，升级慢、部署难；QUIC 在 UDP 之上用用户态实现可靠传输、TLS1.3、独立 Stream、连接 ID 和可迭代拥塞控制，解决了 TCP 的全局队头阻塞、握手延迟、连接迁移成本高和内核僵化问题。</details>

<br>

<br>

## 总结
***
**运输层是端到端通信的守护者：端口把数据交给正确进程，UDP 用极简换速度，TCP 用序号/确认/重传/窗口/拥塞控制换可靠，QUIC 在 UDP 上重造可靠与安全以绕开 TCP 的僵化；复习抓住“进程分发 → UDP/TCP 分工 → 可靠传输 → 窗口/拥塞 → 异常与优化 → QUIC 演化”这条线，运输层就不再是一堆缩写。**
