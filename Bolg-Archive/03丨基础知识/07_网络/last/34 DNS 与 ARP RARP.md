## 痛点引入
***
你在浏览器输入 `www.server.com`，按下回车。

你可能会想：**浏览器怎么找到服务器？**

但真正发数据包之前，至少有两步查询：

1. **域名变 IP**：浏览器得先知道 `www.server.com` 对应的 IP 是多少，这一步靠 DNS。
2. **IP 变 MAC**：知道目标 IP 后，数据包要封装成帧发到链路上，目的 MAC 填谁的？这一步靠 ARP。

再想两个具体场景：

- 如果目标在外网，你 ARP 问的到底是目标主机的 MAC，还是网关的 MAC？
- 你改了一个域名的解析，为什么有的地方立刻生效，有的地方要等好久？

这一章咱们用一条问题链往前走：

1. 域名怎么变成 IP，为什么全世界不能只用一台 DNS 服务器？
2. 一次 DNS 解析到底经过哪些服务器，根服务器会直接告诉你最终 IP 吗？
3. 知道下一跳 IP 后，怎么找它的 MAC，ARP 请求是广播还是单播？
4. 跨网段发送时，ARP 问的是目标主机还是网关？RARP 又是什么？

## 优先级说明
***
这篇是 DNS 与 ARP 的核心，面试常问，项目里排查“域名解析不对”“同网段不通”“跨网段不通”也会用到。先分清主次：

**必须掌握（面试常问、项目真用得上）：**
- DNS 是分层分布式数据库，根 → 顶级域 → 权威
- 根服务器只指路，不直接给最终 IP
- 本地 DNS 对客户端常用递归查询，对上级常用迭代查询
- DNS 普通查询常用 UDP 53，区域传送用 TCP 53
- TTL 影响缓存和变更生效时间，改解析不能立刻全球生效
- hosts 文件可本地覆盖解析结果
- ARP 已知 IP 求 MAC，请求广播、响应单播，结果缓存
- ARP 只在同一链路内工作；跨网段 ARP 问的是网关 MAC
- RARP 是已知 MAC 求 IP，现代更常用 DHCP

**了解即可（知道大概，不展开）：**
- DNSSEC 的签名和验证流程
- ARP 欺骗的原理和防护
- 免费 ARP（Gratuitous ARP）的用途
- RARP 服务器的具体部署

**主线**：域名 → DNS 分层解析成 IP → 知道目标 IP → 判断是否同网段 → 同网段 ARP 目标主机 MAC，跨网段 ARP 网关 MAC → 封装成帧发出去。

## 知识点 1：DNS 分层解析——域名找 IP，根服务器只指路
***
### 问题

域名怎么变成 IP？为什么全世界不能只用一台 DNS 服务器？一次解析到底经过哪些服务器？根服务器会直接告诉你最终 IP 吗？

**你可能会想**：DNS 不就是查个表吗？全世界放一台大服务器，所有域名都查它，不就完了？

不行。**一台服务器背不动全球电话簿。** 单点故障、容量瓶颈、远距离延迟、维护开销，四个问题随便一个都足以让全球解析瘫痪。所以 DNS 设计成分层分布式数据库。

<br>

### 核心概念与方案

先把 DNS 换成你熟悉的场景：**DNS 是互联网电话簿，但不是一本，而是分层的：总目录查方向，分类目录查区域，具体电话簿查号码。**

域名越靠右层级越高：根域 → 顶级域 `.com` → 权威域 `server.com`。

解析时先查浏览器缓存、系统缓存、hosts 文件，再问本地 DNS。本地 DNS 通常代表客户端做**递归查询**，对根、顶级域、权威 DNS 则常用**迭代查询**：

- 根只告诉你“去问 `.com`”。
- 顶级域告诉你“去问 `server.com` 的权威”。
- 权威才返回最终 IP。

结果会按 TTL 缓存。普通 DNS 查询常用 **UDP 53**，区域传送用 **TCP 53**；响应过大或被截断时，普通查询也可能改用 TCP 重查。

**根服务器只指路，不直接给最终答案；缓存让重复查询不用每次从头问。**

<br>

### 最小实验：只看 dig +trace 有没有逐级出现根、顶级域、权威

环境前提：Linux/macOS，或 Windows WSL；已安装 `dig`（`dnsutils` 或 `bind-utils` 包），需要外网。`+trace` 会直接向根服务器发起查询，部分网络可能看不到完整输出，**需按环境核实**。

````bash
dig +trace example.com A | grep -E '^\.|^com\.|^example\.com\.' || true
````

**这次只看一件事**：输出里有没有依次出现 `.`、`com.`、`example.com.` 这三层。

可能看到类似：

````text
.                        ...  NS  a.root-servers.net.
com.                     ...  NS  a.gtld-servers.net.
example.com.             ...  NS  ...
example.com.             ...  A   93.184.216.34
````

从 `.` 到 `com.` 再到 `example.com.`，就是逐级查询的过程。最后一行 `A` 记录，是权威服务器给出的最终答案。

**关键观察点**：根服务器那一行只给 `NS`，不直接给 `A` 记录。**根只指路，不带路。**

如果 `+trace` 输出不完整，可能是网络限制直接向根服务器查询，换网络再试，或只看 `dig example.com A` 的最终结果。

<br>

### 易错点与边界

坑一：**DNS 不只走 UDP**，区域传送用 TCP 53；普通查询响应过大也可能转 TCP。

坑二：**hosts 文件可本地覆盖解析结果**，排查“域名解析不对”时别忘了看它。

坑三：**TTL 影响缓存和变更生效时间**，改解析不能立刻全球生效。

坑四：**CDN 会让同一域名在不同地区解析到不同 IP**，你这边解析结果不代表全球一致。

坑五：**根服务器不存具体域名的最终 IP**，它只指向顶级域。

<br>

### 一句话本质

**DNS 就是互联网电话簿：分层查找、缓存加速，根服务器只指路不带路；本地 DNS 帮你跑腿，递归和迭代分工不同。**

<br>

### 自测

为什么修改域名解析后不能立刻全球生效？根、顶级域、权威 DNS 在一次解析里分别起什么作用？

<details><summary>答案</summary>DNS 结果会在浏览器、操作系统、本地 DNS 服务器、中间代理等多处按 TTL 缓存。改解析后，缓存未过期的节点仍返回旧结果，只有等各缓存点 TTL 陆续过期，才会逐步查到新记录，所以不是全球立刻生效。根服务器只告诉你顶级域在哪，顶级域告诉你权威服务器在哪，权威服务器才返回具体域名的最终记录。</details>

## 知识点 2：ARP 与 RARP——IP 找 MAC，跨网段问的是网关
***
### 问题

知道下一跳 IP，怎么找 MAC？ARP 请求是广播还是单播？响应呢？跨网段发送时，ARP 问的是目标主机 MAC 还是网关 MAC？知道 MAC 又怎么反查 IP？

**你可能会想**：我知道目标 IP 是 `8.8.8.8`，直接 ARP 问 `8.8.8.8` 的 MAC 不就行了？

不行。**ARP 只在同一链路内工作。** `8.8.8.8` 在外网，不在你当前链路里，你的 ARP 广播根本到不了它。跨网段时，你真正要问的是**默认网关的 MAC**，把帧先发给网关，让网关继续转发。

<br>

### 核心概念与方案

先把 ARP 换成你熟悉的场景：**ARP 是在当前小区里喊一嗓子“谁住 101？告诉我你的门牌号”，有人应答就记下来；跨小区时你只能问小区门口保安的地址，让保安帮你转交。**

**ARP** 用于**已知 IP 求 MAC**：主机广播 ARP 请求“谁是 `192.168.1.2`？请告诉我你的 MAC”，目标 IP 匹配的设备**单播**回 ARP 响应，携带自己的 MAC；结果会缓存一段时间，减少重复广播。

**RARP** 反过来：**已知 MAC 求 IP**，常用于早期无盘工作站/嵌入式设备，需要 RARP 服务器；现代更常用 DHCP。

关键边界：**ARP 只在同一链路内工作**。跨网段发送时，目的 IP 是最终主机，但目的 MAC 填的是**网关 MAC**；所以 ARP 问的是网关，不是最终主机。

<br>

### 最小实验：只看同网段 ARP 缓存里有没有目标主机记录

环境前提：Linux/macOS，或 Windows WSL；已安装 `ip` 命令和 `ping`。下面只在本机局域网内操作，不对外网开放。

先 ping 同网段一个地址（换成你局域网里实际存在的地址，比如网关）：

````bash
ping -c 1 -W 1 192.168.1.1 || true
````

再看 ARP 缓存：

````bash
ip neigh | grep '192.168.1.1' || true
````

**这次只看一件事**：ARP 缓存里有没有 `192.168.1.1` 对应的 `lladdr`（MAC 地址）。

可能看到类似：

````text
192.168.1.1 dev eth0 lladdr aa:bb:cc:dd:ee:ff REACHABLE
````

有 `lladdr`，说明 ARP 已经解析出网关的 MAC。**同网段目标，ARP 问的就是目标主机；跨网段目标，ARP 问的是网关。**

如果缓存里没有记录，可能是目标不在线、不同网段、或 ARP 缓存已过期。`ip neigh` 的可用性因系统而异，**需按环境核实**；没有 `ip` 可以改用 `arp -a`。

<br>

### 易错点与边界

坑一：**ARP 只在同一链路内工作**，不能跨路由器直接问最终主机 MAC。

坑二：**跨网段要找网关 MAC，不是最终主机 MAC**；最终主机 MAC 在最后一跳才用到。

坑三：**ARP 缓存会过期**，不是查到就永久有效。

坑四：**RARP 现代很少用**，DHCP 更常见；别把两者混为一谈。

坑五：**ARP 请求是广播，响应通常是单播**；别记反了。

<br>

### 一句话本质

**ARP 是“IP 问 MAC”，RARP 是“MAC 问 IP”；ARP 广播问、单播答，结果缓存；跨网段时 ARP 问的是网关 MAC，不是最终主机 MAC。**

<br>

### 自测

主机要发给外网目标，ARP 请求问的是目标主机 MAC 还是网关 MAC？ARP 请求和响应分别是广播还是单播？

<details><summary>答案</summary>跨网段发送时，ARP 问的是默认网关的 MAC，不是最终主机 MAC；最终主机 MAC 在最后一跳才用到。ARP 请求是广播，响应通常是单播；结果会缓存，减少重复广播。</details>

<br>

## 完整可复现示例：一次“访问网页”把 DNS 和 ARP 串起来
***
你需要 Linux/macOS 或 WSL，已安装 `dig`（或 `nslookup`）、`ip`（或 `arp`）、`ping`。下面每个步骤只看一件事，不展开无关字段。

````bash
set -e

echo "=== 1. DNS：域名解析成 IP ==="
if command -v dig >/dev/null 2>&1; then
  dig example.com A +short
else
  nslookup example.com 2>/dev/null | tail
fi

echo "=== 2. 路由：目标走哪张网卡、下一跳是谁 ==="
ip route get 93.184.216.34 2>/dev/null || true

echo "=== 3. ARP：同链路下一跳的 MAC 缓存 ==="
ip neigh 2>/dev/null | head -n 10 || arp -a 2>/dev/null | head -n 10 || true
````

可能的输出：

````text
=== 1. DNS ===
93.184.216.34

=== 2. 路由 ===
93.184.216.34 via 192.168.1.1 dev eth0 src 192.168.1.10

=== 3. ARP ===
192.168.1.1 dev eth0 lladdr aa:bb:cc:dd:ee:ff REACHABLE
````

**关键观察点**：第 1 步看域名有没有解析出 IP；第 2 步看下一跳是不是网关；第 3 步看网关的 MAC 有没有缓存。

验证结果：DNS 把域名解析成 IP；路由表判断目标在外网，下一跳是网关；ARP 缓存里保存的是网关的 MAC，不是最终主机的 MAC。**跨网段时，ARP 问的是网关，不是目标主机。**

注意：`example.com` 的 A 记录会随站点和网络环境变化；ARP 缓存里不一定有目标主机的记录，跨网段时通常只有网关的记录；`ip`、`arp`、`dig` 的可用性和输出因系统而异，**需按环境核实**。

## 排障速查表
***
| 现象 | 先查什么 | 常用命令/观察点 | 解释 |
|---|---|---|---|
| 域名打不开，IP 能打开 | DNS 解析 | `dig 域名 A +short`；`getent hosts 域名` | 先分清“解析失败”还是“连不上端口” |
| 改了解析本地还是旧 IP | 缓存、TTL | `dig 域名 A` 看 TTL；清系统缓存 | 缓存未过期时仍返回旧结果；等 TTL 过期或主动清缓存 |
| 有的地区解析到 A，有的解析到 B | CDN、分地域解析 | `dig @不同DNS 域名 A`；多地区测试 | CDN 或智能解析会按地区返回不同 IP，不一定是故障 |
| 同网段不通 | ARP 缓存、掩码 | `ip neigh` 看 MAC；`ip addr` 看掩码 | ARP 没解析出 MAC、掩码配错都可能同网段不通 |
| 跨网段不通 | 默认网关、网关 ARP | `ip route` 看默认网关；`ip neigh` 看网关 MAC | 默认网关缺失或网关 MAC 没解析，包出不去 |
| ARP 缓存为空 | 是否同链路、是否刚通信 | `ip neigh`；`ping` 目标后再看 | 没有通信就不会有 ARP 记录；跨网段只有网关记录 |
| ARP 请求广播、响应单播分不清 | 抓包看目的 MAC | `tcpdump -i any arp` | 请求目的 MAC 是全 F 广播，响应是单播 |
| 看到 `169.254.x.x` | DHCP 是否失败 | `ip addr`；查 DHCP 服务器 | 链路本地地址通常表示 DHCP 没拿到地址 |

## 常见误区
***
- **以为 DNS 只用 UDP**：普通查询主要 UDP/53，区域传送用 TCP/53，截断等场景可能转 TCP。
- **以为根服务器存了所有域名 IP**：根只指路，具体记录在权威服务器。
- **以为改了解析全球立刻生效**：多个缓存点按 TTL 缓存，要等过期才逐步生效。
- **以为 hosts 文件不影响解析**：hosts 可本地覆盖解析结果，排查时别忘了看。
- **以为 ARP 能跨路由器问最终主机**：ARP 只在同一链路内工作，跨网段问的是网关。
- **把 ARP 请求和响应记反**：请求是广播，响应通常是单播。
- **以为 ARP 缓存永久有效**：缓存会过期，需要时重新解析。
- **把 RARP 和 DHCP 混为一谈**：RARP 已知 MAC 求 IP，现代更常用 DHCP。

## 自测三问
***
1. DNS 解析中根、顶级域、权威 DNS 各起什么作用？为什么根服务器不直接给最终 IP？
2. ARP 请求是广播还是单播？响应呢？跨网段发送时，ARP 问的是谁的 MAC？
3. RARP 和 DHCP 都涉及地址分配，它们的主要区别是什么？为什么现代更常用 DHCP？

<details><summary>参考答案</summary>1. 根服务器只告诉你顶级域在哪，顶级域告诉你权威服务器在哪，权威服务器才返回具体域名的最终记录。根不直接给最终 IP，是因为它只负责指方向，具体记录分散在各级权威服务器，分层分布式才能分摊全球查询压力。2. ARP 请求是广播，响应通常是单播；跨网段发送时，ARP 问的是默认网关的 MAC，不是最终主机 MAC。3. RARP 是已知 MAC 求 IP，需要 RARP 服务器，功能比较单一；DHCP 不仅能分配 IP，还能下发掩码、网关、DNS、租期等配置，更灵活，所以现代更常用 DHCP。</details>

<br>

<br>

## 总结
***
**DNS 分层把域名解析成 IP，根只指路、缓存加速；ARP 在同一链路内广播问 IP 对应的 MAC、单播答、结果缓存；跨网段时 ARP 问的是网关 MAC，不是最终主机 MAC；RARP 是 MAC 反查 IP，现代更常用 DHCP。**
