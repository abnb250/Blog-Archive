## 场景问题

***

你在浏览器地址栏敲下 `https://example.com`，页面出来了。DevTools 的 Network 面板里躺着十几条请求，每一条都有状态码、耗时、大小。

你大概知道“HTTP 是请求—响应”，于是面试时被问到“一次网页请求到底发生了什么”，你回答：**客户端发一个 HTTP 请求，服务器回一个 HTTP 响应，结束了**。

面试官追问：**那 TCP 握手呢？TLS 握手呢？为什么有的请求复用了连接、有的没有？DNS 算不算“请求”？**

这一篇要建立的就是“端到端”的直觉：**你看到的“一次请求”，在底层远不止一次报文交互；但你也不必在第 1 篇就钻进 TCP 状态机和 TLS 密码学**。先学会在 DevTools 里“看见”分层，知道哪些事情正在发生，以及出问题时先怀疑哪一层。

<br>

<br>

## 核心概念

***

### 客户端—服务器：不是“一台电脑对另一台电脑”

<br>

**客户端（client）** 是发起请求的一方，**服务器（server）** 是等待并回应的一方。这个模型的关键不在于“两台机器”，而在于**谁先开口**。

浏览器是客户端。你打开 `example.com`，是浏览器主动向托管 `example.com` 的服务器发起连接。服务器不会无缘无故给你推数据。这个方向性会一直保留到后面的 TCP 和 HTTP：**客户端先发 SYN，客户端先发 HTTP 请求**。

<br>

### 协议分层：每一层只关心自己那一小段

<br>

**协议分层**的直觉很简单：**你不需要在写 HTTP 请求时操心网线有没有插好**。每一层把下一层当作“可靠的黑盒传输通道”。

对开发者来说，最有用的是**应用层和运输层的分界**：

- 应用层：HTTP、DNS、TLS（严格说 TLS 在应用层和运输层之间，但开发者通常把它归到“HTTP 底下的那一层”）。
- 运输层：TCP、UDP。你写代码时操作的 **Socket** 就在这里。
- 网络层/链路层：IP、以太网、Wi-Fi。第 1 篇只需要知道它们“在更下面”，不展开。

**一个常见的误解是把“HTTP 请求”等同于“网络交互”。** 实际上，一个 HTTPS 请求要真正到达应用层的 HTTP 处理器之前，可能已经经历了 DNS 查询、TCP 握手、TLS 握手；HTTP 响应回来之后，连接还可能被复用给下一个请求。你看到的“一次请求”，在底层可能没有新的连接建立握手（复用了已有连接），也可能要经历 TCP 三次握手和若干次 TLS 报文。

<br>

### 端到端视角：用户感受到的“快慢”，由最慢的那一段决定

<br>

**端到端（end-to-end）** 的意思是：从浏览器进程里的一个 URL，到服务器进程返回最后一个字节，中间任何一段慢了，用户都会觉得“这个页面慢”。可能是 DNS 慢，可能是 TCP 建连慢，可能是 TLS 握手慢，可能是服务器处理慢，也可能是浏览器在排队。

DevTools 的 **Timing** 瀑布图就是把这个“端到端”拆开给你看。第 1 篇不要求你读懂每一个阶段，但你要知道：**你写代码时调一个接口，日志里如果只记录“耗时 2s”，那 2s 可能花在任何一个你没有直接控制权的环节上。**

为了面试复述，可以先记住一个**粗粒度时序**，不展开细节：

```text
浏览器                     DNS服务器/系统解析器              服务器
  |---- 解析 example.com ----------->|                         |
  |<--------------- IP 地址 ---------|                         |
  |---- TCP 建连（首次，粗略）--------------------------------->|
  |<-------------------------------- 建连完成 -----------------|
  |---- TLS 握手（HTTPS，首次，粗略）-------------------------->|
  |<-------------------------------- 安全通道建立 -------------|
  |---- HTTP 请求 --------------------------------------------->|
  |<-------------------------------- HTTP 响应 -----------------|
  |---- 后续请求可能复用连接，不再重复 TCP/TLS 建连 ---------->|
```

**这张图只建立“端到端有哪几段”的感觉，不表示每个报文的具体字段和状态迁移。** TCP 状态机、TLS 密码学细节分别留给后续章节；以当前主流实现为准，具体版本行为需查证。

<br>

## 动手实验：在 DevTools 里“看见”分层

***

### 实验目标

<br>

打开一个真实页面，不写任何代码，只通过 Chrome DevTools 的 Network 面板，**看到**下面三件事：

1. 一个页面加载**不止一个 HTTP 请求**。
2. 每个请求的 **Protocol** 列会告诉你它用的是 HTTP/1.1、HTTP/2（h2）还是 HTTP/3（h3）。
3. 在 **Timing** 里可以看到“Stalled/Queueing”“DNS Lookup”“Initial connection”“SSL”这些阶段，它们对应着你还没学的下层机制。

<br>

### 步骤

<br>

**步骤一：打开 Network 面板并启用必要列。**

在 Chrome 中打开 `https://example.com`，按 F12（或 Ctrl+Shift+I / Cmd+Option+I），切换到 **Network** 标签。刷新页面。

在请求表格的表头区域**右键**，勾选：

- **Protocol**（显示协议版本）
- **Connection ID**（可选，显示连接复用情况）

<br>

**步骤二：观察“请求列表”。**

你会看到至少一条请求，Name 是 `example.com` 或 `/`，Status 通常是 `200`，Type 是 `document`。如果页面引用了 CSS、JS、图片，还会有更多行。**一个网页的加载是一组资源请求，不是一次请求。**

<br>

**步骤三：点开第一条请求，看 Timing。**

在右侧面板找到 **Timing** 标签。你会看到类似下面的分段（不同 DevTools 版本的显示名称可能略有差异）：

- **Stalled/Queueing**：请求在浏览器内部排队等待的时间。HTTP/1.1 下常见原因是同源连接数达到上限；HTTP/2 下多路复用减轻了连接数排队，但 Stalled 仍可能来自连接池阻塞、握手未完成或优先级调度，不能一概而论。
- **DNS Lookup**：域名解析耗时。如果命中缓存，可能显示 0 ms 或非常短。
- **Initial connection**：浏览器建立连接的总耗时，通常包含 TCP 握手（以及重试）和 TLS 协商（HTTPS 场景）。
- **SSL**：TLS 握手耗时（HTTPS 才有）。注意 Initial connection 与 SSL 的显示关系可能因 DevTools 版本不同而有差异；排查时不要把 Initial connection 直接等同于 TCP 握手。
- **Request sent** / **Waiting (TTFB)** / **Content Download**：HTTP 层面的发送、等待首字节、下载。

**注意：你在第 1 篇不需要背每个阶段的精确含义。** 你只需要建立一个条件反射：**“慢”不一定慢在你写的业务代码里**。如果 Initial connection 很长，说明连接建立阶段慢，需要结合 SSL 阶段和网络环境区分是 TCP 还是 TLS；如果 SSL 阶段单独很长，问题更可能在 TLS 层；如果 Stalled/Queueing 很长，可能是浏览器连接池在排队，也可能是优先级调度。

<br>

**步骤四（命令行补一刀）：用 `curl -v` 看协议协商结果。**

先执行 `curl -V`，确认输出里包含 `HTTP2`。如果没有，后续关于 h2 协商的预期不适用，请以 DevTools 的 Protocol 列作为主要观察手段。

在终端执行：

```bash
curl -v -o /dev/null https://example.com
```

> **预期输出片段（示意，以当前主流 curl 和服务器实现为准，具体细节可能因版本而异）：**
>
> ```text
> * Connected to example.com (...) port 443
> * ALPN: curl offers h2,http/1.1
> * TLSv1.3 (OUT), TLS handshake, Client hello (1):
> ...
> * ALPN: server accepted h2
> ...
> > GET / HTTP/2
> ...
> < HTTP/2 200
> ```

HTTP/2 中 authority 由 `:authority` 伪头承载；部分 curl 版本的调试输出可能仍以 `Host:` 形式显示，以协议语义为准。

**看到 `ALPN: server accepted h2` 说明什么？**

说明客户端在 **TLS 握手**里通过 **ALPN（Application-Layer Protocol Negotiation，应用层协议协商）** 告诉服务器“我支持 h2 和 http/1.1”，服务器选择了 h2。**你看到的 HTTP 请求，是在 TLS 握手协商完协议之后才发出去的。** 这就是“分层”在真实工具里的痕迹。

如果服务器不支持 h2，你会看到 `ALPN: server accepted http/1.1`，后续请求行是 `GET / HTTP/1.1`。不同 curl 版本和服务器配置下输出格式可能不同，需以实际环境为准。

<br>

### 常见失败原因与解决办法

<br>

| 现象 | 可能原因 | 怎么办 |
|---|---|---|
| Protocol 列显示 `http/1.1` 而不是 `h2` | 服务器未启用 HTTP/2，或你访问的是明文 HTTP 而非 HTTPS | 换 `https://` 再试；HTTP/2 在现代浏览器中通常要求 TLS（h2c 是明文 TCP 上的 HTTP/2，普通网页很少用） |
| Timing 里没有 SSL 阶段 | 你访问的是 `http://example.com`，没有 TLS | 改用 `https://` |
| curl 输出没有 `ALPN` 行 | curl 版本较旧，或编译时未启用 HTTP/2 支持 | 升级 curl；或直接用 DevTools 的 Protocol 列作为主要观察手段 |

<br>

### 关于“HTTP/3”的边界说明

<br>

如果你在 Protocol 列看到 `h3`，说明浏览器和服务器协商使用了基于 QUIC 的 HTTP/3。QUIC 是跑在 UDP 上的新传输层，HTTP/3 依赖它。

HTTP/3 的**发现**和**协商**要分开看：

1. **发现**：客户端通常通过 HTTP/2 响应头 `Alt-Svc`（或 HTTPS DNS 记录）得知服务器支持 h3。
2. **协商**：客户端随后尝试向 `Alt-Svc` 指示的主机和端口发起 QUIC 连接；在这条 QUIC 连接的 TLS 握手中，客户端通过 ALPN 提供 `h3`，服务器选择 `h3`，才完成 HTTP/3 的协议确认。

所以更准确的说法是：`Alt-Svc` 是发现手段，真正的协议确认发生在 QUIC 的 TLS 握手里，而不是在已有 HTTP/2 连接内部“升级”。第 1 篇不需要展开 QUIC 内部机制，只需要知道：**Protocol 列可能出现的值不止 h2 和 http/1.1，h3 代表更下一代的传输方式，但开发者在这一层看到的仍然是“HTTP 请求”。** 具体版本行为以当前主流实现为准，需查证。

## 开发启示

***

### 启示一：日志里只记“总耗时”，等于什么都没记

<br>

**现象**：接口偶尔超时，你把超时从 1s 调到 3s，好了几天，又超了。你无法解释为什么。

**底层原因**：一次 HTTPS 请求的端到端耗时由多个阶段叠加：DNS 解析、TCP 建连、TLS 握手、请求排队/连接复用、服务器处理、响应传输。**不同阶段的故障模式完全不同**。DNS 慢通常是解析器或网络问题；TCP 建连慢可能是网络不可达或防火墙丢包；TLS 握手慢可能是证书链问题或服务器 CPU 吃紧；TTFB 慢才是“服务器处理慢”的强信号。

**可操作动作 / 面试答法**：在客户端（或网关）日志中，**至少记录 HTTP 状态码、协议版本（h2/http1.1）、总耗时，以及如果条件允许的话，把连接建立耗时和 TLS 耗时分开**。面试时如果被问“接口超时怎么排查”，先说“分层看”，再举 DevTools Timing 或 curl 的 `time_appconnect` / `time_connect` 作为落地手段。**不要一上来就说“加机器”或“调超时”。**

<br>

### 启示二：面试说“一次请求一次响应”，会被追问到底

<br>

**现象**：面试官问“一次 HTTP 请求发生了什么”，你回答“客户端发请求，服务器回响应，2 次交互”。

**底层原因**：在应用层语义上，你说得没错。但面试官追问的是**端到端实际发生了什么**。一次 HTTPS 请求，如果没有复用连接，底层至少有 TCP 三次握手、TLS 握手、HTTP 请求、HTTP 响应，以及连接关闭时的四次挥手。TLS 1.3 的首次完整握手通常约 1 RTT；在会话复用场景下可以进一步做到 0-RTT。TLS 1.2 的首次完整握手通常约 2 RTT，具体受实现和会话复用影响。如果连接被复用，后续请求才可能接近“2 次交互”。**把“HTTP 语义”和“网络报文交互”混为一谈，是这道题最常见的失分点**。

**面试答法**：先分层回答——“从 HTTP 语义看是请求 + 响应；从运输层看，首次请求还要叠加 TCP 握手和 TLS 握手；但现代浏览器会复用连接，所以第二个请求可能真的只有 HTTP 层面的往返。” 这样既展示了应用层理解，又展示了对下层机制的 awareness，还给后续章节（TCP、TLS）留了接口。

<br>

### 启示三：排障第一步不是看代码，是看“请求卡在哪一段”

<br>

**现象**：页面加载慢，你打开自己的业务代码，一行一行读，没发现明显问题。

**底层原因**：业务代码只负责“服务器收到请求之后”的逻辑。如果请求在 **Stalled/Queueing**（浏览器排队）或 **DNS Lookup** 或 **Initial connection** 阶段就慢了，你的业务代码根本还没开始执行。**端到端排障的第一步是定位阶段，而不是读业务逻辑。**

**可操作动作 / 面试答法**：先用 DevTools Network 的 Timing 或 curl 的分阶段耗时判断“卡在哪一段”，再决定去看 DNS、连接、TLS 还是服务端日志。面试时可以说：“我会先看是建连慢、握手慢还是 TTFB 慢，因为这三类问题的排查路径完全不同。” 这比泛泛说“看日志”更可信。

<br>

## 小结

***

回到开头的问题：**DNS 算不算“请求”？** 从 HTTP 语义看，DNS 不是 HTTP 请求；但从端到端看，DNS 解析是浏览器发出 HTTPS 请求之前的准备步骤，DevTools 的 Timing 里会以 DNS Lookup 出现。**TCP/TLS 握手算不算？** 它们不是 HTTP 请求，但首次 HTTPS 请求通常必须经过；如果连接被复用，后续请求可能没有新的 TCP/TLS 握手。**所以更准确的说法是：你看到的是“一次 HTTP 请求—响应”，底层可能是“DNS + TCP + TLS + HTTP”的组合，也可能因为复用而只剩 HTTP 往返。**

下一篇会讲 **IP、端口与 Socket：应用如何找到彼此**，把“客户端先开口”落到具体的地址和端口上，并用一个极简 TCP echo 实验让你看到 Socket 接口的样子。

自测问题：

**为什么说“一个网页加载”通常不是“一次 HTTP 请求”？**
<details>
<summary>[点击展开]</summary>  
因为一个网页加载通常包含一个 HTML 文档 + 若干子资源：CSS、JS、图片、字体、接口请求、favicon 等，每一项都可能是独立的 HTTP 请求；此外还可能有重定向、预检请求等。即使浏览器复用了同一条 TCP/TLS 连接，连接复用减少的是握手次数，不等于把多个资源合并成一次 HTTP 请求。所以“一个网页加载”在 Network 面板里通常是一组请求，而不是一次请求。
</details>

<br>

**如果 DevTools 里 Initial connection 很长、TTFB 很短，你优先怀疑哪一层？**
<details>
<summary>[点击展开]</summary>
优先怀疑连接建立阶段，也就是 TCP 握手 / TLS 协商这一段，而不是服务器业务处理。

理由：
Initial connection 很长，说明时间花在“把连接建起来”上；
TTFB 很短，说明请求发出去后，服务器很快返回了首字节，业务处理大概率不是瓶颈。

进一步区分：
如果 SSL 阶段单独也很长，优先怀疑 TLS 层：证书链、握手算法、服务器 CPU、网络 RTT 等；
如果 SSL 不长但 Initial connection 仍很长，优先怀疑 TCP/网络层：RTT 大、丢包、SYN 重试、防火墙或代理问题。

所以更准确的说法是：优先怀疑运输层/连接建立阶段（TCP 或 TLS），再结合 SSL 阶段和网络环境细分；不要一上来读业务代码或加机器。
</details>
