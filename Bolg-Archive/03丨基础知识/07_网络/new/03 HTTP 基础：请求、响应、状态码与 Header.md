## 场景问题

***
你写了一个后端接口 `POST /api/orders`，本地测试正常。上线后监控出现零星 `504`，前端同学问：“为什么有时候下单按钮转很久最后提示‘网络错误’，有时候又提示‘请求超时’？这俩是一回事吗？”

你打开 DevTools，看到失败请求状态码是 `504 Gateway Timeout`，但后端服务日志里没有这条请求的 ERROR 记录。你开始困惑：**504 到底是谁返回的？请求到底有没有到达我的服务？** 再进一步，如果前端要做“失败自动重试”，`POST /api/orders` 能不能无脑重试？

这两个问题——**状态码的语义边界**和**方法的幂等性**——都建立在对 HTTP 报文结构的准确理解上。本篇不讨论 TLS、缓存、Cookie，只做一件事：把 HTTP 请求和响应的“骨架”拆清楚，让你看到任何一条 DevTools 记录或 `curl` 输出时，能逐行读懂它在说什么。

<br>

<br>

## 核心概念

***
### 一条 HTTP 报文由哪几部分组成

HTTP（HyperText Transfer Protocol，超文本传输协议）报文无论请求还是响应，结构是同一个模板：**起始行 → 零个或多个首部字段（Header）→ 一个空行 → 可选的消息体（Body）**。

请求报文的起始行叫**请求行**，格式是：

```text
方法 SP 请求目标 SP HTTP版本 CRLF
```

例如 `GET /api/orders HTTP/1.1`。这里的 `SP` 是空格，`CRLF` 是回车换行（`\r\n`）。

响应报文的起始行叫**状态行**，格式是：

```text
HTTP版本 SP 状态码 SP 原因短语 CRLF
```

例如 `HTTP/1.1 200 OK` 或 `HTTP/1.1 504 Gateway Timeout`。

起始行之后是若干 Header，每行形如 `字段名: 字段值`。**Header 部分以一个“空行”结束**——即连续遇到 `CRLF CRLF` 时，头结束，后面是 Body。空行本身只有 `CRLF`，不允许有空格或其他字符。**如果空行缺失或格式不对，接收方会把 Body 的第一行误读为 Header，导致报文解析失败。**

<br>

### 方法不只是“动词”，还有语义承诺

HTTP 方法（Method）除了表达“要做什么”，还隐含三条语义属性：

- **安全（safe）** ：客户端请求不期望改变服务器状态。GET、HEAD、OPTIONS、TRACE 是安全的。
- **幂等（idempotent）** ：同一个请求执行一次和执行多次，对服务器状态的**最终效果相同**。GET、HEAD、PUT、DELETE、OPTIONS 是幂等的；POST 和 PATCH **不保证**幂等。
- **可缓存（cacheable）** ：响应可以被缓存。GET、HEAD 是可缓存的；POST 只在响应显式带新鲜度信息和 `Content-Location` 时才可能被缓存。

“幂等”是开发中比“GET 取数据、POST 提交数据”更重要的概念。幂等的方法，客户端和中间层可以**安全地自动重试**；非幂等的方法，自动重试可能造成重复下单、重复扣款。

<br>

### 状态码的第一位数字决定“谁该负责”

状态码是三位数，第一位数字划分类别：

- 2xx：成功。典型代表 `200 OK`、`201 Created`、`204 No Content`。
- 3xx：重定向。典型代表 `301`、`302`；`304` 与缓存相关，本篇不展开。
- 4xx：**客户端错误**。典型代表 `400`、`401`、`403`、`404`、`408`、`429`。
- 5xx：**服务器错误**。典型代表 `500`、`502`、`503`、`504`。

4xx 和 5xx 的分界线是排障起点：**4xx 通常意味着请求本身有问题（格式、认证、权限、资源不存在、限流），5xx 意味着请求已经到达某个服务器，但服务器或其上游处理失败**。

但状态码的“归属”有一个容易忽略的细节：**5xx 不一定是你的业务代码返回的。** 反向代理（proxy，代理服务器）、网关（gateway）或负载均衡器可以在请求根本没有到达后端服务的情况下，自己构造 `502` 或 `504` 返回给客户端。这正是开头场景的核心：**504 出现而后端无日志，说明请求大概率卡在代理层与上游之间，而不是你的控制器里。** 具体是代理返回还是业务返回，取决于部署结构，需结合代理日志查证。

<br>

### Header：连接控制与内容描述

本阶段只需要盯住几个“骨架级” Header：

- `Host`：HTTP/1.1 要求请求必须携带 `Host`，用来在同一个 IP 上区分不同的虚拟主机。没有 `Host`，服务器不知道你要访问哪个站点。
- `Content-Type`：描述 Body 的媒体类型，例如 `application/json`、`application/x-www-form-urlencoded`、`text/html; charset=utf-8`。
- `Content-Length`：Body 的字节长度。接收方依赖它判断 Body 何时结束；如果 Body 被压缩（`Content-Encoding: gzip`），它通常是压缩后的字节数，具体以实现为准。
- `Connection`：控制连接是否复用。HTTP/1.1 默认持久连接（`keep-alive`）；`Connection: close` 表示本次交换后关闭 TCP 连接。

**`Content-Length` 的值是字节数，不是字符数。** 一个包含中文的 UTF-8 JSON Body，字符数 10 时 `Content-Length` 可能是 30 左右。自己实现客户端或解析器时，按字节处理，不要按字符串长度处理。

<br>

### 一条请求-响应的关键时序（HTTP/1.1，面试可复述）

```text
客户端                                  服务器/代理
  | 建立 TCP 连接（本篇不展开）              |
  |---- 请求行（方法 目标 版本） ----------->|
  |---- Header... ------------------------>|
  |---- 空行 CRLF ------------------------->|
  |---- Body（如有） ---------------------->|
  |                                       | 读到空行，Header 结束
  |                                       | 处理请求
  |<--- 状态行（版本 状态码 原因短语） -------|
  |<--- Header... -------------------------|
  |<--- 空行 CRLF --------------------------|
  |<--- Body（如有） -----------------------|
  | 根据 Connection 关闭或复用连接            |
```

代理超时的时序可以这样复述：客户端把请求发给代理，代理再转发给上游；代理等待上游响应超过自身超时时间后，**由代理构造 `504` 返回给客户端**，此时上游可能还没收到请求，也可能已经收到但还没处理完。**所以“504 + 业务无日志”并不矛盾，它恰好提示你先查代理与上游之间的链路和耗时。**

<br>

## 动手实验

***
### 实验目标

用 `curl` 亲手构造请求，看到完整的请求报文和响应报文，并验证两件事：**空行是 Header 的结束标志**；**4xx 和 5xx 的响应体可能来自不同的“责任方”**。实验以 HTTP/1.1 为主，`example.com` 的实际状态码和 Header 可能随环境变化，但报文结构一致；`curl` 以当前稳定版为准，输出细节可能略有差异。

<br>

### 环境与工具

- `curl`：当前稳定版即可，macOS/Linux 自带或通过包管理器安装。
- 目标域名统一使用 `example.com`，不依赖你自己的服务。
- 如果 `example.com` 在你的网络环境下返回 `301` 或 `403`，不影响观察起始行、Header 和空行结构。

<br>

### 步骤一：用 `curl -v` 看到请求和响应的完整骨架

```bash
curl -v http://example.com/ 2>&1
```

`-v` 把 `>` 开头的行标为**客户端发出的请求**，`<` 开头的行标为**服务器返回的响应**。预期输出片段如下，结构一致，状态码和 Header 可能不同：

> ````text
> > GET / HTTP/1.1
> > Host: example.com
> > User-Agent: curl/8.x.x
> > Accept: */*
> >
> < HTTP/1.1 200 OK
> < Content-Type: text/html; charset=UTF-8
> < Content-Length: 1256
> < Connection: close
> <
> <!doctype html>
> <html>
> ...
> ````

**看到什么说明什么**：

- `> GET / HTTP/1.1` 是**请求行**。`/` 是请求目标，host 由 `Host` 头携带。
- `> Host: example.com` 是 HTTP/1.1 的**必填 Header**。去掉它，很多服务器会返回 `400 Bad Request`。
- `>` 单独一行、后面没有内容——这就是**Header 结束的空行**。它之后如果还有内容，就是 Body。
- `< HTTP/1.1 200 OK` 是**状态行**。
- `<` 单独一行是响应 Header 的结束，之后是响应 Body。
- `Connection: close` 说明本次交换后连接关闭；如果换成 `keep-alive` 或该头不出现，HTTP/1.1 默认倾向复用连接。

**常见失败原因**：

1. **`curl: (6) Could not resolve host`**：DNS 解析失败，与 HTTP 无关。先用 `dig example.com` 确认解析，或换一个能上网的环境。
2. **`curl: (7) Failed to connect`**：TCP 连不上。若用 `http://` 访问只监听 443 的站点，改用 `https://`；本地服务则确认端口和监听地址。
3. **看不到 `>` 和 `<` 调试行**：`-v` 的调试信息走 stderr，只重定向 stdout 会丢失。用 `2>&1` 合并。

<br>

### 步骤二：用 `curl -i` 和 `curl -I` 观察响应头与 Body 的边界

```bash
curl -i http://example.com/
```

`-i` 把**响应 Header 和 Body 一起打印**，适合快速观察状态行和 Header，又不想被连接过程信息干扰。预期开头类似：

> ````text
> HTTP/1.1 200 OK
> Content-Type: text/html; charset=UTF-8
> Content-Length: 1256
> Connection: close
>
> <!doctype html>
> ...
> ````

如果只想看 Header、不要 Body，用 `-I`（大写 i），它发送的是 `HEAD` 请求：

```bash
curl -I http://example.com/
```

> ````text
> HTTP/1.1 200 OK
> Content-Type: text/html; charset=UTF-8
> Content-Length: 1256
> ````

**看到什么说明什么**：`-I` 的响应只有 Header 没有 Body。这验证了 `HEAD` 方法的语义——与 `GET` 相同的响应头，但**不返回消息体**。如果你自己写 HTTP 客户端，收到 `HEAD` 响应却按 `Content-Length` 读取 Body，就会一直阻塞等待永远不会到来的字节。

**常见失败原因**：

1. 把 `-I` 写成 `-i`，结果多出 Body，误以为 `HEAD` 返回了 Body。
2. 看到 `Content-Length` 非零就以为 `HEAD` 一定会带 Body；**`HEAD` 的 `Content-Length` 描述的是对应 `GET` 可能返回的长度，不是本次响应的 Body 长度**，这是常见误解。

<br>

### 步骤三：制造一个 4xx，观察“错误也是结构化响应”

```bash
curl -i http://example.com/this-path-does-not-exist-12345
```

`example.com` 对不存在的路径通常返回 `404 Not Found`；若你的环境返回其他 4xx，观察结构即可。预期片段：

> ````text
> HTTP/1.1 404 Not Found
> Content-Type: text/html
> Content-Length: 345
>
> <!doctype html>
> <html>
> <head><title>404 Not Found</title></head>
> ...
> ````

**看到什么说明什么**：**4xx 也是完整的 HTTP 响应，同样有状态行、Header 和 Body。** 不要以为“出错就没有响应体”。很多客户端框架在状态码非 2xx 时直接抛异常、丢弃 Body，导致你丢失服务端在 4xx Body 里返回的具体错误信息。好的客户端应当**先把响应体读完，再做状态码分支判断**。

**常见失败原因**：

1. 客户端只判断状态码、不读 Body，导致看不到服务端返回的 `{"code":"ORDER_AMOUNT_INVALID"}` 之类信息。
2. 把 4xx 当成“网络错误”。4xx 是服务器明确返回的响应，说明 HTTP 交换已经完成；网络错误通常表现为连接失败、超时、连接重置，连状态码都没有。

<br>

### 步骤四：验证“空行是 Header 结束标志”

```bash
curl --trace-ascii - http://example.com/ 2>&1 | head -40
```

预期输出中会出现类似片段：

> ````text
> => Send header, 78 bytes (0x4e)
> 0000: GET / HTTP/1.1
> ...
> 0036: Host: example.com
> 0049:
> <= Recv header, 17 bytes (0x11)
> 0000: HTTP/1.1 200 OK
> ...
> <= Recv header, 2 bytes (0x2)
> 0000:
> ````

**看到什么说明什么**：`0049:` 后面为空的那一行，以及 `<= Recv header` 中 `0000:` 后面为空的那一行，就是 `CRLF` 空行。**空行之后，Header 阶段结束。** 这正是 HTTP/1.1 报文解析的核心边界规则。如果你自己实现一个极简 HTTP 解析器，就必须在遇到连续 `\r\n\r\n` 时停止读取 Header，剩余字节才进入 Body 处理逻辑。

**常见失败原因**：

1. `--trace-ascii` 输出量大，`head` 可能截断关键部分；把输出重定向到文件后搜索空行位置更可靠。
2. 把 `--trace-ascii` 的十六进制偏移量当成报文内容；偏移量只是行号，空行看冒号后是否为空。
3. 在 HTTP/2 环境下观察不到同样的文本报文边界，因为 HTTP/2 是二进制分帧；本篇实验以 HTTP/1.1 为准，HTTP/2 行为需查证。

<br>

## 开发启示

***
### 启示一：拿到 5xx 先问“这个状态码是谁返回的”，不要直接翻业务代码

**现象**：接口偶发 `502 Bad Gateway` 或 `504 Gateway Timeout`，业务服务日志里没有任何对应请求的错误记录。

**底层原因**：`502` 和 `504` 的语义本身就指向**代理/网关与上游服务器之间的失败**。Nginx、API 网关、负载均衡器在“连接上游失败”或“等待上游响应超时”时，会自己构造 `502`/`504` 返回给客户端，请求可能根本没有到达你的进程。业务代码没有日志，恰恰符合这个语义。

**可操作动作 / 面试答法**：

- 排障第一步不是搜业务日志，而是**看代理层日志**（如 Nginx 的 `error.log`、网关 access log），确认上游地址、连接耗时、上游返回码。
- 如果代理日志显示 `upstream timed out`，问题在上游处理太慢或网络不通，而不是业务逻辑抛了异常。
- 面试被问“502 和 504 的区别”，答：**502 是网关从上游收到了无效响应或连接失败；504 是网关等待上游响应超时，上游没有在时限内返回响应。** 两者都可能是代理层直接返回的，不一定来自业务进程。

<br>

### 启示二：给非幂等方法做自动重试，必须加“去重键”

**现象**：前端或网关对 `POST /api/orders` 做了“失败自动重试 3 次”，结果用户被扣了两次款。

**底层原因**：`POST` **不是幂等方法**。同一个 POST 执行两次，可能创建两条订单、扣两次款。网络层的“超时”不代表请求没有到达服务端——服务端可能已经处理成功，只是响应在返回路上丢了。自动重试等于让服务端再处理一次。

**可操作动作 / 面试答法**：

- **只对幂等方法做无脑自动重试**：GET、HEAD、PUT、DELETE 可在合理条件下重试；DELETE 重试后返回码可能从 200 变成 404，业务要能接受。
- 非幂等接口如果需要重试，由客户端生成一个**幂等键**（Idempotency-Key），服务端在键相同的情况下返回第一次的结果，而不是重复执行副作用。
- 面试被问“POST 能不能重试”，不要答“不能”，答：**POST 本身不保证幂等，直接重试有重复副作用风险；如果业务需要可重试的写操作，应通过幂等键或服务端去重把接口在业务层做成幂等的，而不是在网络层盲目重试。**

<br>

### 面试追问陷阱：GET 和 POST 的区别，你说对了吗？

一个高频但容易踩坑的面试题是“GET 和 POST 有什么区别”。很多资料会列出一堆“区别”，但其中不少是**浏览器行为**或**历史实现**，不是 HTTP 协议本身的强制规定。正确的回答思路要区分三个层次：

1. **协议语义层**：GET 是安全且幂等的，语义是“获取资源表示”；POST 不安全、不幂等，语义是“让服务器处理请求体中的表示”。
2. **报文层**：GET 的参数通常放在请求目标里，POST 的数据通常放在 Body 里；但协议并没有禁止 GET 带 Body 或 POST 带查询参数，具体实现支持程度需查证。
3. **实现层**：浏览器地址栏、缓存、日志、长度限制等行为，是浏览器或服务器实现约束，不是“HTTP 规定 POST 一定比 GET 安全”。

**面试答法**：先说语义，再说报文，最后说实现差异；不要一上来就说“GET 不安全、POST 安全”。**GET 参数出现在 URL 里更容易被日志和浏览器历史记录，但安全性取决于是否使用 HTTPS 以及服务端是否做了权限控制，方法本身不提供加密。**

## 小结与下一篇预告

***
开头两个问题现在可以闭环回答：**`504` 很可能是代理/网关在等待上游超时后自己返回的，业务日志没有记录并不奇怪；请求可能到了代理但没到业务，也可能到了业务但没在代理时限内完成，需要查代理日志和上游耗时。** `POST /api/orders` **不能无脑自动重试**，因为 POST 不保证幂等，超时不代表服务端没处理；要重试就加幂等键或服务端去重。

下一篇讲 Cookie、Session 与缓存：登录态和性能从哪来，我们会继续用 DevTools 观察 Cookie 和缓存命中。

自测问题：

1）`HEAD` 响应的 `Content-Length` 非零，是否意味着有 Body？

<details>
<summary>点击查看问题 1 答案</summary>

**不意味着有 Body。**

- **HEAD 响应按 HTTP 语义不应包含消息体**。服务器返回的 `Content-Length` 描述的是“如果对同一资源发 GET，响应表示会有多大”，而不是 HEAD 响应本身携带了多少字节。
- 因此，`HEAD` 响应里看到 `Content-Length: 12345` 是正常的，**它只是元数据，不代表后面跟着 12345 字节 Body**。
- 实践判断：**看请求方法**。如果是 `HEAD`，不要按 `Content-Length` 去读 Body；客户端/抓包工具也不应期待 Body。若确实收到 Body，属于实现不规范，不能作为协议语义依据。

</details>

<br>

2）为什么 `504` 出现时业务日志可能完全没有记录？
<details>
<summary>点击查看问题 2 答案：为什么 504 出现时业务日志可能完全没有记录？</summary>

**因为 504 通常由网关/代理/负载均衡生成，而不是业务应用生成。**

常见原因：

1. **请求根本没到业务应用**：网关到上游的 TCP 建连超时、DNS 解析失败、TLS 握手超时、连接池排队超时，业务进程没有收到请求，自然没有日志。
2. **网关先超时，业务还在处理**：网关等待上游响应超过自身超时时间，直接返回 `504 Gateway Timeout`；业务应用可能稍后才处理完，日志时间晚于 504，甚至因为异常路径没有记录。
3. **上游无响应或半开连接**：业务进程卡死、线程池耗尽、GC 停顿、下游依赖阻塞，网关等不到响应，但业务侧没有正常请求完成日志。
4. **日志层面遗漏**：日志级别、采样、异步刷盘延迟、请求未进入业务框架的访问日志，都可能让业务日志“看起来完全没有记录”。

**排查方向**：先确认 504 是**谁生成的**（网关访问日志、上游连接日志、超时配置），再看请求是否到达业务应用（接入层日志、连接数、线程池），最后才查业务日志。**504 不等于业务代码返回了 504**。

</details>
