## 场景问题

上周同事发了个版本，改了一个 `app.js` 里的按钮逻辑。部署上线后，测试同学说“按钮还是旧的，是不是没发成功？”同事本地 `curl` 了一下，服务端返回的确实是新文件。但测试同学的浏览器打开 DevTools，Network 里 `app.js` 那一行的 Size 列显示 `(memory cache)`，状态码 200，时间 0 ms——**请求根本没到服务器，浏览器直接用了本地缓存的旧副本**。

另一个常见困惑是登录：用户明明已经登录了，换个标签页或者过一会儿再操作，接口却返回 401，提示“请重新登录”。打开 Network 看请求头，`Cookie` 字段在有些请求里有、有些请求里没有。

这两个问题的底层是同一类机制：**HTTP 本身是无状态的，但浏览器在替你做“记忆”**。缓存记的是“资源要不要重新拿”，Cookie 记的是“你是谁”。这一篇把这两条线拆开，并且落到开发里怎么设、怎么查。

<br>

## 核心概念

***

### 缓存解决的是“别重复拿”，不是“永远不拿”

浏览器第一次请求一个资源，服务器可以返回一个或多个缓存相关的响应头，告诉浏览器：**这个东西多久之内可以不用再问我，直接用本地的**。

最核心的字段是 `Cache-Control`。`max-age=3600` 的意思是：从响应生成那一刻起 3600 秒内，这个响应对浏览器来说都是“新鲜的”（fresh），后续请求只要还在这个时间窗口里，浏览器可以不发请求，直接复用本地副本。这就是**强缓存**：浏览器“不联系服务器，自己做主”。

和 `max-age` 并列的还有两个容易踩坑的指令：

- `no-cache`：**可以存，但每次用之前必须问服务器**。它不等于“不缓存”。很多人把 `no-cache` 理解成“完全不存”，这是最常见的误解之一。
- `no-store`：**完全不存**，任何缓存都不应该保留这个响应的任何内容。

在 HTTP/1.0 时代还有一个 `Expires` 头，它给的是一个**绝对时间**，比如 `Expires: Wed, 21 Oct 2026 07:28:00 GMT`。问题在于服务器和客户端时钟不一致时，这个“绝对时间”会失真。**HTTP/1.1 的 `Cache-Control: max-age` 优先级更高**，因为它给的是相对秒数，不依赖时钟同步。

<br>

### 强缓存之外，还有“问一句再决定”：协商缓存

强缓存时间过了，浏览器不会直接重新下载，而是可以带上一个**验证标识**去问服务器：“我手上这个副本还能用吗？”服务器如果判断没变，返回 `304 Not Modified`，浏览器继续用本地副本；如果变了，返回 `200` 和新内容。这就是**协商缓存**：**请求发出去了，但响应体可以很小**。

协商缓存有两对控制头，通常是成对出现：

| 服务器首次响应 | 浏览器下次请求带上 | 服务器判断依据 |
|---|---|---|
| `Last-Modified` | `If-Modified-Since` | 资源最后修改时间 |
| `ETag` | `If-None-Match` | 资源的唯一标识（内容指纹） |

`ETag` 的精度通常高于 `Last-Modified`，因为文件内容变了但修改时间可能没变（比如同一秒内多次写入，或者构建工具保留了时间戳）。**当两者同时存在时，服务器通常优先用 `ETag` / `If-None-Match` 来判断**。

把强缓存和协商缓存放在一起，浏览器处理一个资源的决策顺序可以简化成：

```text
请求一个资源
  │
  ├─ 本地有缓存副本，且 Cache-Control: max-age 未过期？
  │     └─ 是 → 直接用本地副本（强缓存），不发请求
  │
  └─ 否（没有缓存，或已过期）
        ├─ 有 ETag / Last-Modified 可以用？
        │     ├─ 带上 If-None-Match / If-Modified-Since 发请求
        │     ├─ 304 → 用本地副本（协商缓存命中）
        │     └─ 200 → 用新响应，更新缓存
        └─ 没有验证标识 → 正常请求，拿新响应
```

**强缓存不发请求，协商缓存发请求但可能只回一个 304**。这是排障时区分两者的第一判据。

<br>

### Cookie：HTTP 无状态，所以浏览器替你带一张“便签”

HTTP 协议本身不记得“上一个请求是谁发的”。你登录了，下一个请求服务器凭什么知道是你？

答案不是 HTTP 协议本身记住了你，而是**浏览器在每次请求时自动附上一段键值对**，这段东西就是 Cookie。服务器在登录成功时通过响应头 `Set-Cookie` 把 `session_id=abc123` 交给浏览器，浏览器存下来；之后**同站**的每一个请求，浏览器都会自动在请求头里带上 `Cookie: session_id=abc123`。服务器拿到这个值，就能在服务端找到对应的会话数据。

Cookie 的几个关键属性直接关系到开发中的安全与排障：

- `HttpOnly`：**JavaScript 的 `document.cookie` 读不到这个 Cookie**。会话标识符一定要设 `HttpOnly`，否则一旦页面有 XSS，攻击者一行脚本就能把 session 偷走。
- `Secure`：**只在 HTTPS 请求中发送**。HTTP 明文连接下浏览器不会带上它，防止中间人直接嗅探。
- `SameSite`：控制**跨站请求时要不要带这个 Cookie**。`Strict` 最严格，`Lax` 是主流浏览器的默认折中值，`None` 必须同时配合 `Secure`。跨域登录态丢失，第一怀疑对象就是 `SameSite` 策略。
- `Path` / `Domain`：限定 Cookie 生效的路径和域名范围，**能收窄就收窄**，不要为了省事设成 `/` 或顶级域。

<br>

### Session 不是“另一个 Cookie”，它是服务端的一张表

把 Cookie 和 Session 对立起来记，容易产生一个误解：“Session 存在服务器上，所以和 Cookie 没关系”。实际上，**Session 的可用性依赖于一个“会话 ID”在客户端和服务端之间的往返**，而最常见的往返载体就是 Cookie。

服务端在登录成功后创建一条会话记录，可以理解成哈希表里的一行：`Key` 是服务器生成的唯一字符串（Session ID），`Value` 是这个用户在这个会话里的状态（用户 ID、权限、过期时间等）。服务器把 Session ID 通过 `Set-Cookie` 发给浏览器；之后浏览器每次请求自动带回这个 ID；服务器拿 ID 去表里查，查到就把对应用户的状态“恢复”出来。

所以更准确的表述是：**Cookie 是客户端侧的传输机制，Session 是服务端侧的存储机制，Session ID 是两者之间的桥**。Cookie 里可以不放 Session ID（比如放一个自包含的 Token），Session ID 也可以不走 Cookie 传递（比如放在 URL 里，但不推荐，容易泄漏）。它们经常一起用，但不是绑死的。

<br>

## 动手实验

***

### 实验一：用 curl 看缓存头的“优先级”和协商缓存全过程

**目标**：亲眼看到 `Cache-Control` 覆盖 `Expires`，以及 `ETag` 在第二次请求时如何产生 `304`。

**步骤**：对 `example.com` 发两次请求，第一次正常拿响应头，第二次模拟浏览器带上 `If-None-Match`。

```bash
# 第一次：看服务器返回了哪些缓存相关的头
curl -sI https://example.com/ | grep -Ei 'HTTP/|cache-control|expires|etag|last-modified'
```

预期输出大致如下（具体值以实际服务器为准，`ETag` 和日期会不同）：

> ```text
> HTTP/2 200
> last-modified: Thu, 17 Oct 2024 07:28:00 GMT
> etag: "abc123"
> cache-control: max-age=86000
> expires: Fri, 18 Oct 2024 07:28:00 GMT
> ```

**看到什么说明什么**：`cache-control: max-age=86000` 和 `expires` 同时存在。浏览器会**优先采用 `max-age`**，因为它是相对秒数，不受客户端时钟影响。`ETag` 和 `Last-Modified` 同时存在，说明服务器为协商缓存准备了两个验证通道。

**第二次**，手动模拟浏览器的协商行为：

```bash
curl -sI -H 'If-None-Match: "abc123"' https://example.com/
```

如果 `ETag` 仍然匹配，预期看到：

> ```text
> HTTP/2 304
> ```

**看到 304 说明什么**：服务器没有返回响应体，只告诉你“你手上的副本还是对的”。**协商缓存命中时，网络传输的是验证信息，不是资源本身**。如果返回 200，说明 `ETag` 不匹配或服务器不支持该验证方式。

**常见失败原因**：

1. **`curl -I` 默认发 `HEAD` 请求**，某些服务器对 `HEAD` 和 `GET` 的缓存头处理不一致。如果要精确模拟 `GET` 的响应头，用 `curl -s -D - -o /dev/null <url>`。
2. **`ETag` 值带引号，必须原样回传**。`If-None-Match: abc123` 和 `If-None-Match: "abc123"` 在严格实现下可能不同。
3. **中间代理或 CDN 改写了缓存头**。如果 `curl` 拿到的 `Cache-Control` 和你本地代码里写的不一样，先确认请求有没有经过网关。

<br>

### 实验二：DevTools 里区分“强缓存命中”和“协商缓存命中”

**目标**：在真实浏览器里看到 `(memory cache)`、`(disk cache)` 和 `304` 的差别。

**步骤**：

1. 打开 Chrome DevTools → Network 面板，确认 **Disable cache 不要勾选**。
2. 访问一个页面，在 Network 列表中找到任意一个 `.js` 或 `.css` 资源，记下它的 `Cache-Control: max-age` 值。
3. 在不关闭标签页的情况下，**再次刷新页面**（普通 F5，不是 Ctrl+F5）。
4. 观察 Size 列和 Status 列。

预期现象会落入下面三类之一：

> ```text
> - Size 显示 (memory cache) 或 (disk cache)，Status 显示 200 → 强缓存命中，请求根本没有出浏览器。
> - Status 显示 304，Size 很小 → 协商缓存命中，请求到了服务器，服务器只回了验证结果。
> - Size 显示具体大小（如 45.2 KB）→ 未命中缓存，完整响应从网络传输。
> ```

**`memory cache` 和 `disk cache` 的区别**：内存缓存是临时的，关闭标签页后释放；磁盘缓存是持久的。浏览器读缓存的顺序通常先内存后磁盘。**但两者都属于强缓存命中，都没有向服务器发请求**。

**常见失败原因**：

1. **DevTools 的 “Disable cache” 勾选了**。这个选项会让浏览器绕过所有缓存，看到的一切都是 200 和新响应。
2. **普通刷新（F5）和强制刷新（Ctrl+F5 / Cmd+Shift+R）行为不同**。普通刷新会复用缓存，强制刷新会带上 `Cache-Control: no-cache` 绕过强缓存和协商缓存。排查“缓存到底有没有生效”时，先确认自己用的是哪种刷新。
3. **HTML 页面本身通常不应该设长强缓存**。如果你把 HTML 也设了 `max-age=31536000`，用户可能永远看不到新版本，因为浏览器连“去问服务器 HTML 变没变”这一步都省了。

<br>

### 实验三：DevTools 看 Cookie 是否被带上

**目标**：确认一个请求的 `Cookie` 请求头里有没有你期望的会话标识。

**步骤**：

1. 在 DevTools 中进入 **Application → Cookies**，查看当前域名下有哪些 Cookie，记录某个 Cookie 的 `HttpOnly`、`Secure`、`SameSite`、`Path` 列。
2. 切换到 Network 面板，点击任意一个同站接口请求，查看 **Request Headers** 中的 `Cookie` 字段。
3. 再找一个跨站请求（如果有的话），对比它的 `Cookie` 字段。

**看到什么说明什么**：

- 如果 `Cookie` 请求头里没有你在 Application 面板看到的那个 Cookie，检查它的 `Path` 是否覆盖了当前请求路径、`Domain` 是否匹配、`SameSite` 是否阻止了跨站携带。
- 如果 Application 面板里 `HttpOnly` 列显示 ✓，而在 Console 里执行 `document.cookie` 看不到这个 Cookie，**这是正常的，说明 `HttpOnly` 生效了**，不是 bug。

**常见失败原因**：

1. **`Secure` Cookie 在 HTTP 页面下不会发送**。本地开发用 `http://localhost` 时，如果后端给 Cookie 设了 `Secure`，浏览器可能不保存或不回传。本地调试需要单独配置。
2. **`SameSite=Strict` 下，从外部链接跳转进来的第一个请求不带 Cookie**。这不是登录失效，是设计行为。如果产品要求“从邮件链接点进来仍然保持登录”，通常需要 `Lax` 而不是 `Strict`。

## 开发启示

***

### 启示一：静态资源用“长强缓存 + 文件名版本号”，HTML 和接口走“协商或不缓存”

**现象**：发版后用户看到的还是旧 JS/CSS，但服务端文件确实是新的。

**底层原因**：静态资源的 `Cache-Control: max-age` 设得太长，而文件名没有随内容变化。浏览器在有效期内直接复用强缓存，**请求没有到达服务器**，所以服务端日志里看不到这次请求，误以为“用户没刷新”。

**可操作动作**：构建时为静态资源文件名加上内容哈希，比如 `app.a1b2c3.js`。内容变，文件名就变，浏览器会把它当成一个全新的 URL 去请求，旧缓存自然失效。带 hash 的静态资源可以放心设 `Cache-Control: public, max-age=31536000, immutable`。**HTML 页面不要设长强缓存**，用 `Cache-Control: no-cache`（可以存，但每次协商验证）或者更保守的短 `max-age`，保证部署后用户至少会“问一句”服务器。接口响应如果不希望被缓存，用 `Cache-Control: no-store`；如果希望允许缓存但必须验证，用 `no-cache`，不要混用。

**面试答法**：“`no-cache` 不是不缓存，是缓存但每次使用前必须重新验证；`no-store` 才是完全不存储。静态资源靠文件名 hash 做缓存失效，而不是靠把 `max-age` 设成 0。”

<br>

### 启示二：登录 Cookie 三件套 `HttpOnly` + `Secure` + `SameSite`，一个都不能少

**现象**：本地或测试环境登录正常，上线后偶发登录态丢失；或者安全扫描报告指出会话 Cookie 缺少安全属性。

**底层原因**：会话标识符如果可以被 JavaScript 读取，XSS 就能直接偷走；如果在 HTTP 明文连接中传输，中间人可以嗅探；如果跨站请求无条件携带，CSRF 风险会放大。

**可操作动作**：后端 `Set-Cookie` 时显式设置 `HttpOnly; Secure; SameSite=Lax`（或按业务需要 `Strict`）。**`SameSite=None` 只在确实需要跨站携带且全站 HTTPS 时使用**，并且必须同时带 `Secure`。登录态 Cookie 的 `Path` 尽量收窄到实际需要的路径，不要无脑 `/`。

**面试答法**：“`HttpOnly` 防的是 XSS 读 Cookie，不防 CSRF；`SameSite` 才是直接限制跨站携带的。三个属性各自防不同的面，所以通常一起上，但不要把 `HttpOnly` 当成 CSRF 的解法。”

<br>

### 启示三：排障时先看“请求有没有到服务器”，再看“到了之后为什么没被认出来”

**现象**：用户反馈“页面不对”或“登录失效”，开发第一反应是查服务端日志，但日志里可能根本没有那条请求。

**底层原因**：强缓存命中时浏览器根本不发请求；`SameSite` 或 `Secure` 限制下，Cookie 可能没有被附加上去。这两类问题的现场都在客户端，不在服务端。

**可操作动作**：拿到用户反馈后，先让用户打开 DevTools Network，看目标请求的 **Status / Size / Request Headers 中的 Cookie**。如果 Size 是 `(disk cache)` 或 `(memory cache)`，问题在缓存策略；如果请求发出去了但 Cookie 字段为空或缺少会话键，问题在 Cookie 属性或跨站策略。**服务端日志只能回答“请求到了之后发生了什么”，回答不了“请求为什么没来”**。

**面试答法**：“强缓存和 Cookie 未携带这两种情况，服务端是无感知的。排查登录态问题，第一步是在浏览器侧确认请求头里有没有会话标识，而不是直接翻服务端日志。”

<br>

### 初学者常见误解：`no-cache` = 不缓存

**错误理解**：“`Cache-Control: no-cache` 就是告诉浏览器不要缓存。”

**正确回答思路**：`no-cache` 的字面意思容易误导，但它实际的含义是 **“可以存储，但每次重用之前必须去源服务器验证”**。真正“完全不存”的是 `no-store`。区分方法很简单：看一个资源在 DevTools 里第二次请求的状态码——如果出现 `304`，说明它被存下来了，只是被重新验证了；如果连 `304` 都没有、每次都是完整 `200`，才可能是 `no-store` 或没有缓存能力。

<br>

## 小结与下一篇预告

这一篇把浏览器替 HTTP 补上的两件事拆开了：**缓存**让浏览器在“资源还新鲜”时不去打扰服务器，**Cookie** 让无状态的 HTTP 在多次请求之间还能认出同一个人。强缓存看 `max-age`，协商缓存看 `ETag` / `Last-Modified` 和 `304`；Cookie 看 `Set-Cookie` 的属性，Session 是服务端那张用 Session ID 索引的表。

下一篇进入应用层的另一个基础协议：**DNS**——你输入 `example.com` 之后，浏览器到底向谁问了路，递归和迭代分别发生在哪一步，以及为什么有时候“域名解析慢”比“接口慢”更难排查。

**自测问题**：

1. 一个资源响应同时有 `Cache-Control: max-age=600` 和 `Expires: Mon, 01 Jan 2024 00:00:00 GMT`（一个已经过去的时间），浏览器会怎么处理？为什么？
<details>
<summary>[点击展开]</summary>
浏览器会用 max-age=600，忽略已经过去的 Expires，在 600 秒内直接走强缓存，不发请求。
原因：Cache-Control 是 HTTP/1.1 的缓存控制头，优先级高于 HTTP/1.0 的 Expires；而且 max-age 是相对秒数，不依赖客户端和服务端的时钟是否一致。Expires 虽然已经过期，但被更高优先级的 max-age 覆盖了。
</details>

<br>


2. 登录接口返回了 `Set-Cookie: sid=abc; HttpOnly; Secure; SameSite=Strict`。用户从一封邮件里的链接点击进入站点，第一个请求的 `Cookie` 头里会带上 `sid` 吗？为什么？
<details>
<summary>[点击展开]</summary>
第一个请求不会带上 sid；后续同站请求会带上。
原因：SameSite=Strict 表示跨站来源的请求不携带该 Cookie。从邮件链接点进来，对站点来说属于跨站跳转，所以第一个请求不带 Cookie；进入站点后，同站内发起的请求会正常携带 sid。补充一句：Secure 要求走 HTTPS，如果邮件链接是 http://，Secure Cookie 本来也不会发送。
</details>
