## 场景问题：浏览器能打开，curl 却报证书错误
***
你负责的一个内部服务要调用外部 API `https://api.example.com`。本地用浏览器访问页面，地址栏有小锁，一切正常；但同一个 URL 放到后端代码里，用 curl 或 HTTP 客户端一跑，直接挂掉：

```text
curl: (60) SSL certificate problem: unable to get local issuer certificate
```

第一反应通常是“证书有问题”，但浏览器明明没报错。于是开始怀疑 curl 太严格、代码配置不对、环境有问题，甚至想加 `-k` 一了百了。这个困惑的本质不是“证书坏了”，而是**证书链的信任建立方式和不同客户端的信任库不同**。这篇会先把 TLS 握手中“谁信谁、凭什么信”讲清楚，再用 `openssl s_client` 和 `openssl verify` 把这条链拆开看，最后回到这个场景给出可操作的排查顺序。

<br>



## 核心概念：握手是在“验身份”和“商量密钥”
***
TLS（Transport Layer Security）的目标可以压缩成两件事：**客户端确认服务端真的是它声称的那个域名**，以及**双方在不安全的信道上商量出一把只有彼此知道的对称密钥**。对称加密用来加密后续 HTTP 数据，非对称机制用来安全地完成“确认身份”和“商量密钥”这两步。开发者不需要会推导密码学，但需要知道握手阶段在做什么、失败时卡在哪一步。

<br>

### 证书链：根证书在客户端，不在服务器

服务端证书（也叫叶证书，Leaf Certificate）不是凭空被信任的。它由中间 CA（Intermediate CA）签名，中间 CA 由根 CA（Root CA）签名，形成一条**信任链**：

```text
服务器证书（叶） ← 中间证书 ← 根证书
```

关键直觉是：**根证书由客户端操作系统或浏览器内置，服务器不需要也不应该发送根证书**。服务器在握手时发送的是“叶证书 + 中间证书”，客户端拿自己信任库里的根证书去“接上”这条链。

链的顺序不能乱：**叶证书必须在最前面，后面跟着直接签发它的中间证书**，逐级向上。顺序错了或者中间证书漏了，部分客户端就会报 `unable to get local issuer certificate`。

<br>

### TLS 1.2 与 1.3：差的是往返次数

TLS 1.2 的完整握手（简化到核心）大致是：

```text
ClientHello
    →
ServerHello + Certificate + ServerKeyExchange + ServerHelloDone
    ←
ClientKeyExchange + ChangeCipherSpec + Finished
    →
ChangeCipherSpec + Finished
    ←
```

客户端需要先等服务端把证书和密钥交换参数发完，才能算出预主密钥并发回去，所以 TLS 自身通常需要 **2 个 RTT**（Round-Trip Time，往返时间）。

TLS 1.3 的关键改动是把密钥交换参数提前塞进 `ClientHello`。客户端一上来就带上自己的 key share，服务端收到后立刻能算出共享密钥，于是 `ServerHello`、证书、`Finished` 可以连续发出，客户端回一个 `Finished` 就结束，**TLS 握手只要 1 个 RTT**。被砍掉的还包括 RSA 密钥交换（没有前向保密）、静态 DH 套件、CBC 模式、压缩和重协商。

面试里常说的“TLS 1.3 更快”，在低延迟链路上差距可能不明显，但在跨国、高延迟场景下，1 个 RTT 的差距就是几十毫秒。**TLS 1.3 只是把握手往返减少了，证书链验证、域名匹配、过期检查仍然是客户端要做的事**，配错了照样被中间人攻击。

<br>

### 客户端验证证书时到底在查什么

客户端拿到服务端发来的链之后，至少会检查这几件事：

1. **链是否能接到信任根**：用本地信任库里的根证书去验证链的签名关系。
2. **叶证书是否过期**：当前时间是否在 `notBefore` 和 `notAfter` 之间。
3. **域名是否匹配**：访问的域名是否在证书的 SAN（Subject Alternative Name）列表里。
4. **用途是否匹配**：证书是否允许用于服务器身份认证（EKU）。

这四项里任何一项失败，客户端都会拒绝连接。浏览器报错通常会给具体错误码，例如证书过期在 Chromium 系浏览器里是 `NET::ERR_CERT_DATE_INVALID`；而 curl 和 OpenSSL 的命令行错误信息粒度不同，往往只告诉你“链接不上”，需要手动往下挖。

<br>

### 为什么浏览器行、curl 不行：信任库不是同一个

这是场景问题的直接答案。**浏览器和命令行工具使用的根证书信任库很可能不是同一套**。浏览器可能内置了自己的根证书集合，或者在遇到缺少中间证书时有一定的补全能力；而 curl 在 Linux 上通常走 OpenSSL 或 GnuTLS，读取的是系统信任库（例如 `/etc/ssl/certs`）。如果系统信任库缺少某个根证书，或者服务端没有发送中间证书，浏览器可能正常，curl 却报 `unable to get local issuer certificate`。

另一种常见情况是**服务端证书链本身不完整**：只配置了叶证书，忘了把中间证书拼进去。浏览器有时候能从自己的缓存或 CA 的 AIA（Authority Information Access）扩展里把中间证书补回来，命令行工具不一定有这个行为。**浏览器成功不代表证书链在“所有客户端”视角下都是完整的**。

<br>

### 常见误解：加 `-k` 不是“修复”，是关掉验证

`curl -k` 或 `--insecure` 会让客户端跳过证书验证。它能让命令跑通，但**并没有修复链、过期或域名匹配问题**，只是把身份验证关掉了。生产代码里用 `-k` 或把 HTTP 客户端的 `verify=False` 当作长期方案，等于主动放弃了对中间人攻击的防御。**可以临时用于定位问题，但不能作为解决方案提交。**

<br>



## 动手实验：用 openssl 把证书链和握手拆开看
***
实验目标：观察服务端实际发出的证书链是否完整，并手动验证“叶证书 + 中间证书”能否接到一个根证书上。示例域名统一用 `example.com`，具体证书内容以实际连接结果为准。

<br>

### 步骤一：查看服务端发出了哪些证书

```bash
openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null 2>/dev/null
```

`-servername` 在 SNI（Server Name Indication）场景下必须带上，否则服务端可能返回默认站点证书，而不是目标域名的证书。`-showcerts` 会打印服务端发送的整条链。

> 输出中会出现 `Certificate chain` 段落，并依次列出若干 `s:` 和 `i:` 行。`s:` 是 Subject，`i:` 是 Issuer。**正常情况下第一张是叶证书，第二张是中间证书**；如果只看到一张证书，说明服务端没有发送中间证书，链不完整。

<br>

### 步骤二：只看验证结果和证书有效期

```bash
echo | openssl s_client -servername example.com -connect example.com:443 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
```

> 如果输出里 `notAfter` 已经早于当前时间，说明证书过期；如果 `subjectAltName` 里没有你访问的域名，说明域名不匹配。链不完整时，这一步仍然可能输出证书信息，因为 `s_client` 默认不会因为验证失败而中断输出。

<br>

### 步骤三：手动验证链（关键实验）

先分别保存叶证书和中间证书。最直接的方式是从步骤一的 `-showcerts` 输出中把 `-----BEGIN CERTIFICATE-----` 到 `-----END CERTIFICATE-----` 的块按顺序提取出来：

```bash
# 假设 leaf.pem 是叶证书，intermediate.pem 是中间证书
# 验证：叶证书 + 中间证书，能否被某个根证书“接上”
openssl verify -CAfile /path/to/root.pem -untrusted intermediate.pem leaf.pem
```

如果你手头有系统信任库的根证书包，也可以直接把 `-CAfile` 指向它来做“当前系统视角下是否可验证”的检查。但更干净的做法是先从服务端链中识别出根证书对应的 CA，再单独取该根证书来验证，这样可以排除“系统信任库版本差异”的干扰。

> 成功时输出类似：`leaf.pem: OK`。失败时会出现 `error 20 at 0 depth lookup: unable to get local issuer certificate`，**说明验证器没有找到能签发叶证书（或链中某张证书）的受信任根证书**。这正是场景问题中 curl 报错的底层原因。

<br>

### 步骤四：如果验证失败，缩小范围

先确认服务端到底发了几张证书：

```bash
openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null 2>/dev/null \
  | grep -c "BEGIN CERTIFICATE"
```

> 如果只输出 `1`，说明服务端只发了叶证书，**中间证书缺失**。如果输出 `2` 或更多，但 `openssl verify` 仍然失败，问题更可能出在客户端信任库：验证时用的 `-CAfile` 里没有对应根证书，或者根证书本身过期/缺失。

<br>

### 常见失败原因与处理

1. **服务端只配了叶证书，没拼中间证书**：Nginx 的 `ssl_certificate` 应指向 `fullchain.pem`（叶证书 + 中间证书），而不是单独的 `cert.pem`。修改配置后需要 reload 服务，只替换文件不 reload 不会生效。
2. **`-CAfile` 指向的根证书不对**：验证时用的根证书必须是对应 CA 的根证书，不能随便拿一张自签证书或别的 CA 的根来替代。
3. **客户端信任库过旧或容器基础镜像缺少 CA 包**：精简容器或老旧系统可能没有更新 `ca-certificates`，导致根证书缺失。这不是服务端证书的问题，但同样会触发 `unable to get local issuer certificate`。

<br>

### 可选：观察 TLS 1.3 的协议版本和套件

```bash
openssl s_client -connect example.com:443 -servername example.com -tls1_3 -brief </dev/null
```

> `-brief` 会输出协商到的协议版本和套件。如果连接成功且显示 `TLSv1.3`，说明服务端支持 1.3；如果失败，可能是服务端未启用 1.3，或中间设备不支持。这一步用来区分“证书验证失败”和“协议/套件协商失败”，避免把两类问题混在一起。

<br>



## 开发启示
***

<br>

### 启示一：`unable to get local issuer certificate` 不等于“证书过期”

**现象**：curl 或 HTTP 客户端报 `unable to get local issuer certificate`，但浏览器打开正常。

**底层原因**：这个错误码的语义是“验证器无法把服务端发来的证书链接到一个受信任的根证书上”。常见原因有两个方向：服务端没有发送中间证书，或者客户端信任库缺少对应根证书。浏览器和命令行工具使用不同的信任库和补全策略，所以会出现“一边行一边不行”。

**可操作动作**：先用 `openssl s_client -showcerts` 数一下服务端发了几张证书。只有一张，优先查服务端 `fullchain` 配置；有两张以上，再用 `openssl verify -CAfile <根证书> -untrusted <中间证书> <叶证书>` 在客户端侧复现，确认是链的问题还是信任库的问题。**不要用 `-k` 或 `verify=False` 作为修复提交**。

**面试答法**：先区分“链不完整”和“信任库不匹配”，再指出浏览器和 curl 的信任库不是同一套，最后给出排查命令的顺序。

<br>

### 启示二：TLS 1.3 的快是“少一次往返”，不是“跳过验证”

**现象**：面试或技术讨论里经常听到“上 TLS 1.3 就快了”，但实际项目里换到 1.3 后延迟改善不明显，或者仍然出现证书错误。

**底层原因**：TLS 1.3 把 TLS 握手从 2-RTT 降到 1-RTT，省掉的是密钥交换参数和证书分两趟走的时间。但在低延迟内网里，1 个 RTT 的差距可能只有几毫秒；**证书链验证、域名匹配、过期检查在 1.3 里仍然由客户端执行**，不会因为协议版本升级而消失。

**可操作动作**：如果要评估 TLS 1.3 的收益，先看客户端到服务端的 RTT，而不是只看协议版本。高延迟链路（跨地域、移动网络）收益更明显；同机房短连接场景不要预期有数量级变化。**证书问题仍然按证书链的路径排查，不要因为“已经 TLS 1.3”就跳过 `openssl` 验证**。

<br>

### 启示三：服务端配置证书时，先问“客户端拿什么根来验”

**现象**：更新证书后，自己的机器和浏览器都正常，但部分用户或后端服务开始报证书错误。

**底层原因**：不同客户端信任的根 CA 集合不同。如果你的证书链依赖一个较新的根证书，而某些客户端（老系统、精简容器、特定语言运行时）的信任库还没有更新，它们就无法完成链验证。反过来，服务端如果漏配中间证书，浏览器可能靠补全机制掩盖问题，命令行工具则直接暴露。

**可操作动作**：部署或续签证书后，至少用两个“视角”验证：浏览器 + 一个命令行工具（`openssl s_client` 或 `curl`）。命令行工具的错误更接近后端代码实际会看到的行为。**容器化部署时，检查基础镜像是否包含更新到当前时间的 `ca-certificates`**，不要假设系统信任库永远完整。

<br>

### 常见误解与面试追问陷阱

**误解**：“浏览器能打开，说明证书配置没问题。”  
**正确理解**：浏览器成功只能说明“在这个浏览器的信任库和补全策略下能通过”，不能推出“服务端发出的链对所有客户端都完整”。后端服务、移动端 WebView、老旧系统、精简容器使用的信任库和验证行为可能不同。**证书链的正确性要在目标客户端的视角下验证**，而不是用浏览器代替全部。

<br>

### 场景问题的闭环回答

回到开头：浏览器能打开 `https://api.example.com`，curl 报 `unable to get local issuer certificate`。最可能的情况是**服务端没有发送中间证书，或者 curl 所在环境的根证书信任库与服务端链不匹配**。排查顺序不是“换客户端”，而是：先用 `openssl s_client -showcerts` 看服务端发了几张证书；如果只有叶证书，修服务端 `fullchain`；如果链看起来完整但 `verify` 仍失败，用 `openssl verify` 指定正确的根证书在客户端侧复现，再决定是补信任库还是换根证书。**`-k` 只用于临时定位，不是修复。**

<br>

## 小结与下一篇预告
***
TLS 握手是在“验身份”和“商量密钥”；证书链的信任根在客户端，服务端负责把“叶证书 + 中间证书”按顺序发完整；TLS 1.3 把握手从 2-RTT 压到 1-RTT，但证书验证一步都没少。**浏览器能打开不等于链对所有人都完整**，排查证书问题要先分清“服务端发链”和“客户端信任库”两个方向。

**自测问题**：
1. 服务端在 TLS 握手中应该发送根证书吗？为什么？
2. TLS 1.3 的 1-RTT 握手省掉的是哪部分往返？证书验证是否也因此被简化？

<details>
<summary>点击查看答案</summary>

1. **不应该。** 根证书由客户端操作系统或浏览器内置在信任库中。服务端只需要发送叶证书和中间证书，让客户端用本地根证书去“接上”这条链。服务端发送根证书不仅不增加信任，反而说明对信任模型的理解有偏差。
2. **省掉的是 TLS 1.2 中“等服务端发完证书和密钥交换参数，客户端才能算出预主密钥并发回”的那趟往返**，把密钥交换参数提前到 `ClientHello` 里，使 TLS 握手从 2-RTT 变为 1-RTT。**证书验证没有被简化**：链验证、域名匹配、过期检查仍然由客户端执行，配错了照样失败。

</details>
