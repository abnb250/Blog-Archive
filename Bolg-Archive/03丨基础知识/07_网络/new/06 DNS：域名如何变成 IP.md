## 场景问题

***

你负责的一个 Java 服务要连 MySQL。运维把数据库域名 `db.example.com` 从旧 IP 切到了新 IP，控制台显示“解析已生效”。你在浏览器里打开 `http://db.example.com` 一切正常，但你的 Java 服务重启后**依然连旧 IP**，日志里没有任何 DNS 报错。

你怀疑 DNS 没生效，运维让你 `dig` 一下，`dig db.example.com` 明明返回了新 IP。**命令行 `dig` 是新的，Java 服务却还拿着旧的，问题到底在哪？**

更隐蔽的版本：新服务上线，域名记录晚了 45 秒才创建。运维补上记录后，浏览器很快恢复，但一批后台客户端**持续报“域名不存在”好几分钟**，即使权威 DNS 已经返回正确地址。

这两个场景指向同一件事：**“域名变成 IP”不是一个瞬时动作，而是一条带有缓存的分布式查询链。** 你看到的 `dig` 结果，只是这条链上某一个节点的视角。

<br>

<br>

## 核心概念

***

### DNS 不是“一台服务器”，而是一套分工协作的查询系统

<br>

**DNS（Domain Name System，域名系统）** 的核心工作是把人类可读的域名翻译成机器可路由的 IP 地址。但这个翻译不是由某一台“总机”完成的。

当你 `dig example.com`，你的机器通常先问**递归解析器（recursive resolver）**——可能是你的 ISP 提供的，也可能是 `8.8.8.8` 或 `1.1.1.1`。递归解析器对客户端承诺：“你只需要问我，**最终答案由我负责**”。如果它自己没有缓存，它会代替你向根服务器、顶级域服务器、权威服务器逐级追问，直到拿到答案。

**递归（recursive）** 是“把活全包了”：客户端发出请求后等待最终结果，中间过程由递归解析器完成。**迭代（iterative）** 是“指路不代劳”：被问的服务器只返回“你下一个该去问谁”，让请求方自己继续追。**开发者日常接触的客户端查询几乎都是递归**；迭代发生在递归解析器与权威服务器之间，是 `dig +trace` 想让你看到的东西。

<br>

### hosts 文件：本地静态映射，优先级高于 DNS

<br>

操作系统在做名称解析时，**不是直接去问 DNS**。它会先查 **hosts 文件**——一个本地的纯文本映射表。如果 hosts 里有匹配条目，系统**直接使用该 IP，不发起任何 DNS 查询**。

hosts 文件的位置固定：Windows 是 `C:\Windows\System32\drivers\etc\hosts`，macOS / Linux 是 `/etc/hosts`。格式是“**IP 地址 + 域名**”，例如：

```text
127.0.0.1 test.local
```

这意味着一个开发中极容易被忽视的事实：**如果你在 hosts 里把某个域名指向了某个 IP，`dig` 可能仍然返回 DNS 上的记录，但你的程序实际连接时走的是 hosts 里的 IP。** `dig` 只查 DNS，它不读 hosts。排查“DNS 看起来对但程序行为不对”时，hosts 是第一个要排除的变量。

<br>

### 常见记录类型：A、CNAME、MX、TXT

<br>

DNS 记录有类型之分，不同类型回答不同问题。开发者最常撞上的几类：

**A 记录** 把域名指向一个 IPv4 地址。**AAAA 记录** 同理，指向 IPv6。**CNAME 记录** 是别名：`www.example.com` 可以 CNAME 到 `example.com`，或者 CNAME 到某个 CDN 厂商的域名。**CNAME 可以形成链**——`a` CNAME 到 `b`，`b` CNAME 到 `c`，最终由 `c` 的 A 记录给出 IP。**`dig` 的 ANSWER SECTION 可能会把整条链和最终 A 记录一起返回**，也可能需要你逐层追。

**MX 记录** 指定邮件服务器。**TXT 记录** 存放文本信息，常用于域名所有权验证和邮件安全配置（如 SPF）。第 6 篇的重心是“域名到 IP”，A/AAAA 和 CNAME 是主线；MX 和 TXT 知道“它们回答的是别的问题”即可。

<br>

### TTL：改完 DNS 为什么“还没生效”

<br>

每条 DNS 记录带有一个 **TTL（Time To Live，生存时间）**，单位是秒。它告诉缓存该记录的一方：“你可以把这个答案保留多久”。

修改权威 DNS 上的记录是**即时生效**的，但**全球各级缓存持有的旧记录会继续存活到各自 TTL 过期**。所以“改完 DNS”存在两个时间线：权威端已经变了，缓存端还没变。TTL 设得越长，旧答案在缓存里活得越久。你 `dig` 到的可能是缓存里的旧值，也可能是权威端的新值，取决于 `dig` 走的是哪条路径、有没有命中缓存。

<br>

### 负缓存：为什么“记录不存在”也会被记住

<br>

DNS 不只缓存“成功找到 IP”的结果，也会缓存**否定结果**。如果某次查询返回了 **NXDOMAIN（域名不存在）** ，递归解析器可以把这个“不存在”的结论缓存一段时间，这就是 **负缓存（negative caching）** 。在这段时间内，即使权威 DNS 已经补上了记录，解析器仍可能直接返回“不存在”，而**不再去问权威**。恢复延迟可能从几十秒到几分钟不等，具体时长取决于响应中的 SOA 记录和解析器实现，**不能假设固定秒数**。

**这解释了开头第二个场景**：记录晚创建 45 秒，负缓存已经把“不存在”记住了；权威端后来有了，但缓存还没过期。

<br>

### 应用层缓存：DNS 之外还有“第二层 TTL”

<br>

即使 DNS 层面已经正确，你的**编程语言运行时或数据库驱动**可能还有自己的 DNS 缓存。

以 Java 为例，JVM 对成功解析和失败解析都有缓存，由 `networkaddress.cache.ttl` 和 `networkaddress.cache.negative.ttl` 控制。**如果 `networkaddress.cache.ttl` 被设为 `-1`，成功结果会被永久缓存**，DNS 改了，进程不重启就不会重新解析。以当前主流 JDK 实现为准，默认值在不同版本和部署环境下可能不同，**具体值需查证**，但“永久缓存”这个行为一旦启用，就是排障时必须检查的开关。

MySQL 也有自己的主机缓存（host cache）。MySQL 服务端可能缓存客户端主机名与 IP 的映射；在反向 DNS 慢的环境里，这个缓存甚至会影响连接建立。应用侧如果走 JDBC，连接参数和 MySQL 的 `skip_name_resolve` 设置也会改变 DNS 在连接路径上的参与程度。

**结论：排查“DNS 改了没生效”时，至少要问三层——hosts、DNS 缓存（含负缓存）、应用运行时缓存。** `dig` 只覆盖第二层的一部分。

<br>

<br>

## 动手实验：用 `dig +trace` 看迭代，用 hosts 看优先级

***

### 实验一：`dig +trace` 观察迭代查询路径

<br>

**目标**：亲眼看到递归解析器代替你，从根服务器开始逐级追问的过程。

```bash
dig +trace example.com
```

> **预期输出片段（示意，以当前根/顶级域/权威服务器实际地址为准）：**
>
> ```text
> .                       518400  IN  NS  a.root-servers.net.
> ...
> com.                    172800  IN  NS  a.gtld-servers.net.
> ...
> example.com.            172800  IN  NS  a.iana-servers.net.
> ...
> example.com.            86400   IN  A   93.184.216.34
> ```

**看到什么说明什么**：`+trace` 让 `dig` 自己执行**迭代**，而不是把“递归”交给本地解析器一次性完成。输出中每一段 NS 记录代表一层转介（referral）：根服务器说“`.com` 去找这些服务器”，`.com` 服务器说“`example.com` 去找这些权威服务器”，最后权威服务器给出 A 记录。**如果中间某一层超时或返回 SERVFAIL，故障点就暴露在那一层**，而不是笼统的“DNS 坏了”。

常见失败原因：某些网络环境或解析器配置可能使 `+trace` 输出不完整或被拦截；`+trace` 走的是迭代路径，**不反映你日常程序实际使用的递归缓存**，所以它适合“看机制”，不适合直接替代排查客户端解析结果。

<br>

### 实验二：修改 hosts，观察“DNS 还在，但程序走 hosts”

<br>

**目标**：验证 hosts 优先级高于 DNS，并理解 `dig` 和实际连接可能不一致。

**步骤（Linux / macOS）**：

```bash
# 备份（如果需要）
sudo cp /etc/hosts /etc/hosts.bak

# 添加一条映射（示例使用不会冲突的测试域名）
echo "127.0.0.1 example.com" | sudo tee -a /etc/hosts
```

然后分别执行：

```bash
dig example.com A +short
curl -v -o /dev/null http://example.com 2>&1 | head -5
```

> **预期现象**：
>
> - `dig` 仍然返回 DNS 上的真实 A 记录（`93.184.216.34` 或类似），**因为它不读 hosts**。
> - `curl` 的 `Connected to example.com (127.0.0.1)` 表明实际连接走的是 hosts 里的 `127.0.0.1`。

**看到这个现象说明什么**：**hosts 在解析链中优先于 DNS**。`dig` 的结果只代表“DNS 世界认为是什么”，不代表“你的程序实际连了什么”。排查“解析结果对但连接行为不对”时，先 `grep` 一下 hosts。

**清理**：实验结束后删除对应行，或还原备份。

<br>

### 实验三：用 `dig` 看 CNAME 链

<br>

**目标**：理解一个域名可能经过多跳别名才落到 IP，以及 `dig` 如何呈现这条链。

```bash
dig www.example.com A
```

如果 `www.example.com` 配置了 CNAME，ANSWER SECTION 可能类似：

> ```text
> www.example.com.        300  IN  CNAME  example.com.
> example.com.            300  IN  A      93.184.216.34
> ```

**看到什么说明什么**：**CNAME 不直接给 IP，它给的是“下一个该解析的域名”**。最终 IP 来自链尾的 A 记录。如果只看到 CNAME 而没有 A 记录，可能是解析器没有把链追完，也可能是 CNAME 指向的目标本身不存在——这时候要接着 `dig` CNAME 的目标域名。

<br>

### 常见失败原因与解决办法

<br>

| 现象 | 可能原因 | 怎么办 |
|---|---|---|
| `dig` 返回 `NXDOMAIN` | 域名不存在、记录未创建，或命中了负缓存 | 用 `dig @8.8.8.8 example.com` 绕开本地递归缓存，对比结果；如果公共 DNS 有而本地没有，怀疑负缓存或本地解析器 |
| `dig` 正常但程序连不上 / 连旧 IP | hosts 文件、Java DNS 缓存、MySQL 主机缓存、连接池长连接未重新解析 | 先查 hosts；再查运行时缓存配置；长连接场景需要重启或显式刷新 |
| `dig +trace` 中途超时 | 网络拦截、权威服务器不可达，或环境不支持完整迭代 | 换网络环境重试；用 `dig @公共DNS` 先确认递归路径是否正常 |
| 改完 DNS 后部分客户端仍用旧 IP | TTL 未过期，各级缓存仍在服务旧记录 | 在变更前提前调低 TTL，等待旧 TTL 过期后再切换，而不是改完才降 TTL |

<br>

## 开发启示

***

### 启示一：`dig` 对，程序不对——先怀疑 hosts 和运行时缓存

<br>

**现象**：`dig db.example.com` 返回新 IP，Java 服务重启后仍连旧 IP，日志无报错。

**底层原因**：`dig` 只走 DNS 查询，**不经过 hosts，也不经过 JVM 的 DNS 缓存**。程序实际解析域名时，可能先命中 hosts；如果 hosts 没有，才进入 JVM 缓存；如果 JVM 缓存持有旧值且未过期（或 `networkaddress.cache.ttl=-1` 永久缓存），就不会再向 DNS 发起查询。MySQL 连接池中的长连接甚至可能根本没有重新解析的机会。

**可操作动作 / 面试答法**：排查顺序固定为 **hosts → JVM 缓存配置 → 连接池/长连接状态**。Java 服务检查 `networkaddress.cache.ttl` 和 `networkaddress.cache.negative.ttl`（以当前 JDK 实际生效值为准，默认值需查证）；数据库连接场景再确认 MySQL 的 `skip_name_resolve` 是否关闭了反向解析。面试时不要只说“DNS 有缓存”，要能区分 **DNS 递归缓存、操作系统缓存、应用运行时缓存**三层，并给出各层的检查手段。

<br>

### 启示二：DNS 变更不是“瞬时开关”，发布顺序比 TTL 更可控

<br>

**现象**：新服务上线，权威 DNS 刚补上记录，部分后台客户端持续报“域名不存在”，几分钟后才恢复。

**底层原因**：客户端之前已经查到了 NXDOMAIN，递归解析器把这个**负响应**缓存了下来。权威端恢复后，负缓存未过期之前，解析器可能**根本不去问权威**，继续返回“不存在”。负缓存时长受 SOA 和解析器策略影响，不能靠“等 TTL”精确预估。

**可操作动作 / 面试答法**：**先创建并验证 DNS 记录，再启动依赖它的客户端或切流**，不要反过来。如果变更涉及 IP 切换，提前把 TTL 调低，给缓存留出收敛窗口，而不是在切换瞬间才改。面试被问“DNS 改完多久生效”，正确答案不是“立即”或“等 TTL”，而是“**权威端立即，缓存端受 TTL 和负缓存影响，应用端还可能叠加运行时缓存**”。

<br>

### 启示三：面试陷阱——“DNS 用 UDP，所以不可靠”

<br>

**常见误解**：DNS 跑在 UDP 上，所以 DNS 查询“可能丢、不可靠”，因此程序需要自己处理 DNS 重试。

**正确思路**：DNS 的查询通常走 UDP，但**递归解析器和客户端协议栈本身已经包含了超时与重试机制**；UDP 不保证送达，不等于上层没有补偿。真正需要开发者关心的“不可靠”来源，往往不是单次 UDP 丢包，而是**缓存一致性**：TTL、负缓存、应用运行时缓存、连接池长连接——这些才会让“DNS 明明对了”和“程序行为不对”同时成立。面试时把话题从“UDP 可不可靠”引向“缓存分层与变更窗口”，是更成熟的答法。

<br>

<br>

## 小结与下一篇预告

***

回到开头：**“改了 DNS，为什么程序还连旧 IP？”** 因为 `dig` 看到的只是 DNS 查询路径上的一个快照；程序实际解析时，hosts、JVM 运行时缓存、数据库主机缓存、连接池长连接都可能把旧值留在原地。**DNS 解析不是一次查询，而是一条带缓存的链；排障要看“程序实际走了哪一层”，而不是只看 `dig` 的输出。**

下一篇进入应用层实时通信的选型：**WebSocket、SSE 与轮询：实时通信怎么选**。轮询、长轮询、SSE、WebSocket 各自解决什么问题、在什么场景下不该用，会把“连接该由谁维持、消息该往哪个方向推”这条线拉直。

自测问题：

1. 递归查询和迭代查询，分别由谁承担“追到底”的责任？`dig +trace` 模拟的是哪一种？
2. 权威 DNS 已经更新，客户端仍然解析到旧 IP，列出至少三层可能的原因。

<br>

<details>
<summary>点击查看自测问题答案</summary>

**第 1 题答案**

- **递归查询**：由**递归解析器（recursive resolver）**承担“追到底”的责任。客户端只发一次请求，然后等最终结果；中间向根、顶级域、权威服务器追问的过程由解析器代为完成。
- **迭代查询**：由**请求方自己**逐级追问。被问到的服务器只返回“下一步该去问谁”的转介（referral），不替你继续追。
- **`dig +trace` 模拟的是迭代查询**：它让 `dig` 自己从根服务器开始，一层层追问 NS 记录，直到拿到最终 A 记录。所以 `+trace` 看到的是“迭代路径”，而不是你日常程序使用的那条“递归缓存路径”。

**第 2 题答案**

权威 DNS 已更新、客户端仍拿到旧 IP，至少可以从下面三层里找原因（答出任意三层即可）：

1. **hosts 文件**：本地静态映射优先于 DNS；`dig` 不读 hosts，所以 `dig` 对但程序仍连旧 IP 时，先检查 `/etc/hosts` 或 Windows hosts。
2. **DNS 递归缓存 / 负缓存**：递归解析器持有的旧 A 记录未过 TTL，或之前缓存了 NXDOMAIN，在负缓存过期前不再向权威查询。
3. **应用运行时缓存**：如 JVM 的 `networkaddress.cache.ttl` / `networkaddress.cache.negative.ttl`；设为 `-1` 时成功结果永久缓存，DNS 改了进程不重启也不会重新解析。MySQL 还有自己的 host cache。
4. **连接池 / 长连接**：连接已经建立并保持，后续请求复用旧连接，根本不会触发重新解析域名。
5. **操作系统解析缓存**：部分系统有 nscd、systemd-resolved 等本地缓存层，行为随发行版和配置而异（具体需查证）。

</details>
