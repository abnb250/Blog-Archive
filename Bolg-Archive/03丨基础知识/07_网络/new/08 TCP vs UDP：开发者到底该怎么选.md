## 场景问题

***

你写了一个实时对战小游戏的服务端，用 TCP 传输玩家位置。办公室测试一切正常。上线后，有玩家反馈“偶尔卡一下，然后角色瞬移”。你抓包发现：某个位置包丢了，TCP 在等重传，**重传到达之前，后面所有已经到达的位置更新都被压在接收缓冲区里，一个都读不出来**。等重传到了，一堆积压的位置包在一瞬间被应用层读完，角色就从 A 点“瞬移”到了 D 点。

你开始怀疑：**是不是该换成 UDP？** 但换成 UDP 之后，你又发现位置包会丢，角色会“飘”。于是你在 UDP 之上自己加了序号和重传——**这不就是在重新发明 TCP 吗？**

这个困惑在面试里也很常见：**“TCP 可靠，UDP 不可靠，所以需要可靠就用 TCP，需要快就用 UDP。”** 这句话听起来对，但它解释不了两件事：为什么 HTTP/3 要把可靠传输**建立在 UDP 之上**？为什么在线游戏宁可丢包也不用 TCP？

这一篇要建立的选型直觉是：**TCP 和 UDP 不是“好协议 vs 坏协议”，而是两种不同的责任分配方式。** TCP 把可靠性、顺序、拥塞控制打包成默认服务，代价是你必须接受“等待丢失的数据”。UDP 把这些责任全部退回给应用层，代价是你得自己决定“等不等、等多久、丢不丢”。**选型的第一步不是问“哪个快”，而是问“我的应用能不能容忍一次丢包带来的延迟”。**

## 核心概念

***

### 一个比喻：挂号信 vs 明信片

<br>

GitHub 上一篇流传很广的笔记把这个区别压缩成一个很准的比喻：**TCP 是挂号信，UDP 是明信片**。

挂号信寄之前要确认对方在（**握手**），保证送达（**重传**），保证顺序（**按序交付**），对方签收（**ACK**）。可靠，但每一步都有手续。明信片直接丢进邮筒，不握手、不保证送达、不保证顺序、不确认。快、简单，但“尽力而为”。

这个比喻的关键不在于“哪个更好”，而在于**手续的成本落在谁身上**。TCP 的手续是协议栈替你办的，你写 `send()` 和 `recv()` 就行，但你必须接受“丢失的数据会让后面的数据一起等”。UDP 没有手续，协议栈只负责把数据报扔出去，**“接下来怎么办”变成了你的应用代码要回答的问题**。

<br>

### TCP 的“可靠”到底带来了什么代价

<br>

TCP 提供的是**面向连接的、可靠的、有序的字节流**。这三件事是捆绑在一起的：连接意味着握手和状态维护；可靠意味着丢包会重传；**有序意味着一个包丢了，后面已经到达的包也不能先交给应用层**——这就是队头阻塞在传输层的体现。

Decodo 的对比文章把这个机制写得比较清楚：TCP 用序号、确认、校验和、重传来处理丢失或损坏的数据，同时做流量控制和拥塞控制[reference:1]。对开发者来说，最需要内化的不是这些机制的细节（那是第 9–11 篇的事），而是它们组合起来的效果：**TCP 承诺“你读到的字节，和发送方写入的字节，完全一致且顺序相同”** 。这个承诺的代价是时间：丢失的数据要等重传，重传期间后面的数据被压住。

<br>

### UDP 的“不可靠”不是缺陷，是责任转移

<br>

UDP 是**无连接的、尽力而为的数据报协议**。它不建立连接，不保证送达，不保证顺序，不重传，不做拥塞控制[reference:2]。从功能清单上看，它比 TCP“少做很多事”。

但“少做”恰恰是它在某些场景下的价值。DNS 查询用 UDP，因为一次问答就结束，为它先握手不值得；实时音视频用 UDP，因为**晚到的帧没有价值**，宁可丢帧也不要让整个流卡住等重传；在线游戏用 UDP，因为位置更新是**持续覆盖**的，丢一个旧位置包，下一个新位置包到了就可以直接覆盖，等重传反而制造了“卡顿 + 瞬移”。

**UDP 把可靠性从“默认提供”变成了“按需自建”。** 你需要可靠，就在 UDP 之上自己做确认和重传；你不需要，就享受它不做任何多余事情带来的低延迟和简单性。

<br>

### 字节流 vs 数据报：一个在写代码时会直接撞上的差异

<br>

TCP 和 UDP 的差异不只是“可靠 vs 不可靠”，还有一个在 Socket 编程层面立刻能感受到的区别：**TCP 是字节流，UDP 是面向报文的**。

TCP 不保留应用层的消息边界。你调用两次 `send()`，接收端可能一次 `recv()` 把两段数据一起读出来，也可能分三次读到。**“粘包”不是 TCP 的 bug，是字节流模型的必然结果**——TCP 只保证字节的顺序和完整性，不告诉你“应用层的一条消息到哪里结束”。应用层必须自己定义边界：长度前缀、分隔符、或者固定长度。

UDP 则保留报文边界。发送方一次 `sendto()` 对应接收方一次 `recvfrom()` 拿到一个完整的数据报。UDP 的 `send()` 是**原子性的**：要么整个数据报发出去，要么报错，不会出现“发了一半”的情况。但 UDP 的报文边界也带来一个硬限制：**一个 UDP 数据报不能超过 65507 字节**（IPv4 下扣除头部后的理论上限，实际还受路径 MTU 影响，需查证）。超过这个大小，应用层必须自己分片。

<br>

### QUIC/HTTP/3 为什么“回到 UDP”

<br>

这是面试里最容易暴露理解深度的一个点。**HTTP/3 使用 UDP，不是因为 UDP 比 TCP“更快”，而是因为 TCP 的可靠传输是在内核里实现的，应用层无法改造它的队头阻塞行为。**

TCP 的队头阻塞是协议本身的设计：一个字节丢了，后面所有字节都不能交付，无论它们属于哪个 HTTP 请求。HTTP/2 的多路复用把多个请求放在一条 TCP 连接上，**TCP 层的一个丢包会卡住所有流**。QUIC 的做法是：**在 UDP 之上，在用户态重新实现一套可靠传输，但把“流”作为独立单元来管理**。一个流丢包只阻塞那个流，其他流照常交付[reference:6]。同时，QUIC 把传输层握手和 TLS 握手合并，首次连接 1 RTT，会话复用后可以 0 RTT[reference:7]。

**所以 QUIC 不是“UDP 替代了 TCP”，而是“在 UDP 之上重建了一个更可控的 TCP”。** UDP 在这里的角色是“最小干扰的底层通道”，让 QUIC 可以在用户态自由实现自己想要的可靠性和多路复用，而不受内核 TCP 实现和中间盒对 TCP 特殊处理的束缚。

<br>

## 动手实验：用 UDP echo 模拟丢包，对比 TCP 的“等待”行为

***

### 实验一：UDP echo 服务端 + 客户端，人为丢包

<br>

**目标**：亲眼看到 UDP 的“尽力而为”在应用层的表现——丢了一个包，客户端就是收不到回应，**没有重传，没有等待**。

下面是一个可以人为丢弃 30% 数据报的 UDP echo 服务端（Python，保存为 `udp_lossy_echo.py`）：

```python
import random
import socket

sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
sock.bind(("127.0.0.1", 9001))
print("UDP lossy echo server on 127.0.0.1:9001 (30% drop)")

while True:
    data, addr = sock.recvfrom(65535)
    if random.random() < 0.3:          # 30% 概率假装没收到
        print(f"DROP from {addr}: {data[:20]!r}")
        continue
    sock.sendto(data, addr)
```

客户端连续发送 10 条带序号的数据报，记录哪些收到了回应：

```python
import socket

sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
sock.settimeout(0.5)

for i in range(10):
    sock.sendto(f"msg-{i}".encode(), ("127.0.0.1", 9001))
    try:
        data, _ = sock.recvfrom(65535)
        print(f"seq {i}: echo = {data.decode()}")
    except socket.timeout:
        print(f"seq {i}: timeout (no echo)")
```

> **预期现象（示意，每次运行结果不同）：**
>
> ```text
> seq 0: echo = msg-0
> seq 1: timeout (no echo)
> seq 2: echo = msg-2
> seq 3: echo = msg-3
> seq 4: timeout (no echo)
> seq 5: echo = msg-5
> ...
> ```
>
> 服务端日志会显示 `DROP from ('127.0.0.1', ...)`。

**看到什么说明什么**：**UDP 不会因为丢了 `msg-1` 就阻塞 `msg-2` 的交付**。`msg-2` 照常到达并 echo 回来。丢失的数据报就是丢了，协议栈不会替你重传。**“丢包之后怎么办”完全取决于应用层有没有自己的超时、重试或容错逻辑。**

**常见失败原因**：如果服务端和客户端在同一台机器上，丢包完全由你写的 `random.random() < 0.3` 决定，不会受到真实网络丢包干扰，实验可复现。如果端口被占用，换一个端口即可。

<br>

### 实验二（对照直觉）：TCP 的“有序交付”意味着丢失会卡住后面

<br>

不需要真的制造网络丢包，只需要理解 TCP 的字节流语义，就能推理出这个行为。但如果你想亲眼看到“字节流没有消息边界”，可以写一个最小的 TCP 服务端，连续发送两段数据，客户端用一次 `recv` 读：

```python
# TCP server: 连续 send 两条“消息”，但没有边界
import socket
s = socket.socket()
s.bind(("127.0.0.1", 9002)); s.listen(1)
conn, _ = s.accept()
conn.sendall(b"hello")
conn.sendall(b"world")
conn.close()
```

客户端：

```python
import socket
c = socket.socket()
c.connect(("127.0.0.1", 9002))
print(repr(c.recv(1024)))
```

> **预期现象**：很可能输出 `b'helloworld'`，也可能分两次 `recv` 才读完。**但无论如何，TCP 没有告诉你“hello 和 world 是两条消息”**。

**看到这个现象说明什么**：**TCP 只保证字节的顺序和完整性，不保留应用层的消息边界**。如果你想在 TCP 上传输“一条一条的消息”，必须自己定义分帧规则（长度前缀或分隔符）。**这正是 TCP 和 UDP 在 API 手感上最直接的差异：UDP 的每一次 `recvfrom` 天然对应一个完整的数据报，TCP 的 `recv` 只是从字节流里取一段。**

<br>

### 常见失败原因与解决办法

<br>

| 现象 | 可能原因 | 怎么办 |
|---|---|---|
| UDP 客户端一直 timeout，服务端没有 `DROP` 日志 | 服务端没启动，或端口被防火墙拦截 | 先在本机 `127.0.0.1` 上验证，排除网络因素 |
| TCP 客户端 `recv` 返回 `b''` | 对端关闭了连接 | TCP 的 `recv` 返回空字节表示 EOF；UDP 没有“连接关闭”的概念，只有超时 |
| 想用 UDP 发超过 64KB 的数据 | 单个 UDP 数据报有大小上限 | 应用层自己分片，或改用 TCP/QUIC（需查证具体 MTU 路径限制） |

## 开发启示

***

### 启示一：选型先问“丢包能不能等”，不要先问“哪个快”

<br>

**现象**：实时对战游戏用 TCP，偶尔卡顿后角色瞬移；换成 UDP 后丢包导致角色“飘”，于是又在 UDP 上自己加重传，复杂度陡增。

**底层原因**：TCP 的“可靠”不是免费的，它的代价是**有序交付带来的等待**。丢失的数据必须重传，重传期间后面已经到达的数据被压住。对于**持续覆盖型**的数据（位置、视频帧），等待旧数据没有意义——新数据已经到了，旧数据晚到反而制造了“瞬移”。对于**累积型**的数据（文件、表单提交、API 响应），缺失就是缺失，必须等。

**可操作动作 / 面试答法**：选型时先问一个具体问题：**“如果这个包晚到 200ms，我的应用会更好还是更差？”** 晚到更好 → TCP（或者需要可靠有序的语义）。晚到更差 → UDP，丢包由应用层决定是忽略、覆盖还是选择性重传。面试时把“TCP 可靠、UDP 快”升级成“**TCP 用等待换确定性，UDP 用不确定性换时效性**”，再举游戏位置更新和文件传输作为两端例子。

<br>

### 启示二：UDP 的 `send()` 是“整条发出”，TCP 的 `send()` 只是“写进缓冲区”

<br>

**现象**：用 TCP 写了一个“一条消息一次 `send`”的协议，接收端偶尔把两条消息粘在一起读出来；换成 UDP 后，同样的代码却“一条是一条”了。

**底层原因**：**TCP 是字节流，`send()` 只是把字节写进内核发送缓冲区**，什么时候真正发出去、怎么分片，由 TCP 自己决定。接收端的 `recv()` 从字节流里读，不保留发送端的调用边界。**UDP 的 `sendto()` 是原子性的**：一个数据报要么完整发出，要么出错，接收端的 `recvfrom()` 一次拿到一个完整数据报。UDP 保留了“消息”这个概念，TCP 没有。

**可操作动作 / 面试答法**：在 TCP 上设计应用层协议时，**必须显式定义消息边界**（长度前缀或分隔符），不能假设“一次 `send` 对应一次 `recv`”。面试被问“TCP 粘包怎么办”，不要只说“加分隔符”，要先指出**粘包是字节流模型的正常现象，不是错误**，然后给出长度前缀/分隔符/固定长度三种方案，并说明选择取决于消息是否定长、是否包含分隔符本身。

<br>

### 启示三：面试陷阱——“UDP 不可靠，所以生产环境不能用”

<br>

**常见误解**：UDP 会丢包、乱序，所以只有“不重要的东西”才用 UDP；需要可靠性的场景一律用 TCP。

**正确思路**：**可靠性不是只有“TCP 提供”和“完全没有”两种状态。** 你可以在 UDP 之上按需构建**恰好够用的可靠性**：DNS 自己做超时重试；实时音视频接受丢帧但不接受卡顿；QUIC 在 UDP 上重建了可靠有序的流传输，同时避免了 TCP 的跨流队头阻塞。**“UDP 不可靠”描述的是协议栈默认不提供保证，不是描述你的应用不能自己提供保证。** 事实上，现代传输层演进的方向恰恰是“在 UDP 的简单性之上，由用户态实现可控的可靠性”。

**面试答法**：先说“UDP 把可靠性责任交给应用层”，再举 QUIC 作为“在 UDP 上构建可靠传输”的实例，最后补一句“所以选型不是 TCP 或 UDP 二选一，而是**问可靠性应该由协议栈默认提供，还是由应用层按场景定制**”。

<br>

## 小结与下一篇预告

***

回到开头：**实时对战该用 TCP 还是 UDP？** 如果位置更新是持续覆盖的，**TCP 的有序等待会让旧数据阻塞新数据，UDP 的“丢了就丢了、新包覆盖旧包”反而更符合实时性**。但 UDP 不是“什么都不用做”——你需要自己处理丢包的容错、必要时加序号丢弃过期数据，甚至按需实现轻量重传。**选型的核心不是背“TCP 可靠、UDP 快”，而是判断你的数据“晚到有没有价值”。**

下一篇进入 TCP 的连接生命周期：**三次握手与四次挥手：连接的一生**。你会用 Wireshark 抓一次完整的连接建立和关闭，看清 `SYN`、`SYN-ACK`、`ACK`、`FIN`、`TIME_WAIT` 这些状态在真实报文里长什么样，以及为什么 `TIME_WAIT` 过多会成为服务端的一个实际排障问题。

自测问题：

1. TCP 的“有序交付”在丢包时会导致什么后果？为什么这个后果对文件传输可以接受、对实时位置更新可能有害？
2. QUIC 为什么选择在 UDP 之上实现，而不是直接修改 TCP？UDP 在 QUIC 中扮演了什么角色？

<br>

<details>
<summary>点击查看自测问题答案</summary>

**第 1 题答案**

- **后果**：TCP 保证有序交付，一个字节丢了，**后面已经到达的字节也不能先交给应用层**，必须等丢失的数据重传到达。这就是传输层的队头阻塞。
- **文件传输可以接受**：文件是累积型数据，缺失的字节必须补上，晚一点到达不影响最终正确性。
- **实时位置更新可能有害**：位置是持续覆盖型数据。旧位置包丢失后，新位置包已经到了，如果等旧包重传，应用层读到的是“过期位置”，表现为卡顿；重传到达后积压数据被一次性读出，表现为瞬移。**丢旧包、直接使用新包，反而更符合实时语义。**

**第 2 题答案**

- **为什么不在 TCP 上改**：TCP 的可靠传输和有序交付是在**内核**里实现的，应用层无法改变它的队头阻塞行为。HTTP/2 的多路复用把多个流放在一条 TCP 连接上，TCP 层的一个丢包会阻塞所有流，这是协议设计本身的问题，应用层绕不开。
- **UDP 的角色**：UDP 在这里是**最小干扰的底层通道**。它不提供可靠性、顺序、拥塞控制，把所有这些责任交给上层的 QUIC 在**用户态**实现。QUIC 因此可以按“流”的粒度管理丢包和重传，一个流丢包不阻塞其他流，同时合并传输层和 TLS 握手来降低建连延迟。

</details>
