## 场景问题

***

你从一台云主机往另一台云主机传一个大文件，`scp` 显示的速度曲线像锯齿：冲到 80 MB/s，掉到 20 MB/s，再爬回 80 MB/s，再掉。带宽监控显示链路额定 1 Gbps，峰值利用率却只有 60% 左右。你问运维，运维说“网络没丢包，链路正常”。

你在自己机器上跑 `ss -ti`，看到某个连接的 `cwnd` 在几十到几百之间反复横跳，`ssthresh` 也跟着变。旁边还挂着 `rtt` 和 `retrans` 字段。**你能看到窗口在动，但说不清它在“涨”是在试探什么，“退”又是在回应什么。**

更常见的一个误判：**你看到 `cwnd` 很小，就认为“网络拥塞了”** ，开始调内核拥塞参数；但真正的瓶颈可能是接收端应用读取太慢，`rwnd` 才是那个卡住发送方的东西（第 10 篇的零窗口）。**流控和拥塞控制是两个方向相反的“刹车”，踩错了刹车，问题不会消失。**

这一篇要把“网速忽快忽慢”翻译成两个可以分开观察的变量：**接收窗口 `rwnd` 管“接收方还能收多少”** ，**拥塞窗口 `cwnd` 管“发送方认为网络还能承受多少”** 。发送方实际能发多少，取两者的**较小值**。然后你会用 `ss -ti` 直接看到 `cwnd`、`ssthresh`、`rtt`、`retrans` 这些字段，把第 10 篇的“重传和窗口”接到这一篇的“窗口为什么会变”上。

## 核心概念

***

### 一个水管，两个阀门：发送窗口 = min(rwnd, cwnd)

<br>

第 10 篇已经讲过**接收窗口 `rwnd`** ：接收方通过 ACK 里的 `Window Size` 字段告诉发送方“我的缓冲区还能收多少”。它是**流量控制**，防的是发送方压垮接收方。

**拥塞窗口 `cwnd`** 是发送方**自己维护**的变量：发送方在不确知网络剩余容量的情况下，用一个窗口值来“试探”当前能安全发多少数据。它是**拥塞控制**，防的是发送方压垮中间网络。

**发送方实际能发多少，取两者的较小值**：

```math
发送窗口 = min(rwnd, cwnd)
```

如果 `rwnd` 先见底，瓶颈在接收端；如果 `cwnd` 先见底，瓶颈在发送方对网络的判断。**`cwnd` 在 `ss -ti` 里可以直接看到，`rwnd` 需要从对端 ACK 的窗口字段推断。** 这两条排查路线完全不同，混在一起就会“调错参数”。

<br>

### 慢启动：从很小开始，每个 RTT 翻一倍

<br>

连接刚建立时，发送方不知道链路能承受多少。如果一上来就把 `rwnd` 允许的量全部发出去，中间路由器可能因为队列溢出而丢包。**慢启动（slow start）** 的做法是：**从一个较小的初始窗口开始，每收到一个 ACK 就把 `cwnd` 增加一个 MSS**，效果是**每个 RTT 窗口翻倍**。

RFC 2001 的描述很清晰：慢启动为发送方的 TCP 增加了一个拥塞窗口 `cwnd`，新连接建立时初始化为 1 个段，每收到一个 ACK 就加 1 个段；发送方最多能发 `min(cwnd, advertised window)`[reference:0]。现代 Linux 内核的初始窗口通常约为 **10 个 MSS**（具体值以当前内核版本为准，需查证），而不是 RFC 2001 时代的一个段[reference:1]。

**“慢启动”这个名字有误导性**：它的起点小，但增长是**指数级**的。它慢的是“起步”，不是“增长”。在高带宽高时延的**长肥管道（Long Fat Network）** 上，窗口爬到足够大需要好几个 RTT，小文件传输的吞吐上不去，往往就是慢启动还没爬到位就结束了[reference:2]。

<br>

### 拥塞避免：到阈值之后，从翻倍改成每 RTT 加一

<br>

`cwnd` 不能永远指数涨下去。发送方维护一个**慢启动阈值 `ssthresh`** ：当 `cwnd < ssthresh` 时走慢启动；当 `cwnd` 达到或超过 `ssthresh` 后，进入**拥塞避免（congestion avoidance）** 。

**拥塞避免的经典行为是“每个 RTT 大约增加 1 个 MSS”** （加性增，Additive Increase）。具体到 ACK 级别，每收到一个 ACK，`cwnd` 增加 `MSS × MSS / cwnd`，效果就是每个 RTT 只涨约 1 个 MSS[reference:3]。相比慢启动的翻倍，这是线性增长，用来在接近链路容量时**缓慢试探**，而不是猛冲。

**`ssthresh` 本身会在丢包时被更新**，它标记了“上一次拥塞发生时的窗口水平”。`cwnd` 和 `ssthresh` 的关系，就是 `ss -ti` 里你看到的两个数字在讲的故事。

<br>

### 丢包的两种信号，回退强度完全不同

<br>

拥塞控制需要从“丢包”中推断“网络是不是堵了”。但**不同的丢包信号，可信度不同**。

**超时（RTO 到期）** ：发送方等不到 ACK，认为某个段可能彻底丢了。这是**强信号**——网络可能严重拥塞，连后续的 ACK 都回不来。响应动作很剧烈：`ssthresh = cwnd / 2`，`cwnd` **回到 1 个 MSS**，重新进入慢启动。吞吐会断崖式下跌，再慢慢爬回来。

**3 个重复 ACK**：接收方在反复说“我在等某个段”，但后续段还在到达，说明网络**还在交付**，只是个别包丢了。这是**弱信号**。发送方走**快速重传 + 快速恢复（fast recovery）** ：`ssthresh = cwnd / 2`，`cwnd` **减半**（Reno 中通常设为 `ssthresh + 3 MSS`，因为那 3 个重复 ACK 代表已经有 3 个包离开了网络），然后继续拥塞避免，而不是回到 1[reference:4]。

**这就是“网速忽快忽慢”锯齿的来源**：窗口线性爬到某个水平，遇到丢包信号，乘性减半（或断崖回 1），再线性爬回去。**锯齿本身是拥塞控制在正常工作**，不是故障。问题在于：如果丢包不是真的“网络拥塞”，这个锯齿就是在为错误的信号买单。

<br>

### 为什么“丢一个包就减半”会被诟病，以及 CUBIC / BBR 在改什么

<br>

经典的 Reno 式拥塞控制是**丢包驱动**的：把丢包当作拥塞信号。这在早期网络中合理，但在**高 BDP 链路**（卫星、跨洋、万兆）上，**一个随机丢包就可能让窗口腰斩**，吞吐损失与链路容量不成比例[reference:5]。

**CUBIC** 是 Linux 很长一段时间里的默认算法。它仍然以丢包为信号，但窗口恢复**不再按 RTT 线性增长，而是按“距上次丢包的时间”做三次函数增长**：离峰值远时涨得快，接近峰值时涨得慢，从而在高带宽长时延链路上恢复更快，且增长速率对 RTT 不那么敏感[reference:6]。

**BBR** 换了信号来源：**不再把丢包当作拥塞信号**，而是估计**瓶颈带宽（BtlBw）** 和**最小 RTT**，用两者的乘积（BDP）来建模“管道能装多少”，据此控制发送速率[reference:7]。它在**随机丢包**的链路上表现更好，因为随机丢包并不一定意味着瓶颈队列在堆积。但 BBR 也有边界：它与 CUBIC 混跑时的公平性受瓶颈缓冲区大小影响，且不同版本行为差异较大，**具体结论需以版本和部署环境为准**[reference:8]。

**面试里不要简单说“BBR 比 CUBIC 好”** 。更准确的表述是：**丢包驱动的算法把“丢包”当拥塞，在有随机丢包的链路上会过度回退；BBR 把“带宽和时延”当信号，在随机丢包场景下更稳，但公平性和部署效果依赖具体环境。**

<br>

### 一个容易踩的边界：云厂商限速丢包，看起来和拥塞一模一样

<br>

云环境的 EIP / 共享带宽限速可能在**发送方完全感知不到链路拥塞**的情况下丢包。从发送方看，这和“中间队列满了”没有区别：`cwnd` 被减半、`retrans` 上升、吞吐出现锯齿。**但 RTT 可能并没有同步上升**——如果是真实拥塞导致的队列堆积，RTT 通常会先涨；如果是限速策略在带宽打满时直接丢包，RTT 未必跟着涨。**先确认“是不是真的拥塞”，再谈调算法**，否则换 BBR 可能只是把问题从“窗口减半”变成“重传更多”[reference:9]。

<br>

<br>

## 动手实验：用 `ss -ti` 观察窗口字段，用 `tc netem` 制造可控丢包

***

### 实验一：`ss -ti` 看一条活跃连接的 cwnd / ssthresh / rtt / retrans

<br>

**目标**：不靠猜，直接在命令行看到拥塞控制的内部变量在连接存续期间如何变化。

**步骤**：先建立一条持续传输数据的连接（比如从远端拉一个大文件，或者用 `iperf3` 打流），然后在发送端执行：

```bash
ss -ti dst :443
```

或者更通用地列出所有已建立连接并显示 TCP 内部信息：

```bash
ss -tin state established
```

> **预期输出（示意，字段值取决于实际连接）：**
>
> ```text
> ESTAB  0  0  192.0.2.10:54321  93.184.216.34:443
>      cubic wscale:7,7 rto:204 rtt:12.3/4.1 ato:40 mss:1448
>      cwnd:10 ssthresh:7 bytes_acked:... segs_out:... retrans:0/0
> ```
>
> 关键字段：**`cwnd`** 当前拥塞窗口，**`ssthresh`** 慢启动阈值，**`rtt`** 平滑 RTT / 方差，**`retrans`** 已重传次数 / 总重传次数，**`cubic`** 表示当前使用的拥塞控制算法。

**看到什么说明什么**：**`cwnd` 和 `ssthresh` 的相对关系告诉你当前处于哪个阶段**。`cwnd < ssthresh` 时通常还在慢启动（指数增长）；`cwnd` 接近或超过 `ssthresh` 后转入拥塞避免（线性增长）。如果 `retrans` 在短时间内上升，同时 `cwnd` 突然下降，说明刚发生了一次丢包触发的窗口回退。**`rtt` 突然变大往往说明中间队列在堆积（bufferbloat），是“发太快”的信号**，而不是“网络变差了”[reference:10]。

**边界**：`ss -ti` 显示的是**发送端视角**的 `cwnd`；`rwnd` 是接收端通告的，需要从抓包或对端 `ss` 看。不要用一个字段解释所有窗口变化。

<br>

### 实验二：用 `tc netem` 注入延迟和丢包，观察 cwnd 和吞吐的响应

<br>

**目标**：把“丢包 → 窗口回退 → 吞吐锯齿”的因果链在可控环境中复现出来，而不是在生产上猜。

**步骤**（在 Linux 上，需要 `tc` 权限；建议在测试机或网络命名空间中操作）：

```bash
# 给出口网卡注入 1% 随机丢包和 50ms 延迟（参数仅为示意，按环境调整）
sudo tc qdisc add dev eth0 root netem loss 1% delay 50ms
```

然后建立一条传输并观察：

```bash
# 终端 1：打流或 scp 大文件
# 终端 2：反复观察 ss -ti
watch -n 1 'ss -tin state established | grep -A1 443'
```

> **预期现象**：在 1% 丢包下，`cwnd` 会出现周期性的**减半和恢复**；如果用的是丢包驱动算法（如 CUBIC），吞吐曲线呈锯齿；`retrans` 计数持续上升。把丢包率改成 0%，锯齿会明显减弱。

**看到什么说明什么**：**窗口的“退”是在响应丢包信号，“涨”是在试探可用带宽**。1% 的随机丢包在丢包驱动算法下可能被当成拥塞，导致不必要的窗口回退。**这也解释了为什么在有随机丢包的链路上，BBR 这类不把丢包当拥塞信号的算法可能表现更好**——不是因为它“更快”，而是因为它**不把非拥塞丢包翻译成窗口减半**。

**清理**：

```bash
sudo tc qdisc del dev eth0 root
```

**常见失败原因**：`tc` 需要 root 和内核支持；在容器或云主机上可能没有 `NET_ADMIN` 权限。如果无法注入丢包，可以只做实验一，用 `ss -ti` 观察真实连接的窗口变化，**但不要在生产机上随意加 `netem`**。

<br>

### 常见失败原因与解决办法

<br>

| 现象 | 可能原因 | 怎么办 |
|---|---|---|
| `ss -ti` 看不到 `cwnd` / `ssthresh` | `ss` 版本较旧，或连接处于非 ESTABLISHED 状态 | 升级 `iproute2`；确认连接已建立 |
| `cwnd` 一直很小，但 `retrans` 没有上升 | 瓶颈在接收端 `rwnd`，不是拥塞控制 | 看接收端 socket 缓冲区、应用读取速度；不要调 `tcp_congestion_control` |
| 注入 1% 丢包后吞吐直接崩了 | 算法对随机丢包过度反应（经典丢包驱动行为） | 对比 CUBIC 和 BBR 在同一环境下的表现；注意 BBR 的公平性和版本差异 |
| 云上 `retrans` 高但 `rtt` 不涨 | 可能是带宽限速/策略丢包，而非真实队列拥塞 | 先确认丢包是否集中在带宽打满时刻；不要直接归因于“网络拥塞” |

## 开发启示

***

### 启示一：`cwnd` 小不等于“网络拥塞”，先看 `rwnd`

<br>

**现象**：`ss -ti` 看到 `cwnd` 只有几十，吞吐上不去，第一反应是“网络拥塞，调拥塞参数”。

**底层原因**：发送窗口是 `min(rwnd, cwnd)`。如果接收端应用读取慢，`rwnd` 很小，`cwnd` 再大也发不出去。**`cwnd` 小可能是拥塞控制正常回退，也可能是它根本没有机会增长，因为 `rwnd` 一直是瓶颈。** 第 10 篇的零窗口就是 `rwnd = 0` 的极端情况。

**可操作动作 / 面试答法**：先确认瓶颈在哪一侧。如果 `retrans` 不高、`rtt` 稳定、但窗口就是上不去，**优先查接收端应用和 socket 缓冲区**，而不是调 `tcp_congestion_control`。面试时说“**发送窗口取 min(rwnd, cwnd)，窗口小先分清是接收端不让发还是发送方不敢发**”，比直接背“慢启动、拥塞避免”更有排障价值。

<br>

### 启示二：锯齿不是故障，但“为随机丢包买单”是

<br>

**现象**：传输速度周期性冲高回落，监控上 `cwnd` 和 `ssthresh` 反复变化，团队想“消除锯齿”。

**底层原因**：**锯齿是 AIMD 的正常形态**：加性增、乘性减。真正需要关注的是**窗口回退是否由真实拥塞引起**。如果丢包是随机噪声、链路限速或 MTU 问题，丢包驱动算法会把它当拥塞，导致不必要的吞吐损失。

**可操作动作 / 面试答法**：先看 `retrans` 和 `rtt` 的对应关系。**真实拥塞通常伴随 RTT 上升**（队列堆积）；随机丢包或策略丢包可能 RTT 不涨。如果确认是随机丢包场景，再评估是否切换到对丢包不敏感的算法（如 BBR），**但要同时考虑公平性和部署环境**。面试陷阱：“慢启动和拥塞避免的区别是什么？”不要只背“指数 vs 线性”，要补一句“**慢启动是不知道容量时的试探，拥塞避免是接近容量后的缓慢逼近；丢包信号的可信度决定了回退强度**”。

<br>

### 启示三：面试追问——“流量控制和拥塞控制是一回事吗？”

<br>

**常见误解**：把“窗口”笼统地当成一个东西，认为窗口小就是网络问题。

**正确思路**：**流量控制（flow control）是接收方通过 `rwnd` 防止发送方压垮自己**，属于端到端语义；**拥塞控制（congestion control）是发送方通过 `cwnd` 防止压垮中间网络**，属于发送方对路径的判断。两者独立维护，发送方取 `min`。**零窗口是流控问题，窗口锯齿是拥塞控制行为，两者不能混为一谈。**

**面试答法**：先给公式 `发送窗口 = min(rwnd, cwnd)`，再各给一个典型现象（零窗口 vs 锯齿），最后说“**排查时先判是哪个变量在限制发送**”。这个回答既展示机制，又展示排障顺序。

## 小结与下一篇预告

***

回到开头：**网速忽快忽慢，到底是谁在踩刹车？** 可能有两脚刹车：**接收端的 `rwnd`** 和**发送端的 `cwnd`** 。`cwnd` 的锯齿是拥塞控制在“试探—回退—再试探”，本身不是故障；但如果回退是由随机丢包或限速策略触发的，那就是在为错误信号买单。**`ss -ti` 让你直接看到 `cwnd`、`ssthresh`、`rtt`、`retrans`，但看之前先问：这个窗口小，是因为接收方不收，还是因为发送方不敢发？**

下一篇进入 TCP 排障的实战篇：**常见 TCP 问题排查：超时、重置与队头阻塞**。你会把第 9–11 篇的 TIME_WAIT、重传、窗口串成一条排查链，用 `tcpdump` 抓一个异常连接案例，分清 RST、超时和队头阻塞在抓包里分别长什么样。

自测问题：

1. 发送窗口由哪两个变量决定？如果 `cwnd` 很小但 `retrans` 没有上升，优先怀疑哪一侧？
2. 超时重传和 3 个重复 ACK 触发的窗口回退，强度为什么不同？这对应 `ss -ti` 里的哪些字段变化？

**第 1 题答案**

- **发送窗口 = min(rwnd, cwnd)**。`rwnd` 是接收方通告的接收窗口（流控），`cwnd` 是发送方维护的拥塞窗口（拥塞控制）。
- 如果 `cwnd` 很小但 `retrans` 没有上升，**优先怀疑接收端**：可能是 `rwnd` 限制了发送窗口，`cwnd` 根本没有机会增长。应查接收端应用读取速度、socket 缓冲区，而不是调拥塞控制算法。如果 `retrans` 同时上升，才更可能是拥塞控制因丢包在回退 `cwnd`。

**第 2 题答案**

- **超时重传**是强信号：发送方等不到 ACK，认为链路可能严重拥塞，响应是 `ssthresh = cwnd/2`，**`cwnd` 回到 1 个 MSS**，重新慢启动。`ss -ti` 中会看到 `cwnd` 断崖式下降，`ssthresh` 减半。
- **3 个重复 ACK**是弱信号：后续报文还在到达，说明网络还在交付，只是个别包丢了。响应是快速重传 + 快速恢复，**`cwnd` 减半而不是回到 1**（Reno 中通常设为 `ssthresh + 3 MSS`），然后继续拥塞避免。`ss -ti` 中 `cwnd` 下降幅度较小，恢复更快。
- 强度不同的根本原因：**超时的信息量更悲观**（连后续 ACK 都等不到），重复 ACK 说明路径仍在工作。两者对应的 `cwnd` 下降幅度和恢复路径不同，在 `ss -ti` 的 `cwnd` / `ssthresh` 变化中可以观察到。
