一个微服务调用另一个微服务，客户端日志里偶尔出现 `Connection reset by peer`，但服务端业务日志干干净净，没有任何异常记录。你抓包一看，确实有一个 `[RST]` 从服务端 IP 发过来，但服务端代码里根本没有主动关闭连接的逻辑。

另一种情况更让人无从下手：客户端报“超时”，但服务端日志显示请求已经处理完了。抓包发现客户端反复重传同一个数据段，`ss -ti` 里 `retrans` 在涨、`rto` 在退避，但 **对端到底收没收到，你不确定**。

第三种情况只在高并发下出现：HTTP/2 开启了多路复用，理论上多个请求可以并行，但某个请求慢了，**同一连接上的其他请求也跟着一起慢**。你怀疑是服务端处理慢，但服务端监控显示每个请求的处理时间都正常。

这三个现象分别指向 TCP 排障的三个核心问题：**RST 是谁发的、超时卡在哪一段、队头阻塞是不是协议本身在等你**。这一篇不教你背所有 TCP 状态，而是给你一条**“症状 → 抓包证据 → 根因方向”的排查链**，并用 `tcpdump` 把 RST 和重传亲手抓出来。

<br>

<br>

## 核心概念

***

### RST 不是一种“错误”，它是连接被强制终止的信号

<br>

**RST（Reset）** 是 TCP 头里的一个标志位，含义是“**立即终止这条连接，不要走四次挥手**”。它不携带优雅关闭的语义，收到 RST 的一方会直接丢弃连接状态，任何在途数据都可能丢失。

**RST 可以从三个不同位置发出，排查时必须先分清来源**：

**第一，对端主机主动发送。** 常见于：目标端口没有进程监听（SYN 到达后直接回 RST）；应用调用了 `SO_LINGER` 且 `l_linger=0`，`close()` 时跳过 FIN 直接发 RST；或者应用在未完成读取的情况下异常终止，内核代为发送 RST。**从对端 IP 发出的 RST，通常意味着对端在主动拒绝或强制终止**，但不绝对——中间设备可以伪造源 IP。

**第二，中间设备生成。** 防火墙的 `REJECT` 规则、负载均衡器的空闲超时、NAT 连接跟踪表项过期，都可能由**中间设备的 IP**（或伪造的端点 IP）发出 RST。这类 RST 在报文层面和对端主动发的 RST **无法仅凭标志位区分**，必须结合两端抓包和中间设备日志交叉验证[reference:3]。

**第三，协议栈对“不该到达的报文”的响应。** 例如，已经关闭的连接收到迟到的数据段，内核会回 RST，告诉对方“这条连接不存在了”。这类 RST 是协议栈的正常保护行为，不是故障。

**一个立刻能用的判定顺序**：**先看 RST 的源 IP 是不是真正的对端**；如果是，再查对端应用是否监听了端口、是否有 `SO_LINGER=0` 或异常 abort；如果源 IP 是中间设备或可疑，查防火墙、负载均衡、NAT 超时。**仅凭一个 RST 包不能定性**，这是 RST 排查最容易犯的错误[reference:4]。

<br>

### 超时的两种形态：SYN 没人理，和数据发出去没人 ACK

<br>

“超时”在 TCP 里至少对应两种完全不同的场景，排查路径不同。

**连接建立阶段的超时**：客户端发出 `SYN`，但**没有收到 `SYN-ACK`**。抓包表现为同一个 `SYN` 被反复重传，中间没有任何来自服务端的响应[reference:5]。可能原因包括：服务端没有监听、防火墙**静默丢弃**（而非 REJECT 回 RST）、路由不可达。**区分“静默丢弃”和“端口关闭”的关键证据是：有没有 RST 回来**。有 RST → 端口关闭或主动拒绝；没有 RST、SYN 反复重传 → 路径上有设备在丢包或拦截[reference:6]。

**数据传输阶段的超时**：连接已经建立，发送方发出数据段，但在 **RTO（Retransmission Timeout）** 内没有收到覆盖该数据的 ACK，触发**超时重传**。RTO 在每次超时后**指数退避**，所以如果链路持续不通，重传间隔会越来越长，客户端要等很久才报错[reference:7]。**超时重传比快速重传更伤延迟**，因为它在等一个可能永远不会来的 ACK，而不是被重复 ACK 提前唤醒。

**排查数据传输超时的第一步不是调 RTO**，而是确认**数据到底有没有到达对端**。在两端同时抓包：如果发送端看到重传，接收端完全没有收到原始段，问题在路径丢包；如果接收端收到了原始段但 ACK 没有回到发送端，问题在反向路径的 ACK 丢失或延迟[reference:8]。

<br>

### 队头阻塞：HTTP/2 解决了应用层，但没解决传输层

<br>

**队头阻塞（Head-of-Line Blocking）** 在 TCP 语境下有一个非常具体的含义：**一个数据段丢了，后面所有已经到达的段都不能先交付，必须等丢失的段重传完成**。这是 TCP 有序交付的直接后果。

**HTTP/1.1 的队头阻塞发生在应用层**：一条连接上同一时刻基本只能处理一个请求，后面的请求排队等待。浏览器通过开 **6 条 TCP 连接**来缓解，但每条连接内部仍然是串行的[reference:9]。

**HTTP/2 用多路复用解决了 HTTP/1.1 的应用层队头阻塞**：一条 TCP 连接上可以并行几十上百个流。**但 HTTP/2 仍然跑在 TCP 上**，TCP 本身的有序交付没有变。**一个 TCP 段丢失，整条连接上所有流都会暂停**，等待那个段重传[reference:10]。这就是 **TCP 层的队头阻塞**。

**一个反直觉但重要的数据点**：在 2% 的丢包率下，HTTP/1.1 的表现可能**优于** HTTP/2。因为 HTTP/1.1 有 6 条独立连接，一条连接被阻塞时，其他连接仍然可以传输；而 HTTP/2 把所有流集中到一条 TCP 连接上，**一次丢包就阻塞全部**[reference:11]。

**QUIC 的解法不是在 TCP 上打补丁，而是把可靠传输搬到 UDP 之上，以“流”为独立单元管理重传**。一个流丢包只阻塞那个流，其他流继续交付[reference:12]。**边界说明**：这并不意味着“上 QUIC 就没有队头阻塞了”——QUIC 解决的是**传输层跨流的队头阻塞**，单个流内部的按序交付仍然存在；HTTP/3 头部帧等细节不在本篇展开，以当前主流实现为准。

## 动手实验：用 `tcpdump` 抓 RST，用 `tshark` 区分超时与重传

***

### 实验一：抓一次“对 SYN 的 RST 拒绝”

<br>

**目标**：亲眼看到“端口没有监听”时，服务端在 SYN 之后直接回 RST，而不是 SYN-ACK。

**步骤**：在一台 Linux 机器上，对一个**确定没有进程监听**的端口发起连接（以 `example.com` 的 9 端口为例，discard 服务通常未启用；也可以用本机一个随机高位端口）：

```bash
# 终端 1：抓 SYN 和 RST
sudo tcpdump -i any -nn 'tcp[tcpflags] & (tcp-syn|tcp-rst) != 0 and host example.com'

# 终端 2：尝试连接
nc -zv -w 2 example.com 9
```

> **预期输出（示意）：**
>
> ```text
> IP 192.0.2.10.54321 > 93.184.216.34.9: Flags [S], seq ...
> IP 93.184.216.34.9 > 192.0.2.10.54321: Flags [R.], seq 0, ack ...
> ```
>
> 第一条是客户端发出的 `SYN`，第二条是服务端回来的 `RST`。

**看到什么说明什么**：**`SYN` 之后紧跟着 `RST`，说明目标端口确实没有进程在监听，或者防火墙规则是 `REJECT` 而不是 `DROP`**。如果 `SYN` 反复重传但**没有任何 RST 或 SYN-ACK**，说明报文在路径上被**静默丢弃**了，排查方向转向防火墙 `DROP` 规则、安全组或路由[reference:13]。**“有 RST”和“没 RST”是两条完全不同的排查分支。**

**如果你的环境无法连接外部 example.com 的 9 端口**，可以在本机用一个未被监听的端口验证，行为一致。

<br>

### 实验二：`tcpdump` 抓重传，`tshark` 统计超时与快速重传

<br>

**目标**：不靠 Wireshark 图形界面，用命令行从抓包文件里直接区分“超时重传”和“快速重传”，并判断对端有没有收到原始数据。

**步骤**：先抓一段包含重传的流量（可以用第 10 篇的 `tc netem` 注入丢包，或直接在生产低谷期抓取已知有重传的连接）：

```bash
sudo timeout --signal=INT 60 tcpdump -i eth0 -w /tmp/tcp-issue.pcap 'tcp port 443'
```

然后用 `tshark` 提取重传事件：

```bash
tshark -r /tmp/tcp-issue.pcap \
  -Y "tcp.analysis.retransmission or tcp.analysis.fast_retransmission" \
  -T fields -e frame.time -e ip.src -e ip.dst -e tcp.seq \
  -e tcp.analysis.retransmission -e tcp.analysis.fast_retransmission
```

> **预期输出（示意）：**
>
> ```text
> 12:00:05.100  192.0.2.10  93.184.216.34  1001  1  0
> 12:00:05.200  192.0.2.10  93.184.216.34  1001  1  0
> 12:00:05.400  192.0.2.10  93.184.216.34  1001  1  0
> ```
>
> 同一个 `Seq=1001` 出现了多次，`tcp.analysis.retransmission` 列为 `1`，间隔在拉大（0.1s → 0.2s）。

**看到什么说明什么**：**同一个序号反复出现、间隔在扩大，是超时重传 + RTO 指数退避的典型形态**。如果看到的是 `fast_retransmission`（`tcp.analysis.fast_retransmission=1`），说明发送方是被重复 ACK 提前唤醒的，而不是等 RTO。**超时重传对延迟的伤害更大**，因为它意味着发送方在“死等”一个可能永远不会来的 ACK[reference:14]。

**判断“谁的问题”**：如果发送端抓到了原始段的重传，但接收端**从未收到原始段**，问题在正向路径丢包；如果接收端收到了原始段、但没有发出对应的 ACK，问题在接收端协议栈或应用未及时读取；如果接收端发出了 ACK、但发送端没有收到，问题在反向路径[reference:15]。**两端抓包是区分“正向丢”和“反向丢”的唯一可靠办法。**

**常见失败原因**：`tcpdump` 本身不做流分析，`tcp.analysis.*` 字段来自 `tshark`/Wireshark。如果没有 `tshark`，可以用 `tcpdump -r` 查看原始序号，手动判断“同一序号是否重复出现”[reference:16]。

<br>

### 常见失败原因与解决办法

<br>

| 现象 | 可能原因 | 怎么办 |
|---|---|---|
| `tcpdump` 抓不到 RST，但客户端报 reset | RST 可能在**中间设备**发出，不在你抓包的网卡路径上 | 在客户端和服务端**同时抓包**，对比 RST 的源 IP；查防火墙/负载均衡日志 |
| `SYN` 反复重传，没有 `RST` 也没有 `SYN-ACK` | 路径上有设备**静默丢弃**（`DROP` 而非 `REJECT`） | 检查安全组、iptables `DROP` 规则、路由；在服务端网卡确认 SYN 是否到达 |
| `tshark` 报“没有 `tcp.analysis` 字段” | `tshark` 版本较旧，或抓包文件不完整 | 升级 `tshark`；或直接用 `tcpdump -r` 观察重复序号 |
| HTTP/2 连接在高丢包下整体变慢 | **TCP 层队头阻塞**，不是应用层多路复用失效 | 结合丢包率判断；如果丢包率较高且无法降低，评估 QUIC/HTTP/3 的迁移成本，但不要指望调 HTTP/2 参数能根治 |

## 开发启示

***

### 启示一：RST 先看“谁发的”，再看“为什么发”

<br>

**现象**：客户端偶发 `Connection reset`，服务端业务日志无异常，抓包有一个从服务端 IP 发出的 RST。

**底层原因**：RST 可能来自**对端应用**（端口关闭、`SO_LINGER=0`、异常 abort）、**中间设备**（防火墙 REJECT、负载均衡空闲超时、NAT 表项过期），或**对端协议栈**（收到不该到达的报文）。**仅凭“RST 来自服务端 IP”不能断定是服务端应用发的**——中间设备可以伪造源 IP[reference:18]。

**可操作动作 / 面试答法**：**两端同时抓包**，对比 RST 的源 IP 和到达时间；如果客户端抓到了 RST，但服务端抓包显示服务端**没有发出过这个 RST**，高度怀疑中间设备。然后再查：服务端应用是否监听了端口、是否有 `SO_LINGER` 配置、负载均衡/NAT 的空闲超时是否短于业务连接的存活时间。面试时说“**RST 不是一种错误，是一个来源需要被定位的信号**”，比直接说“服务端异常关闭了连接”更准确。

<br>

### 启示二：超时先分“阶段”，不要一上来调 RTO

<br>

**现象**：客户端报超时，`ss -ti` 里 `retrans` 在涨、`rto` 在退避，团队第一反应是调小 `tcp_retries2` 或 RTO 下限。

**底层原因**：**连接建立阶段的超时（SYN 无响应）和数据传输阶段的超时（数据无 ACK）是完全不同的故障**。SYN 超时通常是端口/防火墙/路由问题；数据超时可能是正向丢包、反向 ACK 丢失、或接收端处理慢。**调 RTO 只是改变“等多久放弃”，不解决“为什么等不到”**。而且 RTO 指数退避是防止网络雪崩的正常机制，在根因未定位前压低它，只会让问题以更隐蔽的方式出现[reference:19]。

**可操作动作 / 面试答法**：先看抓包里超时发生在**握手阶段还是数据传输阶段**。握手阶段只有 SYN 没有 SYN-ACK → 查监听和防火墙；数据传输阶段有重传 → 两端抓包确认**原始段是否到达、ACK 是否回来**。面试时不要直接给参数，要先说“**超时分阶段，先定位哪一段没有回应**”，再谈排查手段。

<br>

### 启示三：面试陷阱——“HTTP/2 多路复用解决了队头阻塞”

<br>

**常见误解**：HTTP/2 引入了多路复用，所以队头阻塞问题已经彻底解决了。

**正确思路**：HTTP/2 解决的是 **HTTP/1.1 的应用层队头阻塞**（一条连接上请求串行排队），但 **HTTP/2 仍然跑在 TCP 上，TCP 的有序交付意味着一个段丢失会阻塞整条连接上的所有流**[reference:20]。在高丢包环境下，HTTP/2 的表现甚至可能**不如** HTTP/1.1 的多连接并行[reference:21]。**QUIC/HTTP/3 才是把可靠传输搬到 UDP 上、以流为独立单元管理重传，从而解决传输层跨流队头阻塞的方案**，但单个流内部的有序交付仍然存在，不是“绝对没有队头阻塞”。

**面试答法**：先说“HTTP/2 解决应用层，没解决传输层”，再补“**TCP 队头阻塞是协议固有代价，不是配置错误**，所以 QUIC 选择在 UDP 上重建传输层”；最后加一句边界：“QUIC 消除的是跨流阻塞，单流内部仍然按序。” 这样既展示分层，又避免了“HTTP/2 万能”或“QUIC 零阻塞”的过度概括。

<br>

## 小结与下一篇预告

***

回到开头三个现象：**RST 要定位来源**，对端主动拒绝、中间设备超时、协议栈保护行为，处理方式完全不同；**超时先分阶段**，SYN 无响应查路径，数据无 ACK 两端抓包确认方向；**队头阻塞不是“调参能修”的问题**，HTTP/2 over TCP 的跨流阻塞是协议设计的固有代价，QUIC 的解法是把可靠传输搬到 UDP 并按流隔离。**排障的第一步永远是“用抓包把现象翻译成证据”，而不是先动参数。**

下一篇离开运输层，进入网络层与链路层的第一站：**IP、路由与 NAT：数据包怎么找到路**。你会用 `traceroute` 观察数据包经过的路径，理解 IP 寻址、路由选择和 NAT 在跨网段通信中的角色——这也是为什么“抓包看到了 RST，但它不一定来自你以为的那个地方”的底层原因之一。

自测问题：

1. 抓包看到一个 `SYN` 之后紧跟着 `RST`，和 `SYN` 反复重传但没有 `RST`，分别指向什么排查方向？
2. HTTP/2 的多路复用为什么没有消除 TCP 层的队头阻塞？QUIC 在这一点上改变了什么？

<br>

<details>
<summary>点击查看自测问题答案</summary>

**第 1 题答案**

- **`SYN` → `RST`**：目标端口**没有进程监听**，或者防火墙规则是 **`REJECT`**（主动拒绝）而不是 `DROP`。排查方向是：服务端应用是否真的监听了该端口、iptables/安全组是否配置了 `REJECT`。如果是中间设备发的 RST，源 IP 可能是中间设备而非真正的服务端[reference:22][reference:23]。
- **`SYN` 反复重传、没有 `RST` 也没有 `SYN-ACK`**：报文在路径上被**静默丢弃**（`DROP` 规则、安全组拦截、路由不可达）。排查方向是路径和防火墙策略，而不是服务端端口监听。在服务端网卡同时抓包：服务端看不到 SYN → 问题在链路中间；服务端看到了 SYN 但不回 → 问题在服务端本机[reference:24]。

**第 2 题答案**

- **为什么 HTTP/2 没消除**：HTTP/2 的多路复用把多个流放在**一条 TCP 连接**上，但 TCP 本身仍然是**有序交付的字节流**。一个 TCP 段丢失，后面所有已经到达的段都不能先交付，**整条连接上的所有流一起阻塞**，直到丢失段重传完成[reference:25]。HTTP/2 解决的是 HTTP/1.1 的**应用层**请求排队，不是 TCP 的**传输层**队头阻塞。
- **QUIC 改变了什么**：QUIC 把可靠传输搬到 **UDP 之上**，在用户态以**流（stream）** 为独立单元管理序号和重传。一个流丢包只阻塞那个流，其他流继续交付，从而消除了**跨流的传输层队头阻塞**[reference:26]。但单个流内部仍然保持按序交付，所以不是“完全没有队头阻塞”。
