## 场景问题

***

你写了一个 P2P 文件传输功能，两端都通过 STUN 服务器拿到了自己的“公网地址”，信令交换也成功了。但在某些用户那里，**双方都拿到了地址，连接却永远建不起来**。日志里没有任何异常，STUN 返回的 IP 和端口看起来完全正常。你开始怀疑是代码 bug，但同样的代码在办公室测试时一切正常。

换到另一个场景：你在云主机上 `traceroute` 一个外部地址，输出里某一跳开始全是 `* * *`，但 `ping` 目标地址却是通的。你不知道是该担心“链路断了”，还是该忽略这些星号。

还有一个更隐蔽的：两个服务在同一台机器上，一个用 `127.0.0.1` 访问另一个正常，但换成内网 IP 或域名就偶尔超时。你检查了防火墙，没有拒绝规则，`ss` 显示端口也在监听。

这三个现象的共同点是：**它们都不是“TCP 或 HTTP 哪里写错了”，而是数据包在“找到对方”的过程中被 IP 寻址、路由选择或 NAT 改写了路径。** 第 13 篇要把“IP 地址、路由表、NAT”这三个开发者平时不太碰的东西，拉回到排障的第一现场：**你的程序以为自己在和谁说话，和数据包实际去了哪里，可能不是同一回事。**

<br>

## 核心概念

***

### IP 地址不是“门牌号”，是“网络号 + 主机号”

<br>

IPv4 地址是 32 位，但它的结构不是“一个整体编号”。**子网掩码（subnet mask）** 决定了哪些位是网络号、哪些位是主机号。把 IP 地址和子网掩码做**按位与（AND）** ，得到的就是网络地址；剩下的位标识这个网络里的具体主机[reference:0]。

现代表示法用 **CIDR（无类别域间路由，Classless Inter-Domain Routing）** ，写成 `a.b.c.d/n`，`/n` 表示前 n 位是网络号。例如 `192.0.2.0/24` 表示前 24 位是网络号，后 8 位是主机号，这个网络里最多 254 个可用主机地址[reference:1]。

对开发者来说，**判断两个 IP “是不是同一个子网”** ，只需要比较它们的网络地址是否相同。**同一子网内的通信不走默认网关，直接通过链路层交付；跨子网才需要把包交给路由器**。这就是为什么“改了一个 IP，本机 `ping` 不通但同网段其他机器能通”——很可能是新 IP 和默认网关不在同一个子网里。

<br>

### 路由选择：最长前缀匹配 + 默认网关兜底

<br>

一台主机或路由器要发送数据包时，会查**路由表**。路由表里每一行是一个“目的网络 + 下一跳”。当目的地址匹配多个表项时，**选择前缀最长的那一个**——这就是**最长前缀匹配（longest prefix match）** 。前缀越长，网络越具体，路由越精确[reference:2]。

如果没有任何具体表项匹配，就用**默认路由**。IPv4 的默认路由写成 `0.0.0.0/0`，前缀长度为 0，匹配所有地址，是“最后的选择”。主机上的默认路由通常就叫**默认网关（default gateway）** [reference:3]。

**面试里常问的“最长前缀匹配”不是理论题，它有直接的排障含义**：如果你的机器上同时有一条 `10.0.0.0/8` 和一条 `10.1.2.0/24`，发往 `10.1.2.3` 的包会走 `/24` 那条，因为 `/24` 更具体。**多网卡、VPN、容器网络叠加时，路由表可能比你想象的复杂**，`ip route` 的输出值得在排障时认真看一眼。

<br>

### NAT：改写地址，维持一张“谁对应谁”的状态表

<br>

**NAT（Network Address Translation，网络地址转换）** 的核心动作是在数据包经过边界设备时，**改写 IP 头里的地址（以及端口）** 。它解决的是 IPv4 公网地址不够用的问题：大量内网设备共享少量公网 IP 上网[reference:4]。

**SNAT（源 NAT）** ：内网发往外网时，把**源 IP** 改成公网 IP。家用路由器默认行为就是这个，让所有设备看起来都从同一个公网 IP 发出。**DNAT（目的 NAT）** ：外网访问内网服务时，把**目的 IP** 改成内网服务器的地址，典型场景是端口映射。

**NAT 的关键状态是一张映射表**：出站时记录“内网五元组 ↔ 公网五元组”，入站时查表还原。没有表项，入站包就被丢弃。**这张表是有超时的**——不活跃的连接，NAT 表项会被老化删除。这解释了一个常见现象：**连接明明没断，但过一段时间再发数据就不通了**，因为 NAT 已经忘了这条连接的映射。

<br>

### NAT 对开发者的真正影响：P2P 打洞不是“概率问题”，是“类型问题”

<br>

NAT 破坏了**端到端直连**：外网无法主动连接内网设备，因为 NAT 没有对应的入站表项。P2P 应用试图通过 **UDP 打洞（hole punching）** 来绕过这一点：双方同时向对方的外部地址发包，试图在各自的 NAT 表里“凿”出一个入站映射。

**但打洞能否成功，取决于 NAT 的类型**。**锥形 NAT（cone NAT）** 在同一个内网源端口向不同目标发包时，**映射到同一个外部端口**，打洞成功率较高。**对称型 NAT（symmetric NAT）** 则对**每个不同的目标地址分配不同的外部端口**，一方通过信令拿到对方端口后，真正发包时端口可能已经变了[reference:9]。**当双方都是对称型 NAT 时，打洞成功率几乎为零**，工具只能回落到中继[reference:10]。

**这对开发者的含义是**：如果你的 P2P 功能在部分用户那里“永远建不起来”，不要只怀疑信令或代码，**先确认双方的 NAT 类型**。对称型 NAT 在真实网络中占比不低，直连失败不是 bug，是网络环境的结构性限制[reference:11]。

<br>

<br>

## 动手实验：用 `ip route` 看路由选择，用 `traceroute` 解读路径

***

### 实验一：`ip route get` 直接问“这个包会走哪条路”

<br>

**目标**：不靠猜，用一条命令确认内核实际会为某个目的地址选择哪条路由、从哪个接口发出。

**步骤**：在 Linux 上执行：

```bash
ip route get 8.8.8.8
ip route get 192.168.1.1
ip route get 10.0.0.5
```

> **预期输出（示意，取决于本机路由表）：**
>
> ```text
> 8.8.8.8 via 192.168.1.1 dev eth0 src 192.168.1.100
>      cache
> 192.168.1.1 dev eth0 src 192.168.1.100
>      cache
> local 10.0.0.5 dev lo src 10.0.0.5
> ```
>
> `via` 后面是下一跳，`dev` 是出口接口，`src` 是选定的源地址。

**看到什么说明什么**：`ip route get` 是**内核路由查找结果的直接输出**，比 `ip route` 里肉眼匹配最长前缀更可靠。如果目的地址和本机在同一子网，输出里通常没有 `via`（直接通过 `dev` 交付）；如果跨子网，会显示 `via` 默认网关或具体下一跳。**如果 `src` 选了一个你意想不到的地址（多网卡、VPN、容器网络），这就是“服务监听了但客户端连不上”的一个常见原因**——回包从另一个源地址出去，对端可能丢弃。

**如果你看到 `local` 开头**，说明目的地址是本机地址，内核直接本地交付，不走网络。

<br>

### 实验二：`traceroute` 看路径，正确解读星号

<br>

**目标**：区分“这一跳真的不通”和“这一跳不回复探测包”。

**步骤**：

```bash
traceroute -n example.com
```

> **预期输出（示意）：**
>
> ```text
> traceroute to example.com (93.184.216.34), 30 hops max, 60 byte packets
>  1  192.168.1.1  1.234 ms  1.456 ms  1.789 ms
>  2  * * *
>  3  10.10.0.1  5.678 ms  5.901 ms  6.123 ms
>  4  93.184.216.34  10.234 ms  10.456 ms  10.678 ms
> ```

**看到什么说明什么**：`traceroute` 的原理是**递增 TTL**：发出 TTL=1 的探测包，第一跳路由器把 TTL 减到 0，返回 **ICMP Time Exceeded**；然后 TTL=2，第二跳返回；以此类推，直到到达目的地[reference:12]。

**第 2 跳的 `* * *` 不一定表示故障**。常见原因包括：该路由器**不回复 ICMP Time Exceeded**（策略或速率限制）；**ICMP 被防火墙过滤**；**非对称路由**导致回程 ICMP 走了另一条路[reference:13]。**关键判断依据是“星号之后是否恢复正常”** ：如果 `* * *` 后面继续出现正常的跳，且目的地址可达，**那一跳的星号是探测包/回复被过滤，不是路径断了**。如果星号从某一跳开始**持续到结尾**，且 `ping` 目标也不通，才更可能是真实丢包或阻断[reference:14]。

**常见失败原因**：

| 现象 | 可能原因 | 怎么办 |
|---|---|---|
| 某一跳 `* * *`，后续跳正常 | 该路由器过滤 ICMP 或限速 | 忽略；用 `traceroute -I`（ICMP 模式）或 `-T`（TCP 模式）交叉验证[reference:15] |
| 从某一跳开始全是 `* * *`，目标不可达 | 真实丢包、防火墙阻断、路由不可达 | 结合 `ping` 和 `traceroute -T -p 80` 确认；检查目标侧安全组和路由 |
| `traceroute` 最后一跳就是目标 IP，但应用端口不通 | 路径可达，端口/应用层问题 | 用 `telnet`/`nc` 测试目标端口，不要继续在路由层纠缠 |

<br>

### 实验三：检测 NAT 类型（可选，取决于环境）

<br>

**目标**：确认自己所在网络是不是对称型 NAT，理解 P2P 打洞失败的结构性原因。

如果你有可用的 STUN 服务或 NAT 类型检测工具，可以对比**向两个不同目标地址**获取到的映射端口是否相同。**锥形 NAT** 通常对同一内网源端口映射到**同一个外部端口**；**对称型 NAT** 对不同目标会分配**不同的外部端口**。如果两个目标拿到的端口不一致，基本可以判断为对称型 NAT，P2P 直连的成功率会显著下降[reference:16]。

**边界说明**：NAT 类型的精确分类（全锥形、地址限制锥形、端口限制锥形、对称型）依赖具体实现和检测方法，**不同工具的判断结果可能有差异，需以实际环境为准**。

## 开发启示

***

### 启示一：P2P 连不上，先查 NAT 类型，不要先改代码

<br>

**现象**：P2P 功能在部分用户那里永远建不起连接，STUN 拿到的地址和端口看起来正常，信令交换也成功，但直连始终失败。

**底层原因**：**对称型 NAT 对不同目标分配不同的外部端口**，一方通过信令获知的端口在真正发包时已经失效。双方都是对称型 NAT 时，打洞成功率接近零，工具只能回落到中继[reference:17]。这不是你的代码写错了，是 NAT 的映射行为决定了直连在结构上不可行。

**可操作动作 / 面试答法**：在 P2P 功能中**显式检测 NAT 类型**，并在对称型 NAT 场景下**准备好中继回落策略**，而不是把“直连失败”当作异常无限重试。面试时不要说“打洞有概率失败”，要说出“**打洞失败是 NAT 类型不匹配的结构性问题，对称型 NAT 下直连不可行，需要中继兜底**”。

<br>

### 启示二：`traceroute` 星号先别慌，区分“不回复”和“不通”

<br>

**现象**：`traceroute` 某一跳全是 `* * *`，但目标服务实际可用；或者从某一跳开始持续星号，目标真的连不上。

**底层原因**：星号只表示“在超时时间内没有收到预期响应”。**中间路由器不回复 ICMP Time Exceeded 是常见策略**（速率限制、过滤、控制平面保护），**不代表它不转发数据包**[reference:18]。真正的故障信号是“星号持续到目标，且应用层不可达”。

**可操作动作 / 面试答法**：先看星号之后是否恢复。**单跳星号 + 后续正常 = 大概率是过滤/限速，可以忽略**。持续星号 + `ping` 不通 = 进一步用 `traceroute -T -p 80`（TCP 模式）或 `traceroute -I`（ICMP 模式）确认，因为不同探测类型可能被不同策略处理[reference:19]。面试时把“星号”翻译成“探测包或回复被丢弃”，而不是直接说“这一跳断了”。

<br>

### 启示三：面试陷阱——“NAT 只是地址转换，不影响应用”

<br>

**常见误解**：NAT 是网络层的事，开发者只需要关心 IP 和端口，不需要理解 NAT 的行为。

**正确思路**：NAT **破坏了端到端可达性**，它的影响直接落到应用层：P2P 打洞失败、IPsec/VPN 兼容性问题、基于 IP 地址的访问控制失效、NAT 表项老化导致长连接静默断开。**你的应用“以为”对端地址不变，但 NAT 的超时和端口映射行为随时可能改变可达性。**

**面试答法**：先说“NAT 解决地址短缺，但代价是端到端语义被打破”，再举 P2P 打洞和长连接老化作为开发者能感知的后果。**不要说“NAT 是运维的事”** ——当你的连接在 NAT 后面表现异常时，应用层的超时、重连、保活策略都需要针对 NAT 行为做设计。

<br>

## 小结与下一篇预告

***

回到开头：**P2P 在部分用户那里建不起来，不是代码 bug，是对称型 NAT 让“信令告诉你的端口”在真正发包时已经失效**；**`traceroute` 的星号不一定是链路断了，中间路由器不回复探测包是常态**；**同一台机器上 `127.0.0.1` 通、内网 IP 不通，先看 `ip route get` 选了什么源地址和出口，而不是先怀疑防火墙**。**IP 地址决定了“你和谁同网段”，路由表决定了“包从哪个口出去”，NAT 决定了“对方看到的你是谁”——这三件事任何一件和你以为的不一样，连接行为就会和你以为的不一样。**

下一篇进入链路层的最后一站：**ARP 与以太网：局域网里怎么找到对方**。你会看到“IP 地址找到了，但 MAC 地址还不知道”时，ARP 如何在局域网里喊话，以及 `arp` 表和二层广播为什么是“同子网能通、跨子网不通”的关键。

自测问题：

1. `ip route get` 的输出里，`via` 和 `dev` 分别告诉你什么？如果目的地址和本机在同一子网，输出有什么不同？
2. `traceroute` 某一跳显示 `* * *`，但后续跳正常且目标可达，最可能的原因是什么？为什么不能直接判定“这一跳故障”？

<br>

<details>
<summary>点击查看自测问题答案</summary>

**第 1 题答案**

- **`via`**：下一跳的 IP 地址。跨子网时通常是默认网关或具体路由器；同子网时通常**没有 `via`**，因为可以直接通过链路层交付，不需要经过路由器。
- **`dev`**：数据包从哪个网络接口发出。多网卡、VPN、容器网络环境下，`dev` 可能和你预期的不一样，这是“服务监听了但连不上”的一个常见排查点。
- **同一子网**：输出通常没有 `via`，只有 `dev` 和 `src`，表示直接通过该接口交付，不经过路由器。

**第 2 题答案**

- **最可能的原因**：该跳路由器**不回复 ICMP Time Exceeded**（策略过滤、速率限制、控制平面保护），或者回复的 ICMP 在回程被丢弃/走了非对称路径。它**仍然在正常转发数据包**，只是不响应 `traceroute` 的探测。
- **为什么不能判定故障**：星号只表示“没有收到预期响应”，不表示“没有转发”。**如果后续跳正常、目标可达**，这一跳的星号对实际数据路径没有影响。真正的故障信号是**星号持续到目标且应用层不可达**，此时才需要进一步用 TCP/ICMP 模式交叉验证。

</details>
