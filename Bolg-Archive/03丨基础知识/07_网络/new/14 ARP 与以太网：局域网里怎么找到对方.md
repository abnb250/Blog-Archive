## 场景问题

***

你在一台机器上启动了一个服务，监听 `0.0.0.0:8080`。同一台机器的另一个进程用 `127.0.0.1:8080` 访问，正常。换成本机的内网 IP `192.0.2.10:8080`，也正常。但让同网段的另一台机器 `192.0.2.20` 访问 `192.0.2.10:8080`，**连接超时**。你检查了服务端防火墙，没有拒绝规则；`ss -tlnp` 显示端口在监听；`ping` 也能通。

你开始怀疑是应用层的问题，但 `ping` 能通说明 IP 层是活的。**IP 地址找到了对方，但数据包到了链路层之后，需要知道“这个 IP 对应哪块网卡”** 。这个转换如果出了问题，表现就是“IP 能 ping 通，但 TCP 连不上”——因为 `ping` 的 ICMP 和 TCP 的 SYN 走的是同一条链路，但如果 ARP 缓存里有脏数据，或者 ARP 请求没有得到正确应答，两者都可能时通时不通。

另一个更隐蔽的场景来自生产环境：一台服务做迁移，新机器的 IP 和旧机器相同（或者负载均衡的虚拟 IP 漂移到了新节点），**旧机器的 ARP 缓存里还留着“这个 IP 对应旧 MAC”的记录**，网关继续把流量发给旧机器，新机器收不到任何请求。旧机器可能已经下线，流量直接黑洞。你查服务端日志，干干净净；查网络，IP 是通的——因为 `ping` 可能恰好触发了新的 ARP 解析，但长连接和已缓存的流量仍然走在错误的方向上。

这一篇要把“IP 地址找到了对方”之后的最后一步补上：**在以太网里，真正把帧送到对方面前的，是 MAC 地址，而不是 IP 地址**。ARP 就是那个“在局域网里喊一嗓子，问这个 IP 是谁”的机制。**它简单、无状态、没有认证，所以既好用，也容易被污染。开发者不需要成为二层专家，但必须知道：当“IP 通但服务不通”或者“迁移后流量不跟过来”时，ARP 是排障链上不能跳过的一环。**

## 核心概念

***

### 以太网靠 MAC 地址交付，IP 地址只是“逻辑目的地”

<br>

IP 地址是**网络层**的逻辑标识，用于路由选择：数据包从源到目的地，经过哪些路由器，由 IP 头里的目的地址决定。但当数据包到达**最后一个路由器**，或者在同一局域网内直接交付时，**链路层（以太网）需要的是 MAC 地址**——一块 48 位的硬件地址，烧录在网卡上（或以软件方式配置）。

**以太网帧的目的 MAC 地址决定了“这块帧被哪块网卡接收”** 。交换机根据 MAC 地址表转发帧；如果目的 MAC 是广播地址 `ff:ff:ff:ff:ff:ff`，则泛洪到同一 VLAN 内的所有端口[reference:0]。**IP 地址告诉网络“要去哪里”，MAC 地址告诉链路“这一跳交给谁”** 。在跨网段通信中，目的 MAC 是**下一跳路由器的 MAC**，而不是最终目的主机的 MAC；只有在同一子网内，目的 MAC 才是最终主机的 MAC。

<br>

### ARP 的工作方式：广播提问，单播回答，缓存结果

<br>

**ARP（Address Resolution Protocol，地址解析协议）** 做的事情非常窄：**给定一个 IPv4 地址，找出对应的 MAC 地址**。

流程只有三步[reference:1][reference:2]：

**第一步，查缓存。** 每台主机维护一个 **ARP 缓存表**，记录“IP → MAC”的映射。发送数据前，先查表。如果命中，直接用缓存里的 MAC 封装以太网帧。

**第二步，广播请求。** 如果缓存里没有，发送方构造一个 **ARP 请求**，以**广播**形式发出。以太网帧的目的 MAC 是 `ff:ff:ff:ff:ff:ff`，ARP 载荷里写着“**谁拥有 IP X？请告诉 IP Y**”。同一广播域内的所有主机都会收到这个请求[reference:3]。

**第三步，单播应答。** 只有 IP 匹配的那台主机（或者代表它应答的设备）会回复一个 **ARP 应答**，以**单播**形式直接发回请求方。应答里包含自己的 MAC 地址。请求方收到后，把这条映射写入 ARP 缓存，然后用这个 MAC 发送数据[reference:4]。

**关键点在于：ARP 请求是广播，ARP 应答是单播**。这是抓包时区分两者的第一依据。**ARP 缓存有老化机制**，Linux 下相关状态包括 `REACHABLE`、`STALE`、`DELAY`、`PROBE` 等，条目不会永久有效。`gc_stale_time` 的默认值在主流实现中通常为 **60 秒**，用于控制检查过期条目的频率，**具体行为以当前内核版本为准，需查证**。

<br>

### 免费 ARP：没有人问，自己主动说“这个 IP 现在是我”

<br>

**免费 ARP（Gratuitous ARP）** 是一种特殊的 ARP 报文：**发送方 IP 和目标 IP 都是自己的 IP**，目的 MAC 是广播地址。它不期待有人回答，它的作用是**主动宣告**：“这个 IP 现在绑定在我的 MAC 上，请更新你们的缓存。”

免费 ARP 有两个开发中会撞上的用途：

**第一，IP 地址冲突检测。** 主机启动或配置新 IP 时，发送免费 ARP。如果收到应答，说明**同一个 IP 已经被另一台设备占用**，当前主机应该报冲突而不是继续使用[reference:8]。

**第二，通知缓存更新。** 当 IP 不变但 MAC 变了（网卡更换、虚拟机迁移、虚拟 IP 漂移到新节点、主备切换），免费 ARP 可以让局域网内的其他设备**尽快把旧 MAC 替换成新 MAC**，而不必等到缓存自然老化[reference:9]。**服务迁移后“新机器收不到流量”的经典问题，往往就是免费 ARP 没有被正确发送或没有被网络接受。**

<br>

### ARP 没有认证：这是设计选择，也是安全边界

<br>

ARP 协议设计于 1982 年，**设计目标是效率，不是安全**。它**无状态、无认证**：一台设备即使**没有发送过 ARP 请求**，也会接受别人主动发来的 ARP 应答（免费 ARP）；**没有机制验证应答的发送者是否真的是它声称的那个 IP 的所有者**；新的 ARP 信息会**自动覆盖**缓存中的旧条目[reference:10][reference:11]。

这个特性直接催生了 **ARP 欺骗（ARP spoofing）** 和 **ARP 中毒（ARP poisoning）** ：攻击者向受害者和网关分别发送伪造的 ARP 应答，把“网关的 IP”绑到攻击者的 MAC，把“受害者的 IP”也绑到攻击者的 MAC。此后双方流量都经过攻击者，形成**中间人（MitM）** 位置，可以嗅探、篡改或丢弃[reference:12]。**ARP 欺骗是局域网内的攻击，前提是攻击者与目标在同一个二层广播域**；跨网段无法直接进行[reference:13]。

**防御的核心思路不是“让 ARP 变安全”——ARP 本身没有安全机制——而是在二层网络上增加验证**。**DAI（Dynamic ARP Inspection，动态 ARP 检测）** 在交换机上拦截 ARP 报文，将其与 **DHCP snooping 绑定表**（IP ↔ MAC ↔ 端口 ↔ VLAN）比对，丢弃伪造的应答[reference:14][reference:15]。此外，静态 ARP 绑定、端口安全、网络分段、端到端加密也是常见的纵深防御手段[reference:16]。

<br>

## 动手实验：用 `tcpdump` 看广播请求与单播应答，用 `arp` 操作缓存

***

### 实验一：`tcpdump` 抓一次完整的 ARP 请求与应答

<br>

**目标**：亲眼看到 ARP 请求以广播发出、应答以单播返回，以及缓存命中和未命中时的差异。

**步骤**：在 Linux 机器上，先清空目标 IP 的 ARP 缓存（用 root），然后在两个终端分别操作。

```bash
# 终端 1：抓 ARP 包（-e 显示以太网头部，便于看到广播/单播 MAC）
sudo tcpdump -n -e -i any arp

# 终端 2：先删除同网段某个 IP 的 ARP 缓存，然后 ping 它触发解析
# 假设同网段目标为 192.0.2.20
sudo arp -d 192.0.2.20
ping -c 1 192.0.2.20
```

> **预期输出（示意）[reference:17]：**
>
> ```text
> aa:bb:cc:dd:ee:01 > ff:ff:ff:ff:ff:ff, ethertype ARP, Request who-has 192.0.2.20 tell 192.0.2.10
> 00:11:22:33:44:55 > aa:bb:cc:dd:ee:01, ethertype ARP, Reply 192.0.2.20 is-at 00:11:22:33:44:55
> ```
>
> 第一行的目的 MAC 是 `ff:ff:ff:ff:ff:ff`（广播），第二行的目的 MAC 是请求方的单播 MAC。

**看到什么说明什么**：**`who-has` 那一行是广播请求，`is-at` 那一行是单播应答**。如果只看到 `who-has` 反复出现、**始终没有 `is-at`**，说明目标 IP 没有主机在应答（或者应答被中间设备拦截），表现为“ARP 解析失败”，上层连接会超时。如果 `is-at` 里的 MAC 和你预期的对端 MAC 不一致，就要怀疑 ARP 缓存被污染或存在代理 ARP。

**按操作码精确过滤**：ARP 头中 `opcode` 位于偏移 6，长度 2 字节。`arp[6:2] = 1` 只抓请求，`arp[6:2] = 2` 只抓应答[reference:18]：

```bash
sudo tcpdump -n -e -i eth0 'arp[6:2] = 1'
sudo tcpdump -n -e -i eth0 'arp[6:2] = 2'
```

<br>

### 实验二：用 `arp -a` 查看缓存，用免费 ARP 触发更新

<br>

**目标**：观察 ARP 缓存的条目状态，并理解免费 ARP 如何主动改写其他设备的缓存。

**查看当前缓存**：

```bash
arp -a
# 或更现代的路由工具：
ip neigh show
```

> **预期输出（示意）：**
>
> ```text
> ? (192.0.2.1) at aa:bb:cc:dd:ee:ff [ether] on eth0
> ? (192.0.2.20) at 00:11:22:33:44:55 [ether] on eth0
> ```

**触发免费 ARP**：在一台 Linux 主机上，**重新启用接口或重新配置 IP** 通常会触发免费 ARP 发送。你也可以手动用 `arping` 发送（如果系统安装了 `iputils-arping`）：

```bash
# 以广播方式发送免费 ARP 宣告（示意，具体参数以 arping 版本为准）
sudo arping -U -c 3 -I eth0 192.0.2.10
```

在另一台同网段机器上用 `tcpdump` 抓包，你会看到**发送方 IP 和目标 IP 都是 `192.0.2.10`** 的 ARP 请求，目的 MAC 是广播地址[reference:19]。**这就是免费 ARP 的形态**。

**看到什么说明什么**：免费 ARP 不期待回答，它的作用是**让收到广播的设备把“192.0.2.10 对应的 MAC”更新为新值**。如果服务迁移后网关没有更新缓存，可以在新主机上触发免费 ARP，**但能否生效取决于网络设备是否接受未经请求的 ARP 更新**（有些安全配置会过滤免费 ARP）。这就是为什么生产环境迁移往往需要网关侧配合清理 ARP 缓存或使用 GARP 工具，而不是只靠主机侧操作。

<br>

### 常见失败原因与解决办法

<br>

| 现象 | 可能原因 | 怎么办 |
|---|---|---|
| `tcpdump` 只看到 `who-has`，没有 `is-at` | 目标 IP 没有主机、目标主机关闭了 ARP 应答、或应答被 ACL 拦截 | 确认目标主机在线且 IP 配置正确；检查中间交换机是否有 ARP 过滤 |
| `arp -a` 中同一个 MAC 对应多个 IP | 可能是 **ARP 欺骗** 或代理 ARP | 对比网关和关键服务器的真实 MAC；结合 `tcpdump` 定位异常应答源 |
| 迁移后流量不跟到新机器 | 旧机器或网关缓存中保留了旧 MAC，免费 ARP 未生效 | 在新主机触发免费 ARP；必要时在网关/交换机侧清除 ARP 缓存或配置 GARP 更新 |
| `arp -d` 提示权限不足 | 删除 ARP 条目需要 root 或 `CAP_NET_ADMIN` | 用 `sudo`；在容器中需要相应 capability |

## 开发启示

***

### 启示一：IP 通但 TCP 不通，把 ARP 加入排查链

<br>

**现象**：`ping` 目标 IP 通，但 `curl` 或 TCP 连接超时；服务端端口在监听，防火墙没有拒绝。

**底层原因**：`ping` 和 TCP 连接**都依赖 ARP 解析同一跳的 MAC**。如果 ARP 缓存中存在**错误但未过期的条目**，或者免费 ARP 更新不完整，某些流量可能走到错误的 MAC 上。**`ping` 的 ICMP 可能恰好触发了新的 ARP 解析而成功，而已建立的 TCP 重传路径仍然使用旧的缓存条目**，表现为“ping 通、TCP 不通”。更深层的情况是 ARP 欺骗：攻击者把网关 IP 绑到自己 MAC，受害者的流量被劫持，`ping` 可能时通时不通。

**可操作动作 / 面试答法**：排障顺序中加入 `arp -a` 或 `ip neigh show`，**检查关键 IP（网关、目标服务器）的 MAC 是否与预期一致**。如果同一个 MAC 对应多个 IP，或网关 MAC 异常，优先怀疑 ARP 污染。面试时不要只说“ARP 是找 MAC 的”，要补一句“**ARP 缓存错误会导致 IP 层可达但链路层交付错误，表现为 ping 通服务不通**”。

<br>

### 启示二：服务迁移/虚拟 IP 漂移，免费 ARP 是必须验证的一步

<br>

**现象**：负载均衡的虚拟 IP 从旧节点漂移到新节点后，部分客户端或网关仍然把流量发给旧节点，新节点收不到请求，旧节点已经下线导致黑洞。

**底层原因**：IP 迁移了，但**局域网内其他设备的 ARP 缓存仍然保留“虚拟 IP → 旧 MAC”的映射**，直到缓存老化或被免费 ARP 强制更新。**免费 ARP 的发送和接受不是“必然成功”的**：新节点可能没有发送免费 ARP，或者发送了但交换机/网关的安全策略将其过滤。生产环境中，LVS 等场景还可能出现虚拟网卡通过 ARP 发布地址、导致上游绑定关系混乱的情况[reference:22]。

**可操作动作 / 面试答法**：把**免费 ARP 发送和验证**作为 IP 迁移流程的一部分，而不是迁移完成后的“可选动作”。在迁移后，从上游网关或同网段机器上检查 `ip neigh show <VIP>` 的 MAC 是否已经指向新节点。如果网络设备过滤免费 ARP，需要在网关侧主动清理缓存或使用管理工具更新。面试时说“**ARP 缓存是 IP 迁移的隐性状态，免费 ARP 是显式的纠正手段，但它的生效依赖二层网络策略**”，比笼统说“发 GARP 就行”更准确。

<br>

### 启示三：面试陷阱——“ARP 是 IP 协议的一部分，跨网段也需要 ARP”

<br>

**常见误解**：既然 ARP 用来把 IP 解析成 MAC，那么任何 IP 通信都需要 ARP 解析**最终目的 IP**。

**正确思路**：**ARP 只在同一个广播域（同一子网/VLAN）内解析最终目的 MAC**。跨网段通信时，主机 ARP 解析的对象是**默认网关或下一跳路由器的 IP**，而不是最终目的 IP。目的 IP 在主机的路由表中决定“下一跳是谁”，ARP 只负责“把下一跳的 IP 变成 MAC”。**最终目的主机的 MAC 在跨网段场景中不可见、也不需要可见**。这也是为什么 ARP 欺骗**只能影响同一个二层广播域**内的通信[reference:23]。

**另一个相邻陷阱**：认为“ARP 缓存永久有效”。实际上 ARP 缓存有状态迁移和老化，`REACHABLE` 条目在默认约 30 秒（随机化 15–45 秒）后会变为 `STALE`，再次使用时会重新验证。**缓存会变，所以 ARP 问题可能是间歇性的**，而不是“要么一直坏、要么一直好”。

**面试答法**：先说“ARP 解析的是下一跳 MAC，不是最终目的 MAC”，再补“所以 ARP 是链路层范围内的机制，跨网段时它解析的是网关；ARP 欺骗也只能在同一广播域内生效”。这样既区分了层次，又解释了安全边界。

<br>

## 小结与下一篇预告

***

回到开头：**同网段另一台机器 `ping` 得通但 TCP 连不上，问题可能不在应用层，而在 ARP 缓存或 ARP 应答**。`ping` 和 TCP 共享同一条链路，但 ARP 缓存的状态可能让不同流量走到不同的 MAC 上。**服务迁移后新机器收不到流量，同样是因为“IP 到了，但链路层仍然指向旧 MAC”** ，免费 ARP 是纠正手段，但它能否生效取决于二层网络是否接受未经请求的 ARP 更新。**ARP 是“IP 找到对方”之后的最后一步，也是开发者最容易跳过的一步；它简单到没有认证，所以排查时必须把缓存和应答源纳入证据链。**

下一篇是应用层到运输层、网络层串讲的收束：**从输入 URL 到页面展示：全链路串讲**。你会把第 1–14 篇的 DNS、TCP、TLS、HTTP、路由、ARP 串成一条完整时序，画出一张从浏览器地址栏到服务器返回首字节的全景图，并分清每个阶段“慢”应该先怀疑谁。

自测问题：

1. ARP 请求和 ARP 应答在以太网帧的目的 MAC 上有什么根本区别？这个区别在抓包时如何用来判断“有没有人应答”？
2. 服务迁移后 IP 不变但 MAC 变了，为什么“新机器已经在运行”不等于“流量会自动跟过来”？免费 ARP 在这里起什么作用，它可能失效的原因是什么？

<br>

<details>
<summary>点击查看自测问题答案</summary>

**第 1 题答案**

- **ARP 请求**的目的 MAC 是**广播地址 `ff:ff:ff:ff:ff:ff`**，因为请求方不知道谁拥有目标 IP，必须让同一广播域内所有设备都收到。**ARP 应答**的目的 MAC 是**请求方的单播 MAC**，因为应答方已经知道是谁在问，直接单播回复[reference:25]。
- **抓包判断**：用 `tcpdump` 看到 `who-has ... tell ...` 且目的 MAC 为广播，是请求；看到 `is-at ...` 且目的 MAC 为单播，是应答。**如果只反复看到 `who-has` 而没有 `is-at`，说明目标没有应答或应答被拦截**，ARP 解析失败，上层连接会超时。

**第 2 题答案**

- **“新机器运行”不等于“流量跟过来”**：IP 迁移了，但局域网内其他设备（尤其是网关）的 **ARP 缓存仍然保留“这个 IP → 旧 MAC”的映射**，直到缓存老化或被免费 ARP 强制更新。新机器在监听端口，但流量在链路层被发到了旧 MAC，新机器根本收不到。
- **免费 ARP 的作用**：新主机主动广播“这个 IP 现在绑定在我的 MAC 上”，让收到广播的设备更新缓存，从而把流量纠正到新机器[reference:26]。
- **可能失效的原因**：网络设备**过滤未经请求的 ARP 更新**（安全策略）；新主机**没有发送免费 ARP**；或者发送了但**交换机/网关不接受**。因此生产环境迁移往往需要网关侧配合清理缓存，而不是只依赖主机侧免费 ARP。
