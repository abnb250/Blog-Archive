## 场景问题

***

第 15 篇给了你一把尺子：DevTools 的 Timing 瀑布图能告诉你“慢在哪一段”。但尺子只能量，不能取证。真实排障中，你经常遇到的是**DevTools 量不到、APM 看不见、日志干干净净，但问题确实存在**的场景。

比如：P99 从 80ms 突然飙到 5s，但 CPU、内存、GC、慢查询全部正常，APM 链路追踪显示“下游服务只处理了 12ms”，**5 秒凭空消失了**。或者：客户端偶发 `Connection reset by peer`，服务端日志没有任何异常，抓包有一个 RST，但你不知道这个 RST 是谁发的。再或者：`dig` 一会儿正常、一会儿返回 `SERVFAIL`，换成 `8.8.8.8` 又好了，过两天又坏了，你始终不知道根因在哪一层。

这一篇不引入新协议，而是**把第 6–14 篇的工具和证据意识串成一条固定的排查链**。三个案例分别对应三类症状：**慢请求、连接失败、DNS 问题**。每一个案例都遵循同一个方法论：**先分层定位“哪一层在说话”，再用抓包拿到“谁、在什么时间、发了什么”的证据，最后才决定修什么**。

## 核心概念

***

### 抓包排障的本质是分层归因，不是“打开 Wireshark 看一眼”

<br>

抓包排障最常见的错误，是**还没确定问题在哪一层就开始读报文**。看到一个 RST，就断定“服务端重置了连接”；看到重传，就断定“网络丢包”。这两种判断都可能错，因为**同一个现象在不同层有不同的解释，而抓包点不同，看到的“事实”也不同**。

正确的顺序是**自顶向下归因**：应用层看 HTTP 状态码和语义，传输层看 TCP 时序、重传、窗口和 RST，网络层看路径和 ICMP，链路层看 ARP 和二层转发。**每一层只回答自己那一层的问题，不越界下结论**。第 15 篇的全链路串讲给了你分段的直觉，这一篇把它变成取证流程。

**一个必须内化的前提：抓包位置决定了你能看到什么。** 在客户端抓包，你看到的是“客户端视角”；在服务端抓包，你看到的是“服务端视角”；在中间设备抓包，你看到的是“路径视角”。**当两端抓包不一致时，差异本身就是证据**——它告诉你问题发生在哪一段路径上，或者哪个中间设备介入过。

<br>

### 慢请求的两条根因线：TCP 重传 vs 零窗口

<br>

慢请求在传输层的证据分两条完全不同的线，**混在一起就会修错方向**。

**重传线**：发送方发出了数据，但在 RTO 或重复 ACK 触发下不得不重发。抓包特征是同序号数据段反复出现，`tshark` 里 `tcp.analysis.retransmission` 或 `tcp.analysis.fast_retransmission` 为真。**根因在路径丢包、乱序或接收端丢弃**，修复方向是查网络路径、MTU、网卡，或者评估拥塞控制算法。

**零窗口线**：接收方通过 ACK 通告窗口为 0，发送方**根本没有发送权限**，只能发零窗口探测。抓包特征是 `tcp.analysis.zero_window` 和周期性的 `zero_window_probe`。**根因在接收端应用读取太慢或缓冲区耗尽**，调发送端的任何重传参数都不会让零窗口消失。

**面试里的关键区分**：**重传是“发了但没被确认”，零窗口是“接收方不让发”** 。两者的证据都在抓包里，但指向完全不同的修复对象。

<br>

### 连接失败不是一种失败：SYN 无应答、RST 拒绝、半开连接

<br>

“连不上”在 TCP 层至少对应三种不同的失败形态，抓包证据和根因方向各不相同。

**SYN 无应答（unanswered SYN）** ：客户端发出 SYN，反复重传，**始终没有 SYN-ACK，也没有 RST**。根因通常是**防火墙静默丢弃（DROP 而非 REJECT）** 、服务器 down、或路由不可达。**没有 RST 是关键证据**：说明路径上有设备在“吞掉”SYN，而不是主动拒绝。

**RST 拒绝**：服务端收到 SYN 后**直接回 RST**，而不是 SYN-ACK。根因是**端口没有进程监听**，或者防火墙规则是 `REJECT`。**RST 的源 IP 需要核实**：它可能来自真正的服务端，也可能来自中间设备。

**半开连接**：服务端发出 SYN-ACK，但客户端**没有回最后的 ACK**，连接停在 `SYN_RECEIVED`。抓包特征是在服务端用 `ss -tn state syn-recv` 看到堆积。根因可能是客户端异常、SYN flood 攻击，或者最后的 ACK 被路径丢弃。

**RST 还有一个隐蔽变体**：连接**已经关闭**之后，收到了迟到的数据段，协议栈会回一个 RST。这种 RST 的 **IP Identification 字段通常为 0**，和正常业务流量的 RST 形态不同，可以作为辅助判断线索。

<br>

### DNS 问题的第一步不是换 8.8.8.8，是区分 NXDOMAIN、SERVFAIL 和 NODATA

<br>

DNS 排障最常见的“玄学”操作是直接换公共 DNS，换了好了就以为解决了。但 **`dig` 的返回状态码本身就在告诉你故障在哪一层**，不读状态码等于放弃了最重要的证据。

**NXDOMAIN**：域名**不存在**。可能是拼写错误，也可能是记录创建在了错误的 zone。**NXDOMAIN 会被负缓存**，权威端后来补上记录，缓存端的“不存在”可能还会持续一段时间。

**SERVFAIL**：解析器**无法给出答案**。原因可能是 DNSSEC 验证失败、权威服务器无响应、zone 配置错误、或上游超时。**遇到 SERVFAIL 的第一个动作是 `dig +cd`** ：如果关闭 DNSSEC 验证后能解析成功，说明问题在 DNSSEC，不在 zone 本身。

**NODATA**：域名**存在，但请求的记录类型没有对应值**。返回的是 `NOERROR` 但 ANSWER 为空。这和 NXDOMAIN 完全不同——域名是存在的，只是你要的 A 记录或 MX 记录不存在。

**一个常用的隔离手段**：用 `dig @1.1.1.1 example.com` 和 `dig @8.8.8.8 example.com` 对比。如果两个解析器给出不同答案，**问题在解析器或缓存层，不在权威端**；如果两个都返回同样的异常状态，问题更可能在权威端或域名配置本身。

<br>

## 动手实验：三个案例，三种证据链

***

### 案例一：慢请求——TCP 重传和零窗口的区分

<br>

**症状**：接口 P99 偶发 5s，应用层指标全部正常，APM 显示下游只花了 12ms，但客户端确实等了 5 秒。

**取证步骤**：在客户端和服务端同时抓包，先粗筛，再精读。

**粗筛：找出耗时异常的 TCP 流。**

```bash
# 在客户端抓包（-s 0 抓完整包，-w 保存到文件）
sudo tcpdump -i eth0 -nn -s 0 -w /tmp/slow.pcap 'tcp port 443'
```

然后用 `tshark` 统计重传和零窗口事件：

```bash
# 重传统计
tshark -r /tmp/slow.pcap -q -z expert,error

# 只看重传的帧
tshark -r /tmp/slow.pcap -Y "tcp.analysis.retransmission || tcp.analysis.fast_retransmission" \
  -T fields -e frame.time -e ip.src -e ip.dst -e tcp.seq

# 只看零窗口
tshark -r /tmp/slow.pcap -Y "tcp.analysis.zero_window || tcp.analysis.zero_window_probe" \
  -T fields -e frame.time -e ip.src -e ip.dst
```

> **预期现象（示意）：**
>
> 如果 `tcp.analysis.retransmission` 命中，你会看到**同一个 Seq 的数据段在时间上重复出现**，间隔逐渐拉大（RTO 指数退避）。如果 `tcp.analysis.zero_window` 命中，你会看到接收方发出的 **Window 为 0 的 ACK**，随后是发送方的 1 字节探测。
>
> **看到重传** → 问题在路径或发送/接收端的丢包处理，**不是“下游服务处理慢”**。**看到零窗口** → 问题在接收端应用读取速度或缓冲区配置，**不是网络丢包**。

**两端对比**：如果客户端抓到了原始段的重传，但服务端**从未收到原始段**，问题在正向路径；如果服务端收到了但 ACK 没有回到客户端，问题在反向路径。**只有两端抓包才能区分方向**。

**清理**：删除临时 pcap 文件即可。如果使用了 `tc netem` 注入丢包来复现，记得删除 qdisc。

<br>

### 案例二：连接失败——RST 是谁发的

<br>

**症状**：客户端偶发 `Connection reset by peer`，服务端业务日志无异常，抓包有一个 RST。

**取证步骤**：在客户端和服务端同时抓包，过滤 SYN 和 RST，对比 RST 的源 IP 和 Identification 字段。

```bash
# 在客户端抓包，只抓 SYN 和 RST
sudo tcpdump -i any -nn -w /tmp/rst-client.pcap \
  'tcp[tcpflags] & (tcp-syn|tcp-rst) != 0 and host 93.184.216.34'

# 在服务端抓包，同样过滤
sudo tcpdump -i any -nn -w /tmp/rst-server.pcap \
  'tcp[tcpflags] & (tcp-syn|tcp-rst) != 0 and host 192.0.2.10'
```

用 `tshark` 提取 RST 的关键字段：

```bash
tshark -r /tmp/rst-client.pcap -Y "tcp.flags.reset == 1" \
  -T fields -e frame.time -e ip.src -e ip.dst -e tcp.srcport -e tcp.dstport -e ip.id
```

> **预期现象（示意）：**
>
> 如果 RST 的 **源 IP 是服务端 IP**，但**服务端抓包中没有对应的 RST 发出**，高度怀疑**中间设备伪造**。一个辅助线索是 **IP Identification（`ip.id`）** ：如果 RST 的 `ip.id` 和紧邻的客户端业务包相同，而不是服务端正常递增的序列，说明这个 RST 可能是中间设备“借用”了客户端的包构造的。
>
> 如果 RST 的 `ip.id` 为 **0**，且连接已经处于关闭状态，可能是**协议栈对迟到报文的保护性响应**，不是业务故障。

**判定顺序**：**先看 RST 源 IP 是不是真正的对端 → 再看两端抓包是否一致 → 最后用 `ip.id` 和 TTL 辅助判断是否中间设备伪造**。仅凭一个 RST 包不能定性，这是 RST 排查最容易犯的错误。

<br>

### 案例三：DNS 问题——状态码和隔离对比

<br>

**症状**：`dig example.com` 时而正常、时而 `SERVFAIL`，应用日志报“域名不存在”。

**取证步骤**：不换 DNS 先读状态码，再用多解析器对比隔离问题层。

```bash
# 第一步：看状态码
dig example.com A

# 如果返回 SERVFAIL，关掉 DNSSEC 验证再试
dig +cd example.com A

# 对比两个上游解析器
dig @1.1.1.1 example.com A +short
dig @8.8.8.8 example.com A +short

# 模拟应用的解析路径（绕过 shell 和浏览器的额外缓存）
getent hosts example.com
```

> **预期现象与判定（示意）：**
>
> - `dig +cd` 成功而普通 `dig` 失败 → **问题在 DNSSEC 验证**，不是 zone 本身。
> - `1.1.1.1` 返回正常 IP、`8.8.8.8` 返回 `NXDOMAIN` → **问题在解析器或缓存层**，权威端可能是正常的。
> - 两个公共解析器都返回 `SERVFAIL` → 问题更可能在**权威端或域名配置**，不是本地网络。
> - `dig` 正常但 `getent hosts` 失败 → 应用侧的解析路径可能被 **hosts 文件、nscd、或运行时缓存**干扰，不是 DNS 本身的问题。

**关于“换 8.8.8.8 就好了”** ：这只能说明**本地递归解析器有问题**，不能说明“DNS 已经修好了”。如果负缓存已经记住了 `NXDOMAIN`，换解析器只是绕开了旧缓存，问题可能还会回来。

<br>

### 常见失败原因与解决办法

<br>

| 现象 | 可能原因 | 怎么办 |
|---|---|---|
| `tshark` 没有 `tcp.analysis.*` 字段 | `tshark` 版本较旧，或抓包文件不完整 | 升级 `tshark`；用 `tcpdump -r` 手动看重复序号 |
| RST 在客户端抓到，服务端抓包没有 | 中间设备伪造或路径上的设备发出的 | 对比 `ip.id` 和 TTL；查防火墙、负载均衡、NAT 日志 |
| `dig +cd` 成功但普通 `dig` SERVFAIL | DNSSEC 验证失败 | 检查 DS/DNSKEY 链；确认权威端签名有效 |
| `dig` 正常但应用仍解析失败 | hosts、运行时缓存、连接池长连接未重新解析 | 查 `/etc/hosts`；查 JVM `networkaddress.cache.ttl`；重启或刷新连接池 |

## 开发启示

***

### 启示一：慢请求的“5 秒消失”，先分清重传还是零窗口，再决定修哪一端

<br>

**现象**：APM 显示下游服务只花了 12ms，但客户端等了 5 秒。应用层指标全部正常，但 P99 确实高了。

**底层原因**：**时间可以“消失”在传输层**。发送方的数据可能因为丢包在等重传（`tcp.analysis.retransmission`），也可能因为接收方窗口为 0 而根本没有发出去（`tcp.analysis.zero_window`）。**这两种慢的根因方向相反**：重传查路径/发送端，零窗口查接收端应用。**APM 只测量“应用处理”的时间，不测量数据在 TCP 缓冲区里等待的时间**，所以 APM 正常不等于端到端正常。

**可操作动作 / 面试答法**：在客户端和服务端同时抓包，**先过滤 `tcp.analysis.flags` 看 Wireshark 自动标出的异常，再区分 `retransmission` 和 `zero_window`**。面试时说“**慢请求在传输层有两条证据线：重传是发了没被确认，零窗口是接收方不让发；先分清哪一条，再决定修哪一端**”，比笼统说“抓包看网络”要准确得多。

<br>

### 启示二：RST 先定位来源，不要直接认定“服务端重置了连接”

<br>

**现象**：客户端偶发 `Connection reset`，服务端日志正常，抓包有一个 RST。

**底层原因**：RST 可能来自**对端应用**（端口关闭、`SO_LINGER=0`、异常退出）、**中间设备**（防火墙 `REJECT`、负载均衡空闲超时、NAT 表项过期），或**协议栈对迟到报文的保护响应**。**“RST 来自服务端 IP”不等于“服务端应用发的”** ——中间设备可以伪造源 IP。`ip.id` 是一个有用的辅助线索：如果 RST 的 `ip.id` 和紧邻的客户端包相同，而不是服务端正常递增的序列，中间设备伪造的可能性更高。

**可操作动作 / 面试答法**：**两端同时抓包**，对比 RST 的源 IP 和 `ip.id`。如果服务端抓包显示它**没有发出过这个 RST**，优先怀疑中间设备。面试时把 RST 翻译成“**一个来源需要被定位的信号**”，而不是“服务端主动关闭了连接”。

<br>

### 启示三：面试陷阱——“换 8.8.8.8 好了，DNS 问题就解决了”

<br>

**常见误解**：DNS 解析异常时换成公共 DNS 就好了，说明问题已经修复。

**正确思路**：换 8.8.8.8 只是**绕开了有问题的本地递归解析器或缓存**，没有修复根因。如果问题在**负缓存**，旧解析器的缓存过期后可能再次异常；如果问题在**DNSSEC 验证**，换一个不验证或验证策略不同的解析器只是掩盖了配置错误。**真正的修复要看 `dig` 的状态码，区分 NXDOMAIN、SERVFAIL 和 NODATA，再用 `+cd` 和多解析器对比隔离到具体层**。

**面试答法**：先说“换 8.8.8.8 是隔离手段，不是修复手段”，再给判定顺序：“**先读状态码 → SERVFAIL 先试 `+cd` 排除 DNSSEC → 对比两个解析器判断是缓存层还是权威层**”。这样既展示了工具，又展示了归因逻辑。

<br>

## 小结与下一篇预告

***

回到开头三个症状：**慢请求的 5 秒可能消失在 TCP 重传或零窗口里**，证据在 `tcp.analysis.retransmission` 和 `tcp.analysis.zero_window`，先分清哪一条再修；**连接失败的 RST 必须先定位来源**，两端抓包对比 `ip.id` 和源 IP，不要默认是服务端发的；**DNS 问题先读状态码**，`SERVFAIL` 先用 `+cd` 排除 DNSSEC，多解析器对比隔离缓存层和权威层。**抓包排障的本质是分层归因：每一层只回答自己那一层的问题，抓包点差异本身就是证据。**

下一篇是系列的收尾：**面试高频与知识地图：接下来学什么**。你会把第 1–16 篇的知识点压缩成一张可复述的地图，用自测清单检查自己哪些章节能讲清楚、哪些还停在“背过”的层面，并拿到后续深入的方向——拥塞控制、QUIC、TLS 1.3、HTTP/3、可观测性。

自测问题：

1. 抓包看到同一个 Seq 的数据段反复出现，和看到接收方通告窗口为 0，分别指向哪条排查线？各自应该修哪一端？
2. RST 的源 IP 是服务端，但服务端抓包显示它没有发出过这个 RST。你的下一步判断是什么？可以用什么辅助字段来支持这个判断？

**第 1 题答案**

- **同一个 Seq 反复出现**：指向**重传线**（`tcp.analysis.retransmission` 或 `fast_retransmission`）。发送方发了数据但没被确认，**根因在路径丢包、乱序，或发送/接收端的丢包处理**。修复方向是查网络路径、MTU、网卡，或评估拥塞控制算法。
- **接收方通告窗口为 0**：指向**零窗口线**（`tcp.analysis.zero_window`）。接收方缓冲区满，发送方**根本没有发送权限**，只能发零窗口探测。**根因在接收端应用读取太慢或缓冲区太小**，修复方向是接收端应用和 socket 缓冲区，不是发送端重传参数。

**第 2 题答案**

- **下一步判断**：高度怀疑 **RST 来自中间设备伪造**（防火墙、负载均衡、NAT），而不是服务端应用。
- **辅助字段**：**IP Identification（`ip.id`）** 。如果 RST 的 `ip.id` 和紧邻的客户端业务包相同，而不是服务端正常递增的序列，说明中间设备可能“借用”了客户端的包来构造 RST。**TTL** 也可以辅助判断路径跳数是否与预期一致。最终确认需要结合两端抓包和中间设备日志。
