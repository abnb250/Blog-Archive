## 小节一：工程化拆解与 CMake 库构建

### 1.1 本节最小必要理论（危机推演式）
**如果不这么做会怎样？**
假设你继续把代码全塞在 `main.cpp` 里，到了 Day 8 你要加定时器和多线程，你会发现 `accept`、`recv`、`epoll_wait` 的逻辑死死纠缠在一起。你想改一个连接的超时处理，结果不小心把监听逻辑改崩了。
更致命的是，到了 Day 9 你想写个压测脚本客户端，你需要一套底层的网络收发代码，结果发现全在 `main` 函数的死循环里，根本抽不出来。
**为什么现在必须引入？**
拆模块是为了“物理隔离”。今天我们就通过 CMake 的 `add_library`，把这 6 个模块打包成一个静态库，以后不管是写服务器还是写测试客户端，直接链接这个库就行。

### 1.2 代码实现与设计意图

```bash
# 创建目录
mkdir -p include/net include/base src/net src/base examples docs tests scripts
```

编写 `CMakeLists.txt`：

```cmake
# =============================================================================
# CMakeLists.txt：项目总装配图（从 .cpp 到可执行程序的完整说明书）。
#
# 本文件组成（自上而下 5 块）：
#   A 工程声明       —— cmake 最低版本、项目名、使用语言
#   B 编译标准       —— 统一 C++17，且必须是标准 C++
#   C 全局编译/链接选项 —— 对所有目标生效：警告、调试、Sanitizer、产物目录、头文件路径
#   D 库目标         —— reactor_net（静态库）：网络层可复用单元
#   E 可执行目标     —— reactor_skeleton：示例程序，链接 D
#
# 【设计意图】库（实现）+ 可执行（使用）两层拆分：
#   以后再加 examples 或测试程序，只需 link 一下 reactor_net，不必复制 .cpp。
# =============================================================================


# ---- 块 A：工程声明 ----
# 作用：声明最低 CMake 版本、工程名、使用的语言。
# 【常见坑】cmake_minimum_required 必须是第一条有效命令，否则报错。
cmake_minimum_required(VERSION 3.16)
project(cpp-reactor-server LANGUAGES CXX)


# ---- 块 B：编译标准 ----
# 作用：统一全工程的 C++ 标准，避免不同编译器行为不一致。
set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
# 【设计意图】关闭 GNU 扩展，强制标准 C++，保证代码在 clang/gcc 下表现一致。
set(CMAKE_CXX_EXTENSIONS OFF)


# ---- 块 C：全局编译 / 链接选项 ----
# 作用：对所有目标生效的“全局开关”，分 4 小类。
#       注意：此处对“全工程”生效；更规范写法是用 target_* 按目标设置。

# ---- C1 编译选项 ----
# 作用：开警告 + 带调试信息 + 关优化 + 挂 Sanitizer。
# 【常见坑】-fsanitize 在编译和链接时都要带上，否则链接会报 undefined reference to __asan_init
set(CMAKE_CXX_FLAGS "${CMAKE_CXX_FLAGS} -Wall -Wextra -g -O0 -fsanitize=address,undefined")

# ---- C2 链接选项 ----
# 作用：把 Sanitizer 的运行时库链接进可执行文件（与 C1 配对出现）。
set(CMAKE_EXE_LINKER_FLAGS "${CMAKE_EXE_LINKER_FLAGS} -fsanitize=address,undefined")

# ---- C3 产物目录 ----
# 作用：所有可执行文件统一输出到 <build>/bin，保持源码目录干净。
set(CMAKE_RUNTIME_OUTPUT_DIRECTORY ${CMAKE_BINARY_DIR}/bin)

# ---- C4 头文件搜索路径 ----
# 作用：把 include/ 加入全局搜索路径，使 #include "net/EventLoop.h" 能被找到。
include_directories(${CMAKE_SOURCE_DIR}/include)


# ---- 块 D：库目标 reactor_net（静态库）----
# 作用：把网络层 6 个实现文件打包成可复用的静态库 libreactor_net.a。
#       按目录分两层：src/base/ 为基础设施，src/net/ 为网络层核心。
# 【设计意图】把网络层打包成静态库，避免以后写多个可执行文件时反复复制 .cpp 文件。
add_library(reactor_net
    # —— 基础设施层 ——
    src/base/Buffer.cpp

    # —— 网络层：事件驱动核心 ——
    src/net/Channel.cpp
    src/net/EpollPoller.cpp
    src/net/EventLoop.cpp

    # —— 网络层：连接管理 ——
    src/net/Acceptor.cpp
    src/net/TcpConnection.cpp
)


# ---- 块 E：可执行目标 reactor_skeleton ----
# 作用：把 examples 下的 main 编成可执行文件，并链接块 D 的库。
# 【常见坑】add_executable 必须写在 add_library 之后，否则 target_link_libraries
#           找不到 reactor_net，会报 “Target ... links to target not found”。
add_executable(reactor_skeleton examples/reactor_skeleton.cpp)
target_link_libraries(reactor_skeleton PRIVATE reactor_net)
```

## 小节二：EventLoop 与 Channel 的解耦绑定

### 2.1 本节最小必要理论（危机推演式）
**如果不这么做会怎样？**
在 Day 2 的代码里，`epoll_wait` 返回后，你只能拿到一个 `int` 类型的 `fd`（比如 4 号）。然后你写了一大串 `if (fd == 4) { 读操作 } else if (fd == 5) { 写操作 }`。
现在才几个客户端，到 Day 14 如果有 1 万个并发，你难道要写一万个 `if-else` 吗？
**为什么现在必须引入？**
我们需要一个叫 `Channel` 的东西，它的作用就是“认领” fd。`Channel` 记录着“我对应的 fd 是谁”、“可读时该调哪个回调”、“可写时该调哪个回调”。
而 `EventLoop` 是包工头，它不关心具体干什么，只负责拿着监听到的 `Channel` 列表，挨个喊：“哎，你的事发生了，去执行你的回调吧。”

### 2.2 代码实现与设计意图

编写 `include/net/Channel.h`：

```cpp
// =============================================================================
// Channel：一个 fd + 关心的事件 + 事件回调 的打包对象。
//
// 本文件组成（自上而下 5 块）：
//   A 头文件保护与依赖     —— 防重复展开 + 引入 uint32_t / std::function
//   B 命名空间与前向声明   —— 划定 reactor 命名空间，前向声明 EventLoop
//   C public 接口（5 小类）—— Channel 对外的全部能力
//       C1 类型别名   EventCallback          —— 统一回调类型
//       C2 构造/析构  Channel(loop,fd) / ~Channel() —— 生命周期入口
//       C3 访问器     fd()                   —— 只读暴露本对象代表的 fd
//       C4 回调设置   setReadCallback / setCloseCallback —— 使用方注入回调
//       C5 行为方法   enableReading / handleEvent —— 与 EventLoop 的握手接口
//   D private 区（1 方法 + 4 组数据）—— Channel 内部靠什么支撑 C 区
//       D0 内部方法   update()               —— 把关心的事件同步给 poller
//       D1 环境组     loop_                  —— 属于哪个 EventLoop
//       D2 身份组     fd_                    —— 代表哪个 fd
//       D3 状态组     events_ / revents_     —— 关心什么 / 实际发生什么
//       D4 回调组     readCallback_ / closeCallback_ —— 事件到了调谁
//   E 命名空间收尾         —— 与 B 的 namespace 配对
//
// 【设计意图】把“fd → 回调”的映射封进对象，
//   EventLoop 拿到 Channel* 直接 handleEvent()，无需自己查表分发。
// =============================================================================
#pragma once
#include <cstdint>
#include <functional>

// ---- 块 B：命名空间与前向声明 ----
// 作用：划定 namespace reactor，并用前向声明引入 EventLoop 类型名。
// 【设计意图】loop_ 只存指针，前向声明即可，避免与 EventLoop.h 循环包含。
namespace reactor {
class EventLoop;

// ---- 块 C：public 接口 ----
// 作用：Channel 对外暴露的全部能力，按 5 小类排列。
class Channel {
public:
    // ---- C1 类型别名 ----
    // 作用：给 std::function<void()> 起短名，供 C4 / D4 共用。
    // 【设计意图】将来改签名只动这一处。
    using EventCallback = std::function<void()>;
    // 【面试考点】为什么 void()？回调是“一个动作”，fd 由对象自己记着，无需传参。

    // ---- C2 构造 / 析构 ----
    // 作用：构造绑定 loop 与 fd；析构留空，明确“我不拥有 fd”。
    Channel(EventLoop* loop, int fd);
    ~Channel(); // 【常见坑】不要 close(fd_)——Channel 不拥有 fd，谁创建谁 close。

    // ---- C3 访问器 ----
    // 作用：只读暴露 fd，供 EventLoop 做 map 查找 / 打日志。
    int fd() const { return fd_; }

    // ---- C4 回调设置器 ----
    // 作用：由使用方（Acceptor / TcpConnection）注入回调。
    // 【设计意图】Channel 不决定“事件到了做什么”，只负责调用。
    void setReadCallback(EventCallback cb) { readCallback_ = std::move(cb); }
    void setCloseCallback(EventCallback cb) { closeCallback_ = std::move(cb); }

    // ---- C5 行为方法 ----
    // 作用：enableReading 向 loop 注册关心的事件；handleEvent 由 loop 回调我。
    // 【设计意图】这两个方法构成 EventLoop ↔ Channel 的握手协议。
    void enableReading();
    void handleEvent(uint32_t revents);

private:
    // ---- 块 D：private 区 ----
    // 作用：1 个内部方法 + 4 组数据，按职责分组排列，便于对号入座。

    // ---- D0 内部方法 ----
    // 作用：把 events_ 的“关心位”同步给 EpollPoller。
    void update();

    // ---- D1 环境组 ----
    // 作用：记录所属 EventLoop，注册/注销都经它转发。
    EventLoop* loop_;

    // ---- D2 身份组 ----
    // 作用：记录本对象代表的 fd；只借用，不关闭。
    int fd_;

    // ---- D3 状态组 ----
    // 作用：events_ 存“关心什么”，revents_ 存“实际发生什么”。
    // 【常见坑】两者只差一个 r，极易写反；命名改成 interest_/ready_ 更防错。
    uint32_t events_ = 0;
    uint32_t revents_ = 0;

    // ---- D4 回调组 ----
    // 作用：存放 C4 注入的回调，由 handleEvent 按 revents_ 分派。
    // 【面试考点】回调里若 delete 了 Channel 自身，返回后不能再访问 this。
    EventCallback readCallback_;
    EventCallback closeCallback_;
};

// ---- 块 E：命名空间收尾 ----
// 作用：与 B 的 namespace 配对，标明 reactor 作用域结束。
} // namespace reactor
```

编写 `src/net/Channel.cpp`：

```cpp
// =============================================================================
// Channel.cpp：Channel 的实现文件（对应 Channel.h 的接口，这里写具体行为）。
//
// 本文件组成（自上而下 4 块）：
//   A 头文件包含   —— 自身头文件 + 依赖头文件 + 标准库
//   B 构造 / 析构  —— 绑定 loop 与 fd；析构留空（不拥有 fd）
//   C 对外行为实现 —— enableReading / handleEvent（EventLoop 调用的入口）
//   D 内部方法实现 —— update()（同步事件给 EpollPoller，当前空实现）
//
// 【设计意图】骨架阶段只打日志、不写真实 epoll 逻辑：
//   先用桩实现验证调用链（main → EventLoop → Channel）能跑通，
//   真正的 epoll_ctl 留到 Day 5/6 再填。
// =============================================================================

// ---- 块 A：头文件包含 ----
// 作用：自身头文件保证声明与定义一致；EventLoop.h 因 update() 将来要用完整类型；
//       <iostream> 供骨架阶段打印。
#include "net/Channel.h"
#include "net/EventLoop.h"
#include <iostream>

// ---- 块 B：构造 / 析构 ----
// 作用：构造仅绑定 loop 与 fd；析构为空，明确不 close fd。
namespace reactor {
Channel::Channel(EventLoop* loop, int fd) : loop_(loop), fd_(fd) {}
Channel::~Channel() {} 
// 【常见坑】这里不写 close(fd_)——Channel 不拥有 fd，谁创建谁 close。

// ---- 块 C：对外行为实现 ----
// 作用：EventLoop 与 Channel 的两个握手接口，骨架阶段只打印，验证调用链通了。

void Channel::enableReading() {
    // 【设计意图】这里未来会去操作 epoll，今天先打个日志证明接口通了。
    std::cout << "Channel: 准备监听 fd " << fd_ << " 的读事件" << std::endl;
}

void Channel::handleEvent(uint32_t revents) {
    // 【设计意图】未来按 revents 的位分派到 readCallback_ / closeCallback_。
    std::cout << "Channel: fd " << fd_ << " 发生事件 " << revents << std::endl;
}

// ---- 块 D：内部方法实现 ----
// 作用：update() 预留给“把 events_ 同步给 EpollPoller”，当前空实现。
void Channel::update() {}
} // namespace reactor
```

编写 `include/net/EventLoop.h`：

```cpp
// =============================================================================
// EventLoop.h：事件循环（Reactor 的心脏），持有 EpollPoller，负责“等事件 → 分发”。
//
// 本文件组成（自上而下 4 块）：
//   A 头文件保护与依赖   —— 防重复展开 + 引入 <memory>（unique_ptr）
//   B 命名空间与前向声明 —— 划定 reactor；前向声明 EpollPoller / Channel
//   C public 接口        —— 构造/析构 + loop() / updateChannel()
//   D private 数据成员   —— 只持有一个成员：独占持有的 poller_
//
// 【设计意图】EventLoop 只做“调度”，不存 fd/回调；
//   具体 fd、事件、回调都封在 Channel 里，它只持有“等待器” EpollPoller。
// =============================================================================
#pragma once
#include <memory>

// ---- 块 B：命名空间与前向声明 ----
// 作用：划定 namespace reactor，并用前向声明引入两个依赖类型名。
// 【设计意图】头文件里只出现二者的指针/引用，前向声明足够，
//   可避免与 EpollPoller.h / Channel.h 循环包含，也加快编译。
namespace reactor {
class EpollPoller;
class Channel;

// ---- 块 C：public 接口 ----
// 作用：EventLoop 对外暴露的全部能力，按“生命周期 + 两个核心行为”排列。
class EventLoop {
public:
    // ---- C1 构造 / 析构 ----
    // 作用：构造时创建 poller；析构必须在 .cpp 里实现（原因见下方常见坑）。
    EventLoop();
    ~EventLoop(); // 【常见坑】如果这里写 = default，会报 incomplete type（因为 EpollPoller 是前向声明）

    // ---- C2 行为方法 ----
    // 作用：loop() 是主循环入口；updateChannel() 供 Channel 增删时转发给 poller。
    void loop();
    void updateChannel(Channel* channel);

private:
    // ---- 块 D：private 数据成员 ----
    // 作用：用 unique_ptr 独占持有 poller，实现 RAII：构造创建、析构自动释放。
    // 【设计意图】unique_ptr 表达“EventLoop 是 poller 的唯一拥有者”；
    //   也因此析构函数不能写在头文件里——见 C1 的常见坑。
    std::unique_ptr<EpollPoller> poller_;
};

} // namespace reactor
```

### 2.3 现象追踪与验证
编写 `examples/reactor_skeleton.cpp`：

```cpp
// =============================================================================
// reactor_skeleton.cpp：示例程序（可执行目标 reactor_skeleton 的 main 所在文件）。
//
// 本文件组成（自上而下 3 块）：
//   A 头文件包含   —— 只引“用得到的”头文件（EventLoop / Channel / iostream）
//   B main() 装配  —— 4 步：构造 loop → 构造 channel → 注册关心的事件 → 启动 loop
//   C 返回与析构   —— 栈对象按声明逆序自动析构（RAII）
//
// 【设计意图】本文件不实现任何网络逻辑，只做“组装 + 驱动”：
//   把 reactor_net 库里的组件按正确顺序拼起来跑一遍，证明骨架可用。
//   后续新增 examples 时，只要 link 一下 reactor_net，无需复制任何 .cpp。
// =============================================================================

// ---- 块 A：头文件包含 ----
// 作用：使用方需完整定义（要 new 栈对象、调成员函数），所以包含具体头文件；
//       头文件之间互相只用前向声明，耦合在 .cpp 侧才展开。
#include "net/EventLoop.h"
#include "net/Channel.h"
#include <iostream>

int main() {
    // ---- 块 B：main() 装配 ----
    // 作用：按 4 步搭起最小 Reactor 骨架。
    //   ① 构造事件循环          ② 构造事件通道
    //   ③ 声明关心的事件        ④ 启动循环
    // 【设计意图】4 步是所有 Reactor 程序的最小骨架；
    //   写真实服务器时顺序不变，只是 ②③ 换成 Acceptor 注册监听 fd、
    //   以及每来一个连接新建一个 TcpConnection。

    // ① 构造事件循环：内部会 make_unique<EpollPoller>() 创建“等待器”，
    //    此时还没有任何 fd 被注册，循环也还没跑。
    reactor::EventLoop loop;
    
    // ② 构造事件通道：把“fd + 关心事件 + 回调”打包成对象；
    //    参数分别是“属于哪个 loop”和“代表哪个 fd”。
    // 模拟一个 fd 为 3 的连接
    reactor::Channel mock_channel(&loop, 3);

    // ③ 声明关心的事件：告诉 Channel “fd=3 可读时请通知我”。
    //    骨架版只打印一行日志；真实版本会写 events_ 并调 update() 同步给 poller。
    mock_channel.enableReading();
    
    // 打印标记：证明 main 已走到“启动循环”之前。
    std::cout << "reactor skeleton ok" << std::endl;

    // ④ 启动事件循环：骨架版只打印一次就返回（不做死循环，保证程序能退出）；
    //    真实版本会在此一直循环：epoll_wait → 就绪 fd → 分发到对应 Channel。
    loop.loop();

    // ---- 块 C：返回与析构 ----
    // 【常见坑】栈对象按声明逆序析构：mock_channel 先于 loop 析构——
    //   恰好安全，因为 Channel 只持 loop 的指针，loop 必须活得更久。
    //   若把 loop 声明放到 channel 之后，channel 析构时 loop_ 会成悬空指针。
    return 0;
}
```

## 小节三：职责边界——Acceptor 与 TcpConnection

### 3.1 本节最小必要理论（危机推演式）
**如果不这么做会怎样？**
如果你把 `accept` 拿到新连接 `fd`，以及 `recv` 处理数据的逻辑全写在一个类里，那到了 Day 12 你搞多线程时，主线程负责 `accept`，从线程负责 `recv`，你的代码就会互相打架、疯狂加锁。
**为什么现在必须引入？**
职责分离！让 `Acceptor` 只干一件事：死死盯着监听端口，一有新连接就生下来。让 `TcpConnection` 干另一件事：接管连接后的生命周期、收发数据、断开清理。今天只需要把它们的头文件框架搭出来，定义好接口边界。

### 3.2 代码实现与设计意图

编写 `include/net/Acceptor.h`：

```cpp
// =============================================================================
// Acceptor.h：监听器——“接客的门”，负责建监听 socket、accept 新连接，把新 fd 甩给上层。
//
// 本文件组成（自上而下 4 块）：
//   A 头文件保护与依赖   —— 防重复展开 + 引入 functional / memory
//   B 命名空间与前向声明 —— 划定 reactor；前向声明 EventLoop / Channel
//   C public 接口        —— 类型别名 / 构造析构 / listen() / setNewConnectionCallback()
//   D private 区         —— D0 handleRead() + D1~D4 四组数据（环境/监听/通道/回调）
//
// 【设计意图】Acceptor 的职责止于“拿到新 fd”：
//   自己不处理读写，也不认识 TcpConnection，只通过回调把 fd 交给上层，
//   模块边界清晰、可独立复用。
// =============================================================================
#pragma once
#include <functional>
#include <memory>

// ---- 块 B：命名空间与前向声明 ----
// 作用：划定 namespace reactor，并前向声明两个依赖类型名。
// 【设计意图】loop_ 只是指针，acceptChannel_ 只在头文件里作为 unique_ptr 的模板参数，
//   二者都只需前向声明；完整定义留给 Acceptor.cpp（构造/析构 unique_ptr 时才需要）。
namespace reactor {
class EventLoop;
class Channel;

// ---- 块 C：public 接口 ----
// 作用：Acceptor 对外暴露的全部能力，按“回调类型 → 生命周期 → 启动 → 注入回调”排列。
class Acceptor {
public:
    // ---- C1 类型别名 ----
    // 作用：定义“新连接到来”事件的统一回调类型。
    // 【设计意图】只暴露“新建了连接”的事件，把刚 accept 的 fd 扔给上层去处理。
    // 【面试考点】为什么传 int 而不是 TcpConnection*？——Acceptor 不该依赖上层类型；
    //   传 fd 让 Acceptor 与 TcpConnection 完全解耦，谁消费由上层决定。
    using NewConnectionCallback = std::function<void(int sockfd)>;

    // ---- C2 构造 / 析构 ----
    // 作用：构造记录 loop 与端口；析构负责 close(listenFd_)。
    //   析构必须在 .cpp 里实现——acceptChannel_ 是 unique_ptr<Channel>，
    //   而 Channel 在头文件里只是前向声明（同 EventLoop.h 那个坑）。
    Acceptor(EventLoop* loop, int port);
    ~Acceptor();

    // ---- C3 启动监听 ----
    // 作用：一次性完成 socket → bind(port) → listen → 包成 Channel → 注册进 loop。
    void listen();

    // ---- C4 注入回调 ----
    // 作用：上层（TcpServer）把“如何处理新 fd”注入进来。
    void setNewConnectionCallback(NewConnectionCallback cb) { newConnectionCallback_ = std::move(cb); }

private:
    // ---- 块 D：private 区 ----
    // 作用：D0 核心动作 + D1~D4 四组数据，按职责分组便于对号入座。

    // ---- D0 核心动作 ----
    // 作用：acceptChannel_ 可读时被回调，accept() 出新 fd 后交给 newConnectionCallback_。
    // 【常见坑】一次可读可能对应多个就绪连接；骨架里先 accept 一个，
    //   生产实现通常配合循环 accept 直到 EAGAIN（ET 模式下必须如此）。
    void handleRead(); // 监听 fd 可读 -> accept

    // ---- D1 环境组 ----
    // 作用：记录注册到哪个 EventLoop（只持指针，不拥有）。
    EventLoop* loop_;

    // ---- D2 监听资源组 ----
    // 作用：监听 socket 的 fd；Acceptor 拥有它，析构时 close。
    //   -1 表示“尚未创建”的标志值。
    int listenFd_ = -1;

    // ---- D3 事件通道组 ----
    // 作用：把 listenFd_ 包成 Channel 以便被 EventLoop 调度；unique_ptr 表示独占持有。
    std::unique_ptr<Channel> acceptChannel_;

    // ---- D4 向上回调组 ----
    // 作用：新连接到来时把 fd 甩给上层。
    NewConnectionCallback newConnectionCallback_;
};
} // namespace reactor
```

编写 `include/net/TcpConnection.h`：

```cpp
// =============================================================================
// TcpConnection.h：一条已建立 TCP 连接的对象化表示（fd + 两类回调）。
//
// 本文件组成（自上而下 4 块）：
//   A 头文件保护与依赖   —— 防重复展开 + 引入 functional / memory
//   B 命名空间与前向声明 —— 划定 reactor；前向声明 EventLoop / Channel / Buffer
//   C public 接口        —— 类型别名 / 构造析构 / fd() / 两个 setCallback
//   D private 区         —— D0 三个事件处理函数 + D1~D3 三组数据（环境/身份/回调）
//
// 【设计意图】TcpConnection 只做“一条连接”的三件事：
//   收数据（handleRead）、发数据（handleWrite）、断开清理（handleClose），
//   然后把“收到数据 / 连接关闭”两个业务事件通过回调上报，不处理业务本身。
//   它不负责 accept（那是 Acceptor），也不决定业务逻辑（那是 TcpServer / 示例）。
// =============================================================================
#pragma once
#include <functional>
#include <memory>

// ---- 块 B：命名空间与前向声明 ----
// 作用：划定 namespace reactor，并前向声明三个依赖类型名。
// 【设计意图】loop_ 只持指针、三个 handleXxx 的形参也只出现 Buffer*，
//   头文件里都不需要完整定义，前向声明足够，可减少头文件耦合、加快编译。
namespace reactor {
class EventLoop;
class Channel;
class Buffer;

// ---- 块 C：public 接口 ----
// 作用：TcpConnection 对外暴露的全部能力，按“回调类型 → 生命周期 → fd → 注入回调”排列。
class TcpConnection {
public:
    // ---- C1 类型别名 ----
    // 作用：定义“收到数据”和“连接断开”两个业务事件的统一回调类型。
    // 【面试考点】Day 4 先用 int 替代 shared_ptr 传参，等 Day 8 真正引入生命周期管理再升级。
    //   ——为什么用 Buffer* 不传 std::string：避免每次回调都拷贝数据；
    //   ——为什么传 int 不传 TcpConnection*：回调里拿不到对象指针，就无法安全删除自身。
    using MessageCallback = std::function<void(int sockfd, Buffer*)>;
    using CloseCallback = std::function<void(int sockfd)>;

    // ---- C2 构造 / 析构 ----
    // 作用：构造接管一个已 accept 的 fd；析构负责 close(fd_)。
    //   与 Channel / Acceptor 不同，TcpConnection **拥有**这条连接，
    //   所以这里确实要 close。骨架阶段暂无 unique_ptr 成员，析构可先留 .cpp。
    TcpConnection(EventLoop* loop, int sockfd);
    ~TcpConnection();

    // ---- C3 访问器 ----
    // 作用：给上层一个稳定的“连接标识”，用于 map 查找 / 打日志。
    int fd() const { return fd_; }

    // ---- C4 回调设置器 ----
    // 作用：由上层（TcpServer）注入两个业务回调；Channel 不决定业务。
    void setMessageCallback(MessageCallback cb) { messageCallback_ = std::move(cb); }
    void setCloseCallback(CloseCallback cb) { closeCallback_ = std::move(cb); }

private:
    // ---- 块 D：private 区 ----
    // 作用：D0 三个事件处理函数 + D1~D3 三组数据，按“事件 → 支撑数据”分组排列。

    // ---- D0 事件处理函数 ----
    // 作用：未来由内部 Channel 的可读/可写/关闭回调触发，分别做 recv / send / 清理。
    //   命名规则 handleXxx = “Xxx 事件发生了，我要做什么”。
    // 【设计意图】三条 handle 对应 epoll 的三类事件（EPOLLIN / EPOLLOUT / EPOLLHUP|ERR），
    //   骨架阶段为空实现，Day 5/6 与 Channel 接上后填实。
    void handleRead();   // 连接 fd 可读 -> recv
    void handleWrite();  // 连接 fd 可写 -> send
    void handleClose();  // 连接断开

    // ---- D1 环境组 ----
    // 作用：记录注册到哪个 EventLoop（只持指针，不拥有）。
    EventLoop* loop_;

    // ---- D2 身份组 ----
    // 作用：本连接的 socket fd；TcpConnection 拥有它，析构时 close。
    int fd_;

    // ---- D3 向上回调组 ----
    // 作用：把“有数据 / 断开”两个业务事件告知上层，具体怎么处理由上层决定。
    MessageCallback messageCallback_;
    CloseCallback closeCallback_;
};
} // namespace reactor
```

## 小节四： 总结与提交
***
### 4.1 一句话总结作用：
- EventLoop：驱动整个服务器运转的事件循环发动机，一个线程一个。
- EpollPoller：封装底层 epoll 系统调用的黑盒情报员，只负责向内核要活跃事件。
- Channel：把底层 fd 和上层业务回调绑定在一起的桥梁。
- Acceptor：只负责监听端口并 accept 迎接新客人，绝不碰聊天（读写）。
- TcpConnection：管理一条已建立连接的完整生命周期（收发数据、断开清理）。
- Buffer：解决 TCP 字节流粘包/半包的输入输出应用层仓库。

EventLoop 驱动 EpollPoller 监听内核，有事件发生后通过 Channel 分发回调：如果是新连接，交由 Acceptor 接收并创建 TcpConnection；如果是已连数据，交由 TcpConnection 配合 Buffer 完成收发。
