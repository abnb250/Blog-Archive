## 小节一：Channel 事件位管理——从“只会读”到“能读能写能出错”
***

### 1.1 本节最小必要理论（危机推演式）

**如果不补全会怎样？**

Day 5 的 `handleEvent` 只写了：

```cpp
if (revents & EPOLLIN) { if (readCallback_) readCallback_(); }
```

问题有三个，今天不补，Day 8 写 `TcpConnection` 会直接卡死：

1. **`send` 返回 `EAGAIN` 时你没有任何出路**。Day 3 你已经踩过这个坑——发送缓冲区满了，只能丢数据打日志。真正的解法是“注册 `EPOLLOUT`，等内核可写再发”，而 `EPOLLOUT` 要 `enableWriting()` 才能注册。`Channel` 不会写事件位，Day 8 的 `TcpConnection` 就没法“等可写”。
2. **对端关闭/出错时你收不到通知**。连接被 `RST`、对端 `close` 后你继续 `recv`，`errno` 变 `ECONNRESET`，你现在只能当“真错误”处理，没有专门的关闭回调入口，清理逻辑散得到处都是。
3. **一个 fd 可能同时可读 + 可写 + 出错**。`epoll_wait` 返回的 `events` 是**位图**，不是枚举值。你只判 `EPOLLIN`，`EPOLLOUT` 和 `EPOLLERR` 就被静默吞掉。

**大白话**：`Channel` 是“这个 fd 关心什么、发生了什么、该叫谁”的登记簿。今天把登记簿的三栏（`events_` 关心位、`revents_` 发生位、三个回调）全部填齐。

<br>

### 1.2 代码实现与设计意图

改 `include/net/Channel.h`（全文替换，改动点已标出）：

```cpp
// =============================================================================
// Channel.h：一个 fd + 关心的事件 + 三类回调 的打包对象（Reactor 的分发单元）。
//
// 本文件组成（自上而下 5 块）：
//   A 头文件保护与依赖     —— 防重复展开 + epoll 事件位 + function/cstdint
//   B 命名空间与前向声明   —— 划定 reactor；前向声明 EventLoop
//   C public 接口（5 小类）—— 类型别名 / 生命周期 / 访问器 / 回调注入 / 事件位操作
//   D private 区           —— 1 个内部方法 + 4 组数据
//   E 命名空间收尾
//
// 【设计意图】Channel 只认“事件位 → 回调”，不认识监听/连接的业务差异；
//   业务差异全部由使用方注入的回调表达。
// =============================================================================
#pragma once
#include <cstdint>
#include <functional>
#include <sys/epoll.h>

// ---- 块 B：命名空间与前向声明 ----
namespace reactor {
class EventLoop;

// ---- 块 C：public 接口 ----
class Channel {
public:
    // ---- C1 类型别名 ----
    using EventCallback = std::function<void()>;

    // ---- C2 构造 / 析构 ----
    // 【常见坑】析构今天要调 remove()，所以析构必须写进 .cpp（loop_ 需要完整类型）。
    Channel(EventLoop* loop, int fd);
    ~Channel();

    // ---- C3 访问器 ----
    int fd() const { return fd_; }
    // 给 EpollPoller 读“关心位”，Day 5 已加，今天继续用
    uint32_t events() const { return events_; }

    // ---- C4 回调注入 ----
    // 三个回调各管一类事件：可读 / 可写 / 关闭或出错
    void setReadCallback(EventCallback cb)  { readCallback_  = std::move(cb); }
    void setWriteCallback(EventCallback cb) { writeCallback_ = std::move(cb); }
    void setCloseCallback(EventCallback cb) { closeCallback_ = std::move(cb); }

    // ---- C5 事件位操作 ----
    // 作用：改 events_ 的位，再 update() 同步给 epoll。
    // 【设计意图】enableXxx / disableXxx 成对出现，调用方不必手写位运算。
    void enableReading();
    void enableWriting();
    void disableWriting();
    void disableAll();

    // 作用：把自己从 epoll 摘掉（Day 6 新增，见小节二）
    void remove();

    // 作用：事件到了，按 revents 位分派到回调（由 EventLoop 调用）
    void handleEvent(uint32_t revents);

private:
    // ---- 块 D：private 区 ----
    // D0 内部方法：把 events_ 同步给 EventLoop
    void update();

    // D1 环境组
    EventLoop* loop_;      // 只持指针，不拥有
    // D2 身份组
    int fd_;               // 只借用，不 close
    // D3 状态组
    // 【常见坑】events_/revents_ 只差一个 r；改名叫 interest_/ready_ 更防错。
    uint32_t events_  = 0; // 我关心什么
    uint32_t revents_ = 0; // 实际发生了什么（handleEvent 时写入）
    // D4 回调组
    EventCallback readCallback_;
    EventCallback writeCallback_;
    EventCallback closeCallback_;
};

} // namespace reactor
```

改 `src/net/Channel.cpp`（全文替换）：

```cpp
// =============================================================================
// Channel.cpp：Channel 的实现，本节把事件位操作补全 + handleEvent 改成完整位分派。
//
// 本文件组成（自上而下 4 块）：
//   A 头文件包含      —— 自身头文件 + EventLoop.h
//   B 构造 / 析构     —— 构造绑定 loop/fd；析构调 remove()（见小节二）
//   C 事件位操作      —— enableReading / enableWriting / disableWriting / disableAll
//   D 分发实现        —— handleEvent 按位分派到三类回调
//
// 【设计意图】事件位操作只做两件事：改位 + update()；
//   Channel 不碰 epoll_ctl，同步动作一律转交 EventLoop。
// =============================================================================
#include "net/Channel.h"
#include "net/EventLoop.h"

namespace reactor {

// ---- 块 B：构造 / 析构 ----
Channel::Channel(EventLoop* loop, int fd) : loop_(loop), fd_(fd) {}
// 【常见坑】析构必须调 remove()：Channel 死了但 fd 还挂在 epoll 里，
//   内核把 fd 复用给新连接后，epoll_wait 会把事件投给这个已析构对象 → UAF。
Channel::~Channel() { remove(); }

// ---- 块 C：事件位操作 ----
void Channel::enableReading() {
    events_ |= EPOLLIN;     // 追加“可读”位
    update();
}

void Channel::enableWriting() {
    // 【面试考点】EPOLLOUT 默认几乎一直就绪（发送缓冲区空就触发），
    //   所以只在“确实有数据发不出去”时才 enableWriting，发完立即 disableWriting。
    events_ |= EPOLLOUT;
    update();
}

void Channel::disableWriting() {
    // 【常见坑】~EPOLLOUT 会把其他位也清掉，必须先 & 再取反
    events_ &= ~EPOLLOUT;
    update();
}

void Channel::disableAll() {
    events_ = 0;
    update();
}

void Channel::remove() {
    loop_->removeChannel(this);
}

void Channel::update() {
    loop_->updateChannel(this);
}

// ---- 块 D：分发实现 ----
void Channel::handleEvent(uint32_t revents) {
    revents_ = revents;

    // 【面试考点】EPOLLHUP(挂断) / EPOLLERR(错误) 不需要注册也会被报告，
    // 这是 epoll 的特性：内核主动告诉你这个 fd 坏了。
    // 这两个事件你没法通过 epoll_ctl 去「订阅」或「取消」，内核只在 revents 里报给你
    // 【设计意图】错误/挂断优先处理并直接返回，避免在“已坏”的连接上继续 recv/send。
    if (revents & (EPOLLHUP | EPOLLERR)) { //错误优先
        if (closeCallback_) closeCallback_();
        return;
    }
    // EPOLLRDHUP：对端关闭写端；LT 下 EPOLLIN 也会触发，但显式列出来更好读
    // EPOLLPRI  : 带外数据（OOB/紧急数据）可读
    if (revents & (EPOLLIN | EPOLLPRI | EPOLLRDHUP)) {
        if (readCallback_) readCallback_();
    }
    if (revents & EPOLLOUT) {
        if (writeCallback_) writeCallback_();
    }
}

} // namespace reactor
```

**面试官问**：“你的 Channel 是怎么管理事件的？”

**你回答**：“`Channel` 内部维护两个位图：`events_` 是‘我关心的’，`revents_` 是‘本次实际发生的’。对外提供 `enableReading / enableWriting / disableWriting` 成对接口，内部只做位运算 + 调 `update()` 同步给 epoll。`handleEvent` 收到内核返回的位图后，按位分派：`EPOLLHUP|EPOLLERR` 走关闭回调并直接返回，`EPOLLIN|EPOLLRDHUP` 走读回调，`EPOLLOUT` 走写回调。这里有个关键设计：`EPOLLERR` 和 `EPOLLHUP` 不需要注册也会被 epoll 上报，所以必须优先处理，否则会在已失效的连接上继续读写。”

## 小节二：Channel 的摘除——remove / 析构自动 DEL
***
### 2.1 本节最小必要理论（危机推演式）

**如果不做会怎样？**

Day 5 的代码里，`Channel` 只有一个“注册”入口，没有“注销”入口。你 `close(fd)` 之后，epoll 里还挂着这个 fd 的注册项。会发生什么？

```text
1. 连接 fd=5 关闭 → close(5)
2. 新客户端连上 → 内核把 fd=5 复用给新连接
3. 新连接有数据到达 → epoll_wait 返回 data.fd=5
4. EpollPoller 查表 channels_[5] → 拿到的是【旧的 Channel 对象】
5. 旧 Channel 可能已经析构 → handleEvent 访问野指针 → 段错误
```

这就是 **UAF（Use-After-Free）**，而且是那种“跑一百次不炸、演示时炸一次”的偶发 bug，GDB 抓起来极其痛苦。

**结论**：`epoll_ctl(EPOLL_CTL_DEL)` 必须在 `close(fd)` **之前**发生，而且必须**自动**发生——靠人记得调 `remove()` 是不可靠的，因为 `Channel` 可能被 `unique_ptr` 析构、被栈回滚析构、被异常路径析构。今天就把 `remove()` 写进 `~Channel()`。

<br>

### 2.2 代码实现与设计意图

`Channel::remove()` 已在上一节写好，本节补两处：

**改动 1**：`include/net/EventLoop.h` 的 public 区加一行声明：

```cpp
// ---- C2 行为方法 ----
void loop();
void updateChannel(Channel* channel);
void removeChannel(Channel* channel);   // Day 6 新增
```

**改动 2**：`src/net/EventLoop.cpp` 加实现：

```cpp
void EventLoop::removeChannel(Channel* channel) {
    // 【设计意图】与 updateChannel 对称：EventLoop 只做转发，不碰 epoll 细节。
    poller_->removeChannel(channel);
}
```

**改动 3**：`src/net/EpollPoller.cpp` 的 `removeChannel` 加“未注册就返回”的判断（关键，否则 `Channel` 没 `enableReading` 就析构会调到 `epoll_ctl DEL` 一个不存在的 fd）：

```cpp
void EpollPoller::removeChannel(Channel* channel) {
    int fd = channel->fd();
    auto it = channels_.find(fd);
    // 【常见坑】Channel 构造后没 enableReading 就析构，或已 remove 过，直接返回。
    //   不加这行，epoll_ctl DEL 一个未注册 fd 返回 ENOENT，你会误以为是 bug。
    if (it == channels_.end()) return;

    epoll_ctl(epfd_, EPOLL_CTL_DEL, fd, nullptr);
    channels_.erase(it);
}
```

```cpp
// day6_remove_test.cpp：验证 Channel 析构会自动从 epoll 摘除 fd。

// 本文件组成（自上而下 3 块）：
//   A 头文件包含   —— Reactor 组件 + unistd
//   B main 装配    —— 建 loop + 建管道拿一对 fd + 栈上建 Channel
//   C 生命周期验证 —— 内层作用域结束 → Channel 析构 → strace 看到 DEL
//
// 【设计意图】用 pipe() 拿一对 fd 当“假连接”，避免开端口和 nc，
//   让验证只聚焦“析构 → DEL”这一件事。
// =============================================================================
#include "net/EventLoop.h"
#include "net/Channel.h"
#include <unistd.h>
#include <cstdio>

int main() {

        ch.enableReading();

    }   // ← 作用域结束：~Channel() → remove() → EPOLL_CTL_DEL

    printf("[day6] channel destroyed, fd=%d should be removed from epoll\n", fds[0]);
    close(fds[0]);
    close(fds[1]);
    return 0;
}
```

### 2.4 面试表达话术

**面试官问**：“连接关闭时你怎么保证 epoll 里不残留已关闭的 fd？”

**你回答**：“我把摘除动作写进了 `Channel` 的析构函数，形成 RAII：`~Channel()` 里调 `remove()`，`remove()` 转给 `EventLoop::removeChannel`，再转给 `EpollPoller::removeChannel`，最终执行 `epoll_ctl(EPOLL_CTL_DEL)` 并从 `fd → Channel*` 映射表里擦除。这样无论 `Channel` 是被 `unique_ptr` 析构、栈回滚析构还是异常路径析构，摘除都不会漏。而 `close(fd)` 我放在使用方（`TcpConnection` 的析构）里，顺序是先 `remove` 再 `close`——因为 `epoll_ctl` 用的是 fd 编号，先 `close` 的话 fd 可能已被内核复用，DEL 就会摘掉别人的连接。”

## 小节三：监听 fd + 连接 fd 双 Channel 联调

### 3.1 本节最小必要理论（危机推演式）

**为什么现在必须做这个联调？**

到现在为止你只验证过“监听 fd 一个 Channel”。但 Reactor 的核心设计是：**一个 fd 对应一个 Channel，所有 fd 共享同一个 `EventLoop`**。监听 fd 和连接 fd 走的是**同一个 `Channel` 类、同一个 `handleEvent`、同一个 `EventLoop::loop`**，区别只在于“回调里干什么”。

如果今天不验证，Day 7 写 `Acceptor` 时你会以为 `accept` 出的新连接需要特殊处理；Day 8 写 `TcpConnection` 时你会在“监听 Channel”和“连接 Channel”之间搞混注册时机。今天用 30 行代码把这件事钉死：**监听 fd 的 Channel 回调用 accept 建新 Channel，连接 fd 的 Channel 回调用 recv/send**。

**为什么注册 `EPOLLOUT` 会触发 `EPOLL_CTL_MOD`？**

`EpollPoller::updateChannel` 里用 `channels_.find(fd)` 判断 ADD 还是 MOD。第一次 `enableReading()` → ADD；紧接着 `enableWriting()` → 已在 map 里 → MOD。这是 Day 5 写好的自动切换逻辑，今天第一次真正跑到 MOD 分支——必须亲眼看到。

<br>

### 3.2 代码实现与设计意图

新建 `examples/day6_channel_test.cpp`：

```cpp
// =============================================================================
// day6_channel_test.cpp：Day 6 验证程序——监听 fd 与连接 fd 各占一个 Channel。
//
// 本文件组成（自上而下 4 块）：
//   A 头文件包含      —— Reactor 组件 + socket 系统调用
//   B 工具函数        —— set_nonblocking / create_listenfd（Day 2 同款）
//   C make_connection —— 给新 fd 建 Channel，挂三组回调，注册进 EventLoop
//   D main 装配       —— 监听 Channel + 容器 + 启动 loop
//
// 【设计意图】这是“双 Channel”的最小验证：监听 fd 的 Channel 读回调里 accept，
//   连接 fd 的 Channel 读回调里 echo、写回调里 disableWriting、关闭回调里清理。
//   Day 7 有 Acceptor、Day 8 有 TcpConnection 后，本文件删除。
// =============================================================================
#include "net/EventLoop.h"
#include "net/Channel.h"
#include <sys/socket.h>
#include <netinet/in.h>
#include <arpa/inet.h>
#include <fcntl.h>
#include <unistd.h>
#include <signal.h>
#include <cerrno>
#include <cstdio>
#include <cstdlib>
#include <memory>
#include <vector>

// ---- 块 B：工具函数（Day 2 同款）----
static int set_nonblocking(int fd) {
    int flags = fcntl(fd, F_GETFL, 0);
    if (flags == -1) return -1;
    return fcntl(fd, F_SETFL, flags | O_NONBLOCK);
}

static int create_listenfd(int port) {
    int listenfd = socket(AF_INET, SOCK_STREAM, 0);
    if (listenfd < 0) { perror("socket"); exit(1); }
    int opt = 1;
    setsockopt(listenfd, SOL_SOCKET, SO_REUSEADDR, &opt, sizeof(opt));
    sockaddr_in addr{};
    addr.sin_family = AF_INET;
    addr.sin_addr.s_addr = htonl(INADDR_ANY);
    addr.sin_port = htons(port);
    if (bind(listenfd, (sockaddr*)&addr, sizeof(addr)) < 0) {
        perror("bind"); exit(1);
    }
    if (listen(listenfd, SOMAXCONN) < 0) {
        perror("listen"); exit(1);
    }
    if (set_nonblocking(listenfd) < 0) {
        perror("set_nonblocking"); exit(1);
    }
    return listenfd;
}

// 关闭一条连接：先摘除注册，再 close，顺序不能反
// 【设计意图】close 后 fd 可能被复用，此时再 DEL 会摘掉别人的注册。
static void close_connection(reactor::Channel* ch) {
    int fd = ch->fd();
    ch->remove();     // EPOLL_CTL_DEL + 擦除映射
    close(fd);        // 真正关闭 fd
    printf("[day6] fd=%d closed\n", fd);
}

// ---- 块 C：make_connection ----
// 作用：给一个刚 accept 的 fd 建 Channel，挂读/写/关闭三组回调。
// 【设计意图】连接对象放进 conns 容器统一持有；本程序不做连接生命周期管理，
//   关闭后对象留在容器里（Day 8 用 shared_ptr 重做），这样回调里析构自身的问题就不会出现。
static void make_connection(reactor::EventLoop* loop, int connfd,
                            std::vector<std::unique_ptr<reactor::Channel>>& conns) {
    auto ch = std::make_unique<reactor::Channel>(loop, connfd);
    reactor::Channel* raw = ch.get();

    // 读回调：recv → echo；返回 0 或真错误 → close_connection
    raw->setReadCallback([raw]() {
        char buf[4096];
        ssize_t n = recv(raw->fd(), buf, sizeof(buf), 0);
        if (n > 0) {
            // MSG_NOSIGNAL：对端已关时不触发 SIGPIPE
            ssize_t w = send(raw->fd(), buf, n, MSG_NOSIGNAL);
            printf("[day6] fd=%d echo %zd/%zd bytes\n", raw->fd(), w, n);
        } else if (n == 0) {
            printf("[day6] fd=%d peer closed (recv=0)\n", raw->fd());
            close_connection(raw);
        } else {
            if (errno == EAGAIN || errno == EWOULDBLOCK) return;  // LT 下正常
            if (errno == EINTR) return;
            perror("recv");
            close_connection(raw);
        }
    });

    // 写回调：证明 EPOLLOUT 分派通了；打印后立即 disableWriting
    // 【面试考点】EPOLLOUT 是“几乎一直就绪”的事件，不 disable 会空转烧 CPU。
    raw->setWriteCallback([raw]() {
        printf("[day6] fd=%d EPOLLOUT fired, disableWriting\n", raw->fd());
        raw->disableWriting();
    });

    // 关闭回调：EPOLLHUP / EPOLLERR
    raw->setCloseCallback([raw]() {
        printf("[day6] fd=%d EPOLLHUP/ERR\n", raw->fd());
        close_connection(raw);
    });

    raw->enableReading();
    raw->enableWriting();   // 故意注册，验证 ADD → MOD 切换

    conns.push_back(std::move(ch));
}

// ---- 块 D：main 装配 ----
int main() {
    signal(SIGPIPE, SIG_IGN);

    int listenfd = create_listenfd(8888);
    printf("[day6] listenfd=%d\n", listenfd);

    reactor::EventLoop loop;
    std::vector<std::unique_ptr<reactor::Channel>> conns;

    reactor::Channel listenChannel(&loop, listenfd);
    listenChannel.setReadCallback([&]() {
        // 【常见坑】LT 下监听 fd 可读可能对应多个就绪连接，必须循环 accept 到 EAGAIN
        for (;;) {
            sockaddr_in cli{};
            socklen_t len = sizeof(cli);
            int connfd = accept4(listenfd, (sockaddr*)&cli, &len,
                                 SOCK_NONBLOCK | SOCK_CLOEXEC);
            if (connfd < 0) {
                if (errno == EAGAIN || errno == EWOULDBLOCK) break;
                if (errno == EINTR) continue;
                perror("accept4");
                break;
            }
            char ipbuf[INET_ADDRSTRLEN];
            inet_ntop(AF_INET, &cli.sin_addr, ipbuf, sizeof(ipbuf));
            printf("[day6] accept connfd=%d from %s:%d\n",
                   connfd, ipbuf, ntohs(cli.sin_port));
            make_connection(&loop, connfd, conns);
        }
    });

    listenChannel.enableReading();
    printf("[day6] entering event loop...\n");
    loop.loop();
    return 0;
}
```

### 3.3 现象追踪与验证

**第一步：编译 + `strace` 启动**

```bash
cmake -S . -B build
cmake --build build -j4

# 终端 1
strace -e trace=epoll_ctl,epoll_wait,accept4,recvfrom,sendto ./build/bin/day6_channel_test
```

**预期输出（启动阶段）**：

```text
[day6] listenfd=3
[day6] entering event loop...
epoll_ctl(4, EPOLL_CTL_ADD, 3, {events=EPOLLIN, data={u32=3,...}}) = 0
epoll_wait(4,  <阻塞>
```

**第二步：终端 2 用 nc 连上**

```bash
nc 127.0.0.1 8888
```

**预期终端 1 依次输出**（顺序很重要）：

```text
epoll_wait(4, [{events=EPOLLIN, data={u32=3,...}}], 1024, -1) = 1
accept4(3, {sa_family=AF_INET, sin_port=htons(54321), ...}, [16], SOCK_NONBLOCK|SOCK_CLOEXEC) = 5
[day6] accept connfd=5 from 127.0.0.1:54321
epoll_ctl(4, EPOLL_CTL_ADD, 5, {events=EPOLLIN, data={u32=5,...}}) = 0       ← enableReading
epoll_ctl(4, EPOLL_CTL_MOD, 5, {events=EPOLLIN|EPOLLOUT, data={u32=5,...}}) = 0  ← enableWriting
epoll_wait(4, [{events=EPOLLOUT, data={u32=5,...}}], 1024, -1) = 1
[day6] fd=5 EPOLLOUT fired, disableWriting
epoll_ctl(4, EPOLL_CTL_MOD, 5, {events=EPOLLIN, data={u32=5,...}}) = 0       ← disableWriting
epoll_wait(4,  <继续阻塞>
```

**关键观察（三条，务必亲眼确认）**：

1. **两次 `epoll_ctl` 类型不同**：第一次 `ADD`（监听 fd 3 注册）、第二次 `ADD`（连接 fd 5 首次注册）、第三次 `MOD`（连接 fd 5 追加 EPOLLOUT）。这就证明了 `EpollPoller::updateChannel` 的 ADD/MOD 自动切换逻辑是对的。
2. **`EPOLLOUT` 立刻返回**：因为发送缓冲区是空的，`EPOLLOUT` 一直就绪。这就是为什么写回调里必须 `disableWriting()`——不 disable 就是死循环空转。
3. **`data.u32=5` 与注册时一致**：epoll 原样回传你的私有数据，这就是 `fd → Channel` 映射能成立的前提。

**第三步：终端 2 输入 `hello` 回车**

**预期终端 1**：

```text
epoll_wait(4, [{events=EPOLLIN, data={u32=5,...}}], 1024, -1) = 1
recvfrom(5, "hello\n", 4096, 0, NULL, NULL) = 6
[day6] fd=5 echo 6/6 bytes
sendto(5, "hello\n", 6, MSG_NOSIGNAL, NULL, 0) = 6
epoll_wait(4,  <继续阻塞>
```

终端 2 应看到 `hello` 回显。注意 `strace` 显示的是 `recvfrom/sendto`——glibc 底层用它们实现 `recv/send`，不是 bug。

**第四步：终端 2 按 `Ctrl+C` 断开**

**预期终端 1**：

```text
epoll_wait(4, [{events=EPOLLIN|EPOLLRDHUP, data={u32=5,...}}], 1024, -1) = 1
recvfrom(5, "", 4096, 0, NULL, NULL) = 0
[day6] fd=5 peer closed (recv=0)
epoll_ctl(4, EPOLL_CTL_DEL, 5, NULL) = 0                                    ← remove()
[day6] fd=5 closed
```

**关键观察**：`DEL` 出现在 `close` 之前——这是小节二讲的顺序。同时服务端**不崩**、ASan **无报错**。

**第五步：断开后再开一个 nc**

```bash
nc 127.0.0.1 8888
```

如果内核把 fd=5 复用给新连接，你会看到新的 `epoll_ctl(EPOLL_CTL_ADD, 5, ...)`——而**旧的 Channel 不会收到事件**，因为它已经从 epoll 摘除。这就是小节二那个 UAF bug 被修复的直接证据。

**第六步：录 debug-log**

```bash
cat >> docs/debug-log.md <<'EOF'
## Day 6: Channel 析构未 remove 导致 epoll 残留

### 现象
连接关闭后 close(fd)，但没从 epoll 摘除。客户端反复连接/断开 100 次后，
偶发段错误，GDB backtrace 指向 Channel::handleEvent，但该 Channel 已析构。

### 定位
strace -e epoll_ctl 观察，close(fd) 之后没有 EPOLL_CTL_DEL。
fd 被内核复用给新连接后，epoll_wait 把事件投给旧 Channel 的 data.fd，
EpollPoller 查 channels_ 拿到悬空指针 → UAF。

### 修复
~Channel() 调用 remove()；EpollPoller::removeChannel 加“未注册直接返回”判断。

### 验证
strace 确认 EPOLL_CTL_DEL 出现在 close 之前；反复连接 100 次 ASan 无报错。
EOF
```

### 3.4 面试表达话术

**面试官问**：“一个 fd 对应一个 Channel 是什么意思？监听和连接有什么区别？”

**你回答**：“`Channel` 是 fd 和回调的绑定对象，一个 fd 只能对应一个 `Channel`，否则事件分发就会歧义。监听 fd 和连接 fd 走的是**完全相同的** `Channel` 类和 `handleEvent` 路径，区别只在注入的回调：监听 Channel 的读回调里循环 `accept4`，新 fd 再建一个 Channel；连接 Channel 的读回调里 `recv` 做业务、写回调里处理 `EAGAIN` 剩余数据、关闭回调里做清理。这种设计的价值在于 `EventLoop` 只认 `Channel*`，完全不区分监听还是连接，所以 Day 12 做多线程 Reactor 时，只要把连接 Channel 分配给不同 sub EventLoop，主循环代码一行不用改。”
