## 小节一：Acceptor 骨架——把监听逻辑从 main 里抽出来
***
### 1.1 本节最小必要理论（危机推演式）

**如果不这么做会怎样？**
假设你把 `socket/bind/listen` 和 `accept4` 继续塞在 `main.cpp` 里。Day 8 你要建 `TcpConnection`，accept 回来的 connfd 得交给谁管理？Day 12 你要做多线程 Reactor，主线程只负责 accept、sub EventLoop 负责读写——如果 accept 逻辑散在 main 里，你拿什么去给主线程当“模块”用？

**为什么现在必须引入 Acceptor？**
`Acceptor` 的职责就一句话：**“监听 fd 的专属管家”**——它拥有 listenfd、把它包成 `Channel`、注册到 `EventLoop`，只做 accept 这一件事。谁要新连接，通过回调拿走 fd，Acceptor 不关心后面读写。这样 Day 8 你把回调换成“创建 TcpConnection”，Acceptor 一行都不用改。

Acceptor 只干一件事：listenfd 可读 → 循环 accept4 → 拿到 connfd。  
拿到 connfd 之后呢？Acceptor 不知道，也不该知道。  
Acceptor 是底层机制，它不依赖上层任何具体类型（连 TcpConnection 的头文件都不用 include）；  
它只依赖一个函数签名。上层想干什么就塞什么进来。  

<br>

### 1.2 代码实现与设计意图

先写头文件 `include/net/Acceptor.h`：

```cpp
// =============================================================================
// Acceptor：监听 fd 的专属管家。
//
// 本文件组成（自上而下 4 块）：
//   A 头文件保护与依赖   —— 引入 <functional>（回调）、<memory>（unique_ptr）、<netinet/in.h>（sockaddr_in）
//   B 命名空间与前向声明 —— 前向声明 EventLoop / Channel，避免头文件循环包含
//   C public 接口        —— 构造/析构 + 回调设置 + listen() + listenfd() 访问器
//   D private 区         —— 内部 handleRead() + createListenFd() + 四个成员
//
// 【设计意图】Acceptor 只做一件事：accept。新连接怎么处理由上层回调决定。
//   今天回调里只打印；Day 8 换成“创建 TcpConnection”，Acceptor 无需改动。
// =============================================================================
#pragma once
#include <functional>
#include <memory>
#include <netinet/in.h>

// ---- 块 B：命名空间与前向声明 ----
// 作用：划定 reactor 作用域；EventLoop / Channel 只在指针里出现，前向声明足够。
// 【设计意图】避免 Acceptor.h 去 include EventLoop.h / Channel.h，减少编译依赖。
namespace reactor {
class EventLoop;
class Channel;

// ---- 块 C：public 接口 ----
class Acceptor {
public:
    // ---- C1 类型别名 ----
    // 作用：新连接回调签名——把 connfd 和客户端地址交给上层。
    // 【面试考点】为什么带 sockaddr_in 而不是 string？零拷贝、避免在热路径里做字符串转换。
    using NewConnectionCallback =
        std::function<void(int sockfd, const sockaddr_in& peerAddr)>;

    // ---- C2 构造 / 析构 ----
    Acceptor(EventLoop* loop, int port);
    ~Acceptor();

    // ---- C3 回调设置 ----
    void setNewConnectionCallback(NewConnectionCallback cb);

    // ---- C4 行为方法 ----
    // 作用：listen() 开始监听并把 listenfd 注册进 EventLoop。
    void listen();
    bool listening() const { return listening_; }

    // ---- C5 访问器 ----
    // 作用：只读暴露 listenfd，供 main 打日志 / 测试用。
    int listenfd() const { return listenfd_; }

private:
    // ---- 块 D：private 区 ----
    // 作用：2 个内部方法 + 5 组数据。

    // ---- D0 内部方法 ----
    // 作用：监听 fd 可读时被 Channel 回调，循环 accept4 到 EAGAIN。
    void handleRead();

    // ---- D1 工具方法 ----
    // 作用：socket/bind/listen/setNonBlocking 一条龙，返回非阻塞 listenfd。
    // 【设计意图】监听 fd 的创建属于 Acceptor 职责，不外泄到 main。
    static int createListenFd(int port);

    // ---- D2 环境组 ----
    EventLoop* loop_;

    // ---- D3 身份组 ----
    int listenfd_;

    // ---- D4 通道组 ----
    // 作用：把 listenfd 包成 Channel，注册读事件。
    // 【设计意图】Channel 的 readCallback 指向 handleRead()，形成
    //   EventLoop → Channel → Acceptor::handleRead 的调用链。
    std::unique_ptr<Channel> acceptChannel_;

    // ---- D5 回调组 ----
    NewConnectionCallback newConnectionCallback_;

    bool listening_ = false;
};

} // namespace reactor
```

再写 `src/net/Acceptor.cpp`，今天只写“骨架 + accept 循环 + 打印客户端地址”：

```cpp
// =============================================================================
// Acceptor.cpp：Acceptor 的实现文件。
//
// 本文件组成（自上而下 4 块）：
//   A 头文件包含     —— 自身头 + EventLoop/Channel 依赖 + 系统调用头
//   B 工具函数       —— setNonBlocking + createListenFd
//   C 构造 / 析构    —— 建 listenfd、包 Channel、设置 read 回调
//   D 行为实现       —— listen() + handleRead()（今天核心）
//
// 【设计意图】今天 handleRead 只 accept4 + 调用 newConnectionCallback_，
//   回调里只打印；不创建 TcpConnection、不读写、不碰 Buffer。
// =============================================================================

// ---- 块 A：头文件包含 ----
// 作用：自身头保证声明/定义一致；EventLoop.h、Channel.h 因构造里要 make_unique。
#include "net/Acceptor.h"
#include "net/EventLoop.h"
#include "net/Channel.h"

#include <sys/socket.h>
#include <netinet/in.h>
#include <arpa/inet.h>
#include <fcntl.h>
#include <unistd.h>
#include <cerrno>
#include <cstdio>
#include <cstdlib>

namespace reactor {

// ---- 块 B：工具函数 ----
// 作用：把 Day 2 的 set_nonblocking / create_listenfd 搬进 Acceptor 内部。
static int setNonBlocking(int fd) {
    int flags = fcntl(fd, F_GETFL, 0);
    if (flags == -1) return -1;
    return fcntl(fd, F_SETFL, flags | O_NONBLOCK);
}

int Acceptor::createListenFd(int port) {
    int fd = socket(AF_INET, SOCK_STREAM, 0);
    if (fd < 0) { perror("socket"); exit(1); }

    // 【常见坑】不加 SO_REUSEADDR，Ctrl+C 后立刻重启报 Address already in use
    int opt = 1;
    setsockopt(fd, SOL_SOCKET, SO_REUSEADDR, &opt, sizeof(opt));

    sockaddr_in addr{};
    addr.sin_family = AF_INET;
    addr.sin_addr.s_addr = htonl(INADDR_ANY);
    addr.sin_port = htons(port);
    if (bind(fd, (sockaddr*)&addr, sizeof(addr)) < 0) { perror("bind"); exit(1); }
    if (listen(fd, SOMAXCONN) < 0) { perror("listen"); exit(1); }

    // 【常见坑】listenfd 非阻塞，否则 handleRead 的 accept 循环第一轮就卡死
    if (setNonBlocking(fd) < 0) { perror("setNonBlocking"); exit(1); }
    return fd;
}

// ---- 块 C：构造 / 析构 ----
// 作用：构造时建 listenfd、包 Channel、把 read 回调接到 handleRead。
Acceptor::Acceptor(EventLoop* loop, int port)
    : loop_(loop),
      listenfd_(createListenFd(port)),
      acceptChannel_(std::make_unique<Channel>(loop, listenfd_)) {
    // 【设计意图】lambda 捕获 this，把 Channel 的读事件接到 Acceptor::handleRead。
    acceptChannel_->setReadCallback([this]() { handleRead(); });
}

Acceptor::~Acceptor() {
    // 【常见坑】先 reset Channel（从 epoll 摘除），再 close(listenfd_)，顺序反了会 EBADF
    acceptChannel_.reset();
    close(listenfd_);
}

void Acceptor::setNewConnectionCallback(NewConnectionCallback cb) {
    newConnectionCallback_ = std::move(cb);
}

// ---- 块 D：行为实现 ----

void Acceptor::listen() {
    listening_ = true;
    // 【设计意图】把 listenfd 注册进 epoll，关注 EPOLLIN；
    //   由 Channel::enableReading() → EventLoop::updateChannel → EpollPoller::updateChannel 完成。
    acceptChannel_->enableReading();
}

void Acceptor::handleRead() {
    // 【设计意图】listenfd 可读 = 至少有一个完成三次握手的连接；
    //   必须循环 accept4 直到 EAGAIN，一次 epoll_wait 只接一个会堆积。
    for (;;) {
        sockaddr_in peer{};
        socklen_t len = sizeof(peer);
        // 【常见坑】accept 返回的新 fd 默认阻塞；accept4 直接带 SOCK_NONBLOCK + SOCK_CLOEXEC
        int connfd = accept4(listenfd_, (sockaddr*)&peer, &len,
                             SOCK_NONBLOCK | SOCK_CLOEXEC);
        if (connfd < 0) {
            if (errno == EAGAIN || errno == EWOULDBLOCK) break;  // 取完了
            if (errno == EINTR) continue;                        // 信号打断，重试
            perror("accept4");
            break;
        }

        if (newConnectionCallback_) {
            newConnectionCallback_(connfd, peer);   // 今天回调里只打印
        } else {
            // 【设计意图】没设回调就主动 close，防止 fd 泄漏——养成习惯。
            close(connfd);
        }
    }
}

} // namespace reactor
```

## 小节二：把 Acceptor 接入 EventLoop——让 accept 被 epoll 驱动
***
### 2.1 本节最小必要理论（危机推演式）

**如果不这么做会怎样？**
Acceptor 有了，但它不会自己动——没有 `EventLoop::loop()` 里的 `epoll_wait`，`handleRead` 永远没人调。今天必须把整条调用链跑通：

```
epoll_wait 返回
  → 找到 listenfd 对应的 Channel
  → Channel::handleEvent()
  → readCallback_()
  → Acceptor::handleRead()
  → 循环 accept4
  → newConnectionCallback_() 打印客户端地址
```

**为什么现在必须跑通？**
Day 8 你要把“打印”换成“创建 TcpConnection 并把 connfd 注册到 epoll”——如果今天这条链不通，Day 8 你会发现新连接根本没被 epoll 管理，调试时根本分不清是 accept 问题还是 Channel 注册问题。

<br>

### 2.2 代码实现与设计意图

写 `examples/reactor_acceptor.cpp`：

```cpp
// =============================================================================
// reactor_acceptor.cpp：Day 7 示例——用 Acceptor 接受新连接，只打印不读写。
//
// 本文件组成（自上而下 3 块）：
//   A 头文件包含   —— EventLoop / Acceptor / 打印依赖
//   B main 装配   —— 3 步：建 loop → 建 acceptor 设回调 → listen + loop
//   C 回调实现     —— 拿到 connfd 和 peer 地址，inet_ntop 打印，close 掉
//
// 【设计意图】今天回调里必须 close(connfd)——
//   因为我们还没建 TcpConnection 管理 fd，不 close 就泄漏。
//   Day 8 换成 TcpConnection::create，fd 由连接对象接管。
// =============================================================================

// ---- 块 A：头文件包含 ----
#include "net/EventLoop.h"
#include "net/Acceptor.h"

#include <arpa/inet.h>
#include <cstdio>
#include <unistd.h>

// ---- 块 B：main 装配 ----
int main() {
    reactor::EventLoop loop;
    reactor::Acceptor acceptor(&loop, 8888);

    printf("acceptor listening on 8888, listenfd=%d\n", acceptor.listenfd());

    // ---- 块 C：回调实现 ----
    acceptor.setNewConnectionCallback([](int connfd, const sockaddr_in& peer) {
        // 【设计意图】inet_ntop 线程安全；inet_ntoa 返回静态缓冲区，多线程必炸。
        char ip[INET_ADDRSTRLEN];
        inet_ntop(AF_INET, &peer.sin_addr, ip, sizeof(ip));
        printf("new conn fd=%d from %s:%d\n", connfd, ip, ntohs(peer.sin_port));

        // 【常见坑】今天不读不写，必须 close；Day 8 交给 TcpConnection 管理
        close(connfd);
    });

    acceptor.listen();   // 把 listenfd 注册进 epoll
    loop.loop();         // 进入 epoll_wait 循环

    return 0;
}
```

### 2.3 现象追踪与验证

```bash
cmake -S . -B build
cmake --build build -j4
```

**预期**：`build/bin/reactor_acceptor` 生成成功。

先单客户端验：

```bash
# 终端 1
./build/bin/reactor_acceptor
# 预期：acceptor listening on 8888, listenfd=3

# 终端 2
nc 127.0.0.1 8888
```

**预期终端 1 输出**：

```text
acceptor listening on 8888, listenfd=3
new conn fd=6 from 127.0.0.1:xxxxx
```

**关键点**：`listenfd=3`、`epfd=4`（EventLoop 内部建的）、`connfd=6`——你能从数字上看到“监听 fd 复用了，connfd 每次递增”。这就是为什么必须 close。

再用 `strace` 亲眼看到 `accept4` 被调用，建立“epoll → accept”的因果链：

```bash
# 终端 3
sudo strace -f -e trace=accept4,epoll_wait ./build/bin/reactor_acceptor
# 另开终端 nc 一下
nc 127.0.0.1 8888
```

**预期 strace 输出**：

```text
epoll_wait(4, [{EPOLLIN, {u32=3, u64=3}}], 1024, -1) = 1
accept4(3, {sa_family=AF_INET, sin_port=htons(54321), sin_addr=inet_addr("127.0.0.1")}, [16], SOCK_NONBLOCK|SOCK_CLOEXEC) = 6
```

**看到这两行就锁死**：`epoll_wait` 返回 `u32=3`（listenfd）→ 紧接着 `accept4` 被调用 → 返回 `6`。整条调用链被 strace 抓了个现行。

<br>

### 2.4 面试表达话术

**面试官问**：“新连接是怎么到你服务器代码里的？”

**你回答**：“监听 fd 注册在 epoll 上关注 EPOLLIN。当内核完成三次握手把连接挂到 accept 队列，epoll_wait 会返回这个 fd 可读；EventLoop 找到对应的 Channel 调用 handleEvent，触发 Acceptor::handleRead，里面循环 accept4 直到 EAGAIN。这样新连接就被拉进用户态了，接下来注册到 sub EventLoop 交给 TcpConnection 管理。”

## 小节三：多客户端验收 + 一个都不能丢
***
### 3.1 本节最小必要理论（危机推演式）

**如果不这么做会怎样？**
单客户端跑通不代表 accept 循环写对了。Day 2 你已经踩过“accept 不循环”的坑——今天如果复用了错误的写法，3 个客户端同时连只会打印 1 条。而且如果你只在终端敲一次 `nc` 就下结论，很可能掩盖了 accept 循环里的 `break / continue` 层级错误。

**今天必须复现的两个动作**：

1. **多个 nc 同时连**——验证 accept 循环能一次接完。
2. **20 个短连接压过去**——验证 fd 数不涨、服务端不崩。

<br>

### 3.2 代码实现与设计意图

```bash
done
```

### 3.3 现象追踪与验证

**验收 A：5 个 nc 同时连**

```bash
# 终端 1
./build/bin/reactor_acceptor

# 终端 2
./scripts/test_multi_accept.sh
```

**预期终端 1 输出（5 条，端口各不相同）**：

**验收 B：fd 不泄漏**

```bash

# 20 个短连接
for i in {1..20}; do
    (sleep 0.3) | timeout 2 nc 127.0.0.1 8888 &
done

ls /proc/$(pgrep reactor_acceptor)/fd | wc -l
```

<br>

### 3.4 面试表达话术

**面试官问**：“accept 循环你怎么写的？为什么？”

**你回答**：“listenfd 非阻塞，`accept4` 带 `SOCK_NONBLOCK|SOCK_CLOEXEC`。返回 -1 时：`EAGAIN/EWOULDBLOCK` 表示队列空了，break；`EINTR` 表示被信号打断，continue；其他才是真错误。必须循环到 EAGAIN，否则一次 epoll_wait 只接一个连接，其余排队，延迟高。Day 2 我就在 docs/debug-log.md 里记录过没循环导致多个 nc 只接 1 个的真实 bug。”
