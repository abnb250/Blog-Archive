## 小节一：从“每个任务开一条线程”到“一个队列 + 三件套”
***
### 1.1 本节最小必要理论（危机推演式）

**先看清你现在的处境。**

Day 9 结束时，你的服务器只有一条执行线：`main` 线程进 `loop()`，`accept4`、`readv`、业务回调、`send` 全在这条线上排队。这对 echo 够用，因为 echo 里没有任何“慢”操作。

但 Day 14 要把业务逻辑丢进线程池，Day 16 要用心跳判断连接死没死，Day 17 要解析长度协议。到那天你会面临一个非常具体的问题：**计算放在哪里跑？**

如果今天不把线程池造对，你一定会先掉进两个“看起来很合理”的替代方案：

**方案 A：每来一个任务，`pthread_create` / `std::thread` 一条。**

- 线程创建 + 销毁成本大约 10~20 微秒，默认栈 8MB（虚拟地址，不是立刻占物理内存，但每个线程都要占一块）；
- 1000 个并发任务 = 1000 条线程，内核调度器开始频繁上下文切换，你的 CPU 时间大量花在“换线程”而不是“干活”上；
- 最要命的是**没有地方限流**：任务来得再快，你也只能一条条建线程，线程数完全不受你控制，最后要么 OOM，要么被调度器拖死。

**方案 B：懒得开线程，就在 EventLoop 里直接算。**

只要有一个业务任务耗时 200ms，这条 loop 上的 `epoll_wait` 就停了 200ms。这 200ms 里，其他所有连接的可读事件都没人处理、心跳检查没人做、新连接 accept 不了。

这就是 Reactor 的大忌：**IO 线程里只许做“搬运”和“分发”，不许做“计算”。** 面试官问“你的服务器为什么卡”，十有八九就是这一条。

**线程池解决的是两件事，必须拆开看：**

| 组成 | 负责什么 | 不做会怎样 |
| --- | --- | --- |
| `std::deque<std::function<void()>>` 任务队列 | 把“做什么”和“谁来做”解耦；也是你唯一能统计、能限流的地方 | 任务没有落点，只能当场执行 |
| `std::mutex` | 让多个 worker、多个生产者“碰队列”的那几行串行化 | 两个 worker 同时 `pop_front`，deque 内部指针错乱，随机崩溃 |
| `std::condition_variable` | worker 没活时**睡觉**，有活被**叫醒** | 只能轮询：`while` 空转烧满一个核，或者 `sleep(1ms)` 加延迟、加无意义唤醒 |

**为什么不能用忙等 / 定时轮询？**

空转轮询：一个 worker 一秒空转几百万次，CPU 100%，风扇起飞，什么也没干。
`sleep(1ms)` 轮询：任务来了平均多等 0.5ms，10 万任务就是 50 秒的纯浪费；而且每秒 1000 次无意义唤醒，本身就是负载。

条件变量就是为这件事存在的：**没有任务时线程在内核里睡着，不占 CPU；`enqueue` 一次 `notify_one`，内核把它叫醒。** 这就是“等待从线程里挪到队列里”的物理含义。

**一句话记住今天的原则**：*线程池不是“多开线程”，是把“线程的创建/销毁”变成一次性投资，把“等待”变成队列里的一个元素。*

今天的最小正确集合只有四个字：**能起、能收、能停、不丢**。返回值、异常上报、线程数策略是第三节的事，先把这四个字做对。

<br>

**总结一下到底什么是线程池**  

用开餐馆打比方就好懂了。

**先说它解决什么问题**。 你的服务器现在只有一个厨师，也就是一条线程：接客、点单、做菜、上菜全他一个人干。echo 这种“看一眼就回一句”的活，一个厨师够用。但以后要做“匹配房间”“查数据库”这种要花几十毫秒的菜，厨师一做菜，门口就没人接客了——新客人进不来，老客人的事也没人理。这就是为什么不能把耗时的活放在 IO 线程里干。

那能不能每来一桌客人就临时招一个厨师？也不行。招人、辞退都要花钱（创建销毁线程有开销），每个厨师还得占一个灶台（线程栈），一下子来一千桌你就得招一千个厨师，厨房直接挤爆。所以正确做法是：提前固定雇三个厨师，所有人把订单写在一张单子上，谁空谁去单子上撕一张来做。 这就是线程池。

**它里面就四样东西。**

一是一张**订单清单**，就是任务队列。谁有活要干，就写一张单子放上去；厨师不用知道单子是谁写的，写单子的人也不用关心哪个厨师做。这样“要做什么”和“谁来做”就分开了。

二是一把**锁**。单子只有一张，三个人同时去撕会乱，所以规定：撕单子的时候别人不能动。注意只在“撕单子”这一下上锁，**做菜的时候不能上锁**——要是厨师端着锁去做菜，另外两个人就只能干等着，三个人的厨房变一个人；而且做菜过程中如果又要往单子上加菜，他自己就会被自己锁死。

三是一个**铃铛**，也就是条件变量。厨师没单子的时候不能站在那儿一直盯着单子看（那叫空转，白烧 CPU），也不能每隔一会儿跑过来瞅一眼（浪费还慢）。正确做法是回休息室睡觉，有人放单子就按一下铃把他叫醒。醒来后要先看一眼单子，确认真有活再动手——因为铃有时候会“误响”，这就是所谓虚假唤醒。

四是**几个干活的人**，工作线程。他们的一生就是循环做一件事：看单子 → 有活就撕一张 → 做 → 再看。

**还有一件容易写错的事：打烊。** 不能说“关门了，把没做的单子全扔了”，因为客人已经付过钱了，单子就是承诺。正确做法是：门口挂“不再接单”的牌子，但后厨把已经收下的单子全部做完，做完了厨师才下班。这个叫“优雅关停”，也是你代码验收里“任务不能丢”的意思。

**最后记住一条边界。** 厨师只做菜，不碰前台的事。也就是说，线程池里的线程只做纯计算，不要去碰 socket、连接对象这些东西——那些东西属于某一条 IO 线程，别人乱碰就会出数据错乱和崩溃。算完了把结果交回给对应的 IO 线程，由它去发数据。

带着这个画面去看代码：找那张单子、那把锁、那个铃、那几个循环干活的人，再看打烊逻辑。你会发现一个线程池的骨架，真的就这么点东西。

### 1.2 代码实现与设计意图

**新建 `include/base/ThreadPool.h`：**

```cpp
// =============================================================================
// ThreadPool.h：业务线程池——固定线程数 + 任务队列 + 优雅关停。
//
// 本文件组成（自上而下 3 块）：
//   A 头文件   —— 线程 / 互斥 / 条件变量 / 函数对象 / 队列
//   B 类声明   —— 生命周期、enqueue、观测接口；禁拷贝
//   C 成员     —— 队列、线程组、条件变量、运行标志（全部私有）
//
// 【设计意图】ThreadPool 只认识"可调用对象"，不认识 socket、EventLoop、echo。
//   这样 Day 11 的 sub EventLoop 装配和 Day 14 的业务逻辑都能复用它，
//   而它自己永远不知道业务是什么——库和业务的分界线，从今天开始画。
// =============================================================================
#pragma once

#include <condition_variable>
#include <cstddef>
#include <deque>
#include <functional>
#include <mutex>
#include <string>
#include <thread>
#include <vector>

namespace reactor {

class ThreadPool {
public:
    // threadCount 为 0 时按 1 处理：宁可有池，不要有"零线程池"这种怪状态。
    explicit ThreadPool(std::size_t threadCount, std::string name = "pool");
    ~ThreadPool();

    // ---- 块 B1：生命周期 ----
    // 【常见坑】线程池不可拷贝：内部有 mutex / thread，拷贝语义无法定义，
    //   编译器生成的拷贝构造会直接编译失败，不如显式 delete 把错误挡在前面。
    ThreadPool(const ThreadPool&) = delete;
    ThreadPool& operator=(const ThreadPool&) = delete;

    // 拉起所有 worker；重复调用无副作用（幂等）。
    void start();

    // 优雅关停：不再接新任务，已入队的任务跑完，再 join 所有线程。
    void stop();

    // ---- 块 B2：提交 ----
    // 受理返回 true；池未启动或已停止返回 false。
    // 【设计意图】返回 bool 而不是 void：任务被拒必须让调用方知道，
    //   否则就是"任务悄悄丢了"，而验收标准里写着"无任务丢失"。
    bool enqueue(std::function<void()> task);

    // 只读观测：队列里还没被取走的任务数（不含正在执行的那个）。
    std::size_t pendingTasks() const;

private:
    // ---- 块 B3：worker 主循环 ----
    void workerLoop(std::size_t index);

    const std::size_t threadCount_;
    const std::string name_;

    mutable std::mutex mutex_;                  // 锁，保护下面三样：队列 / 线程组 / 运行标志
                                                //   mutable 只是为了让 const 的 
                                                //     pendingTasks() 也能锁它，
                                                //   因为这个函数只读队列，但锁本身必须能被修改。
    std::condition_variable notEmpty_;          // 条件变量："队列非空"或"要关停"时叫醒 worker
    std::deque<std::function<void()>> tasks_;   // 任务队列：先进先出
    std::vector<std::thread> threads_;          // 工作线程：worker 线程组，stop 时 join
    bool running_ = false;                      // 是否已启动且未停止
};

} // namespace reactor
```

**新建 `src/base/ThreadPool.cpp`：**

```cpp
// =============================================================================
// ThreadPool.cpp：固定线程数 + 无界任务队列 + 优雅关停。
//
// 本文件组成（自上而下 5 块）：
//   A 构造/析构 —— 记下线程数与名字；析构自动 stop，绝不留野线程
//   B start      —— 一次性拉起 N 个 worker，重复调用无副作用
//   C stop       —— 置停止位 → 唤醒全部 → 等队列排空 → join
//   D enqueue    —— 加锁入队 → 解锁 → notify_one
//   E workerLoop —— wait 到有任务或被叫停 → 取一个 → 解锁 → 执行
//
// 【设计意图】锁只包住"碰队列"的那几行，任务体在锁外执行：
//   否则线程池退化成单线程，任务里再 enqueue 还会死锁（同一把非递归 mutex）。
//   关停选"排空再退出"的语义，因为验收要求是"无任务丢失"。
// =============================================================================
#include "base/ThreadPool.h"

#include <cstdio>
#include <utility>

namespace reactor {

// ---- 块 A：构造 / 析构 ----
// 作用：构造只记参数，不起线程；析构兜底 stop，避免 std::thread 析构时 terminate。
ThreadPool::ThreadPool(std::size_t threadCount, std::string name)
    : threadCount_(threadCount == 0 ? 1 : threadCount), name_(std::move(name)) {}

ThreadPool::~ThreadPool() { stop(); }

// ---- 块 B：start ----
// 作用：在持锁状态下把 running_ 置真，再起 N 条线程；幂等的。
// 【面试考点】新线程一启动就会去抢 mutex_，会一直阻塞到 start 释放锁——
//   这是对的：worker 拿到锁时，running_ 和 threads_ 已经是完整状态。
void ThreadPool::start() {
    // 这是一把 RAII 锁：这行代码在构造时自动给 mutex_ 加锁，lock 离开作用域时自动解锁；
    std::lock_guard<std::mutex> lock(mutex_);
    if (running_) return;
    running_ = true;
    threads_.reserve(threadCount_);
    for (std::size_t i = 0; i < threadCount_; ++i) {
        // 直接在vector尾部构造，std::thread(成员函数指针, 对象指针, 成员函数的参数...)
        // 合起来就是 this->workerLoop(i)，也就是线程启动后在新线程里执行 workerLoop(i)。
        threads_.emplace_back(&ThreadPool::workerLoop, this, i);
    }
}

// ---- 块 C：stop ----
// 作用：锁内只置 running_ = false，锁外 notify_all 再 join，最后清空线程。
// 【常见坑】绝不能拿着锁 join：worker 必须拿到锁才能看到 running_ 已经为 false，
//   而 stop 拿着锁等 worker 退出 → 互相等 → 死锁。放锁在前，join 在后，顺序不许换。
// 【设计意图】关停语义 = 排空：worker 的条件是"停止且队列为空"才退出，
//   所以 stop() 返回时，所有已受理的任务都执行完了。
void ThreadPool::stop() {
    {
        std::lock_guard<std::mutex> lock(mutex_);
        if (!running_) return;
        running_ = false;
    }
    notEmpty_.notify_all();          // 叫醒所有睡着的 worker，让它们自己判断走还是留
    for (auto& t : threads_) {
        // 如果当前 std::thread 对应一个还没被处理过的线程（joinable() 为真），就调用 join()
        // join() 做两件事：等这条线程跑完（阻塞当前线程），然后回收它占用的系统资源
        if (t.joinable()) t.join();
    }
    threads_.clear();
}

// ---- 块 D：enqueue ----
// 作用：空任务直接拒；锁内判状态 + 入队；锁外 notify_one。
// 【常见坑】notify 写在锁内不会错，但会让被唤醒的 worker 立刻又阻塞在锁上；
//   放到锁外，worker 醒来就能直接拿锁干活。
bool ThreadPool::enqueue(std::function<void()> task) {
    if (!task) return false;
    {
        std::lock_guard<std::mutex> lock(mutex_);
        if (!running_) return false;
        tasks_.push_back(std::move(task));
    }
    notEmpty_.notify_one();
    return true;
}

// ---- 块 D2：pendingTasks ----
// 作用：给验证程序一个可观测的队列水位。
std::size_t ThreadPool::pendingTasks() const {
    std::lock_guard<std::mutex> lock(mutex_);
    return tasks_.size();
}

// ---- 块 E：workerLoop ----
// 作用：worker 的一生——睡觉、被叫醒、取任务、放锁、执行，直到"停止且队列空"。
void ThreadPool::workerLoop(std::size_t index) {
    (void)index;    // 本节还没用上编号，先压掉 -Wunused-parameter
    for (;;) {
        std::function<void()> task;
        {
            // 允许手动 unlock()/lock()；因为 condition_variable::wait 
            //   在睡眠前需要自动释放锁、醒来后再重新加锁，所以 wait 必须用 unique_lock
            std::unique_lock<std::mutex> lock(mutex_);
            // 【面试考点】wait 必须带谓词。不带谓词就会吃"虚假唤醒"：
            //   内核可能没有任何 notify 也把线程唤醒，此时队列是空的，
            //   一 pop_front 就是未定义行为。带谓词 = 醒来后再验一次条件。
            notEmpty_.wait(lock, [this] { return !running_ || !tasks_.empty(); });//唤醒条件
            if (!running_ && tasks_.empty()) return;   // 停止且已排空：这条 worker 退休
            task = std::move(tasks_.front());
            tasks_.pop_front();
        }
        // 【设计意图】锁在这里已经释放，任务体在锁外执行：
        //   并发度才是真的；任务里再调 enqueue 也不会自己锁死自己。
        task();
    }
}

} // namespace reactor
```

**新建 `examples/day10_threadpool_test.cpp`（第一版，只验并行）：**

```cpp
// =============================================================================
// day10_threadpool_test.cpp：线程池的最小验收——先证明"真的在并行"。
//
// 本文件组成（自上而下 3 块）：
//   A 计时工具 —— steady_clock 毫秒；单调时钟，不受系统改时间影响
//   B 并行性   —— 8 个 200ms 任务丢进 3 线程池，看 wall 和 pthread id
//   C 汇总     —— 退出码用 wall 判定，脚本能直接判对错
//
// 【设计意图】并行不是"看起来快"，是"8 个 200ms 任务在 3 条线程上只花约 600ms"。
//   数字对不上，池就是假的；数字对上了，再去验"不丢"和"能停"。
// =============================================================================
#include "base/ThreadPool.h"

#include <chrono>
#include <cstdio>
#include <pthread.h>
#include <thread>

// ---- 块 A：计时工具 ----
// 作用：返回 steady_clock 的毫秒数。
static long long nowMs() {
    using namespace std::chrono;
    return duration_cast<milliseconds>(steady_clock::now().time_since_epoch()).count();
}

int main() {
    // ---- 块 B：并行性 ----
    reactor::ThreadPool pool(3, "day10");
    pool.start();

    const long long t0 = nowMs();
    for (int i = 0; i < 8; ++i) {
        const bool ok = pool.enqueue([i] {
            std::this_thread::sleep_for(std::chrono::milliseconds(200));
            // 【常见坑】多线程 printf 可能交错：一行只调一次 printf，别拆成好几次。
            std::printf("[B] task %02d on pthread=%lu\n", i,
                        static_cast<unsigned long>(::pthread_self()));
        });
        if (!ok) std::printf("[B] task %02d rejected\n", i);
    }
    pool.stop();          // 排空 8 个任务之后才返回
    const long long wall = nowMs() - t0;
    std::printf("[B] 8 x 200ms on 3 threads: wall=%lldms\n", wall);

    return (wall < 1000) ? 0 : 1;
}
```

### 1.3 现象追踪与验证（如何证明跑通了）

**第一步：编译**

```bash
cmake -S . -B build
cmake --build build -j4
```

**预期**：0 warning。若报 `undefined reference to pthread_create`，就是块 E6-3 的 `PUBLIC Threads::Threads` 没写或写成了 `PRIVATE`。

**第二步：跑起来，先看两个数字**

```bash
./build/bin/day10_threadpool_test
```

**预期**：

```text
[B] task 00 on pthread=139865432123456
[B] task 01 on pthread=139865423730752
[B] task 02 on pthread=139865415337984
[B] task 03 on pthread=139865432123456   ← 线程 0 被复用
...
[B] 8 x 200ms on 3 threads: wall=~605ms
```

**两个判据**：

**你回答**：“固定 N 条 worker 线程、一个 `std::function<void()>` 的任务队列，用互斥锁保护队列、条件变量做唤醒。关键设计有四个：第一，锁的粒度只包住‘碰队列’的几行，任务体在锁外执行，否则池会退化成串行，任务里再提交任务还会死锁；第二，`wait` 带谓词，处理虚假唤醒；第三，`enqueue` 返回 bool，池停了就明确拒收，而不是让任务悄悄消失；第四，关停语义是‘排空再退出’——`stop()` 在锁内置停止位、锁外 `notify_all` 再 `join`，之所以不能在持锁时 `join`，是因为 worker 要拿同一把锁才能看到停止位，会互相等死。验证方式是三个数字：8 个 200ms 任务在 3 线程上 wall≈600ms、pthread id 只有 3 个、`strace` 里 3 次 clone 加大量 futex wait。这也解释了为什么不在 EventLoop 里直接算业务：一个 200ms 的任务会让整条 loop 上所有连接的 `epoll_wait` 停 200ms。”

## 小节二：把并发跑对——五个会让线程池“看起来能用”的坑
***
### 2.1 本节最小必要理论（危机推演式）

第一版能跑，只证明“顺利路径”通了。线程池真正出事，全在**错误路径**上。下面五个坑，每一个都能让服务器“平时好好的，一压就集体掉线”。

**坑一：任务抛异常 → 整个进程直接 abort**

worker 线程里执行 `task()`，没有 `try/catch`。任务里任何一句 `throw`，或者 `std::vector::at` 越界、`std::bad_alloc`，异常会一路穿过 `workerLoop` 到线程入口。C++ 标准规定：**异常逃出线程函数，调用 `std::terminate`**。

结果不是“这个任务失败”，是**整个服务器进程消失**，所有客户端同时断线。而你在日志里只会看到 `terminate called after throwing an instance of 'std::runtime_error'` 然后 abort，GDB 都来不及接。业务代码是会抛异常的（Day 14 的匹配失败、Day 17 的长度非法），这个口子今天必须堵上。

> 注意边界：`try/catch` 只是“别让 worker 死”，**不等于“错误被处理了”**。调用方要拿到失败原因，得靠第三节的 `future` 把异常搬回去。

**坑二：`stop()` 把队列清空，任务凭空消失**

很多教程的写法是：`running_ = false; tasks_.clear(); join();`——为了“快速退出”，把没跑的任务直接扔掉。在你的项目里这是**验收失败**：任务清单上写着“无任务丢失”。

正确语义是**排空（drain）**：停止位只表示“不再接新任务”，worker 醒来后发现“已停止但队列还有活”，就继续干，直到队列空才退休。`stop()` 返回时，所有已受理任务都执行完了。同时 `enqueue` 在停止后必须返回 `false`，让调用方知道“这一条没进去”，而不是默默吞掉。

**坑三：拿着锁 `join`，死锁**

```cpp
// 错误示范
std::lock_guard<std::mutex> lock(mutex_);
running_ = false;
for (auto& t : threads_) t.join();   // ← worker 也要这把锁才能看到 running_=false
```

worker 醒来第一件事是 `lock(mutex_)`，而锁在你手里，你在等 worker 退出。双方互相等，进程永久挂住，`Ctrl+C` 都杀不掉（要 `kill -9`）。

铁律：**置位在锁内，`notify` 和 `join` 在锁外。** 顺序永远是 `lock → 改标志 → unlock → notify_all → join`。

**坑四：在锁内执行任务 → 池退化成单线程，任务里再提交就死锁**

如果把 `task()` 写在 `unique_lock` 的作用域里面，所有 worker 会排成一队，一个跑完下一个才能进——你的“3 线程池”实际并发度是 1。

更糟的是**重入**：任务体里调用 `enqueue` 提交子任务，`enqueue` 要拿同一把非递归 `mutex_`，而当前线程正持有它 → 自己锁死自己，整条 worker 永久卡住。所以顺序必须是：**锁内只 `pop`，锁外再执行**。

**坑五：虚假唤醒 + 惊群 + 任务引用悬空**

- **虚假唤醒**：`cv.wait(lock)` 不加谓词，内核可能在没有任何 `notify` 的情况下唤醒线程，此时队列空，`pop_front()` 就是未定义行为（崩溃或读到垃圾）。必须用 `wait(lock, pred)`。
- **`notify_one` vs `notify_all`**：入队用 `notify_one`（只需要一条线程干活，叫醒全部是无效竞争）；关停必须 `notify_all`（所有 worker 都得看到停止位，漏一个就 `join` 卡死）。
- **漏 `notify`**：任务进了队列却没唤醒任何人，它会一直躺着，直到下一个任务到来才被“顺带”执行——表现是“偶发延迟几秒”，极难查。
- **引用悬空**：`enqueue([&conn]{ conn->send(...); })`，任务还在队列里，`conn` 已经析构。这是 Day 8 的 UAF 教训换个地方重演。**跨线程一律按值捕获**：要对象活着就捕获 `shared_ptr`，要数据就拷贝一份值。

上面五条，正好对应验收里的两个词：**“无崩溃”**（坑一、三、五）和**“无任务丢失”**（坑二、四）。

### 2.2 代码实现与设计意图

**改动 1：给 worker 起名字（以后 `top -H` / GDB 能认出是谁）**

`src/base/ThreadPool.cpp` 顶部 include 区追加：


**改动 2：`workerLoop` 整体替换成下面这版（加线程名 + 异常兜底）**

```cpp
// ---- 块 E：workerLoop ----
// 作用：worker 的一生——睡觉、被叫醒、取任务、放锁、执行，直到"停止且队列空"。
// 【设计意图】这里是线程池唯一需要"防弹"的地方：线程入口一旦漏出异常，
//   整个进程 terminate，所以任务执行必须包在 catch(...) 里。
void ThreadPool::workerLoop(std::size_t index) {
    // ---- 子块 E1：给线程起名 ----
    // 作用：让 top -H / gdb info threads 里能直接看到 day10-0 / day10-1。
    // 【常见坑】Linux 线程名上限 16 字节（含结尾 '\0'），超了会被截断，
    //   这里自己截到 15，别让内核替你悄悄截。
    std::string tname = name_ + "-" + std::to_string(index);
    if (tname.size() > 15) tname.resize(15);
    ::pthread_setname_np(::pthread_self(), tname.c_str());

    for (;;) {
        std::function<void()> task;
        {
            std::unique_lock<std::mutex> lock(mutex_);
            notEmpty_.wait(lock, [this] { return !running_ || !tasks_.empty(); });
            if (!running_ && tasks_.empty()) return;   // 停止且已排空：退休
            task = std::move(tasks_.front());
            tasks_.pop_front();
        }
        // ---- 子块 E2：任务执行 + 异常兜底 ----
        // 作用：一条任务的失败只影响它自己，worker 继续服务后面的任务。
        try {
            task();
        } catch (const std::exception& e) {
            std::fprintf(stderr, "[threadpool:%s] task threw: %s\n", name_.c_str(), e.what());
        } catch (...) {
            // 【面试考点】catch(...) 是最后一道墙：不认识的异常也必须挡住，
            //   否则异常逃出线程函数 → std::terminate → 整个服务器进程没了。
            std::fprintf(stderr, "[threadpool:%s] task threw unknown exception\n", name_.c_str());
        }
    }
}
```

**改动 3：测试程序改造——`main` 末尾的 `return` 整段替换**

先把 include 区补两个头文件：

```cpp
#include <atomic>
#include <stdexcept>
```

把原来最后的 `return (wall < 1000) ? 0 : 1;` 换成：

```cpp
    // ---- 块 C：不丢任务（10 万个） ----
    // 【设计意图】stop() 是"排空"语义，所以这个计数必须精确等于 100000。
    //   少一个都说明有任务被丢掉或被覆盖。
    long long counterFinal = 0;
    {
        reactor::ThreadPool bulk(3, "bulk");
        bulk.start();
        const long long c0 = nowMs();
        std::atomic<long long> counter{0};
        for (int i = 0; i < 100000; ++i) {
            bulk.enqueue([&counter] { counter.fetch_add(1, std::memory_order_relaxed); });
        }
        bulk.stop();     // 排空后才返回——这里就是"不丢"的证明点
        counterFinal = counter.load();
        std::printf("[C] counter=%lld expect=100000 wall=%lldms\n",
                    counterFinal, nowMs() - c0);
    }

    // ---- 块 D：关停后不再受理 ----
    const bool afterStop = pool.enqueue([] { std::printf("[D] BUG: ran after stop\n"); });
    std::printf("[D] enqueue after stop -> %s\n",
                afterStop ? "accepted(BUG)" : "rejected");

    // ---- 块 E：任务抛异常，worker 不能死 ----
    {
        reactor::ThreadPool fault(2, "fault");
        fault.start();
        fault.enqueue([] { throw std::runtime_error("boom from task"); });
        std::atomic<int> after{0};
        fault.enqueue([&after] { ++after; });   // 前一个任务抛了，这个必须照跑
        fault.stop();
        std::printf("[E] task after throw ran=%d\n", after.load());
    }

    // ---- 块 G：任务里再提交任务，不能自己锁死自己 ----
    {
        reactor::ThreadPool chain(1, "chain");
        chain.start();
        std::atomic<int> chained{0};
        chain.enqueue([&chain, &chained] {
            chain.enqueue([&chained] { ++chained; });
        });
        for (int i = 0; i < 1000 && chained.load() == 0; ++i) {
            std::this_thread::sleep_for(std::chrono::milliseconds(1));
        }
        chain.stop();
        std::printf("[G] chained=%d\n", chained.load());
    }

    return (wall < 1000 && counterFinal == 100000 && !afterStop) ? 0 : 1;
```

### 2.4 面试表达话术

**面试官问**：“线程池在线上最容易出什么问题？你怎么处理的？”

**你回答**：“三类。第一类是异常：任务体抛异常如果穿过 worker 线程入口，会触发 `std::terminate` 把整个进程带走，所以线程池必须在执行点用 `catch(...)` 兜底；但兜底只是保证 worker 活着，真正的错误上报要靠 `std::future` 把异常搬回调用方。第二类是关停：很多实现为了退出快，直接清空队列或者 `detach`，已受理的任务就丢了；我做的是排空语义——停止位只表示不再接新任务，worker 直到队列空才退出，`stop()` 返回时所有已受理任务都完成了，同时 `enqueue` 在停止后返回 false，拒绝必须让调用方看见。第三类是锁的顺序：`join` 绝不能持锁，因为 worker 要拿同一把锁才能看到停止位；任务体也必须在锁外执行，否则池退化成串行，任务里再 `enqueue` 会自己锁死自己。验证上我用了 10 万任务计数、停止后拒收、抛异常后继续跑、任务内重入四个用例，再跑一遍 TSan 确认没有数据竞争。”

## 小节三：把接口焊死——`submit` 拿结果，边界划清楚
***
### 3.1 本节最小必要理论（危机推演式）

**只有 `enqueue` 的线程池，是个“黑盒投递口”。**

调用方扔进去一个任务，然后呢？做完了没？成功没？算出来的匹配结果怎么拿回来？`enqueue` 一个都答不了。Day 14 你要把业务丢进池子，业务是要返回结果的（匹配到的房间号、AOI 计算结果、DB 写入是否成功）。

自己拿 `std::promise` 拼也行，但每个任务都要写一遍“建 promise、取 future、塞进 lambda、catch 后 set_exception”，重复且容易漏。标准库已经把这件事封装好了：

- `std::packaged_task<Ret()>`：把一个可调用对象和一块**共享状态**绑在一起，执行时自动把返回值或异常写进共享状态；
- `std::future<Ret>`：共享状态的读端，`get()` 要么拿到值，要么把异常重新抛给你。

所以 `submit` 的本质就三行：**用 bind 把参数固化 → 塞进 packaged_task → 把 packaged_task 丢给 enqueue，返回它的 future。**

**这里有两个必须今天想清楚的设计问题：**

**问题一：`std::bind` 会按值拷贝参数，这是缺陷还是特性？**

是特性。跨线程最怕的就是“两个线程同时摸一块可变内存”。按值拷贝 = 每个任务拿到**属于自己的一份数据**，天然没有竞争。代价是大对象拷贝贵，所以规则是：小数据按值传，大数据/对象传 `shared_ptr`（共享所有权 + 引用计数线程安全），**绝不传裸指针或引用**去指向一个可能已经析构的对象。

**问题二：线程数开多少？**

- 计算密集型（纯 CPU，比如协议解析、AOI 计算）：**核数**。多了只会增加上下文切换。
- 阻塞型（等 DB、等磁盘）：`核数 × (1 + 阻塞时间/计算时间)`。这是 Little 定律的工程近似，面试可以提一句“阻塞系数”。
- 别开几百条：`std::thread::hardware_concurrency()` 是起点，不是答案；线程数是压测调出来的，不是拍脑袋定的。

**最重要的一条：线程池和 Reactor 的边界，今天就要立规矩。**

池线程**绝对不能**直接碰 `fd`、`Channel`、`TcpConnection`。原因不是“怕麻烦”，是三条硬事实：

1. 这些对象**不是线程安全的**，`Channel` 的 `events_`、`TcpConnection` 的 `outputBuffer_` 都是普通成员，两个线程同时改就是数据竞争；
2. 它们的**生命周期绑在 owner EventLoop 上**：连接关闭时 `closeCallback` 会 `erase` 掉最后一个 `shared_ptr`，池线程手里如果是引用/裸指针，立刻 UAF；
3. 你的单线程模型之所以能“到处不加锁”，前提就是**一条连接只属于一个 loop**。这个前提一旦被池线程打破，你就得给每个成员加锁，然后迎接死锁。

所以规矩只有三句：

- 池线程只做**纯计算**：入参是值或 `shared_ptr`，出参是值；
- 结果要回到连接上，必须**投递回 owner loop**（Day 13 的 `runInLoop + eventfd` 就是干这个的，今天不写，但今天要立规矩）；
- **永远不要在 EventLoop 线程里 `future.get()`**。那等于把异步池用成同步调用，`epoll_wait` 照样停住，你白写了线程池。要结果，就让任务算完后回调 / 投递，而不是在 loop 里等。

在 `enqueue` 声明下面、`pendingTasks` 上面插入模板：

```cpp
    // ---- 块 B4：submit ----
    // 作用：提交带返回值的任务，返回 future；任务抛的异常也会被搬进 future。
    // 【设计意图】enqueue 适合"发出去就不管"的活；submit 适合业务要结果的活。
    //   内部仍然是 enqueue，所以队列、锁、关停语义完全复用，没有第二套并发路径。
    // 【常见坑】std::bind 按值拷贝参数——这是跨线程的安全保证，不是性能缺陷；
    //   大对象请传 shared_ptr，别传引用去指向一个可能已经析构的对象。
    template <typename F, typename... Args> // F 表示你要提交的可调用对象的类型，
                                            // Args... 表示它需要接受的任意个参数类型
    auto submit(F&& f, Args&&... args)
        -> std::future<typename std::invoke_result<std::decay_t<F>, std::decay_t<Args>...>::type> {
        
        // 算出 f 被这些参数调用后返回的类型，命名为Ret
        // invoke_result 负责推导返回类型，decay_t 会把引用和 const 去掉，变成能安全保存的普通类型
        using Ret = typename std::invoke_result<std::decay_t<F>, std::decay_t<Args>...>::type;

        // 用 shared_ptr 持有 packaged_task：任务队列里放的是 lambda，
        // lambda 必须能拷贝，而 std::function 要求可拷贝——shared_ptr 正好满足。
        // std::packaged_task<Ret()> 包装一个“无参数、返回 Ret”的可调用对象，并给它配一块共享状态；
        // 执行它时，返回值或异常会被写进共享状态，供对应的 future 取走。
        auto task = std::make_shared<std::packaged_task<Ret()>>(
            // bind把“函数 + 参数”绑成一个新的零参数可调用对象：以后调用 变量名() 就等价于调用 f(args...)；
            // 这正是 packaged_task<Ret()> 需要的“无参数”形态。
            // std::forward 只是为了按原样传递左值/右值，避免多余的拷贝。
            std::bind(std::forward<F>(f), std::forward<Args>(args)...));

        std::future<Ret> fut = task->get_future();
        // 用 (*task)() 触发 packaged_task 执行，从而把结果或异常写进共享状态。
        // 它正好能转换成 std::function<void()>，被 worker 取走并执行
        if (!enqueue([task]() { (*task)(); })) {
            // 池已停止：直接告诉调用方，别返回一个永远等不到的 future。
            throw std::runtime_error("ThreadPool::submit: pool is stopped");
        }
        return fut;
    }
```

```cpp
            std::printf("[F] BUG: exception was swallowed\n");

        }

        calc.stop();
    }
```

````markdown
## 10. 线程池（Day 10）

- 定位：`base/ThreadPool`，纯计算任务的执行器；不认识 socket / EventLoop / 业务协议。
- 结构：`deque<std::function<void()>>` + `mutex` + `condition_variable` + N 条 worker。
- 提交：`enqueue(task)` 返回 bool（受理/拒收）；`submit(f, args...)` 返回 `future`，值或异常都能拿回。
- 关停：`stop()` 置 `running_ = false` → `notify_all` → 队列排空后各 worker 退出 → `join`；`stop()` 幂等，析构自动调用。
- 临界区：锁只包住“碰队列”的几行；任务体在锁外执行（并发度 + 允许任务内再提交）。
- 边界铁律：
  1. 池线程不得直接操作 fd / Channel / TcpConnection；
  2. 结果回投必须经 owner EventLoop（Day 13 的 `runInLoop + eventfd`）；
  3. 绝不在 EventLoop 线程里 `future.get()`。
- 已知限制：队列无界（生产快于消费会涨内存，Day 14 压测后加有界 + 拒绝策略）；线程数固定，无动态扩缩容。
````

### 3.4 面试表达话术

**面试官问**：“你的线程池和 Reactor 是怎么配合的？线程数怎么定？”

**你回答**：“分两层。IO 层是 Reactor，一个 EventLoop 一条线程，负责 `epoll_wait`、accept、读写，连接的状态只由它自己的 loop 线程碰；计算层是线程池，只做纯计算，入参是值或者 `shared_ptr`，不碰 fd、不碰 Channel。两层之间只有一条合法通道：池里算完把结果投递回 owner loop（`runInLoop + eventfd` 唤醒 `epoll_wait`），而不是池线程直接改连接。接口上我提供两种提交方式：`enqueue` 是 fire-and-forget，返回 bool 表示受理还是拒收；`submit` 返回 `future`，用 `packaged_task` 把返回值和异常都搬回调用方。线程数上，计算密集型按核数，阻塞型按 `核数 × (1 + 阻塞/计算)`，最终靠压测定。还有两个纪律：一是绝不在 EventLoop 线程里 `future.get()`，那等于把线程池用成同步调用，loop 照样卡住；二是队列必须设上限，无界队列在生产快于消费时就是内存炸弹。关停我用的是排空语义，`stop()` 返回时已受理任务全部完成。”
